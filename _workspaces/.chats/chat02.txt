## ⚠️ CHALLENGE

**User's Approach:** Create a static SPA dashboard system with LENS integration for multi-repo visualization serving both file:// and http:// protocols.

**Weaknesses:**

| # | Weakness | Impact |
|---|----------|--------|
| 1 | **file:// protocol limitations** — XHR/fetch blocked, CORS issues, no lazy loading | Dashboard won't load JSON data dynamically via file:// |
| 2 | **Manual orchestrator enhancement before onboarding** — sequential bottleneck | Every new repo type delays all onboarding; doesn't scale |
| 3 | **Single dashboard.html for all repos** — state management complexity | URL routing, deep linking, browser history broken under file:// |
| 4 | **Missing schema evolution strategy** — JSON v2.0 locked | Breaking changes when adding tabs invalidate all existing repos |
| 5 | **LLM-generated business summaries not integrated** — manual step | Use case extraction exists but no automated "humanization" pipeline |

**Counter-Proposal:** **Hybrid Architecture with Progressive Enhancement**

| Weakness | → Strength |
|----------|------------|
| file:// limitations | **Embedded JSON** in dashboard.html at build time + **Progressive Web App** for http:// |
| Manual orchestrator enhancement | **Schema-driven tabs** with `data-show-if` visibility — dashboard auto-adapts to available data |
| Single dashboard.html | **Per-repo static HTML generation** with embedded data (file://) OR **SPA with HashRouter** (http://) |
| Schema evolution | **Additive-only schema** with semver + backward-compatible migrations |
| LLM humanization | **LLM post-processing pipeline** integrated into `UseCaseExtractor` with Copilot API |

**Best Practices:**

| Source | Standard | Status |
|--------|----------|--------|
| Company | CORTEX Best Practices | ✅ MCP-first |
| CORTEX | CORE-035 Single Implementation | ✅ Unified aggregator |
| OWASP | Input Validation | ✅ Schema validation |
| 12-Factor | Config externalization | ✅ registry.json |
| Clean Architecture | Separation of concerns | ✅ Crawler→Aggregator→Renderer |

**Verdict:** PIVOT — Enhanced hybrid architecture recommended

### 🔄 Protocol Decision: **HTTP-First with File Fallback**

| Aspect | HTTP:// (Recommended) | File:// (Fallback) |
|--------|----------------------|-------------------|
| **Lazy JSON Loading** | ✅ fetch() works | ❌ Blocked by CORS |
| **HashRouter** | ✅ Full SPA navigation | ⚠️ Limited |
| **CDN Libraries** | ✅ Optimal | ❌ Must bundle |
| **Caching** | ✅ Service Worker + HTTP cache | ❌ None |
| **Deep Linking** | ✅ `#/cortex/security` | ❌ Manual |
| **Solution** | SPA with external JSON | Per-repo embedded HTML |

**Recommendation:** Serve via HTTP (even localhost:8080) for full functionality. Generate file://-compatible embedded HTML as export option.

### 🧪 Error Handling Strategy

```yaml
error_handling:
  crawler_failures:
    strategy: "graceful_degradation"
    behavior: |
      If ASTAnalyzer fails → metrics section shows "Analysis unavailable"
      If SecurityScanner fails → security section shows "Scan pending"
      Dashboard NEVER fails to render — always shows partial data
    
    implementation: |
      try:
          ast_result = ast_analyzer.analyze()
      except Exception as e:
          logger.warning(f"ASTAnalyzer failed: {e}")
          ast_result = ASTResult.empty()  # Safe default

  json_validation:
    strategy: "coerce_and_log"
    behavior: |
      Invalid fields → coerce to type default
      Missing required → use schema default
      Extra fields → ignore (forward compatibility)
    
    implementation: |
      class RepoDashboardModel(BaseModel):
          class Config:
              extra = "ignore"  # Forward compatibility
              validate_assignment = True

  ui_rendering:
    strategy: "show_if_available"
    behavior: |
      Null/empty data → hide component via data-show-if
      Chart data empty → show "No data" card
      Tab entirely empty → hide tab button
    
    implementation: |
      <div data-show-if="security.vulnerabilities.length">
          <div id="vuln-table"></div>
      </div>
      <div data-hide-if="security.vulnerabilities.length" class="empty-state">
          ✅ No vulnerabilities detected
      </div>

  network_failures:
    strategy: "offline_fallback"
    behavior: |
      fetch() fails → check localStorage cache
      Cache miss → show "Data unavailable" with retry button
      file:// mode → use embedded JSON (no network)
```

## The Problem

| Protocol | `fetch()` works? | Why? |
|----------|------------------|------|
| `http://localhost:8080` | ✅ Yes | Same-origin, no CORS issues |
| `file:///C:/dashboards/` | ❌ No | Browsers block XHR/fetch for  due to security |

So if someone double-clicks dashboard.html on their desktop, **JavaScript cannot load external JSON files**.

## Two Approaches

### Option A: HTTP-Only (RECOMMENDED) ✅

```
company/dashboards/
├── spa/
│   └── dashboard.html      ← ONE SPA shell
└── repos/
    ├── cortex/
    │   └── dashboard-data.json   ← External JSON
    └── cortex-brain/
        └── dashboard-data.json   ← External JSON
```

**URL:** `http://localhost:8080/spa/dashboard.html?repo=cortex`

**How it works:**
```javascript
// app.js reads URL param, fetches JSON dynamically
const repo = new URLSearchParams(location.search).get('repo');
const data = await fetch(`../repos/${repo}/dashboard-data.json`);
```

**Pros:** Clean separation, single HTML, proper architecture  
**Cons:** Requires HTTP server (even `python -m http.server` works)

---

### Option B: File-Compatible (Fallback)

For file:// to work, the JSON **must** be in the same HTML file because browsers block external file access. Two sub-options:

#### B1: Embedded `<script>` tag (what I proposed)

```html
<!-- repos/cortex/dashboard.html -->
<script type="application/json" id="dashboard-data">
{
  "repo": { "slug": "cortex", ... },
  "metrics": { ... }
}
</script>
<script src="../../spa/js/app.js"></script>
```

**This is generated at build time** — not manually hardcoded. The orchestrator:
1. Generates dashboard-data.json
2. **Also** generates dashboard.html with the JSON embedded via template

#### B2: JSONP-style callback

```html
<script>
window.dashboardData = { "repo": {...}, "metrics": {...} };
</script>
```

---

## My Recommendation: **Drop file:// support entirely**

| Factor | Verdict |
|--------|---------|
| Who uses file://? | Almost nobody in enterprise |
| Complexity cost | 2x output generation, maintenance burden |
| Alternative | `python -m http.server 8080` takes 2 seconds |

**Proposed architecture (simplified):**

```
company/dashboards/
├── index.html              ← Landing page (repo tiles)
├── registry.json           ← Repo metadata
├── spa/
│   └── dashboard.html      ← SINGLE SPA (reads ?repo= param)
└── repos/
    ├── cortex/
    │   └── dashboard-data.json
    └── {other-repos}/
        └── dashboard-data.json
```

**One HTML file. Many JSON files. HTTP only.**
