1) Recommended approach: “SPA ergonomics, static output”

Use React + Vite (or Angular if you strongly prefer) to get reusable components, but compile to static files and generate multiple HTML entry points:

Root landing: dist/index.html

Per repo: dist/repos/<repoSlug>/index.html

Important: Avoid client-side routing that requires server rewrites. Under file://, a router can be fragile. Use:

Normal links between HTML files (href="./repos/<slug>/index.html")

Or hash navigation inside each page only (optional)

This matches the “static-first” plan direction and avoids the class of “diagrams didn’t load” issues caused by tabs rendering hidden canvases/SVGs.

3) Data model: per-repo hardcoded JSON (embedded, not fetched)
Hard rule

Each repo dashboard must embed its JSON data inside the HTML:

<script type="application/json" id="repo-data">{ ... }</script>


Then JS reads and parses it:

const data = JSON.parse(document.getElementById("repo-data").textContent);

Required objects
Landing manifest

repos.manifest.json is compiled into root index.html similarly:

<script type="application/json" id="repos-manifest">[ ... ]</script>


Each repo in manifest:

slug, displayName, owner, primaryLanguage

healthScore, riskScore

loc, files, servicesCount, coveragePct

lastAnalyzedAt, version

tags[] (e.g., “critical”, “regulated”, “customer-facing”)

8) The #1 reliability requirement: charts must render only when visible

A lot of “broken diagrams” comes from initializing charts when:

Tab panel is hidden (width=0)

Element isn’t mounted

ID mismatch

Script loads after init triggers

Mandatory ChartHost component behavior

Implement ChartHost wrapper that:

Waits until container is visible

Initializes chart once

Reflows on resize

Re-renders when tab becomes active

Required mechanics:

IntersectionObserver or “tab activated” events

requestAnimationFrame twice before init (ensures layout settled)

ResizeObserver to call chart.resize()

A per-chart initialized guard

This is a direct prevention strategy for the “diagrams not loading properly” class of issues.

11) SOLID + DRY implementation rules (Copilot guardrails)

Copilot must follow:

Single Responsibility: each component renders one thing well.

Open/Closed: adding a new chart/tab doesn’t require rewriting tab system.

Dependency Inversion: pages depend on interfaces (RepoDashboardModel) not hardcoded shapes.

DRY:

No repeated chart init logic in multiple places; all through ChartHost.

No repeated card markup; use MetricCard, InfoCard, SeverityCard.

Shared theme tokens in one place (tokens.css).
