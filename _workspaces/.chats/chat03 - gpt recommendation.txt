GitHub Copilot Instructions: Multi-Repo Dashboard Suite + Landing Page + MCP Exposure
Goal

Build a Repo Dashboard Suite that can:

Generate N dashboards (one HTML per repo) with a consistent theme and shared reusable UI components.

Generate a single landing HTML entry point with:

A large hero (style aligned with index.html) 

index

A search + filter + sortable tile grid of all repos (works for 10 repos or 500).

Each tile navigates to the repo’s dashboard HTML (relative links, file:// safe).

Be deployable in production and exposed via MCP such that an MCP tool can generate:

A dashboard for one repo, or

A full suite (landing + all repo dashboards) in one execution.

Non-Negotiable Constraints

No server required to view output; must work from file://.

No runtime network calls from generated dashboards (no fetching JSON, no API calls).

All data is hardcoded into each generated HTML (or embedded as JS objects).

All third-party libraries must be vendored locally (no CDN) to avoid file:// + CSP issues.

Keep it modern and interactive, but don’t overengineer: minimal build steps, maximal clarity.

Data Contract (Hardcoded Data Strategy)

Copilot must implement a single data shape used by both landing and per-repo dashboards.

Required objects

RepoManifest[] used by landing page:

slug, displayName, path, owner, primaryLanguage

healthScore, riskScore, securityFindingsCount

loc, files, servicesCount, testCoveragePct

lastAnalyzedAt, version

RepoDashboardModel used by repo dashboard:

overview metrics

architecture (folders, services, dependency graph)

quality (complexity, duplication, hotspots)

security (vuln breakdown)

testing (coverage, tests, gaps)

useCases (array of use case records, searchable)

actions (recommendations/backlog items)

Embed pattern

For each generated HTML:

Add <script type="application/json" id="repo-data">...</script> containing the JSON.

JS reads it and renders charts.

This avoids messy escaping and keeps file:// safe.

Use case data shape

Each use case item:

id, title, persona (Leadership / Production Owner / Engineer / Security / QA)

category (Delivery, Risk, Compliance, Reliability, Cost, Maintainability, Observability)

tags[]

severity (info/low/med/high/critical)

UX requirement (handles 100+)

Must be searchable (title + summary + tags)

Must support:

Filter chips (persona/category/severity)

“Saved views” (e.g., Leadership view, Security view)

Grouping strategy:

Default grouping: by persona

Secondary toggle: by category

Each use case is a clickable card that opens a side panel/modal with:

Summary

Evidence signals (charts it depends on)

Jump links to relevant dashboard sections

Diagram Strategy: High-Value Upgrades Without Overengineering

Copilot should keep D3/Chart.js where they fit, but upgrade a few diagrams to increase “enterprise value per pixel”.

Replace low-signal D3 visuals with these higher-signal ones

Dependency Force Graph → “Dependency Risk Map”

Same data, but encode:

Node size = transitive dependency count

Node ring = vulnerability count

Edge thickness = coupling strength

Provide a “focus” click: isolate neighborhood of a service/package.

Basic Treemap → “Hotspot Treemap”

Treemap rectangles sized by LOC, colored by churn/complexity.

Clicking a rectangle drills into file metrics + linked issues.

Simple bars → “Pareto Hotspots (Top 20)”

A ranked bar chart for “top 20 risky files” + cumulative line.

This is leadership-friendly and engineering-actionable.

Any hand-rolled D3 tables → “Virtualized Data Grid”

Use a lightweight local grid for large lists (see library section).

Sorting, filtering, sticky header = instantly more enterprise.

Offline-Friendly Visual Libraries (File:// Safe)

Copilot should vendor libraries locally (copy into out/assets/vendor/ and reference relatively).

Recommended options:

ECharts (excellent interactivity; works locally when vendored)

ApexCharts (nice defaults; small and clean)

Tabulator or Grid.js (tables with sorting/filtering/pagination; good for large use case lists)

Tippy.js (tooltips)

Popper.js (if needed for positioning)

noUiSlider (range filtering like “risk 0–100”)

Lunr.js (client-side search index for use cases and file lists)

D3 stays for custom graphs; keep it but focus on diagrams where D3 adds unique value.

Avoid anything that assumes a server or blocks file://.

Front-End Structure: Reusable Components Without SPA Overkill

Even in plain static HTML, Copilot must modularize.

Required component pattern

Implement small JS “renderers”:

renderHero(container, config)

renderRepoTiles(container, repoManifest[])

renderTabs(container, tabModel)

renderUseCaseSearch(container, useCases[])

renderCharts(model) with per-chart functions

All charts must render only when their tab becomes visible (lazy init) to prevent “canvas is null” and “SVG size 0” bugs.

Mandatory chart-loading safeguards

Copilot must implement:

requestAnimationFrame after tab activation before drawing charts

A ResizeObserver to reflow charts when containers resize

A once() guard so each chart initializes exactly once unless explicitly re-rendered

This is the #1 reason “diagrams don’t load properly” in tabbed UIs.

Can We Build This as an SPA (React/Angular) and Still “Static HTML”?

Yes—as a static build artifact.

Rule

You can use React/Angular only if the output is still:

index.html + bundled JS/CSS in assets/

No runtime server required (you open index.html directly)

Practical guidance (file:// reality check)

Many SPA routers assume server rewrite rules. For file://:

Use hash routing (/#/repo/foo) OR avoid routing and use simple links to per-repo HTML.

Keep it simple:

Landing page = static HTML + JS (no router)

Each repo dashboard = static HTML + JS (no router)

If you still want SPA ergonomics:

Use a component build but emit multiple HTML entry points at build time (landing + each repo). That keeps file:// trivial and avoids routing gotchas.

Copilot must add MCP tools that generate dashboards.

MCP tools to implement

Inputs: repo identifier/path + output dir

Output: path to generated dashboard HTML + summary stats

cortex_generate_dashboard_suite

Inputs: list of repos + output dir

Output:

landing page path

list of repo dashboard paths

Output structure

The suite generator must produce:

out/index.html (landing)

out/repos/<repoSlug>/dashboard.html

out/repos/<repoSlug>/data.json (optional; but if used, must still be loaded without fetch—so embed or inline)

out/assets/...

Landing page navigation tiles

Landing tiles must be generated from a repos-manifest.json that is also embedded into landing as application/json (no fetch). Clicking tile opens relative dashboard.

Acceptance Criteria (Copilot must validate)

Suite generation produces:

landing + N dashboards

all open correctly via file://

Landing page:

hero present and visually aligned with index.html 

index

tiles render, search/filter works

Repo dashboards:

all original visualizations remain (or upgraded), none silently removed

“Use Cases” tab exists and supports 100+ use cases with search + grouping

No console errors:

charts render after tab open

no missing assets

“Enterprise usability”:

drill-down interactions exist (click a hotspot -> show details panel)

export button exists (download JSON, or copy-to-clipboard) for offline sharing

What Copilot Should Not Do

Don’t add a backend.

Don’t rely on CDNs.

Don’t fetch JSON at runtime.

Don’t add a complex SPA router unless using hash routing and it’s truly needed.

Don’t remove diagrams just to reduce tabs—use subtabs/accordions instead.

If you want this to feel ridiculously polished without adding complexity, the single highest-leverage move is: landing page + tiles + “Use Cases” search + drill-down side panels. That’s the “enterprise vibe” sweet spot: executive-friendly, operator-friendly, engineer-actionable—without turning the repo into a frontend framework war.
