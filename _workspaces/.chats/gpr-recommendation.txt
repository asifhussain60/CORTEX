1) Root cause #1: file:// breaks fetch() (and anything that acts like an API)
What’s happening

Browsers treat file:// pages as an opaque origin (Origin: null). Many will block fetch('./data/ksessions.json') (or treat it as CORS-unsafe). That means:

Only repos whose JSON is embedded in the HTML will load reliably in file://.

Anything that relies on fetching JSON will be flaky or dead.

Evidence in your SPA logic

Your controller tries:

Embedded JSON first (good idea)

Fetch fallback (breaks on file:// in many setups)

But in your index.html, only one repo is embedded (data-ksessions). Everything else has to fetch and will fail in file mode.

Fix options (pick one; don’t “half-do” both)

Option A (recommended): always run via local HTTP server.
This is the clean solution, and you already have the tooling for it (your dashboard server tool / local server approach). When served as http://localhost:..., fetch() works normally.

Option B: go fully “embedded/offline bundle” for file://.
If you truly want “double-click index.html” offline support:

Embed all repo JSON as <script type="application/json" id="data-<repo>">...</script>

Never call fetch in file mode

Or bundle all JSON into a single embedded registry object

Assumption to challenge: “A rich SPA should run correctly over file://.”
That’s basically fighting the browser security model. You can do it, but you’ll keep paying “weird tax” forever (CORS, fonts, module loading, relative paths, caching quirks). A tiny localhost server is the modern, sane approach.

2) Root cause #2: some visuals are not rendering because of CSS/SVG sizing rules

Your .viz-canvas svg { height: 100%; width: 100%; } pattern is dangerous when the parent doesn’t have an explicit height (only min-height). In many layouts, “100% height” computes to 0 (or collapses strangely), so the SVG exists but is effectively invisible.

This matches your symptom: containers show up (borders, titles, legends) but the graph area is blank.

Fix (do this)

Set real height constraints on the visualization containers, and stop overriding SVG height unless the parent height is explicit.

Recommended CSS pattern

Give .viz-canvas an explicit height per chart type (or via CSS variables)

Let the SVG use its own viewBox sizing

Example approach (conceptual):

.viz-canvas { height: 520px; } for dependency graphs

.viz-canvas--small { height: 320px; }

Remove svg { height: 100%; } unless the parent height is guaranteed

Assumption to challenge: “min-height is enough for SVG 100% height.”
It often isn’t. SVG sizing is a swamp. Give it explicit heights and you’ll stop bleeding.
