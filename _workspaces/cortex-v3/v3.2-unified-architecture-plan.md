## Executive Summary

CORTEX v3.2 layers a lightweight agent+skill architecture on top of the proven Python MCP engine. Agents handle the conversational layer. Python handles the stateful engine. The 381-file orchestrator monolith is incrementally deprecated in 3 waves — not big-bang archived. Each wave validates zero capability loss before proceeding.

This plan consolidates v3.1 after repo-validated review. Key corrections: file counts matched to actual repo (381 orchestrators, not 275; 74 MCP tool files, not 51; 19 existing skills, not 9), overengineered components removed (Release Evidence Mesh, plugin governance, surface parity testing), governance ceremony reduced (76→40 DoD checks, 7→4 gates, 8→5 phases), and a proper testing strategy added that accounts for the 1,428 existing test files.

### Key Outcomes
1. 381 Python orchestrators incrementally deprecated — stateful logic preserved as MCP tools, routing logic replaced by agents
2. 10 CORTEX agents + 12 WORKFLOW agents + 10 Knowledge agents = 32 total agents
3. 19 CORTEX skills + 36 WORKFLOW + 82 Knowledge = 137 unified skills (registered, not duplicated)
4. Three-repo integration: Cortex (engine) + workflow-repo (workflow) + knowledge-repo (knowledge)
5. 2 primary deployment surfaces: Claude Code CLI + VS Code Copilot (Cowork, Cursor, Gemini = bonus)
6. Python MCP tools retained as stateful engine layer — agents invoke, not replace
7. WorkflowComposer retained as MCP bridge — enforcement spine elevated
8. Universal Response Contract: 46K-token system → 500-token YAML spec
9. 40 DoD checks across 8 categories (was 76 across 15)
10. 4 gate skills at real decision points (was 7)
11. Feature Delivery Lifecycle delegates to workflow-repo — CORTEX orchestrates, not reinvents
12. 3-layer pragmatic testing replaces 8-layer Release Evidence Mesh

### Design Principles (7)
1. **Agent-First** — Every capability is an agent. Agents are markdown files, not Python classes.
2. **Skill as Contract** — Skills define what an agent can do. SKILL.md is the interface.
3. **Engine Stays** — Python MCP tools are the stateful engine. TDD, RCA, WorkflowComposer, enforcement — all preserved.
4. **Incremental Deprecation** — No big-bang archive. 3 waves with test validation at each step.
5. **Progressive Intelligence** — Repository understanding builds in layers.
6. **Gate What Matters** — 4 gates at real decision points. No ceremonial duplication.
7. **Three-Repo Unity** — CORTEX orchestrates the lifecycle that workflow-repo defines.

## Testing Strategy (3-Layer Pragmatic)

### Existing Test Base: 1,428 test files — ALL PRESERVED
- **preflight**: `python scripts/run_tests.py preflight` (<10s, every audit gate)
- **changed**: `python scripts/run_tests.py changed` (TDD inner loop)
- **smoke**: `python scripts/run_tests.py smoke` (<60s, pre-commit)
- **unit**: `python scripts/run_tests.py unit` (default local dev)

### Layer 1: Smoke Tests (<60s)
26 drift-lock checks, 802+ YAML schema validation, MCP health check, agent SKILL.md frontmatter validation.
Runs: every commit, every PR, every deprecation wave.

### Layer 2: Agent Routing E2E (<5 min)
34 intent type → agent routing tests, top-10 intents with full response validation, agent → MCP tool chain tested, comparison tests (agent output vs orchestrator output).
Runs: before each deprecation wave, every release.

### Layer 3: Self-Onboard (<2 min)
cortex-intel scans Cortex itself, produces valid model.yaml, downstream agents consume it, cross-repo discovery finds 137 skills.
Runs: every release, P5 certification.

### Deprecation Wave Protocol
1. Run full smoke suite (baseline)
2. Run agent routing E2E for affected intents
3. Run comparison tests (agent vs orchestrator)
4. If pass: move files to _legacy/
5. Re-run smoke suite (no regression)
6. If fail: restore from _legacy/, investigate, fix, retry
7. All 1,428 test files must still pass (refactored for agent+MCP path)

## Registry Governance — ADR-V3-015: Taxonomy Freeze

The `cortex-registry` has grown to **802 YAMLs across 23 top-level directories** with no declared schema for where new files belong. This section defines the anti-sprawl governance model accepted in v3.2.0.

### Sprawl Diagnosis

| Symptom | Detail |
|---------|--------|
| Templates in 4 locations | `artifacts/templates/`, `metrics/dashboards/templates/`, `templates/`, `workflows/templates/` |
| Governance in 3 locations | `governance/`, `rules/`, `core/` |
| Phases in 3 locations | `.archive/.../phases/`, `artifacts/templates/phases/`, `planning/phases/` |
| No schema on most YAMLs | No `schema_version` or `namespace` field — any agent can write anywhere |
| 200 planning YAMLs, no TTL | Completed plans are never archived — the list only grows |
| Loose files at root | `yaml-reader.html` at registry root violates namespace rules |

### 5 Governance Rules

**REGISTRY-001 — Taxonomy Freeze:** No new top-level directories without a new ADR. `registry_manager.py` rejects writes outside the 8 canonical namespaces.

**REGISTRY-002 — Schema-First YAML Creation:** Every new YAML must declare `schema_version: "1.0"` and `namespace: <canonical>` in its front-matter. Validation runs before write. Missing fields → flagged UNREGISTERED on convergence gate.

**REGISTRY-003 — No Loose Files at Registry Root:** Only `README.md` and `cortex-master-v2.yaml` (the index) are permitted at the root.

**REGISTRY-004 — TTL Policy:** Every `planning/` YAML must declare `status: ACTIVE|COMPLETED` or `expires_after: YYYY-MM-DD`. Convergence gate auto-archives completed files 30 days after `completion_date` and active files past `expires_after`.

**REGISTRY-005 — Duplicate Detection on Write:** Before creating a new YAML, CORTEX checks `(namespace + entity_type + entity_name)` for an existing match. If found, the write is rejected and the existing file path is returned.

### 8 Canonical Namespaces (consolidates 23 → 8)

| Namespace | Contents | Absorbs |
|-----------|----------|---------|
| `company/` | repos, domains, infrastructure | existing company/ (no change) |
| `governance/` | SKULL, CORE, compliance, gates, policies | governance/ + rules/ + core/ |
| `knowledge/` | domain knowledge, glossary, archetypes | existing knowledge/ (no change) |
| `planning/` | decisions, phases, roadmaps, migration | existing planning/ + TTL enforcement |
| `workflows/` | templates, patterns, components | workflows/ + artifacts/ + templates/ + metrics/dashboards/templates/ |
| `config/` | system config, memory, metrics | config/ + memory/ + metrics/ + cowork-setup/ |
| `specs/` | HTML view specs, schema definitions | specs/ + html-views/ |
| `_archive/` | completed plans, versioned history (read-only) | .archive/ (renamed) |

### Implementation (in P3)

1. **P3 Week 1:** Tag all 802 existing YAMLs with `schema_version` + `namespace` fields (`scripts/tag_existing_yamls.py`)
2. **P3 Week 2:** Merge duplicate directories (governance+rules+core → governance; all template dirs → workflows/templates)
3. **P3 Week 3:** Enable enforcement in `registry_manager.py` + convergence gate sweep
4. **Ongoing:** TTL sweep runs in every convergence gate — `scripts/run_registry_sweep.py --ttl-archive`

**Impact:** No YAML is deleted. All existing functionality preserved. Only re-tagged and re-organized.
