The first plan is the **architectural capability plan for the YAML Reader itself**. The reader must evolve from a simple file loader into a registry-aware intelligence layer that understands the different semantic classes of YAML stored across the CORTEX registry. The reader should begin with a **type-detection layer** that identifies the YAML category from both directory location and structural signatures. For example, pattern files contain a `pattern` object with fields such as `name`, `type`, `participants`, `when_to_use`, and `anti_patterns`, while governance files define `rules` objects with identifiers, severity levels and enforcement metadata, workflow templates contain `workflow` objects with `stages`, `validation`, and execution metadata, response pattern registries contain hierarchical template definitions and inheritance chains, and planning documents contain extensive `metadata`, counters, analysis sections, and phase lists. Once detected, the reader should dispatch to **schema-specific parsers** implemented as strongly typed domain models (e.g., PatternModel, GovernanceRuleModel, WorkflowTemplateModel, ResponseTemplateModel, MasterPlanModel). These models must support **deep nested structures**, including stage definitions, validation blocks, variable maps, inheritance trees, and rule enforcement configurations. The reader must also support **cross-file resolution**, since many YAMLs reference other YAMLs as sources of truth or templates; therefore it must resolve relative paths, assemble inheritance chains, and construct effective runtime representations. A **lazy-loading cache layer** should be added so large YAMLs are parsed only once and reused. Additionally, the reader must expose **validation utilities** that ensure schema correctness, enforce required fields, verify rule definitions, and detect registry inconsistencies. The design should be extensible through a **parser registration mechanism**, allowing new YAML types to be added without modifying the core reader. Finally, it must provide high-level APIs such as `load_patterns()`, `load_workflows()`, `load_governance_rules()`, and `load_plans()` so orchestrators and intelligence components can consume registry data without knowing file details. The outcome is a reader that behaves less like a file parser and more like a **registry intelligence engine capable of interpreting the entire CORTEX knowledge structure**.

The second plan is the **holistic registry integration and operational plan for the reader within the CORTEX architecture**. The YAML reader must become a foundational service used by orchestrators, governance agents, planning engines, and documentation systems, meaning its design must support large-scale registry orchestration rather than simple configuration loading. First, the reader should build a **registry index at startup**, scanning the entire `cortex-registry` tree and categorizing files into domains such as patterns, governance rules, workflows, response templates, planning phases, and artifacts. This index should store metadata including schema type, version, dependencies, and cross-references so that the system can quickly locate and interpret any registry object. Next, a **dependency graph layer** should map how YAML files relate to one another (for example, workflows referencing execution templates, response registries referencing specific templates, or planning phases referencing execution specs). This graph enables the reader to detect broken references, enforce single-source-of-truth rules, and provide navigable relationships for orchestration and visualization systems. The reader should also implement **governance enforcement hooks**, meaning whenever a YAML is loaded or modified it is automatically validated against governance rules and structural expectations. Another major capability is **semantic querying**, allowing orchestrators to ask questions such as “retrieve all workflow templates that include validation loops” or “list governance rules with severity P0.” The reader should also expose a **change-detection and hot-reload mechanism**, enabling updates to registry YAMLs to be reflected without restarting the system, which is critical for evolving knowledge bases. For observability, the system should generate **registry diagnostics reports** highlighting unused YAMLs, orphaned references, duplicate definitions, and schema drift. Finally, the reader must integrate with documentation generation and visualization tools so the YAML registry can automatically produce diagrams, dashboards, and knowledge graphs. With these capabilities, the YAML reader becomes a **central nervous system component of CORTEX**, transforming static YAML configuration into an actively interpreted knowledge infrastructure that orchestrators, planners, and governance systems can rely upon with high confidence.
