CORTEX Snowball Implementation Plan (Deterministic, Auditable, TDD-First)
Core invariant

No capability may become ACTIVE unless CORTEX can produce a complete, verifiable evidence trail showing:

deterministic routing,

enforced security policy,

verified tests across all layers,

complete audit chain with integrity checks,

zero drift between the evidence bundle and deployed runtime.

If any item cannot be proven, the system fails closed.

1) Explicit lifecycle states and transition rules
1.1 Capability lifecycle state machine

A capability exists in exactly one state at a time:

DRAFT — exists as a spec proposal; cannot run.

SPEC_LOCKED — spec is immutable (signed/hashed); test plan locked.

IMPLEMENTED — code exists; tests not yet proven in CI evidence.

VERIFIED — evidence bundle exists and passes all gates.

SHADOW — receives mirrored inputs; actions are NOOP by construction.

CANARY — receives limited traffic; actions live; rollback triggers armed.

ACTIVE — full traffic; drift monitors armed.

QUARANTINED — auto-demotion due to drift or safety violation.

RETIRED — no longer routable.

Transition table (no ambiguity)

Only these transitions are allowed:

DRAFT → SPEC_LOCKED
Requires: Spec bundle complete + approvals for spec lock.

SPEC_LOCKED → IMPLEMENTED
Requires: Implementation PR merged (code exists).

IMPLEMENTED → VERIFIED
Requires: Evidence Bundle generated and passes gates.

VERIFIED → SHADOW
Requires: Rollout plan exists; shadow safety invariant proven.

SHADOW → CANARY
Requires: Shadow parity thresholds met + zero safety violations.

CANARY → ACTIVE
Requires: Canary success thresholds met continuously for defined window.

ANY → QUARANTINED
Requires: Drift, missing audit spans, policy violation, trigger breach.

QUARANTINED → VERIFIED
Requires: new Evidence Bundle fixes root cause and re-verifies.

ACTIVE → RETIRED
Requires: explicit retirement plan + route removal + audit closure.

Any other transition is invalid and must be rejected by the controller.

2) Artifacts: what must exist, exactly, before each gate
2.1 Spec Bundle (required for SPEC_LOCKED)

A Spec Bundle is a directory or logical package that contains:

capability.yaml

capability_id, version, owner, description

trust_boundaries (explicit list)

action_surface (READ/WRITE/DELETE/EXECUTE/NETWORK as booleans)

routing_rules (patterns + match type + priority)

acceptance_criteria.yaml

each AC is executable as an assertion (see §5)

threat_model.md

enumerated threats + mitigations + out-of-scope

test_plan.yaml

required test categories and minimum counts (see §4)

observability_plan.yaml

required metrics + logs + traces + alert thresholds

rollout_plan.yaml

SHADOW parity thresholds + CANARY triggers + success criteria

policy_delta.yaml

explicit policy updates (allowlist/denylist/approval requirements)

spec_hash.txt

SHA256 of canonicalized Spec Bundle contents

spec_signoff.yaml

reviewer signoffs with timestamps and identities

Spec Lock is a one-way operation: after SPEC_LOCKED, the spec_hash cannot change; any change = new version.

2.2 Evidence Bundle (required for VERIFIED)

An Evidence Bundle is immutable and contains:

evidence_manifest.yaml

capability_id, capability_version

spec_hash, policy_snapshot_id, routing_snapshot_id

build_id, git_sha, environment_fingerprint

test_run_ids[]

test_results/

unit, integration, e2e, negative/security tests

coverage reports

audit_trace_samples/

canonical request → route → policy decision → approval → action plan → execution result → test result chain

runtime_artifacts/

built binaries / package version references

metrics_baseline/

baseline stats used for canary comparisons

integrity/

hash of every file + overall bundle hash

optional signing key metadata

VERIFIED requires the Evidence Bundle to be produced by CI under controlled runners, not locally.

3) The audit ledger: canonical schema and integrity rules
3.1 Audit is not “logs.” It’s a ledger.

Every event is append-only, immutable, and integrity protected.

Required shared fields on every event

trace_id (UUIDv7 preferred)

span_id

parent_span_id (except root)

timestamp

capability_id, capability_version

execution_mode (DRY_RUN | SHADOW | CANARY | ACTIVE)

actor_type (human | system)

actor_id (or service_id)

environment_fingerprint

policy_snapshot_id

routing_snapshot_id

Required event types (must exist in this order)

REQUEST_RECEIVED

INTENT_NORMALIZED

ROUTE_SELECTED

POLICY_EVALUATED

APPROVAL_REQUESTED (only if required)

APPROVAL_RESOLVED (only if requested)

ACTION_PLAN_CREATED

ACTION_EXECUTED (or ACTION_NOOP in SHADOW/DRY_RUN)

RESULT_EMITTED

TESTS_VERIFIED (in verification/CI context)

STATE_TRANSITION (lifecycle changes)

Ledger integrity invariants

Every action must have a preceding POLICY_EVALUATED.

Every approval resolution must reference a prior approval request.

Every state transition must reference an evidence bundle (except DRAFT→SPEC_LOCKED).

No missing spans: the chain must be complete; missing event = fail gate.

Each event includes event_hash and prev_event_hash to form a hash chain per trace_id.

4) Test strategy: required categories, minimums, and STS anchoring
4.1 “Sharpen the saw” first: STS as the ground truth harness

STS (sharpen-cortex) is the pre-capability test system whose only job is to validate:

the orchestration framework,

the gating controller,

the audit chain,

the determinism of routing and policy,

the safety invariants of execution modes.

No real capability work begins until STS passes at defined thresholds.

4.2 Required test categories (for every capability)

Each capability must have tests in these categories, with minimums:

Spec Validation Tests (min 10 assertions)

schema validity, required fields, versioning rules, hash canonicalization

Routing Determinism Tests (min 20 cases)

normalization equivalence classes

tie-break rules

startup conflict detection

confusables policy behavior

Policy Engine Tests (min 20 cases)

allow/deny rules

approval requirements

fail-closed behavior

regression tests for previous vulnerabilities

Executor Safety Tests (min 20 cases)

shell=False invariants

argument grammar validation

filesystem sandbox escapes (symlink/junction/..)

SHADOW / DRY_RUN NOOP behavior

Integration Tests (min 10)

router→policy→executor end-to-end in controlled environment

Negative / Abuse Tests (min 15)

malicious intent strings, unicode tricks, injection payloads, path escapes

expected outcome is DENY or REQUIRE_APPROVAL, not “best effort”

Observability Tests (min 10)

required metrics emitted

audit spans complete

alerts fire under forced conditions

Drift Tests (min 10)

mutation of policy/routing manifests forces QUARANTINE

evidence bundle mismatch prevents activation

Hard rule: test counts are minimums; failures are blocking.

4.3 STS must test the orchestration itself (TDD Orchestration)

STS includes:

golden request corpus (100+ intents)

expected normalized outputs

expected routes

expected policy decisions

expected audit event sequences

expected lifecycle transitions

STS is run in CI and produces its own Evidence Bundle.

5) Acceptance criteria are executable assertions (no prose-only ACs)

Each AC is expressed as a machine-evaluable rule:

AC format

id

scope (routing | policy | audit | rollout | executor)

assertion (a declarative condition evaluated against evidence + runtime)

evidence_required (list of test IDs / metrics / logs)

severity (blocker/high/medium)

Examples (not ambiguous)

“SHADOW must execute NOOP for write/delete/execute/network”

Assertion: forall actions where action.type in [WRITE, DELETE, EXECUTE, NETWORK], ACTION_EXECUTED must be absent and ACTION_NOOP must exist

“Every EXECUTE must validate args against a defined grammar”

Assertion: ACTION_PLAN_CREATED.args_validation == PASS && validator_id exists

“No missing audit spans”

Assertion: event_set contains all required event types in order for every trace_id

If an AC can’t be expressed as an assertion, it’s not an AC yet.

6) Rollout mechanics: deterministic thresholds, sample sizing, and auto-demotion
6.1 SHADOW parity gates

SHADOW runs mirrored inputs, but NOOP execution. You compare:

route parity: % of requests routed identically vs baseline

policy parity: % of decisions matching expected

output parity: semantic diff thresholds (explicitly defined per capability)

audit completeness: 100% required

SHADOW success conditions

All must be true over a rolling window:

route_parity >= 99.5%

policy_parity >= 99.9%

audit_completeness == 100%

safety_violations == 0

minimum sample size: N >= 1000 (or capability-specific, but must be declared)

6.2 CANARY rules

Canary traffic percentage is fixed per capability (default 5%).

Rollback triggers are armed only when sample size minimum is met.

Triggers use consecutive-window logic (single unified policy):

breach must occur in K consecutive windows (default K=3)

window length default 5 minutes

minimum canary events per window must be met (declared in rollout plan)

6.3 Drift and QUARANTINE

Any of these forces immediate QUARANTINE:

policy snapshot hash mismatch

routing snapshot hash mismatch

executor version mismatch

audit schema version mismatch

missing audit spans

safety rule violated (e.g., write executed in SHADOW)

QUARANTINE action is deterministic:

route to safe fallback orchestrator (or DENY)

disable execution actions

require new Evidence Bundle to recover

7) The Snowball: how speed increases without losing safety
7.1 Capability factory (scaffold)

After STS is green, you build a generator that outputs:

Spec Bundle skeleton

AC assertion templates

test vectors + expected audit chain templates

default deny policy deltas

rollout plan defaults

This is what makes later work fast and consistent.

7.2 Reuse rails as mandatory dependency

Every new capability must use:

the same router engine

the same policy engine

the same approval engine

the same executor wrappers

the same audit ledger library

the same evidence bundler

Any exception requires a new capability version and explicit signoff.

8) Implementation plan sequence (explicit, staged deliverables)
Milestone A — STS Foundation (blocking)

Deliverables:

Audit ledger library + hash-chaining

Trace propagation across router/policy/executor

Spec validator + canonical hashing

Evidence bundler + CI integration

Orchestration controller state machine (enforces transitions)

Exit criteria:

STS Evidence Bundle produced in CI

100% audit completeness

deterministic normalization + routing for golden corpus

drift tests demonstrate auto-quarantine

Milestone B — Security & Execution Rail Hardening (blocking)

Deliverables:

Canonical path sandbox with platform-specific canonicalization

Approval engine (state machine, timeout, replay protection)

Executor wrappers (no PowerShell -Command strings; argument vector only)

Argument grammar validators per command class (no {args} free-form)

Exit criteria:

STS security abuse suite passes

no known escape vectors in test corpus

approval and non-interactive fail-closed proven

Milestone C — Routing + Rollout Rails (blocking)

Deliverables:

Normalization pipeline (NFKC, zero-width removal, whitespace collapse, etc.)

Tie-breaking rules + startup conflict detection identical to runtime

Rollout controller (SHADOW parity, CANARY triggers, min sample)

Exit criteria:

router never raises runtime ambiguity

shadow mode proves NOOP invariants

canary triggers validated via simulation tests

Milestone D — Capability Factory (snowball begins)

Deliverables:

capability scaffolder

AC assertion library

test vector generator

“expected audit chain” comparator tool

Exit criteria:

new “toy capability” can be generated and verified end-to-end using only config + tests (no bespoke glue)

Milestone E — Real capability onboarding (repeatable)

For each capability:

generate bundle

implement adapters (if needed)

write tests + negative tests

produce evidence bundle

promote through SHADOW → CANARY → ACTIVE with deterministic thresholds

9) Non-negotiable design decisions (so there’s no ambiguity later)

Audit ledger is mandatory: missing audit = fail closed.

SHADOW is dry-run: cannot execute non-read actions, ever.

No free-form EXECUTE placeholders: every argument must match a declared grammar.

Startup validation must prove runtime determinism: runtime cannot throw ambiguity.

Evidence Bundle binds activation: activation must reference evidence bundle hash; mismatch blocks.

Drift triggers quarantine automatically: no “manual overrides” without a recorded approval trace.

If you implement this exact plan, the snowball effect happens naturally:

early work is slow because you’re building rails + proof machinery,

then each new capability becomes mostly “declare → test → verify → activate,”

and audit + TDD orchestration keep you from building a brittle monster that only works when you’re the one driving.

Next step on paper (not discovery): formalize STS as its own Spec Bundle + Evidence Bundle standard and treat it as Capability 0. Once Capability 0 is VERIFIED, you unlock the factory.
