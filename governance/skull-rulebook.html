What is SKULL Protection?

SKULL (Strategic Knowledge & Universal Logic Layer) is CORTEX's Tier 0 governance system—22 immutable rules enforced by the Brain Protector that prevent common development anti-patterns. These rules are never bypassed, operating as fundamental instincts that protect code quality, maintain TDD discipline, prevent duplication, and enforce Git isolation.

When a developer attempts an action that would violate a SKULL rule, the Brain Protector intervenes with evidence-based reasoning, explaining why the action is problematic and suggesting the correct approach.

The 22 SKULL Rules

🎯 TDD Enforcement (6 rules)

1. TDD_ENFORCEMENT

▼

Rule: RED→GREEN→REFACTOR cycle is mandatory. Implementation blocked until failing tests exist.

Why: Prevents "implementation-first" development that leads to untestable code.

Enforcement: Brain Protector alerts if implementation starts without failing tests.

2. RED_PHASE_VALIDATION

▼

Rule: Tests must fail before implementation begins. Prevents false-positive passing tests.

Why: Validates tests actually check the functionality (not just passing due to bugs).

Enforcement: CORTEX runs tests and confirms failures before GREEN phase.

3. TDD_TEST_FILE_VALIDATION

▼

Rule: All production code must have corresponding test files.

Why: Ensures complete test coverage infrastructure exists.

Enforcement: Automated validation checks for matching test files.

4. TDD_EMPTY_TEST_DETECTION

▼

Rule: No placeholder or empty test functions allowed.

Why: Prevents false sense of test coverage from skeleton tests.

Enforcement: AST analysis detects empty test bodies.

5. TEST_LOCATION_SEPARATION

▼

Rule: App tests in user repo, CORTEX internal tests in tests/.

Why: Maintains clear boundaries between CORTEX and user code.

Enforcement: Path validation prevents test location violations.

6. GREEN_PHASE_VALIDATION

▼

Rule: All tests must pass before moving to REFACTOR phase.

Why: Ensures implementation is correct before optimization.

Enforcement: Test runner blocks REFACTOR phase until 100% pass rate.

🔍 Code Discovery & Duplication Prevention (4 rules)

7. HOLISTIC_CODE_DISCOVERY_ENFORCEMENT

▼

Rule: Search before create. Use semantic_search and grep_search before implementing new functionality.

Why: Prevents duplication of existing functionality.

Enforcement: Brain Protector mandates discovery phase for all new features.

8. REFACTOR_CODE_CLEANUP_ENFORCEMENT

▼

Rule: Remove orphaned and duplicate code during REFACTOR phase.

Why: Maintains clean codebase, prevents technical debt accumulation.

Enforcement: AST analysis identifies unused code for removal.

9. DUPLICATE_FUNCTION_DETECTION

▼

Rule: Detect and flag functionally equivalent implementations.

Why: Prevents code duplication and maintenance overhead.

Enforcement: Similarity analysis compares function implementations.

10. REUSE_OVER_REWRITE

▼

Rule: Extend or refactor existing code rather than rewriting.

Why: Preserves working implementations and reduces regression risk.

Enforcement: Suggests existing implementations before allowing new code.

🔒 Git Isolation & Version Control (4 rules)

11. GIT_ISOLATION_ENFORCEMENT

▼

Rule: CORTEX code never committed to user repositories.

Why: Maintains separation between framework and user code.

Enforcement: Pre-commit hooks block CORTEX files in user repos.

12. CHECKPOINT_BEFORE_MAJOR_CHANGES

▼

Rule: Create git checkpoint before refactoring or major implementation.

Why: Enables easy rollback if changes cause issues.

Enforcement: Orchestrators automatically create checkpoints at phase boundaries.

13. COMMIT_MESSAGE_QUALITY

▼

Rule: Commit messages must follow conventional commit format.

Why: Maintains readable git history and enables automated changelogs.

Enforcement: Validates commit message format before commit.

14. BRANCH_PROTECTION

▼

Rule: Protected branches require tests passing before merge.

Why: Prevents broken code from entering main branches.

Enforcement: CI/CD integration blocks failing test merges.

📚 Documentation & Knowledge Management (4 rules)

15. DOCUMENT_ORGANIZATION

▼

Rule: All docs in cortex-brain/documents/{category}/, never root-level.

Why: Maintains organized documentation structure.

Enforcement: Rejects document creation outside approved directories.

16. DOCSTRING_COMPLETENESS

▼

Rule: All public functions/classes must have docstrings.

Why: Ensures code is self-documenting and maintainable.

Enforcement: Linting detects missing docstrings.

17. KNOWLEDGE_GRAPH_UPDATES

▼

Rule: Update Tier 2 knowledge graph when patterns learned.

Why: Builds institutional knowledge for future operations.

Enforcement: Orchestrators automatically update knowledge graph.

18. TRUTH_SOURCE_VALIDATION

▼

Rule: All facts must trace to truth sources in TRUTH-SOURCES.yaml.

Why: Prevents hallucinations and maintains information accuracy.

Enforcement: Claims validated against registered truth sources.

⚙️ Code Quality & Architecture (4 rules)

19. COMPLEXITY_LIMITS

▼

Rule: Functions exceeding complexity threshold (>30) must be refactored.

Why: Maintains code readability and testability.

Enforcement: AST analysis calculates cyclomatic complexity.

20. SOLID_PRINCIPLES_ENFORCEMENT

▼

Rule: Enforce Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.

Why: Produces maintainable, extensible object-oriented code.

Enforcement: Architectural review validates SOLID compliance.

21. DRY_KISS_YAGNI_ENFORCEMENT

▼

Rule: Don't Repeat Yourself, Keep It Simple Stupid, You Aren't Gonna Need It.

Why: Prevents over-engineering and maintains clean code.

Enforcement: Code review identifies violations.

22. DEPENDENCY_MANAGEMENT

▼

Rule: All dependencies must be pinned with version constraints.

Why: Ensures reproducible builds and prevents dependency conflicts.

Enforcement: Package manager validates version specifications.
