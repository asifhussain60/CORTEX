When a merchant initiates a payout, the payout service saves the record and publishes an event to Kafka. That event is consumed by the finservice, which takes care of calling the external tazapay API. Once tazapay confirms, finservice updates the payout status in the database. After tazapay processes a payout, it sends a Webhook back to us, that is the final confirmation step. The Webhook can come with either a success or a failed status. We consume that Webhook, send the Webbook event to Kafka, which is then consumed by finservice, and update our local payout status, and sometimes even emit downstream events. So, this step helps us complete the payout lifecycle. But because this depends on external callbacks and async processing, the order and timing of events become unpredictable, something we must handle gracefully. At a glance, it looked like a simple three‑step flow, but notice how multiple systems Kafka, Postgres, and tazapay are now part of this single, logical transaction. Each one could fail independently, which means we need strategies to keep them in sync. This is where the concept of distributed commit comes in, the payout service needs to save data to the database and publish event to Kafka, and both operations must happen together. If one succeeds and the other fails, the whole system goes out of sync. At first, it feels tempting to rely on the two‑phase commit protocol, but in a microservice setup involving Kafka and external APIs, that is not practical, it introduces blocking, long‑lived logs, and performance bottlenecks. So we need a better approach, one that embraces eventual consistency instead of enforcing immediate atomicity. Let us look at the first failure case. Here, the payoff service saves the data in the DB, but fails to publish the Kafka event, maybe the broker was down or the connection timed out. Now the database shows the payout as initiated, but finservice never gets the event, so it never calls the tazapay. In effect, we have got an off record, something that looks valid internally, but no actual payout was processed externally. This kind of silent inconsistency is very hard to detect and even harder to fix later. The second scenario flips the problem. Here, the Kafka event is successfully published, but the DB write fails. Finservice happily consume the event and called tazapay. Money moves, but RDB has no record of this payout. When the Webhook returns with a success status, we cannot find the corresponding payout record. The system is now inconsistent across all layers, Kafka, database, and tazapay. This shows why distributed commits are tricky, both sides cannot be guaranteed to succeed simultaneously without a strong coordination mechanism.
Patterns for Reliability and Resilience
This is how we process events currently. The payout service handles a payout transaction in the database, meaning it writes to the database and pushes messages to Kafka in real time. But notice, this design assumes everything works perfectly. If Kafka or the DB goes down, messages might be lost, or partial states might be persisted. And here we can make use of the outbox pattern. The outbox pattern is a clever solution to exactly this kind of problem. Instead of trying to perform two distributed actions at once, write to DB and sent to Kafka, we treat both as a part of one local transaction. We store the intended message inside an outbox table in the same database where our business data resides. That means if the DB transaction commits, both the business change and the event are guaranteed to be saved. Later, a background process reads from this outbox table and reliably sends the event to Kafka. Now, to make this pattern work in our own application, we're going to add three simple, but powerful components to our codebase. First, the outbox table, this is where every event that needs to be published gets recorded. This is what the table looks like. We create a simple table called payout_outbox. Each entry represents a pending message that needs to be published. We store the event ID, payout reference ID, event type, and payload as JSON, and a simple status, NEW, SENT, or ERROR. The table is append only, we never modify or delete events. And by indexing on status and creation time, a relay can pick up and process only unsent events efficiently. So even if Kafka goes down temporarily, we can resume exactly where we left off. Second, we need a relay service. This is a lightweight, scheduled job that runs every few seconds, maybe using Spring's @Scheduled annotation. It queries the outbox table for any records with status NEW, sends them to Kafka, and then marks them as SENT. If any event fails, we simply leave it untouched, this is how we achieve at least once delivery. In our project, this relay can live inside the payout service as a background component that ensures reliability. And finally, we will make a small, but crucial change to our initiatePayout method. Here's how this pattern fits into our existing code. When we initiate a payout, we create a database transaction. Inside it, we save the payout record and an OutboxEvent together. If the transaction commits, both are persisted. The relay picks it up later and publishes it to Kafka. The simple change turns a previously fragile two‑step process into a robust atomic operation, all using a single database transaction. So, in short, the outbox table ensures durability, the relay ensures delivery, the transaction in initiatePayout ensures atomicity between business logic and event creation. So far, we have handled consistency within a single service using the outbox pattern, ensuring our database and Kafka always stay in sync. But what about when multiple services are involved? That is where we need a broader coordination model, something that can handle partial failures gracefully, and that is exactly what the saga pattern gives us. A saga is essentially a sequence of local transactions, each triggered by the success of the previous step. If one of those steps fails, instead of rolling everything back, which is almost impossible in a distributed system, we execute compensating actions to bring the system back to a consistent state. For example, if the finservice fails after the payout was initiated, we might emit a payout‑reversal event, that event could trigger alerts, retries, or even manual reconciliation flows. The key idea is we don't undo previous commits, we add new events that move the system toward a valid state again. So think of sagas as a story, a sequence of independent, but coordinated steps. Each service owns its own data and transactions, but together, through events, they maintain end‑to‑end consistency. Even with all the safeguards in place, outbox for reliable publishing and saga for handling failure across services, there's still one last layer of protection we need. What happens if, despite retries and compensation, a message just keeps failing to process? That is where the dead letter queue, or DLQ, comes in. A DLQ is essentially a safety net in Kafka, a special topic that catches messages that could not be processed successfully after multiple attempts. Let us say finservice receives a payout‑completion event, but fails to update the database because of some malformed data. Instead of blocking the consumer or losing the message, Kafka will move it to the DLQ. Once it is there, we can investigate these messages manually or build automated jobs to review and replay them after the issue is fixed. This approach ensures that a single bad event doesn't bring down the entire system, while still keeping us fully traceable. So putting it all together, the outbox pattern ensures reliable delivery, the saga pattern coordinates compensation across services, and the dead letter queue ensures no event is ever lost beyond recovery. Together, these patterns make our payout system truly resilient, self‑healing, and production ready, and that wraps up our discussion on distributed transactions.
