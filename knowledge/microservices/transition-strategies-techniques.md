Strangler Application Pattern
The Strangler Application Pattern is the core strategy we teach in this course to transition a monolithic application to a microservices architecture, let's first look at what requirements it satisfies, making it the right strategy. A large monolith application is likely to be a successful product with a large customer base, and therefore our transition strategy must not disrupt our services to the customer. The strategy must be risk free. As the business world and our customers needs are dynamic, the ideal strategy must also give us the ability to pause, stop, slow down, and even rollback at any stage. This should also give us the control to build confidence in microservices and the tooling that goes with them. We want to be able to start with the smallest step possible, again to build confidence in microservices, mitigate risk for customers, and have the leftover capacity to deliver fixes and new features. As we get more confident at microservices controlling risk and delivering fixes and enhancements in parallel, we start to transition to microservices faster, always having the ability to pause or even slow down the transition at any point if something else starts to take priority, even having the ability to rollback a microservice and return to the monolith's original functionality, giving us a solid feedback loop on how we are doing with each microservice. Our overall strategy must be consistent of techniques and patterns that we can repeat repeatedly to incrementally transition our current software architecture to microservices. Our strategy needs to be a systematic and a clinical approach, what we don't want as a strategy is a big‑bang approach, where we disappear for months and years to work on microservices, neglecting day‑to‑day bug fixes and enhancements of other existing software because we will lose our customers. The good news is that the microservices transitioning strategy we will teach in this course, the Strangler Application Pattern, meets all the requirements mentioned. Let's see how it works. The pattern has existed for many years and has been successfully used across many projects, but it was formerly given a name when the analogy was made to a certain type of fig which grows on a tree called a Strangler Fig. As this analogy has evolved, the tree has come to represent your monolithic application, and the Strangler Fig represents your microservices architecture. The Strangler Fig starts life by growing in the top half of the tree, in the top branches, using the tree to survive and thrive. In our context, this represents our first extracted microservice which uses the existing monolith application and its database to survive whilst we test and evaluate its performance. This stage is known as the transform stage, where the fig grows using the tree's resources, and we continue to extract microservices incrementally, i.e., one at a time using the monolith application as a resource for some functionalities and data. Each time we identify a capability, i.e., a group of related data and functionalities in the monolith, and then create a new microservice for it. Thanks to the coexistence of capabilities, if a new microservice fails, we can easily roll back the capability in terms of data and functionality to the original monolith version because the monolith is still there, giving us a great feedback loop to evaluate each microservice. This strategy is also incremental, we can control the speed, and we can pause at any time. The second stage, known as coexist, is where the fig has taken over the tree, but quite happily coexists with it. Again, in our context, we have all the microservices to replace the capabilities in the monolithic application. The final stage is the elimination stage where the fig has become completely strong and independent and the tree dies off. In our microservices context, our microservices no longer require anything from the monolith to work independently, and each service also has its own database. These transform, coexist, and eliminate stages have been successfully used for many years. This strategy is the Strangler Application Pattern, which we will use in the rest of this course, along with other supporting patents and techniques. Removing Temporal Coupling
When resolving a missing dependency, we can introduce another issue called temporal coupling. In this clip, we will look at when and how this happens and how to resolve it. In the clip Microservice to Monolith, you saw me resolve a common missing dependency issue by having our new microservice talk to the monolithic app to perform some notifications functionality, this type of downstream service‑to‑service call can introduce the issue known as temporal coupling. Temporal coupling occurs when too many of these downstream calls are chained together, which is most likely what is happening here. The customer uses a frontend app to talk to our web app on the web server, which will then talk to our Customers microservice. As you've seen, our Customers microservice then occasionally talks to our monolith for notifications functionality. This communication, these connections over the network are costly in terms of time, they add more time to other users wait duration before we get a response to our original request. Each connection has a timeout limit, i.e., how long it will wait for a response from the downstream service before it gives up and throws a connection timeout error. If everything responds quickly in the communication chain, nothing times out, nothing gives up waiting, and our client application experiences no slowness issues or timeout errors. However, if something responds too slowly or if we increase the number of downstream connections, i.e, the number of network hops, like we have done here trying to resolve the missing notifications code issue, there's a chance something will timeout and a user will see an error, this is because we increase the time we have to wait every time we add another downstream call across the network, which is what temporal coupling is. One solution is to use asynchronous communication like a fire‑and‑forget connection, this can be easily done in the code and is most effective when you don't need data returned, like in this notification scenario, it's a fire‑and‑forget operation. Eventually, when we separate the notification functionality out into its own microservice, we can again use the same type of asynchronous communication where the customer microservice asks for notifications to be sent, but doesn't wait around for a reply and responds quickly back to the client application. A more advanced way of doing asynchronous communication would be to use a message broker when you place the request to send notifications that a new customer has been created as a message on a queue again using a fire‑and‑forget connection. When a notification microservice is ready to send the notifications, it can pick up notification request messages from the queue at its own leisure. However, there is a temporal coupling scenario that can't be resolved using asynchronous communication. In this scenario, we make a downstream call, expect a response with data, wait for the data, and we can't do a fire‑and‑forget call because we need the data from the response. In this scenario, we can ease the effects of temporal coupling by using a local cache database. So when our customer microservice needs data from the monolith, it first looks at its local cache database for the same data fetched previously. If it has that data and it hasn't expired, that's a cache hit, and we avoid the downstream call to the monolith. However, there is a scenario when we don't have the data from a previous call in our cache database or the data in the cache database has expired. In this cache miss scenario, we have to make the call to the downstream monolith to fetch the data. However, we can be more creative with a cache‑miss scenario to further reduce the effect of temporal coupling. Instead of calling the downstream API when we can't find valid data in the cache, we either serve any matching expired data, a default value for that data, or throw an error that the client application can handle elegantly, i.e., pretend that there was no issue. Also, whenever we have a cache‑miss scenario like this, when we are forced to serve default or expired data, we can start a cache‑healer operation. The cache‑healer operation is a background operation that could even be done using a separate app, it basically makes a note of what data was missing and then fetches it in the background for next time. So now we know what temporal coupling is, during the transition phase, we should constantly worry about it and design in a way with various solutions when making service‑to‑service calls. The solutions may include data warehouses or additional service calls, while managing performance using tools such as a local cache database to mitigate temporal coupling. Your database might not even be a relational database, it could be a NoSql database with elaborate document hierarchies, and you will have to adjust your approach to decomposing that database in this situation accordingly. What if during your analysis you find a table that contains two sets of data, each belonging to a different capability, a different bounded context? What if you also find business logic hidden in the database as part of table triggers, stored procedures, or functions? The business logic may need to be removed from the database and reworked into application‑level code to facilitate easier migration to a microservice. Remember changes like these are not just technical, but also cultural, you may need to start retraining staff to avoid previous pitfalls and learn to work with a distributed data architecture, a complete data culture change. Data security will also become a new concern. You've transitioned from securing a single monolithic database to securing multiple micro databases with increasing amounts of data in transit across the network across components such as cache databases, message brokers, logging systems, and monitoring systems. In a distributed data architecture, traditional transactions with the ability to roll back data become challenging, instead, patterns like the Saga pattern help maintain some traditional asset transaction properties, ensuring data consistency or eventual consistency, which is a significant concept in Microsoft's architecture that may be new to you and the team. What if your database features abstract tables, tables with generic structures that contain different sets of data that belong to multiple different microservices? Again, this might be a precursor task where we split the data into physical tables to work out clear ownership. What if you have business‑logic installed procedures that carry out transactions? We must determine whether it belongs to one microservice for extraction into a microservices database. Alternatively, if multiple microservices use this stored procedure‑based transaction, we may need to move it to application‑level code. Data auditing has also become a new concern. We also need to start thinking about the deletion of data differently. Now that you've got distributed transactions with eventual consistency of the data, do you stick to hard deletes of data, or do you switch to soft deletes? As some linked tables now live behind two different microservices, referential integrity shifts from physical constraints, like foreign keys, to distributed transaction patterns, ensuring only eventual consistency across separate databases. We've already mentioned the use of a data warehouse as a central repository of data that pulled data from services, primarily for reporting purposes, as the ownership of data has been decentralized to micro databases behind each service. But even with the data warehouse, you go from being able to report with real‑time live transaction data to data warehouse data that is always slightly old, if not a few days old, therefore, will it be acceptable to move away from real‑time data reporting and consolidation? Adding New Features During Transition
Next, we examine how to achieve one of the key promises of other Stranglar Application Pattern, transition strategy, the ability to transition incrementally, with the ability to add new features or bug fixes at any point. The first concept is feature freezing, which involves closing off modifications to a specific capability or to the thin slice of a capability we are in the process of transitioning to a microservice. Here, for example, we might find that transitioning the entire customer capability in one sprint is impractical, so we focus solely on address‑related interaction points and feature freeze that aspect within the monolith in the AccountManager API. No changes are allowed to be made to that feature whilst we transition it to a microservice. After safely locking down this feature, we can also now safely add new features or bug fixes to other parts of our application. Once we've completed the transition of this thin slice of our capability and performed the software maintenance, we repeat the entire process in the next sprint and move on to the next thin slice of the other capability that we want to transition. Remember, it's the sharing of the monolithic database that allows us to incrementally transition a capability to a microservice a thin slice at a time, i.e., a few interaction points at a time. If our microservice fails, we can always roll back to the monolith, which will have the same functionality and data thanks to the feature freeze and the shared database. By repeating the process, we transition incrementally using thin slices, keeping customers and stakeholders happy while still safely performing bug fixes and delivering new features. The world, however, is not perfect, there will be instances where we run out of time to deliver a new feature, a bug fix, or even fail to transition the thin slice to a new microservice within the sprint time, i.e., within the available time before a release. This is where our old friends the Branch by Abstraction pattern and feature toggle pattern help avoid releasing anything unfinished to production. The idea remains the same as before, the code that you want to replace with the new feature or bug fix is placed behind an abstraction object and you change the client code to use the abstraction instead. You can then write the code for the new feature or bug fix by creating a new object or set of objects that follow the same abstraction object, this might be a new class that implements the abstraction object as an interface or derives abstract members from the abstract. Then by using the Feature Toggle pattern, you can make the old version and the new version of the code switchable even at runtime. Therefore, if we fail to complete a new feature, we leave the feature toggle off, allowing the old version of the code to be used. Within the BackEndforFrontend‑API, this could allow us to toggle between using the new microservice and the old monolith for a specific capability, enabling our routine component to roll back in real time. Within the monolith, we can use the same patterns to switch off a bug fix that is unfinished and continue using the old implementation with a minor bug that hopefully we can live with for a short while. Within the new microservice, we can use the same patterns to switch off a new feature that isn't finished. So, for example, instead of using new messaging functionality, we continue to use the old notifications functionality because we didn't finish in time. Let's see how this example works in practice. Here we have our Customers microservice, which, as you may be aware, sends notifications every time a new customer is created, this occurs within the Post method of the customer controller, where we utilize the customerService class to invoke a method, and process new customer that sends these notifications. The business has decided that we no longer want to send notifications when a customer is created, instead we want to place a message on a message broker indicating that a new customer record has been created, allowing any downstream services interested in this event to pick up the message and take action. Luckily for us, this old notifications functionality already sits behind an abstraction object, ICustomerService, this means we can use the Branch by Abstraction pattern to create a new ICustomerService implementation that sends messages instead. Our client code won't have to change because the new implementation will slot back in thanks to the ICustomerService interface implementation. We've already done this with our new CustomerServicesNew class, but unfortunately the implementation is complex, and we haven't been able to complete it in time. By using the feature toggle with this Branch by Abstraction pattern, we can have a toggle in the configuration file with a false value to indicate not to use the new CustomerServices implementation. From the dependency injection configuration, you can see how this feature toggle works in conjunction with the Branch by Abstraction pattern to delay the release of the new code. When set to false, we continue using the old notifications implementation of ICustomerService. Hopefully, from this clip, you can take away the concept of transitioning in thin slices and freezing features to enable simultaneous development of new features and bug fixes in addition to other microservices transition. And to prevent unfinished code from delaying new releases, use patterns like Branch by Abstraction and feature toggle. Again, we have a cheat sheet in the course materials that summarizes all this.
