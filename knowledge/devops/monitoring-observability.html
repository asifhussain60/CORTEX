Observability vs Monitoring

Monitoring watches predefined metrics for known failure modes (reactive). Observability enables understanding system behavior through metrics, logs, and traces to explore unknown issues (proactive).

The Three Pillars of Observability

  • Metrics: Numerical measurements over time (CPU, latency, request rate)
  • Logs: Discrete events with timestamp and context for debugging
  • Traces: Request journey through distributed system showing causality
💡 Benefits: 50-70% faster incident resolution (MTTR), proactive problem detection, data-driven optimization, improved reliability.

Metrics

Time-series numerical data for dashboards, alerting, and trend analysis.

Four Golden Signals (Google SRE)

HIGH PRIORITY

Monitor these four metrics for every service.

1. Latency

# Prometheus metric
http_request_duration_seconds{
  method="GET",
  endpoint="/api/users",
  status="200"
}

# Alert on P95 latency
- alert: HighLatency
  expr: histogram_quantile(0.95, http_request_duration_seconds) > 1
  for: 5m
  annotations:
    summary: "P95 latency above 1 second"

2. Traffic (Request Rate)

rate(http_requests_total[5m])

# Alert on traffic drop (potential outage)
- alert: TrafficDrop
  expr: rate(http_requests_total[5m]) < 100
  for: 10m
  annotations:
    summary: "Traffic dropped below 100 req/sec"

3. Errors (Error Rate)

rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m])

# Alert on error rate spike
- alert: HighErrorRate
  expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05
  for: 5m
  annotations:
    summary: "Error rate above 5%"

4. Saturation (Resource Utilization)

node_cpu_seconds_total
node_memory_MemAvailable_bytes

# Alert on high CPU
- alert: HighCPU
  expr: 100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
  for: 5m
  annotations:
    summary: "CPU usage above 80%"

RED Method (for Services)

HIGH PRIORITY

Simplified metrics for request-driven services.

  • Rate: Requests per second
  • Errors: Failed requests per second
  • Duration: Latency distribution (P50, P95, P99)

✅ Implementing RED Metrics

from prometheus_client import Counter, Histogram
import time

# Metrics
requests_total = Counter(
    'http_requests_total',
    'Total HTTP requests',
    ['method', 'endpoint', 'status']
)

request_duration = Histogram(
    'http_request_duration_seconds',
    'HTTP request latency',
    ['method', 'endpoint']
)

@app.route('/api/users')
def get_users():
    start = time.time()
    
    try:
        users = fetch_users()
        requests_total.labels('GET', '/api/users', '200').inc()
        return jsonify(users), 200
    except Exception as e:
        requests_total.labels('GET', '/api/users', '500').inc()
        return jsonify({'error': str(e)}), 500
    finally:
        duration = time.time() - start
        request_duration.labels('GET', '/api/users').observe(duration)

USE Method (for Resources)

MEDIUM PRIORITY

Metrics for infrastructure resources (CPU, memory, disk, network).

  • Utilization: % time resource busy
  • Saturation: Queue depth, wait time
  • Errors: Error count/rate

Structured Logging

Use structured logs (JSON) for better searchability and analysis.

Structured Logging Best Practices

HIGH PRIORITY

Log in JSON format with consistent fields for easy parsing.

✅ Structured Logs (JSON)

import logging
import json
from datetime import datetime

class JsonFormatter(logging.Formatter):
    def format(self, record):
        log_data = {
            'timestamp': datetime.utcnow().isoformat(),
            'level': record.levelname,
            'logger': record.name,
            'message': record.getMessage(),
            'file': record.pathname,
            'line': record.lineno,
            'function': record.funcName
        }
        
        # Add custom fields
        if hasattr(record, 'user_id'):
            log_data['user_id'] = record.user_id
        if hasattr(record, 'request_id'):
            log_data['request_id'] = record.request_id
            
        return json.dumps(log_data)

# Configure logger
handler = logging.StreamHandler()
handler.setFormatter(JsonFormatter())
logger = logging.getLogger(__name__)
logger.addHandler(handler)
logger.setLevel(logging.INFO)

# Usage
logger.info('User logged in', extra={'user_id': 12345, 'request_id': 'abc-123'})

Output: {"timestamp": "2025-12-28T10:30:00", "level": "INFO", "message": "User logged in", "user_id": 12345, "request_id": "abc-123"}

❌ Unstructured Logs

print(f"User {user_id} logged in at {timestamp}")
# Hard to parse, search, analyze

Log Levels

MEDIUM PRIORITY

Use appropriate log levels for filtering and alerting.

  • TRACE/DEBUG: Detailed diagnostic info (dev only)
  • INFO: General informational messages
  • WARN: Potential issues, degraded functionality
  • ERROR: Error events, application can continue
  • FATAL/CRITICAL: Severe errors, application may crash

✅ Appropriate Log Levels

logger.debug(f"Processing {len(items)} items")  # Detailed debugging
logger.info("User registered successfully")       # Normal operation
logger.warning("Cache miss, fetching from DB")    # Potential issue
logger.error("Failed to send email", exc_info=True)  # Error with stack trace
logger.critical("Database connection failed")     # Severe error

Correlation IDs

HIGH PRIORITY

Track requests across services with correlation/trace IDs.

✅ Correlation ID Pattern

import uuid
from flask import request, g

@app.before_request
def before_request():
    # Get or create correlation ID
    g.correlation_id = request.headers.get('X-Correlation-ID', str(uuid.uuid4()))

@app.after_request
def after_request(response):
    # Add correlation ID to response headers
    response.headers['X-Correlation-ID'] = g.correlation_id
    return response

def call_downstream_service():
    # Pass correlation ID to downstream services
    headers = {'X-Correlation-ID': g.correlation_id}
    response = requests.get('https://api.example.com', headers=headers)
    
    logger.info('Called downstream service', extra={
        'correlation_id': g.correlation_id,
        'status_code': response.status_code
    })

✅ Enables tracing request flow through multiple services.

Distributed Tracing

Track requests across microservices to identify bottlenecks and failures.

OpenTelemetry Tracing

HIGH PRIORITY

Use OpenTelemetry for vendor-neutral instrumentation.

✅ Python OpenTelemetry

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.jaeger.thrift import JaegerExporter

# Configure tracer
trace.set_tracer_provider(TracerProvider())
jaeger_exporter = JaegerExporter(
    agent_host_name="localhost",
    agent_port=6831,
)
trace.get_tracer_provider().add_span_processor(
    BatchSpanProcessor(jaeger_exporter)
)

tracer = trace.get_tracer(__name__)

# Instrument application
@app.route('/api/users/')
def get_user(user_id):
    with tracer.start_as_current_span("get_user") as span:
        span.set_attribute("user.id", user_id)
        
        # Child span for database query
        with tracer.start_as_current_span("database.query"):
            user = db.query(User).filter_by(id=user_id).first()
            span.set_attribute("db.rows_returned", 1 if user else 0)
        
        # Child span for cache update
        with tracer.start_as_current_span("cache.set"):
            cache.set(f"user:{user_id}", user)
        
        return jsonify(user)

Effective Alerting

Design actionable alerts that require human intervention.

Alert Design Principles

HIGH PRIORITY

Every alert should be actionable, relevant, and non-redundant.

Good Alert Checklist

  • Actionable: Requires human intervention
  • Relevant: Impacts users or business
  • Timely: Fires when action is needed (not too early/late)
  • Contextualized: Includes runbook link
  • Severity-Appropriate: Critical vs warning vs info

✅ Good Alert

- alert: HighErrorRate
  expr: |
    rate(http_requests_total{status=~"5.."}[5m]) 
    / rate(http_requests_total[5m]) 
    > 0.05
  for: 5m  # Wait 5 minutes to avoid flapping
  labels:
    severity: critical
    team: platform
  annotations:
    summary: "Error rate above 5% for {{ $labels.service }}"
    description: "Error rate is {{ $value | humanizePercentage }} (threshold: 5%)"
    runbook: "https://wiki.company.com/runbooks/high-error-rate"
    dashboard: "https://grafana.company.com/d/errors"

❌ Poor Alert

# Too vague, no context
- alert: SomethingWrong
  expr: errors > 0
  annotations:
    summary: "Errors detected"  # What errors? What should I do?

Alert Fatigue Prevention

HIGH PRIORITY

Reduce noise to ensure alerts get attention.

Strategies

  • Aggregation: Group similar alerts
  • Thresholds: Use appropriate thresholds (not too sensitive)
  • For Durations: Wait before alerting (avoid flapping)
  • Escalation: Warn → Critical → Page
  • Maintenance Windows: Silence during deployments

SLO/SLI/SLA Framework

Define and measure service reliability objectives.

Definitions

HIGH PRIORITY

SLI (Service Level Indicator)

Quantitative measure of service level (e.g., latency, availability, error rate).

Examples:
- Availability: % of successful requests
- Latency: % of requests served under 200ms
- Throughput: Requests per second
- Correctness: % of requests returning correct data

SLO (Service Level Objective)

Target value or range for SLI (e.g., 99.9% availability).

Examples:
- 99.9% of requests succeed (availability SLO)
- 95% of requests complete in <200ms (latency SLO)
- 99% of requests return correct data (correctness SLO)

SLA (Service Level Agreement)

Contract with users specifying consequences if SLO not met.

Example SLA:
- Uptime Guarantee: 99.95%
- If uptime < 99.95%: 10% service credit
- If uptime < 99.0%: 25% service credit

Error Budget

MEDIUM PRIORITY

Amount of downtime allowed within SLO (e.g., 99.9% = 43 minutes/month).

Error Budget Calculation

# 99.9% availability SLO
SLO = 0.999
ERROR_BUDGET = 1 - SLO  # 0.001 = 0.1%

# Monthly downtime budget
MINUTES_PER_MONTH = 43200  # 30 days
ALLOWED_DOWNTIME = MINUTES_PER_MONTH * ERROR_BUDGET
# = 43.2 minutes per month

# Track error budget burn rate
actual_uptime = 0.998  # Current month
error_budget_used = 1 - actual_uptime  # 0.002
error_budget_remaining = ERROR_BUDGET - error_budget_used  # -0.001

if error_budget_remaining < 0:
    print("ERROR BUDGET EXCEEDED! Halt feature releases, focus on reliability")
