What are Design Patterns?

Design patterns are reusable solutions to commonly occurring problems in software design. First cataloged by the Gang of Four (Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides) in their seminal 1994 book "Design Patterns: Elements of Reusable Object-Oriented Software," these patterns represent decades of collective wisdom from experienced software architects.

A design pattern is not a finished design that can be directly transformed into code. Rather, it's a template for how to solve a problem that can be used in many different situations. Patterns show relationships and interactions between classes or objects without specifying the final application classes or objects involved.

Design patterns accelerate development by providing tested, proven development paradigms. They improve code readability for experienced developers and facilitate communication through a shared vocabulary. Well-established patterns create a common language that transcends programming languages and frameworks.

Pattern Selection Guide

Choose the right pattern based on your specific problem:

Object Creation Problems

  • Single instance needed: Singleton
  • Create without specifying class: Factory Method
  • Families of related objects: Abstract Factory
  • Complex object construction: Builder
  • Clone existing objects: Prototype

Object Structure Problems

  • Incompatible interfaces: Adapter
  • Separate abstraction/implementation: Bridge
  • Tree structures: Composite
  • Add responsibilities dynamically: Decorator
  • Simplify complex system: Facade
  • Control object access: Proxy

Object Behavior Problems

  • Chain of handlers: Chain of Responsibility
  • Encapsulate requests: Command
  • Notify multiple objects: Observer
  • Interchangeable algorithms: Strategy
  • Algorithm skeleton: Template Method
  • Behavior based on state: State

When to Use Design Patterns

✅ Use When

  • Building large-scale enterprise applications
  • Working on frameworks or libraries
  • Designing extensible architectures
  • Team needs shared vocabulary for design discussions
  • Problem matches known pattern perfectly
  • Long-term maintainability is priority

❌ Be Cautious When

  • Building simple applications (avoid over-engineering)
  • Team unfamiliar with patterns (training needed)
  • Pattern doesn't fit problem (force-fitting anti-pattern)
  • Simpler solution exists
  • Pattern adds unnecessary complexity
  • Performance is critical concern (some patterns add overhead)

Creational Patterns

Singleton Pattern

Intent: Ensure a class has only one instance and provide global access point

The Singleton pattern restricts instantiation of a class to a single instance. This is useful when exactly one object is needed to coordinate actions across the system, such as database connections, configuration managers, or logging services.

Structure

Singleton
├── static instance: Singleton
├── private constructor()
└── static getInstance(): Singleton

Pros & Cons

Pros:
  • Controlled access to sole instance
  • Reduced namespace pollution vs globals
  • Permits variable number of instances
Cons:
  • Difficult to test (hard to mock)
  • Violates Single Responsibility Principle
  • Thread safety concerns
  • Can hide dependencies

Modern Alternative: Use Dependency Injection instead of Singleton for better testability and clearer dependencies.

Factory Method Pattern

Intent: Define interface for creating object, let subclasses decide which class to instantiate

Factory Method lets a class defer instantiation to subclasses. It provides a way to delegate the instantiation logic to child classes, making the code more flexible and reusable.

Structure

Creator (abstract)
├── factoryMethod(): Product (abstract)
└── operation()

ConcreteCreator
└── factoryMethod(): ConcreteProduct

Product (interface)
├── ConcreteProductA
└── ConcreteProductB

When to Use

  • Class cannot anticipate the class of objects it must create
  • Class wants subclasses to specify objects it creates
  • Classes delegate responsibility to helper subclasses

Builder Pattern

Intent: Separate construction of complex object from its representation

The Builder pattern constructs complex objects step by step. It allows you to produce different types and representations of an object using the same construction code. Particularly useful for objects with many optional parameters.

Key Benefits

  • Construct objects step-by-step with method chaining
  • Reuse same construction code for different representations
  • Isolate complex construction code from business logic
  • Avoid telescoping constructors (constructor with many parameters)

Structural Patterns

Adapter Pattern

Intent: Convert interface of class into another interface clients expect

The Adapter pattern allows incompatible interfaces to work together. It acts as a bridge between two incompatible interfaces by wrapping an existing class with a new interface.

Use Cases

  • Integrate third-party libraries with incompatible interfaces
  • Create reusable classes that work with unforeseen classes
  • Wrap legacy code to work with modern interfaces
  • Enable multiple implementations of same interface

Decorator Pattern

Intent: Attach additional responsibilities to object dynamically

Decorators provide a flexible alternative to subclassing for extending functionality. They wrap objects to add new behaviors without modifying the original object's code.

Advantages

  • More flexible than static inheritance
  • Avoids feature-laden classes high in hierarchy
  • Can add/remove responsibilities at runtime
  • Responsibilities can be combined in different ways

Facade Pattern

Intent: Provide unified interface to set of interfaces in subsystem

The Facade pattern defines a higher-level interface that makes a subsystem easier to use. It provides a simplified interface to a complex system of classes, libraries, or frameworks.

Benefits

  • Shields clients from subsystem components
  • Promotes weak coupling between subsystem and clients
  • Simplifies usage of complex libraries
  • Provides entry point to each subsystem level

Behavioral Patterns

Strategy Pattern

Intent: Define family of algorithms, encapsulate each, make them interchangeable

The Strategy pattern lets the algorithm vary independently from clients that use it. It defines a family of algorithms, puts each in a separate class, and makes their objects interchangeable.

When to Use

  • Many related classes differ only in their behavior
  • Need different variants of an algorithm
  • Algorithm uses data clients shouldn't know about
  • Class defines many behaviors as conditional statements

Observer Pattern

Intent: Define one-to-many dependency so when one object changes, dependents are notified

The Observer pattern establishes a subscription mechanism to notify multiple objects about events that happen to the object they're observing. Also known as Publish-Subscribe pattern.

Key Components

  • Subject: Maintains list of observers, notifies them of state changes
  • Observer: Defines updating interface for objects notified of changes
  • ConcreteSubject: Stores state of interest to observers
  • ConcreteObserver: Maintains reference to subject, implements update

Command Pattern

Intent: Encapsulate request as object, allowing parameterization and queuing

The Command pattern turns a request into a stand-alone object containing all information about the request. This transformation lets you pass requests as method arguments, delay or queue request execution, and support undoable operations.

Use Cases

  • Parameterize objects with operations (menu items, buttons)
  • Queue operations for later execution
  • Support undo/redo functionality
  • Log changes for crash recovery
  • Structure system around high-level operations

Modern Enterprise Patterns

Dependency Injection

Intent: Decouple object creation from dependencies

Dependency Injection is a technique where an object receives other objects it depends on, rather than creating them internally. This inversion of control improves modularity and testability.

Injection Types

  • Constructor Injection: Dependencies provided through constructor (preferred)
  • Property Injection: Dependencies set through public properties
  • Method Injection: Dependencies passed as method parameters

Repository Pattern

Intent: Abstract data access layer

The Repository pattern mediates between domain and data mapping layers using a collection-like interface for accessing domain objects. It provides a more object-oriented view of the persistence layer.

Benefits

  • Centralizes data access logic
  • Provides substitution point for unit tests (mock repositories)
  • Minimizes duplicate query logic
  • Decouples application from persistence technology

Singleton Pattern - Python

❌ Bad: Not Thread-Safe

# ❌ Not thread-safe
class Singleton:
    _instance = None
    
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

# Problem: Race condition in multi-threaded environment

✅ Good: Thread-Safe Implementation

import threading

class Singleton:
    _instance = None
    _lock = threading.Lock()
    
    def __new__(cls):
        if cls._instance is None:
            with cls._lock:  # Double-checked locking
                if cls._instance is None:
                    cls._instance = super().__new__(cls)
        return cls._instance

# Usage
s1 = Singleton()
s2 = Singleton()
assert s1 is s2  # ✅ Same instance

Singleton Pattern - C#

✅ Good: Lazy Thread-Safe Implementation

public sealed class Singleton
{
    private static readonly Lazy lazy =
        new Lazy(() => new Singleton());
    
    public static Singleton Instance => lazy.Value;
    
    private Singleton() 
    {
        // Private constructor prevents external instantiation
    }
}

// Usage
var s1 = Singleton.Instance;
var s2 = Singleton.Instance;
// s1 == s2 (same instance, thread-safe)

Strategy Pattern - Python

✅ Interchangeable Algorithms

from abc import ABC, abstractmethod

# Strategy interface
class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount: float) -> None:
        pass

# Concrete strategies
class CreditCardPayment(PaymentStrategy):
    def __init__(self, card_number: str):
        self.card_number = card_number
    
    def pay(self, amount: float) -> None:
        print(f"Paid ${amount} with credit card {self.card_number}")

class PayPalPayment(PaymentStrategy):
    def __init__(self, email: str):
        self.email = email
    
    def pay(self, amount: float) -> None:
        print(f"Paid ${amount} via PayPal ({self.email})")

class CryptoPayment(PaymentStrategy):
    def __init__(self, wallet_address: str):
        self.wallet_address = wallet_address
    
    def pay(self, amount: float) -> None:
        print(f"Paid ${amount} via crypto to {self.wallet_address}")

# Context
class ShoppingCart:
    def __init__(self, payment_strategy: PaymentStrategy):
        self.payment_strategy = payment_strategy
    
    def checkout(self, amount: float):
        self.payment_strategy.pay(amount)

# Usage - easily switch payment methods
cart = ShoppingCart(CreditCardPayment("1234-5678"))
cart.checkout(100.0)  # Credit card payment

cart.payment_strategy = PayPalPayment("user@example.com")
cart.checkout(50.0)   # PayPal payment

cart.payment_strategy = CryptoPayment("0x123abc")
cart.checkout(75.0)   # Crypto payment

Observer Pattern - TypeScript

✅ Event Notification System

// Observer interface
interface Observer {
    update(data: any): void;
}

// Subject
class Subject {
    private observers: Observer[] = [];
    
    attach(observer: Observer): void {
        this.observers.push(observer);
    }
    
    detach(observer: Observer): void {
        const index = this.observers.indexOf(observer);
        if (index > -1) {
            this.observers.splice(index, 1);
        }
    }
    
    notify(data: any): void {
        this.observers.forEach(observer => observer.update(data));
    }
}

// Concrete observers
class EmailNotifier implements Observer {
    update(data: any): void {
        console.log(`Email sent: ${data.message}`);
    }
}

class SMSNotifier implements Observer {
    update(data: any): void {
        console.log(`SMS sent: ${data.message}`);
    }
}

class PushNotifier implements Observer {
    update(data: any): void {
        console.log(`Push notification: ${data.message}`);
    }
}

// Usage
const subject = new Subject();
subject.attach(new EmailNotifier());
subject.attach(new SMSNotifier());
subject.attach(new PushNotifier());

subject.notify({ message: "Order confirmed!" });
// Output:
// Email sent: Order confirmed!
// SMS sent: Order confirmed!
// Push notification: Order confirmed!

Dependency Injection - Python

❌ Bad: Tight Coupling

# ❌ Tight coupling - hard to test
class UserService:
    def __init__(self):
        self.db = MySQLDatabase()  # Direct dependency!
        self.email = SMTPEmailService()  # Direct dependency!
    
    def register_user(self, user):
        self.db.save(user)
        self.email.send_welcome(user.email)

✅ Good: Dependency Injection

# ✅ Loose coupling - easy to test
from abc import ABC, abstractmethod

class Database(ABC):
    @abstractmethod
    def save(self, entity): pass

class EmailService(ABC):
    @abstractmethod
    def send_welcome(self, email): pass

class UserService:
    def __init__(self, db: Database, email_service: EmailService):
        self.db = db  # Injected dependency
        self.email = email_service  # Injected dependency
    
    def register_user(self, user):
        self.db.save(user)
        self.email.send_welcome(user.email)

# Production usage
service = UserService(
    MySQLDatabase(),
    SMTPEmailService()
)

# Test usage with mocks
service = UserService(
    MockDatabase(),
    MockEmailService()
)

Repository Pattern - C#

✅ Abstract Data Access Layer

// Repository interface
public interface IRepository where T : class
{
    T GetById(int id);
    IEnumerable GetAll();
    void Add(T entity);
    void Update(T entity);
    void Delete(int id);
}

// Concrete repository
public class UserRepository : IRepository
{
    private readonly DbContext _context;
    
    public UserRepository(DbContext context)
    {
        _context = context;
    }
    
    public User GetById(int id)
    {
        return _context.Users.Find(id);
    }
    
    public IEnumerable GetAll()
    {
        return _context.Users.ToList();
    }
    
    public void Add(User entity)
    {
        _context.Users.Add(entity);
        _context.SaveChanges();
    }
    
    public void Update(User entity)
    {
        _context.Users.Update(entity);
        _context.SaveChanges();
    }
    
    public void Delete(int id)
    {
        var user = GetById(id);
        if (user != null)
        {
            _context.Users.Remove(user);
            _context.SaveChanges();
        }
    }
}

// Usage in service layer
public class UserService
{
    private readonly IRepository _userRepository;
    
    public UserService(IRepository userRepository)
    {
        _userRepository = userRepository;
    }
    
    public void RegisterUser(User user)
    {
        _userRepository.Add(user);
    }
}

Design Patterns in CORTEX Architecture

CORTEX extensively uses design patterns throughout its architecture to ensure maintainability, extensibility, and testability. Here's how key patterns are implemented in the CORTEX codebase.

Strategy Pattern: Agent System

CORTEX uses the Strategy pattern for its agent system, allowing different AI agents to be swapped dynamically based on the task.

class BaseAgent(ABC):
    """Strategy interface for agents"""
    @abstractmethod
    def execute(self, context: AgentContext) -> AgentResult:
        pass

# Concrete strategies
class CodeReviewAgent(BaseAgent):
    def execute(self, context: AgentContext) -> AgentResult:
        # Code review logic
        pass

class TestGenerationAgent(BaseAgent):
    def execute(self, context: AgentContext) -> AgentResult:
        # Test generation logic
        pass

# Context that uses strategies
class TaskExecutor:
    def __init__(self, agent: BaseAgent):
        self.agent = agent  # Strategy injected
    
    def run_task(self, context: AgentContext):
        return self.agent.execute(context)

Observer Pattern: Event System

CORTEX uses the Observer pattern for its event notification system, notifying multiple components when significant events occur. 

# cortex-brain/core/events.py
class EventObserver(ABC):
    @abstractmethod
    def on_event(self, event: Event) -> None:
        pass

class HealthMonitor(EventObserver):
    def on_event(self, event: Event) -> None:
        if event.type == EventType.ERROR:
            self.log_health_issue(event)

class MetricsCollector(EventObserver):
    def on_event(self, event: Event) -> None:
        self.record_metric(event)

class EventBus:
    def __init__(self):
        self.observers: List[EventObserver] = []
    
    def subscribe(self, observer: EventObserver):
        self.observers.append(observer)
    
    def publish(self, event: Event):
        for observer in self.observers:
            observer.on_event(event)

Command Pattern: Orchestrators

CORTEX orchestrators use the Command pattern to encapsulate operations, enabling undo/redo and operation queuing. 

# src/orchestrators/commands.py
class Command(ABC):
    @abstractmethod
    def execute(self) -> CommandResult:
        pass
    
    @abstractmethod
    def undo(self) -> None:
        pass

class RefactorCommand(Command):
    def __init__(self, file_path: str, changes: List[Change]):
        self.file_path = file_path
        self.changes = changes
        self.backup = None
    
    def execute(self) -> CommandResult:
        self.backup = self.create_backup()
        return self.apply_changes()
    
    def undo(self) -> None:
        self.restore_backup(self.backup)

class CommandQueue:
    def __init__(self):
        self.commands: List[Command] = []
        self.executed: List[Command] = []
    
    def add_command(self, cmd: Command):
        self.commands.append(cmd)
    
    def execute_all(self):
        for cmd in self.commands:
            result = cmd.execute()
            self.executed.append(cmd)
    
    def undo_last(self):
        if self.executed:
            cmd = self.executed.pop()
            cmd.undo()

Facade Pattern: High-Level API

CORTEX provides a Facade to simplify complex subsystem interactions, offering a clean high-level API. 

# src/cortex_facade.py
class CORTEXFacade:
    """Simplified interface to complex CORTEX subsystems"""
    
    def __init__(self):
        self.brain = BrainManager()
        self.agents = AgentRegistry()
        self.orchestrators = OrchestratorFactory()
        self.validators = ValidationService()
    
    def analyze_code(self, file_path: str) -> AnalysisResult:
        """Simple method that coordinates multiple subsystems"""
        # Load file
        code = self.brain.load_file(file_path)
        
        # Get appropriate agent
        agent = self.agents.get_agent("code_analyzer")
        
        # Run analysis
        analysis = agent.analyze(code)
        
        # Validate results
        validated = self.validators.validate(analysis)
        
        return validated
    
    def run_tdd_cycle(self, test_file: str) -> TDDResult:
        """High-level TDD workflow"""
        orchestrator = self.orchestrators.create("tdd")
        return orchestrator.run(test_file)
