REST API Design Best Practices

Build RESTful APIs Following Industry Standards

API Design Excellence v1.0.0 Production-Ready

What is REST?

REST (Representational State Transfer) is an architectural style for designing networked applications. It relies on stateless, client-server communication, typically over HTTP. REST APIs expose resources (nouns) and use standard HTTP methods (verbs) to manipulate them.

REST Architectural Constraints

Client-Server Separation

Separate concerns between client and server. Server manages data and business logic, client manages UI and user state.

  • Scalability
  • Portability
  • Independent evolution

Statelessness

Each request contains all information needed to process it. No session state stored on server.

  • Scalability
  • Reliability
  • Simplified server

Cacheability

Responses must define themselves as cacheable or not using Cache-Control headers and ETags.

  • Performance
  • Reduced server load
  • Bandwidth savings

Uniform Interface

Standardized way to interact with resources via URIs, representations, self-descriptive messages, and HATEOAS.

  • Simplicity
  • Discoverability
  • Evolvability

Layered System

Client cannot tell if connected directly to end server. Supports proxies, gateways, load balancers.

  • Scalability
  • Security
  • Legacy encapsulation

Resource Naming Conventions

✅ Use Nouns, Not Verbs

Good: /users, /orders, /products

Bad: /getUsers, /createOrder

HTTP methods provide the verbs (GET, POST, PUT, DELETE)

✅ Use Plural Nouns for Collections

Good: /users, /users/123

Bad: /user, /user/123

Consistency - all resources treated as collections

✅ Use Lowercase and Hyphens

Good: /order-items, /shipping-addresses

Bad: /OrderItems, /shipping_addresses

URL case-sensitivity and readability

✅ Nest Resources for Relationships

Good: /users/123/orders, /orders/456/items

Bad: /userOrders?userId=123

Express hierarchy and ownership clearly

✅ Limit Nesting Depth to 2-3 Levels

Good: /authors/123/books/456/reviews

Bad: /publishers/1/authors/2/books/3/chapters/4/sections/5

Avoid complexity and coupling

HTTP Methods

GET

Retrieve resource(s)

  • ✅ Safe
  • ✅ Idempotent
  • ❌ No Request Body

Status: 200, 304, 404

POST

Create new resource

  • ❌ Not Safe
  • ❌ Not Idempotent
  • ✅ Request Body

Status: 201, 400, 409

PUT

Replace entire resource

  • ❌ Not Safe
  • ✅ Idempotent
  • ✅ Request Body

Status: 200, 204, 404

PATCH

Partial update

  • ❌ Not Safe
  • ✅ Idempotent
  • ✅ Request Body

Status: 200, 400, 404

DELETE

Remove resource

  • ❌ Not Safe
  • ✅ Idempotent
  • ❌ No Request Body

Status: 204, 404

HTTP Status Codes

Success (2xx)

  • 200 OK - GET, PUT, PATCH successful with response body
  • 201 Created - POST successful, include Location header
  • 204 No Content - DELETE, PUT successful with no response body

Redirection (3xx)

  • 301 Moved Permanently - Resource permanently moved, include Location header
  • 304 Not Modified - Conditional GET with valid cache

Client Error (4xx)

  • 400 Bad Request - Invalid request syntax or validation error
  • 401 Unauthorized - Authentication required or failed
  • 403 Forbidden - Authenticated but insufficient permissions
  • 404 Not Found - Resource does not exist
  • 409 Conflict - Resource state conflict (e.g., duplicate)
  • 422 Unprocessable Entity - Semantic validation error
  • 429 Too Many Requests - Rate limit exceeded

Server Error (5xx)

  • 500 Internal Server Error - Unexpected server error
  • 503 Service Unavailable - Temporary server overload or maintenance

Pagination Patterns

Offset-Based Pagination

Use page number and size for navigation

Request: GET /users?page=2&limit=20

{
  "data": ["user1", "user2"],
  "pagination": {
    "page": 2,
    "limit": 20,
    "total_pages": 10,
    "total_items": 200
  }
}
  • ✅ Simple and familiar
  • ✅ Supports jumping to specific page
  • ❌ Performance degradation with large offsets
  • ❌ Inconsistent results with concurrent inserts/deletes

Cursor-Based Pagination

Use opaque cursor token for next page

Request: GET /users?cursor=eyJpZCI6MTIzfQ&limit=20

{
  "data": ["user1", "user2"],
  "pagination": {
    "next_cursor": "eyJpZCI6MTQzfQ",
    "has_more": true
  }
}
  • ✅ Consistent results
  • ✅ Better performance
  • ✅ Handles inserts/deletes gracefully
  • ❌ Cannot jump to specific page
  • ❌ More complex implementation

Link Header Pagination

Use standard Link header for pagination URLs

Link: </users?page=3>; rel="next",
      </users?page=1>; rel="first",
      </users?page=10>; rel="last"
  • ✅ Standard (RFC 5988)
  • ✅ Discoverable
  • ✅ Separates concerns

Filtering and Sorting

Filtering Patterns

  • Field-value pairs: GET /users?role=admin&status=active
  • Comparison operators: GET /orders?total[gte]=100&created_at[lt]=2025-01-01
  • Complex filters (JSON): GET /users?filter={"age":{"$gte":18,"$lte":65}}

Filtering Best Practices

  • Support multiple filters with AND logic by default
  • Document available filter fields and operators
  • Validate filter parameters
  • Consider search endpoints for complex queries (POST /users/search)

Sorting Patterns

  • Single field: GET /users?sort=created_at (ascending by default)
  • Multiple fields: GET /users?sort=last_name,first_name
  • Direction prefix: GET /users?sort=-created_at,+name (- for desc, + for asc)

Sorting Best Practices

  • Default to meaningful sort order (e.g., created_at desc)
  • Limit sortable fields to indexed columns
  • Document available sort fields

Error Response Format

Standardized error format with error codes, messages, and field-level details:

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input provided",
    "details": [
      {
        "field": "email",
        "message": "Invalid email format",
        "code": "INVALID_FORMAT"
      },
      {
        "field": "age",
        "message": "Must be between 18 and 120",
        "code": "OUT_OF_RANGE"
      }
    ],
    "request_id": "req_abc123xyz",
    "timestamp": "2025-12-22T10:30:00Z"
  }
}

Standard Error Codes

  • VALIDATION_ERROR (400) - Input validation failed
  • AUTHENTICATION_FAILED (401) - Authentication credentials invalid
  • INSUFFICIENT_PERMISSIONS (403) - User lacks required permissions
  • RESOURCE_NOT_FOUND (404) - Requested resource does not exist
  • CONFLICT (409) - Resource state conflict
  • RATE_LIMIT_EXCEEDED (429) - Too many requests
  • INTERNAL_ERROR (500) - Unexpected server error

Security Best Practices

Authentication

  • OAuth 2.0: Third-party integrations (use Authorization Code + PKCE)
  • JWT: Stateless authentication (use short expiration: 15 minutes)
  • API Keys: Simple server-to-server communication

Authorization

  • Implement Role-Based Access Control (RBAC)
  • Verify permissions on every request
  • Use least privilege principle
  • Return 403 Forbidden for insufficient permissions

Security Headers

  • Strict-Transport-Security - Enforce HTTPS
  • X-Content-Type-Options: nosniff - Prevent MIME sniffing
  • X-Frame-Options: DENY - Prevent clickjacking
  • Content-Security-Policy - Prevent XSS attacks

Resource Naming Examples

✅ Good Resource URIs

GET    /users                    # List users
GET    /users/123                # Get specific user
POST   /users                    # Create user
PUT    /users/123                # Replace user
PATCH  /users/123                # Update user fields
DELETE /users/123                # Delete user

GET    /users/123/orders         # Get user's orders
POST   /users/123/orders         # Create order for user
GET    /orders/456/items         # Get order items
POST   /orders/456/items         # Add item to order

GET    /products?category=books&price[lte]=50  # Filtered products
GET    /users?sort=-created_at&limit=20        # Sorted & paginated

❌ Bad Resource URIs

GET    /getUsers                 # Verb in URL (use GET /users)
POST   /createUser               # Verb in URL (use POST /users)
GET    /user/123                 # Singular (use /users/123)
GET    /UserProfiles             # PascalCase (use /user-profiles)
GET    /users_by_role?role=admin # Underscore (use /users?role=admin)
DELETE /deleteUserById/123       # Verb + mixed naming

API Design Validator

# CORTEX REST API Design Validator
class RestApiValidator:
    def validate_api(self, api_spec: dict) -> List[Violation]:
        violations = []
        
        # Validate resource naming
        for endpoint in api_spec['endpoints']:
            # Check for verbs in URLs
            if self.has_verb_in_url(endpoint.path):
                violations.append(Violation(
                    rule="Use nouns, not verbs",
                    severity="HIGH",
                    endpoint=endpoint.path,
                    suggestion="Remove verb, use HTTP method instead"
                ))
            
            # Check for singular nouns
            if self.is_singular_resource(endpoint.path):
                violations.append(Violation(
                    rule="Use plural nouns for collections",
                    severity="MEDIUM",
                    endpoint=endpoint.path,
                    suggestion=f"Change to plural: {self.pluralize(endpoint.path)}"
                ))
            
            # Check nesting depth
            nesting_depth = endpoint.path.count('/')
            if nesting_depth > 4:  # /users/123/orders/456 = 4 levels
                violations.append(Violation(
                    rule="Limit nesting depth to 2-3 levels",
                    severity="MEDIUM",
                    endpoint=endpoint.path,
                    suggestion="Consider flattening hierarchy"
                ))
        
        # Validate HTTP methods
        for endpoint in api_spec['endpoints']:
            # GET should be idempotent and safe
            if endpoint.method == 'GET' and endpoint.modifies_state:
                violations.append(Violation(
                    rule="GET must not modify state",
                    severity="CRITICAL",
                    endpoint=f"{endpoint.method} {endpoint.path}",
                    suggestion="Use POST for state-changing operations"
                ))
            
            # POST should return 201 Created
            if endpoint.method == 'POST' and 201 not in endpoint.status_codes:
                violations.append(Violation(
                    rule="POST should return 201 Created",
                    severity="MEDIUM",
                    endpoint=f"{endpoint.method} {endpoint.path}",
                    suggestion="Add 201 Created response with Location header"
                ))
        
        # Validate status code usage
        for endpoint in api_spec['endpoints']:
            if endpoint.method == 'DELETE' and 204 not in endpoint.status_codes:
                violations.append(Violation(
                    rule="DELETE should return 204 No Content",
                    severity="LOW",
                    endpoint=f"{endpoint.method} {endpoint.path}"
                ))
        
        return violations

Automated API Testing

# CORTEX REST API Tester
class RestApiTester:
    def test_rest_constraints(self, base_url: str):
        results = []
        
        # Test statelessness
        token = self.authenticate(base_url)
        response1 = self.make_request(f"{base_url}/users", headers={"Authorization": f"Bearer {token}"})
        response2 = self.make_request(f"{base_url}/users", headers={"Authorization": f"Bearer {token}"})
        
        if response1.data != response2.data:
            results.append(TestFailure(
                test="Statelessness",
                message="Same request returned different data (session state?)"
            ))
        
        # Test idempotency of PUT
        user_data = {"name": "Test User"}
        put1 = self.make_request(f"{base_url}/users/123", method="PUT", json=user_data)
        put2 = self.make_request(f"{base_url}/users/123", method="PUT", json=user_data)
        
        if put1.status_code != put2.status_code or put1.data != put2.data:
            results.append(TestFailure(
                test="PUT Idempotency",
                message="PUT requests with same data returned different results"
            ))
        
        # Test cacheability
        response = self.make_request(f"{base_url}/users/123")
        if 'Cache-Control' not in response.headers and 'ETag' not in response.headers:
            results.append(TestWarning(
                test="Cacheability",
                message="No caching headers found (Cache-Control, ETag)"
            ))
        
        return results
