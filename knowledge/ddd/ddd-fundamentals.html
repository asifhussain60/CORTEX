Overview

Domain-Driven Design (DDD) is an approach to software development that focuses on understanding and modeling the business domain, using ubiquitous language shared between developers and domain experts.

DDD Core Principles:
  • Ubiquitous Language: Shared vocabulary between developers and domain experts
  • Bounded Contexts: Clear boundaries for models and teams
  • Focus on Core Domain: Invest in what differentiates your business
  • Continuous Learning: Evolve understanding through collaboration
  • Model-Driven Design: Code reflects domain concepts directly

Strategic Design - Bounded Contexts

Define Explicit Bounded Contexts

HIGH

A bounded context is an explicit boundary where a domain model is defined and applicable. Same term can have different meanings in different contexts.

✅ Good - Separate Bounded Contexts

// Sales Context - Customer means "buyer"
namespace ECommerce.Sales
{
    public class Customer
    {
        public CustomerId Id { get; private set; }
        public string Name { get; private set; }
        public ShoppingCart Cart { get; private set; }
        public List OrderHistory { get; private set; }
        public decimal CreditLimit { get; private set; }
        
        public void PlaceOrder(Order order)
        {
            if (order.Total > CreditLimit)
                throw new InsufficientCreditException();
            
            OrderHistory.Add(order);
        }
    }
}

// Support Context - Customer means "support case subject"
namespace ECommerce.Support
{
    public class Customer
    {
        public CustomerId Id { get; private set; }
        public string Name { get; private set; }
        public string Email { get; private set; }
        public List Tickets { get; private set; }
        public SupportTier Tier { get; private set; }
        
        public void CreateTicket(string issue)
        {
            var ticket = new Ticket(this, issue, Tier);
            Tickets.Add(ticket);
        }
    }
}

// Different models, same concept, different contexts
Context Mapping: Define relationships between bounded contexts using patterns: Shared Kernel, Customer-Supplier, Conformist, Anticorruption Layer, Published Language.

Use Ubiquitous Language Consistently

HIGH

Use domain expert terminology in code, tests, and conversations. No translation layer between business and code.

✅ Good - Domain Language

// Insurance domain terms used directly
class Policy {
  private premium: Money;
  private deductible: Money;
  private coverageLimit: Money;
  
  underwrite(applicant: Applicant): UnderwritingDecision {
    const riskAssessment = this.assessRisk(applicant);
    
    if (riskAssessment.isHighRisk()) {
      return UnderwritingDecision.decline(
        "Applicant exceeds risk tolerance"
      );
    }
    
    return UnderwritingDecision.approve(
      this.calculatePremium(riskAssessment)
    );
  }
  
  // Domain expert would understand this code
}

❌ Bad - Technical Language

// Generic terms, lost domain meaning
class Item {
  private price: number;
  private minPayment: number;
  private maxValue: number;
  
  process(person: Person): Result {
    const score = this.calculate(person);
    
    if (score > 0.7) {
      return Result.reject("Score too high");
    }
    
    return Result.accept(this.computePrice(score));
  }
  
  // Domain expert wouldn't recognize their domain
}

Identify Core, Supporting, and Generic Subdomains

MEDIUM

Core domain provides competitive advantage (invest heavily). Supporting domains are necessary but not differentiating. Generic domains can use off-the-shelf solutions.

Subdomain Strategy:
  • Core Domain: Unique business logic, competitive advantage - Build custom, invest in best team
  • Supporting: Necessary but not special - Build simple, adequate solution
  • Generic: Solved problem (auth, payment) - Buy or use OSS, minimal customization

Tactical Patterns Overview

Apply Tactical Patterns Within Bounded Contexts

HIGH

Tactical patterns (Entities, Value Objects, Aggregates, Repositories, Domain Events) are used within a bounded context to model the domain.

Tactical Pattern Hierarchy:
  • Entity: Object with identity that persists over time
  • Value Object: Immutable object defined by attributes, no identity
  • Aggregate: Cluster of entities/VOs with consistency boundary
  • Aggregate Root: Single entity entry point to aggregate
  • Repository: Abstracts persistence for aggregates
  • Domain Service: Stateless operations not belonging to entities
  • Domain Event: Something significant that happened in domain

Entities vs Value Objects

Use Entities for Objects with Identity

HIGH

Entities have unique identity that persists through lifecycle. Equality based on ID, not attributes.

✅ Good - Entity with Identity

public class Order
{
    public OrderId Id { get; private set; }
    public CustomerId CustomerId { get; private set; }
    public DateTime OrderDate { get; private set; }
    private List _orderLines;
    public OrderStatus Status { get; private set; }
    
    // Entity equality based on ID
    public override bool Equals(object obj)
    {
        if (obj is Order other)
            return Id.Equals(other.Id);
        return false;
    }
    
    // Business logic methods
    public void AddLine(Product product, int quantity)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException(
                "Cannot modify confirmed order"
            );
        
        _orderLines.Add(new OrderLine(product, quantity));
    }
    
    public void Confirm()
    {
        if (!_orderLines.Any())
            throw new InvalidOperationException(
                "Cannot confirm empty order"
            );
        
        Status = OrderStatus.Confirmed;
        // Raise domain event
        DomainEvents.Raise(new OrderConfirmedEvent(Id));
    }
}

Use Value Objects for Descriptive Concepts

HIGH

Value Objects are immutable, defined by attributes, no identity. Two VOs with same attributes are equal.

✅ Good - Value Object

public class Money : IEquatable
{
    public decimal Amount { get; }
    public Currency Currency { get; }
    
    public Money(decimal amount, Currency currency)
    {
        if (amount < 0)
            throw new ArgumentException("Amount cannot be negative");
        
        Amount = amount;
        Currency = currency ?? throw new ArgumentNullException();
    }
    
    // Immutable - operations return new instance
    public Money Add(Money other)
    {
        if (Currency != other.Currency)
            throw new InvalidOperationException(
                "Cannot add different currencies"
            );
        
        return new Money(Amount + other.Amount, Currency);
    }
    
    public Money Multiply(decimal factor)
    {
        return new Money(Amount * factor, Currency);
    }
    
    // Equality based on values
    public bool Equals(Money other)
    {
        if (other is null) return false;
        return Amount == other.Amount && Currency == other.Currency;
    }
    
    public override int GetHashCode()
    {
        return HashCode.Combine(Amount, Currency);
    }
}

❌ Bad - Primitive Obsession

// Using primitives instead of value objects
public class Order
{
    public decimal TotalAmount { get; set; }
    public string Currency { get; set; }
    
    public void AddAmount(decimal amount, string currency)
    {
        // No validation, no invariants
        // Can mix currencies accidentally
        TotalAmount += amount;
        // Lost domain concepts
    }
}

Aggregate Design

Design Small Aggregates

HIGH

Keep aggregates small - just enough to enforce invariants. Large aggregates cause performance and concurrency issues.

✅ Good - Small Aggregate

// Aggregate: Order (root) + OrderLines
class Order {
  private id: OrderId;
  private customerId: CustomerId; // Reference by ID
  private lines: OrderLine[] = [];
  private status: OrderStatus;
  
  // Invariant: Total must be positive
  addLine(productId: ProductId, quantity: number): void {
    if (this.status !== OrderStatus.Draft) {
      throw new Error("Cannot modify confirmed order");
    }
    
    this.lines.push(new OrderLine(productId, quantity));
  }
  
  confirm(): void {
    if (this.lines.length === 0) {
      throw new Error("Cannot confirm empty order");
    }
    
    // Invariants checked before status change
    this.status = OrderStatus.Confirmed;
  }
  
  // Customer is separate aggregate
  // Reference by ID, not object
}

❌ Bad - Large Aggregate

// Overly large aggregate
class Order {
  private id: OrderId;
  private customer: Customer;      // Full object!
  private lines: OrderLine[];
  private shipment: Shipment;      // Full object!
  private invoices: Invoice[];     // Collection!
  private payments: Payment[];     // Collection!
  
  // Loading order loads entire object graph
  // Concurrent updates cause conflicts
  // Performance issues
}

Reference Other Aggregates by ID

HIGH

Aggregates reference other aggregates by ID only, not by object reference. Enforces boundaries and prevents large object graphs.

✅ Good - Reference by ID

# Aggregate Root: Product
class Product:
    def __init__(self, product_id: ProductId, name: str, category_id: CategoryId):
        self._id = product_id
        self._name = name
        self._category_id = category_id  # Reference by ID
        
    def change_category(self, new_category_id: CategoryId):
        # Domain logic
        self._category_id = new_category_id
        
    # Category is separate aggregate
    # Loaded separately when needed

# Repository fetches related data
class ProductService:
    def get_product_with_category(self, product_id: ProductId):
        product = self.product_repo.find_by_id(product_id)
        category = self.category_repo.find_by_id(product.category_id)
        
        return ProductDto(product, category)

Enforce Invariants Within Aggregate Boundaries

HIGH

Aggregate root is responsible for maintaining invariants for entire aggregate. All modifications go through root.

✅ Good - Invariant Enforcement

public class ShoppingCart
{
    private List _items = new();
    private Money _total;
    private const int MaxItems = 50;
    
    // All modifications through root
    public void AddItem(Product product, int quantity)
    {
        // Enforce invariants
        if (_items.Count >= MaxItems)
            throw new DomainException("Cart is full");
        
        if (quantity <= 0 || quantity > 100)
            throw new DomainException("Invalid quantity");
        
        var existingItem = _items.FirstOrDefault(i => i.ProductId == product.Id);
        
        if (existingItem != null)
            existingItem.IncreaseQuantity(quantity); // Through item method
        else
            _items.Add(new CartItem(product.Id, quantity, product.Price));
        
        // Recalculate total to maintain invariant
        RecalculateTotal();
    }
    
    private void RecalculateTotal()
    {
        _total = _items
            .Select(i => i.LineTotal)
            .Aggregate(Money.Zero, (sum, line) => sum.Add(line));
    }
    
    // No public setter for _items
    // Invariants always maintained
}
