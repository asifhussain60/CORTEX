Overview

SQL best practices covering query optimization, proper indexing, transaction management, and security to build performant and secure database applications.

Key SQL Principles:
  • Query Efficiency: Write queries that minimize database load
  • Index Optimization: Strategic indexing for read/write balance
  • Data Integrity: Use transactions and constraints
  • Security: Prevent SQL injection and unauthorized access
  • Normalization: Reduce data redundancy appropriately

Query Optimization

Select Only Required Columns

HIGH

Avoid SELECT * - explicitly list only the columns you need to reduce network transfer and memory usage.

✅ Good - Explicit Column Selection

-- Only select required columns
SELECT 
    u.user_id,
    u.username,
    u.email,
    u.created_at
FROM users u
WHERE u.is_active = 1
ORDER BY u.created_at DESC
LIMIT 100;

-- Join with specific columns
SELECT 
    o.order_id,
    o.order_date,
    c.customer_name,
    c.email
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date >= '2024-01-01';

❌ Bad - SELECT *

-- Retrieves all columns, even unused ones
SELECT *
FROM users
WHERE is_active = 1;

-- Ambiguous in joins - which table's columns?
SELECT *
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id;
-- Gets all columns from both tables
-- Wastes bandwidth, memory, unclear columns
Performance Impact: SELECT * can retrieve BLOB/TEXT columns you don't need, significantly increasing query time and memory usage. It also breaks code when table schema changes.

Use EXISTS Instead of COUNT for Existence Checks

HIGH

When checking if records exist, use EXISTS instead of COUNT(*) - it stops scanning once a match is found.

✅ Good - EXISTS for Checks

-- Stops at first match
SELECT 
    p.product_id,
    p.product_name,
    CASE 
        WHEN EXISTS (
            SELECT 1 
            FROM orders o 
            WHERE o.product_id = p.product_id
        )
        THEN 'Has Orders'
        ELSE 'No Orders'
    END AS order_status
FROM products p;

❌ Bad - COUNT for Existence

-- Counts all matches unnecessarily
SELECT 
    p.product_id,
    p.product_name,
    CASE 
        WHEN (
            SELECT COUNT(*) 
            FROM orders o 
            WHERE o.product_id = p.product_id
        ) > 0
        THEN 'Has Orders'
        ELSE 'No Orders'
    END AS order_status
FROM products p;
-- Scans entire table even if 1000 orders exist

Use UNION ALL Instead of UNION When Possible

MEDIUM

UNION removes duplicates (expensive sort operation). Use UNION ALL if duplicates are acceptable or impossible.

✅ Good - UNION ALL

-- No duplicate removal needed
SELECT order_id, customer_id, order_date
FROM orders_2024
UNION ALL
SELECT order_id, customer_id, order_date
FROM orders_2023
ORDER BY order_date DESC;

-- Duplicates already impossible (distinct sources)
SELECT 'premium' AS tier, user_id FROM premium_users
UNION ALL
SELECT 'basic' AS tier, user_id FROM basic_users;

Indexing Strategies

Index Foreign Keys and WHERE Clauses

HIGH

Create indexes on columns frequently used in WHERE, JOIN, and ORDER BY clauses. Always index foreign keys.

✅ Good - Strategic Indexes

-- Index foreign keys for joins
CREATE INDEX idx_orders_customer_id 
ON orders(customer_id);

-- Index WHERE clause columns
CREATE INDEX idx_users_email 
ON users(email);

-- Composite index for common query patterns
CREATE INDEX idx_orders_customer_date 
ON orders(customer_id, order_date DESC);

-- Covering index includes SELECT columns
CREATE INDEX idx_products_category_covering 
ON products(category_id, product_name, price);
Index Order Matters: In composite indexes like (customer_id, order_date), queries can use the index for customer_id alone, but NOT for order_date alone. Put most selective columns first.

Avoid Over-Indexing

MEDIUM

Too many indexes slow down INSERT/UPDATE/DELETE operations. Balance read vs write performance.

✅ Good - Selective Indexing

-- Analyze query patterns first
-- Index only frequently used query patterns

-- High-read table: More indexes OK
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_username ON users(username);
CREATE INDEX idx_users_created ON users(created_at);

-- High-write table: Minimal indexes
-- Only index critical queries
CREATE INDEX idx_audit_log_timestamp 
ON audit_log(log_timestamp);
-- Avoid indexing columns rarely queried

Transaction Management

Use Transactions for Multi-Step Operations

HIGH

Wrap related operations in transactions to ensure atomicity. Either all operations succeed or all are rolled back.

✅ Good - Transaction for Money Transfer

BEGIN TRANSACTION;

-- Deduct from source account
UPDATE accounts
SET balance = balance - 100.00
WHERE account_id = 12345
  AND balance >= 100.00;

-- Check if deduction succeeded
IF @@ROWCOUNT = 0
BEGIN
    ROLLBACK TRANSACTION;
    RAISERROR('Insufficient funds', 16, 1);
    RETURN;
END

-- Add to destination account
UPDATE accounts
SET balance = balance + 100.00
WHERE account_id = 67890;

-- Record transaction
INSERT INTO transactions (from_account, to_account, amount, timestamp)
VALUES (12345, 67890, 100.00, GETDATE());

COMMIT TRANSACTION;

❌ Bad - No Transaction

-- Without transaction - partial failure possible
UPDATE accounts
SET balance = balance - 100.00
WHERE account_id = 12345;

-- If this fails, money disappears!
UPDATE accounts
SET balance = balance + 100.00
WHERE account_id = 67890;

Set Appropriate Isolation Levels

MEDIUM

Choose transaction isolation level based on concurrency requirements vs performance tradeoff.

✅ Good - Isolation Level Selection

-- READ COMMITTED (default) - prevents dirty reads
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRANSACTION;
SELECT * FROM products WHERE product_id = 123;
COMMIT;

-- REPEATABLE READ - prevents non-repeatable reads
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 456;
-- Same SELECT will return same value even if others update
SELECT balance FROM accounts WHERE account_id = 456;
COMMIT;

-- SNAPSHOT - readers don't block writers
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
-- Reads consistent snapshot, no locks on read
SELECT * FROM orders WHERE order_date >= '2024-01-01';
COMMIT;

SQL Security

Always Use Parameterized Queries

HIGH

Never concatenate user input into SQL strings. Use parameterized queries or prepared statements to prevent SQL injection.

✅ Good - Parameterized Query

# Python with parameterized query
import psycopg2

def get_user(username):
    conn = psycopg2.connect(database="mydb")
    cursor = conn.cursor()
    
    # Parameter placeholder prevents injection
    cursor.execute(
        "SELECT * FROM users WHERE username = %s",
        (username,)
    )
    
    result = cursor.fetchone()
    cursor.close()
    conn.close()
    return result

# C# with Entity Framework
var user = await context.Users
    .Where(u => u.Username == username)
    .FirstOrDefaultAsync();

❌ Bad - String Concatenation (SQL INJECTION!)

# VULNERABLE TO SQL INJECTION
def get_user_unsafe(username):
    conn = psycopg2.connect(database="mydb")
    cursor = conn.cursor()
    
    # NEVER DO THIS!
    query = f"SELECT * FROM users WHERE username = '{username}'"
    cursor.execute(query)
    
    # Attacker input: "' OR '1'='1"
    # Query becomes: SELECT * FROM users WHERE username = '' OR '1'='1'
    # Returns all users!
⚠️ Critical Security Issue: String concatenation allows attackers to inject malicious SQL. They can read, modify, or delete any data, create admin accounts, or even execute system commands.

Apply Principle of Least Privilege

HIGH

Database users should have only the minimum permissions necessary. Never use admin accounts for application connections.

✅ Good - Limited Permissions

-- Create application user with limited permissions
CREATE USER app_reader WITH PASSWORD 'secure_password';

-- Read-only access to specific tables
GRANT SELECT ON users TO app_reader;
GRANT SELECT ON products TO app_reader;
GRANT SELECT ON orders TO app_reader;

-- Create user for API with write access
CREATE USER app_writer WITH PASSWORD 'secure_password';
GRANT SELECT, INSERT, UPDATE ON orders TO app_writer;
GRANT SELECT ON products TO app_writer;
-- NO DELETE permission
-- NO access to sensitive tables like audit_logs

-- Revoke dangerous permissions
REVOKE ALL ON admin_settings FROM app_writer;
