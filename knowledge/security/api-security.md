Understanding JSON Web Tokens
In this module, we'll be discussing JSON Web Token. Now, before we dive into working with JSON Web Token, let's first go through a quick crash course to discuss what they are. JSON Web Tokens, sometimes refer to as JWT, is an open‑source standard. It is a self‑contained way to securely transmit information between two different parties, such as a client and a server. Now that data that is being exchanged is sometimes referred to as a claim, and it is encoded as a JSON on object. Now, we have two use cases, the first one is authentication. Now, typically, how this works is that the user is going to go and log in using a website, and the credentials are going to be sent over to the server where they're going to be validated. Once the credentials are validated, a JSON Web Token is going to be created and sent back over to the client. Now, any time that the user wants to go and access a protected resource, they need to go and include the token as a bearer token, and this needs to be sent back over in any request to protect the resources. The server is then going to go and validate the token, and if it is valid, it'll go and grant the user access to the protected resources. The next use case we have is information exchange. The JSON Web Token is issued, and it could be used to securely transmit information between two different parties. Because the token is signed, the receiving party can go in and then verify the contents has not been tampered with. Okay, let's go and talk about how all this works. A JSON Web Token is broken up into three parts. The first part is going to be the header, followed by the payload, and finally the signature, and we'll be breaking these down in a little bit more detail in a moment. So with these three different parts, they are going to be concatenated together using a period. So, the x's are going to be the header, the y's are going to be the payload, and the z's are the signature. Now the header consists of two components, the algorithm and then the type. The algorithm can be something like an HMAC, a SHA‑256, or a RSA. And in the instance of this example, we have a HS256, which is going to be one of the weaker encryption methods. Now, this is going to be the first part of the JSON Web Token, and it is going to be encoded in base64 URL. The second part of the token is going to be the payload, and the payload is where we go and define our claims. Now, the claim can be anything you want to be for the most part, it is arbitrary, but it is not recommended to include any kind of sensitive data. Typically, something like a user ID is perfectly just fine. Now we have three different types of claims we can use, which is registered, public, and private. A registered claim is a predefined claim that is not mandatory, but is recommended. Public claims can be defined at will. And then we have private claims, and these claims are created to go and share information between two different parties. And the final part of our JSON Web Token is going to be the signature, and it is comprised of three things, the header, the payload, and then we have a secret, which is going to be used to encode both. Now, I also want to point out that both the header and the payload is going to be base64 encoded. Now, the signature is going to be used to go and verify that the message was not tampered with while it was in transit, and the final result is going to be our JSON Web Token. And as you can see, the area that is marked in orange is going to be the header, the pinkish color is the payload, and green is going to be the signature. Now, this is an actual token I created, and you can actually go and decode it. And you can see on the Decoded side, we have the HEADER, HS256. For the algorithm, the type is a JSON Web Token.
