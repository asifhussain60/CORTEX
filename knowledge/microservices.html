Microservices Architecture

Resilience patterns, CQRS, Sagas, and distributed system design for scalable, fault-tolerant services

🎯 Category Overview

Microservices Architecture decomposes applications into independently deployable services, each with clear boundaries and single responsibilities. This category covers resilience patterns, event-driven communication, CQRS, Sagas, and strategies for building fault-tolerant distributed systems.

Key Concepts

  • Resilience Patterns: Circuit breaker, retry, timeout, bulkhead, and fallback patterns for fault tolerance
  • Event-Driven Architecture: Domain events, event sourcing, and asynchronous communication between services
  • CQRS: Command Query Responsibility Segregation for optimized read and write models
  • Sagas: Distributed transaction management with compensation logic
  • Service Boundaries: Defining service boundaries based on bounded contexts
  • Communication Patterns: Synchronous REST/gRPC and asynchronous messaging

Resilience Patterns

Resilience patterns protect your system from cascading failures and enable graceful degradation. Critical for distributed systems where failures are inevitable.

Circuit Breaker Pattern

Automatically stop calling failing service to prevent cascade failures. Opens circuit after threshold of failures, closes after recovery period.

// Using Polly library in C#
var circuitBreakerPolicy = Policy
    .Handle()
    .CircuitBreakerAsync(
        exceptionsAllowedBeforeBreaking: 3,
        durationOfBreak: TimeSpan.FromSeconds(30),
        onBreak: (exception, duration) => {
            Log.Warning("Circuit breaker opened");
        },
        onReset: () => {
            Log.Information("Circuit breaker reset");
        }
    );

// Use the policy
var result = await circuitBreakerPolicy.ExecuteAsync(async () => {
    return await httpClient.GetAsync("https://api.example.com/data");
});
// Using Resilience4j in Java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)              // Open at 50% failure rate
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .slidingWindowSize(10)                  // Last 10 calls
    .permittedNumberOfCallsInHalfOpenState(3)
    .build();

CircuitBreakerRegistry registry = CircuitBreakerRegistry.of(config);
CircuitBreaker circuitBreaker = registry.circuitBreaker("paymentService");

Supplier decoratedSupplier = CircuitBreaker
    .decorateSupplier(circuitBreaker, () -> callExternalService());

Try result = Try.ofSupplier(decoratedSupplier)
    .recover(throwable -> "Fallback response");

Retry Pattern with Exponential Backoff

Handle transient failures by retrying with increasing delays. Use jitter to prevent thundering herd.

import time
import random
from functools import wraps

def retry_with_backoff(max_retries=3, base_delay=1, max_delay=60):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            retries = 0
            while retries < max_retries:
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    retries += 1
                    if retries >= max_retries:
                        raise
                    
                    # Exponential backoff with jitter
                    delay = min(base_delay * (2 ** retries), max_delay)
                    jitter = random.uniform(0, delay * 0.1)
                    time.sleep(delay + jitter)
                    
                    print(f"Retry {retries}/{max_retries} after {delay}s")
        return wrapper
    return decorator

@retry_with_backoff(max_retries=3)
def call_external_api():
    response = requests.get("https://api.example.com/data")
    response.raise_for_status()
    return response.json()

# Retries: 1s, 2s, 4s with jitter

Isolate resources to prevent total system failure. Separate thread pools for different dependencies.

Fallback Pattern - Graceful Degradation

Return cached data or degraded functionality when service fails. Never show full error to users.

async function getUserProfile(userId) {
    try {
        // Try primary service
        const profile = await userService.getProfile(userId);
        await cache.set(`user:${userId}`, profile, 300);  // Cache 5 min
        return profile;
    } catch (error) {
        // Fallback to cache
        const cachedProfile = await cache.get(`user:${userId}`);
        if (cachedProfile) {
            logger.warn('Serving cached profile due to service failure');
            return { ...cachedProfile, stale: true };
        }
        
        // Final fallback - basic profile
        return getDefaultProfile();
    }
}

Event-Driven Architecture

Domain events enable loose coupling between services. Events record what happened in the domain (past tense, immutable).

Domain Event Design

// Base domain event
public abstract class DomainEvent {
    public Guid EventId { get; }
    public DateTime OccurredOn { get; }
    
    protected DomainEvent() {
        EventId = Guid.NewGuid();
        OccurredOn = DateTime.UtcNow;
    }
}

// Specific event (past tense naming)
public class OrderPlaced : DomainEvent {
    public Guid OrderId { get; }
    public Guid CustomerId { get; }
    public Money Total { get; }
    public DateTime OrderDate { get; }
    
    public OrderPlaced(Guid orderId, Guid customerId, Money total, DateTime orderDate) {
        OrderId = orderId;
        CustomerId = customerId;
        Total = total;
        OrderDate = orderDate;
    }
}

// Aggregate collects events
public abstract class AggregateRoot : Entity {
    private readonly List _domainEvents = new();
    
    public IReadOnlyList DomainEvents => _domainEvents.AsReadOnly();
    
    protected void AddDomainEvent(DomainEvent eventItem) {
        _domainEvents.Add(eventItem);
    }
    
    public void ClearDomainEvents() {
        _domainEvents.Clear();
    }
}

// Usage in aggregate
public class Order : AggregateRoot {
    public void Confirm() {
        if (Status != OrderStatus.Pending)
            throw new DomainException("Only pending orders can be confirmed");
        
        Status = OrderStatus.Confirmed;
        
        // Add domain event
        AddDomainEvent(new OrderConfirmed(Id, Total, DateTime.UtcNow));
    }
}

Outbox Pattern - Guaranteed Event Delivery

Save events to database in same transaction as aggregate. Background worker publishes events later.

public class OrderRepository : IOrderRepository {
    public async Task SaveAsync(Order order) {
        using var transaction = await _context.Database.BeginTransactionAsync();
        
        try {
            // Save aggregate
            _context.Orders.Update(order);
            
            // Save events to outbox table (same transaction)
            foreach (var @event in order.DomainEvents) {
                _context.OutboxEvents.Add(new OutboxEvent {
                    EventId = @event.EventId,
                    EventType = @event.GetType().Name,
                    EventData = JsonSerializer.Serialize(@event),
                    CreatedAt = DateTime.UtcNow,
                    Processed = false
                });
            }
            
            await _context.SaveChangesAsync();
            await transaction.CommitAsync();
            
            order.ClearDomainEvents();
        } catch {
            await transaction.RollbackAsync();
            throw;
        }
    }
}

// Background worker processes outbox
public class OutboxProcessor : BackgroundService {
    protected override async Task ExecuteAsync(CancellationToken stoppingToken) {
        while (!stoppingToken.IsCancellationRequested) {
            var pendingEvents = await _context.OutboxEvents
                .Where(e => !e.Processed)
                .Take(100)
                .ToListAsync();
            
            foreach (var outboxEvent in pendingEvents) {
                try {
                    var @event = DeserializeEvent(outboxEvent);
                    await _eventBus.PublishAsync(@event);
                    
                    outboxEvent.Processed = true;
                    outboxEvent.ProcessedAt = DateTime.UtcNow;
                } catch (Exception ex) {
                    outboxEvent.RetryCount++;
                    outboxEvent.LastError = ex.Message;
                }
            }
            
            await _context.SaveChangesAsync();
            await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
        }
    }
}

Event Sourcing

Store all state changes as sequence of events. Rebuild aggregate state by replaying events. Provides complete audit trail and temporal queries.

Event-Sourced Aggregate

public class BankAccount : EventSourcedAggregate {
    public Guid AccountId { get; private set; }
    public decimal Balance { get; private set; }
    public AccountStatus Status { get; private set; }
    
    // Event application methods (state changes)
    private void When(AccountOpened @event) {
        AccountId = @event.AccountId;
        Balance = @event.InitialBalance;
        Status = AccountStatus.Active;
    }
    
    private void When(MoneyDeposited @event) {
        Balance += @event.Amount;
    }
    
    private void When(MoneyWithdrawn @event) {
        Balance -= @event.Amount;
    }
    
    private void When(AccountClosed @event) {
        Status = AccountStatus.Closed;
    }
    
    // Commands generate events
    public static BankAccount Open(Guid accountId, decimal initialBalance) {
        var account = new BankAccount();
        account.ApplyEvent(new AccountOpened(accountId, initialBalance));
        return account;
    }
    
    public void Deposit(decimal amount) {
        if (Status != AccountStatus.Active)
            throw new DomainException("Cannot deposit to inactive account");
        
        if (amount <= 0)
            throw new DomainException("Amount must be positive");
        
        ApplyEvent(new MoneyDeposited(AccountId, amount));
    }
    
    public void Withdraw(decimal amount) {
        if (Status != AccountStatus.Active)
            throw new DomainException("Cannot withdraw from inactive account");
        
        if (amount <= 0)
            throw new DomainException("Amount must be positive");
        
        if (Balance < amount)
            throw new DomainException("Insufficient funds");
        
        ApplyEvent(new MoneyWithdrawn(AccountId, amount));
    }
}

// Repository reconstructs from events
public async Task GetByIdAsync(Guid id) {
    var events = await _eventStore.GetEventsAsync(id);
    
    if (!events.Any())
        return null;
    
    var aggregate = (T)Activator.CreateInstance(typeof(T), true);
    aggregate.LoadFromHistory(events);  // Replay all events
    
    return aggregate;
}

CQRS - Command Query Responsibility Segregation

Separate read and write models. Optimize each independently. Natural fit with event sourcing and microservices.

Level Description Complexity Use Case
CQRS Lite Separate read/write methods, same database LOW Different classes for commands and queries
CQRS with Read Models Separate read models (projections), same database MEDIUM Write to normalized tables, read from denormalized views
CQRS with Separate Stores Different databases for reads and writes HIGH Write to SQL, read from Elasticsearch

CQRS Implementation

// Commands (write operations)
public class CreateOrderCommand {
    public Guid CustomerId { get; }
    public List Items { get; }
}

public class CreateOrderCommandHandler {
    private readonly IOrderRepository _repository;
    
    public async Task Handle(CreateOrderCommand command) {
        var order = Order.Create(command.CustomerId);
        
        foreach (var item in command.Items) {
            order.AddItem(item.ProductId, item.Quantity, item.UnitPrice);
        }
        
        await _repository.SaveAsync(order);
        return order.Id;
    }
}

// Queries (read operations)
public class GetOrderQuery {
    public Guid OrderId { get; }
}

public class GetOrderQueryHandler {
    private readonly AppDbContext _context;
    
    public async Task Handle(GetOrderQuery query) {
        // Read from denormalized view (optimized for reads)
        return await _context.OrderViews
            .Where(o => o.OrderId == query.OrderId)
            .Select(o => new OrderDto {
                OrderId = o.OrderId,
                CustomerName = o.CustomerName,
                Total = o.Total,
                Items = o.Items
            })
            .FirstOrDefaultAsync();
    }
}

// Event handler builds read model (projection)
public class OrderViewProjection : INotificationHandler {
    private readonly AppDbContext _context;
    
    public async Task Handle(OrderPlaced @event) {
        var orderView = new OrderView {
            OrderId = @event.OrderId,
            CustomerId = @event.CustomerId,
            CustomerName = await GetCustomerName(@event.CustomerId),
            Total = @event.Total,
            OrderDate = @event.OrderDate,
            Status = "Placed"
        };
        
        _context.OrderViews.Add(orderView);
        await _context.SaveChangesAsync();
    }
}

Sagas - Distributed Transaction Management

Coordinate long-running business processes across multiple services. Handle failures with compensating transactions.

Orchestration-Based Saga

public class OrderFulfillmentSaga {
    public Guid SagaId { get; private set; }
    public Guid OrderId { get; private set; }
    public SagaState State { get; private set; }
    public PaymentResult Payment { get; private set; }
    public ReservationResult Inventory { get; private set; }
    
    public enum SagaState {
        Started,
        PaymentProcessed,
        InventoryReserved,
        ShipmentCreated,
        Completed,
        Failed
    }
    
    public void Start(Guid orderId) {
        SagaId = Guid.NewGuid();
        OrderId = orderId;
        State = SagaState.Started;
        
        // Send command to payment service
        SendCommand(new ProcessPayment(orderId));
    }
    
    public void Handle(PaymentProcessed @event) {
        Payment = @event.Result;
        State = SagaState.PaymentProcessed;
        
        // Send command to inventory service
        SendCommand(new ReserveInventory(OrderId, @event.Items));
    }
    
    public void Handle(InventoryReserved @event) {
        Inventory = @event.Result;
        State = SagaState.InventoryReserved;
        
        // Send command to shipping service
        SendCommand(new CreateShipment(OrderId, @event.ReservationId));
    }
    
    public void Handle(ShipmentCreated @event) {
        State = SagaState.Completed;
    }
    
    // Compensating transactions for failures
    public void Handle(PaymentFailed @event) {
        State = SagaState.Failed;
        // No compensation needed - payment never happened
    }
    
    public void Handle(InventoryReservationFailed @event) {
        State = SagaState.Failed;
        
        // Compensate: Refund payment
        SendCommand(new RefundPayment(OrderId, Payment.TransactionId));
    }
    
    public void Handle(ShipmentCreationFailed @event) {
        State = SagaState.Failed;
        
        // Compensate: Release inventory and refund payment
        SendCommand(new ReleaseInventory(OrderId, Inventory.ReservationId));
        SendCommand(new RefundPayment(OrderId, Payment.TransactionId));
    }
}

Best Practices

  • Design for Failure: Assume services will fail, use resilience patterns
  • Idempotent Operations: Make handlers safe to retry (check if already processed)
  • Events are Immutable: Past tense naming, no setters, include relevant data
  • Eventual Consistency: Most business processes are async - embrace it
  • Use Outbox Pattern: Guarantees event delivery with transactional consistency
  • Bounded Contexts: Define service boundaries based on domain concepts, not technology
  • Health Checks: Implement /health endpoints for monitoring and orchestration
  • Distributed Tracing: Use correlation IDs to trace requests across services

Key Topics:

  • Circuit Breaker: Prevent cascading failures by failing fast after threshold of failures
  • Retry Patterns: Exponential backoff with jitter, idempotent operations only

Category: Domain-Driven Design (cross-referenced with Microservices)

Focus: Event-Driven Architecture, Domain Events, Event Sourcing, CQRS, Sagas

Domain Events:

  • Definition: Record of something significant that happened in the domain (past tense, immutable)
  • Types: Internal events (within context), Integration events (across contexts), Event sourcing events
  • Structure: Event ID, Aggregate ID, Event Type, Event Data, Metadata (timestamp, user, correlation ID)
  • Naming: Past tense (OrderPlaced, PaymentProcessed), domain language, specific over generic
  • Dispatch: Immediate, deferred (after save), Outbox pattern (guaranteed delivery)

Event Sourcing:

  • Concept: Store all state changes as events, rebuild state by replaying events
  • Benefits: Complete audit trail, temporal queries, event replay, new projections
  • Costs: Increased complexity, event versioning, query performance, storage overhead
  • When to Use: Audit trail critical (finance, healthcare), temporal queries, event-driven systems
  • Snapshots: Periodic state snapshots to avoid replaying millions of events

CQRS:

  • Concept: Separate command model (write) and query model (read)
  • Benefits: Optimize independently, scale separately, simpler single-purpose models
  • Levels: CQRS Lite (same DB), with Read Models (projections), Separate Stores (different DBs)
  • Projections: Event handlers build denormalized read models optimized for queries

Sagas:

  • Purpose: Coordinate long-running processes across services with compensation logic
  • Choreography: Each service listens to events and reacts (no central coordinator)
  • Orchestration: Central saga coordinates all steps (clear flow, easier error handling)
  • Compensation: Undo previous steps when later steps fail (RefundPayment, ReleaseInventory)

Saga Example - Document Generation Workflow

Orchestrated saga coordinating multi-step document generation:

public class DocumentGenerationSaga {
    public Guid SagaId { get; private set; }
    public Guid DocumentId { get; private set; }
    public SagaState State { get; private set; }
    
    public enum SagaState {
        Started,
        KnowledgeCollected,
        ContentGenerated,
        HTMLCreated,
        Validated,
        Published,
        Completed,
        Failed
    }
    
    public void Start(Guid documentId) {
        SagaId = Guid.NewGuid();
        DocumentId = documentId;
        State = SagaState.Started;
        
        SendCommand(new CollectKnowledge(documentId));
    }
    
    public void Handle(KnowledgeCollected @event) {
        State = SagaState.KnowledgeCollected;
        SendCommand(new GenerateContent(DocumentId, @event.KnowledgeData));
    }
    
    public void Handle(ContentGenerated @event) {
        State = SagaState.ContentGenerated;
        SendCommand(new CreateHTML(DocumentId, @event.Content));
    }
    
    public void Handle(HTMLCreated @event) {
        State = SagaState.HTMLCreated;
        SendCommand(new ValidateDocument(DocumentId, @event.HTMLPath));
    }
    
    public void Handle(ValidationPassed @event) {
        State = SagaState.Validated;
        SendCommand(new PublishDocument(DocumentId));
    }
    
    public void Handle(DocumentPublished @event) {
        State = SagaState.Completed;
    }
    
    // Compensation
    public void Handle(ValidationFailed @event) {
        State = SagaState.Failed;
        SendCommand(new CleanupFailedDocument(DocumentId));
    }
}
