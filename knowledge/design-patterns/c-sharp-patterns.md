Describing the Template Method Pattern
The template method pattern is a behavioral pattern from the Gang of Four library of design patterns. Its intent is to define the skeleton of an algorithm in an operation, deferring some steps to subclasses. It lets subclasses redefine certain steps of an algorithm without changing the algorithm structure. Let's clarify that with an example. Imagine that we're writing part of an application that wants to make working with email easier by accumulating mail across different servers and analyzing them. The idea is that the company's proprietary artificial intelligence will ensure that your inbox services the emails that are important to you. To be able to do that, the software must connect to different mail servers and parse emails. So, we've got a few classes, ExchangeMailParser, ApacheMailParser, EudoraMailParser and so on. For the sake of the demo, we'll assume that a parser parses one HTML mail at a time by accepting an identifier. The thing is, a lot of what has to happen in the algorithm to parse one mail is the same for these three classes. First, the server needs to be found, then we need to authenticate to the server. That's probably different for each type of mail server. And then the mail body must be parsed. And it's highly likely that this is exactly the same for each of these servers, but we don't want that kind of code duplication. What we can do is create an abstract base class with a template method on it. That template method, say ParseMailBody, accepting an identifier calls the other three methods in a certain order. The other three methods are thus also defined on this abstract class. Subclasses like ExchangeMailParser or EudoraMailParser call this template method on the base class to parse mail, yet we allow these subclasses to vary the algorithm by overriding abstract methods. We'd make the AuthenticateToServer method abstract because this differs for every class. That means that each subclass must implement this method with its own implementation. Moreover, what we can also do is allow subclasses to optionally overwrite the other methods as well in case they would require changes. We do that in code by making them virtual. In Gang of Four lingo, these types of methods or operations are called hooks. The only thing that absolutely must not be overridden is the template method itself, so ParseMailBody. And this is what a template method pattern is, a straightforward, often used pattern in OO design. Let's map this to the pattern structure.

A variation is that not all methods are primitive operations that are abstract and thus must be overridden, but some methods are virtual so they can be overridden if needed. The other methods we had could optionally be examples of that. The AbstractClass also implements a template method, which defines the skeleton of the algorithm. That's the order in which the other methods are called. It thus calls primitive methods, as well as other methods defined on the abstract class or on other objects. The second player then is the ConcreteClass. This implements the primitive operations to carry out subclass‑specific steps of the algorithm. Its intent is to, given a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language. Detailing the Unit of Work Pattern
In the previous module, we detailed the Repository pattern, which provides an abstraction layer between the data access layer, which contains the actual persistence logic and the rest of your application. When you start using the pattern, you will quickly run into an issue. What if you want to ensure that the data changes you want to persist across different repositories are handled in the same transaction? Take an Order and OrderLines repository as an example. You can create an order and persist it through the Order repository, and you can add and persist OrderLines through the OrderLineRepository, but that may mean you end up with inconsistent data. You may end up in a situation where saving the Order was successful, but saving the OrderLine, or Lines, failed. And that is where the Unit of Work pattern comes to the rescue, its primary goal is to manage transactions and coordinate multiple data operations within a single logical unit. Within this unit, multiple data operations like inserts, updates, and leads of an Order and related OrderLines are grouped together. The Unit of Work then ensures that either all operations within the unit succeed or none of them do. If any operation fails, the entire unit of work is rolled back. All right, so that is what it does, but how do we implement something like that? Well, the first thing to do is create the UnitOfWork interface and base class. The third class is then the actual unit of work, for example, to create an Order with OrderLines. It derives from the base class, so it depends on the DbContext.
