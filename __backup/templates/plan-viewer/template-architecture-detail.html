🎨 3-Layer Response Template Architecture

Phase 2 Enhancement • Weeks 3-4
DESIGN PHASE

📋 Problem Statement

🚨 Current State: 2046-Line Monolith

The response-templates-v4.yaml file has grown to 2046 lines, creating severe maintainability issues:

  • Duplication: Continuation prompts and common patterns repeated across 40+ orchestrators
  • Maintenance Burden: Changes to common patterns require updates in multiple locations
  • Inconsistency: No enforcement mechanism for standard response blocks
  • CORE-002 Violation: Directly violates the anti-bloat governance principle (max 300 lines for knowledge files)
  • Scalability: Per-orchestrator approach would create 80-160 files if decomposed naively

🔍 Root Cause

Templates are defined inline instead of referencing reusable blocks. This architectural flaw leads to exponential growth as new orchestrators are added.

💡 Solution: 3-Layer Hybrid Architecture

✅ Target Architecture

Decompose into 3 composable layers with clear precedence rules and governance enforcement:

  • Total Lines: <300 (down from 2046) — 85% reduction
  • Duplication: 0% (all use core blocks)
  • Consistency: 100% (schema validation enforced)
  • Render Time: <50ms (performance maintained)
  • Maintenance Events: <2/month (down from ~8/month)

Architecture Principles

  • Composition over Inheritance: Build complex templates from atomic blocks
  • Clear Precedence: orchestrator > category > core (no ambiguity)
  • Governance First: CORE-002 enforced at every layer
  • Backwards Compatible: 2-week migration window with fallback

📦 Layer Details

01
Core Blocks
cortex-brain/tier0/response-blocks.yaml
15-20 atomic markdown fragments that serve as building blocks for all responses. Protected by SKULL governance (CORE-002: max 50 lines).
  • header (orchestrator branding)
  • progress (current state)
  • next_steps (actionable items)
  • error (error formatting)
  • warning (warnings formatting)
  • completion (success messaging)
  • understanding (request summary)
  • changes (file modifications)
  • validation (test results)
02
Category Templates
cortex-brain/tier2/response-templates/{category}.yaml
5 category-specific templates that define block composition rules and category overrides. Each file limited to 50 lines.
  • core.yaml (Planning, TDD, Investigation)
  • integration.yaml (ADO, Git, External APIs)
  • maintenance.yaml (Vacuum, Cleanup, Sanitization)
  • conversion.yaml (Data transformers)
  • security.yaml (Security-specific formatting)
03
Orchestrator Overrides
cortex-brain/manifests/orchestrators/{name}.yaml
response_config section in orchestrator manifests containing only deviations from category template. Limited to 15 lines via schema validation.
  • Only deviations from category
  • Inherits category composition
  • Falls back to core blocks
  • Multi-category support (e.g., ADO = integration + planning)

⚖️ Precedence Resolution

The ResponseRenderer applies a hierarchical merge strategy with clear precedence rules:

PRECEDENCE: orchestrator > category > core

Resolution Flow:
1. Load core blocks (tier0/response-blocks.yaml)
2. Load category template (tier2/response-templates/{category}.yaml)
3. Load orchestrator overrides (manifests/{orch}/response_config)
4. Merge with precedence: orchestrator wins conflicts
5. Compose blocks per work breakdown structure
6. Return markdown

Example:
  Core:       header: "# {orchestrator_name}"
  Category:   header: "# 🔧 {orchestrator_name} - {category}"
  Orchestrator: header: "# 🎯 Custom Header"
  
  Result:     "# 🎯 Custom Header" (orchestrator wins)

Multi-Category Inheritance

Orchestrators can inherit from multiple categories for cross-cutting concerns:

  • ADO v2: integration + planning (API calls + task breakdown)
  • Security Scanner: security + maintenance (scanning + cleanup)

Audit logs capture the full resolution path for debugging.
