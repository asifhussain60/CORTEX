🎓 What is SOLID?

SOLID is an acronym for five design principles that make software easier to understand, maintain, and extend. Think of them as "rules of thumb" that prevent code from becoming a tangled mess over time.

S

Single Responsibility Principle (SRP)

"A class should have only one reason to change."

🍳 Analogy: A chef shouldn't also be the accountant, waiter, and dishwasher.

O

Open/Closed Principle (OCP)

"Software should be open for extension, but closed for modification."

🔌 Analogy: A power strip lets you add devices without rewiring.

L

Liskov Substitution Principle (LSP)

"Subtypes must be substitutable for their base types."

🦆 Analogy: If it walks and quacks like a duck, code should work with any duck.

I

Interface Segregation Principle (ISP)

"Clients shouldn't depend on methods they don't use."

📱 Analogy: A TV remote shouldn't have washing machine buttons.

D

Dependency Inversion Principle (DIP)

"Depend on abstractions, not concretions."

🔌 Analogy: USB ports work with any device, not soldered to one mouse.

SOL-01 SRP CRITICAL C#

God Class: UserManager Does Everything

Anti-Pattern: God Object — This single class handles authentication, CRUD operations, email sending, file uploads, and more. With 800+ lines and 35+ methods, it's impossible to test.

❌ BEFORE UserManager.cs (800+ lines) 
// GOD CLASS: Does 12 different jobs!
public class UserManager
{
    private readonly DbContext _context;
    private readonly SmtpClient _smtp;
    
    // Authentication (responsibility 1)
    public string Login(string username, string password) { ... }
    public void Logout(int userId) { ... }
    public void ResetPassword(string email) { ... }
    
    // CRUD Operations (responsibility 2)
    public User CreateUser(UserDto data) { ... }
    public User UpdateUser(int id, UserDto data) { ... }
    public void DeleteUser(int id) { ... }
    
    // Email (responsibility 3)
    public void SendWelcomeEmail(User user) { ... }
    public void SendPasswordReset(User user) { ... }
    
    // File Uploads (responsibility 4)
    public string UploadAvatar(int userId, IFormFile file) { ... }
    
    // ... 25 more methods for 8 more responsibilities
}
✅ AFTER CORTEX Refinement 
// Each class has ONE responsibility

SOL-02 OCP HIGH TypeScript

If/Else Chain: Adding Payment Methods Requires Code Changes

OCP Violation — Every new payment type (Apple Pay, Google Pay) requires modifying this function. The Strategy Pattern lets us add new payment methods without touching existing code.

❌ BEFORE payment.service.ts 
export class PaymentService {
  // Must modify this function for every new payment type!
  processPayment(type: string, amount: number): PaymentResult {
    if (type === 'credit_card') {
      return this.processCreditCard(amount);
    } else if (type === 'debit_card') {
      return this.processDebitCard(amount);
    } else if (type === 'paypal') {
      return this.processPayPal(amount);
    } else if (type === 'stripe') {
      return this.processStripe(amount);
    } else if (type === 'venmo') {
      return this.processVenmo(amount);
    } else if (type === 'crypto') {
      return this.processCrypto(amount);
    }
    // Adding Apple Pay? Modify this file again...
    throw new Error('Unknown payment type');
  }
}
✅ AFTER Strategy Pattern 
// Define an interface (abstraction)
interface PaymentStrategy {
  process(amount: number): Promise<PaymentResult>;
}

// Concrete implementations
class CreditCardPayment implements PaymentStrategy {
  async process(amount: number) { /* ... */ }
}

class PayPalPayment implements PaymentStrategy {
  async process(amount: number) { /* ... */ }
}

// Adding Apple Pay? Just create a new class!
class ApplePayPayment implements PaymentStrategy {
  async process(amount: number) { /* ... */ }
}

@Injectable()
export class PaymentService {
  private strategies = new Map<string, PaymentStrategy>();
  
  register(name: string, strategy: PaymentStrategy) {
    this.strategies.set(name, strategy);
  }
  
  async process(type: string, amount: number) {
    const strategy = this.strategies.get(type);
    if (!strategy) throw new Error('Unknown payment');
    return strategy.process(amount);
  }
}
CORTEX Capability: Planning System → Design pattern recommendation
SOL-03 DIP HIGH C#

Tight Coupling: Can't Swap Database Without Rewriting

DIP Violation — The application creates a specific database class directly. Want to switch from SQL Server to PostgreSQL? Rewrite everything. Dependency Injection solves this.

❌ BEFORE OrderService.cs 
public class OrderService
{
    // TIGHT COUPLING: Directly instantiating concrete class
    private readonly SqlServerDatabase _db = new SqlServerDatabase();
    private readonly SmtpEmailSender _email = new SmtpEmailSender();
    
    public async Task<Order> CreateOrderAsync(OrderDto dto)
    {
        // Can't swap to PostgreSQL without rewriting
        // Can't use mock database for testing
        var order = new Order { /* ... */ };
        await _db.SaveAsync(order);
        await _email.SendAsync(order.CustomerEmail, "Order Confirmed");
        return order;
    }
}
✅ AFTER Dependency Injection 
// Define interfaces (abstractions)
public interface IOrderRepository
{
    Task<Order> SaveAsync(Order order);
    Task<Order?> GetByIdAsync(int id);
}

public interface IEmailService
{
    Task SendAsync(string to, string subject, string body);
}

public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IEmailService _email;
    
    // Inject dependencies via constructor
    public OrderService(IOrderRepository repository, IEmailService email)
    {
        _repository = repository;
        _email = email;
    }
    
    public async Task<Order> CreateOrderAsync(OrderDto dto)
    {
        var order = new Order { /* ... */ };
        await _repository.SaveAsync(order);
        await _email.SendAsync(order.CustomerEmail, "Order Confirmed", "...");
        return order;
    }
}

// Now easily swap: SqlServerRepo, PostgresRepo, MockRepo
CORTEX Capability: Architectural Review → Dependency inversion refactoring
SOL-04 ISP MEDIUM Angular

Fat Interface: Components Forced to Implement Unused Methods

ISP Violation — A "god interface" forces implementing classes to define methods they don't need. Split into smaller, focused interfaces.

❌ BEFORE data-source.interface.ts 
// FAT INTERFACE: Forces all methods on everyone
interface IDataSource {
  // Read operations
  getAll(): Observable<any[]>;
  getById(id: number): Observable<any>;
  search(query: string): Observable<any[]>;
  
  // Write operations
  create(item: any): Observable<any>;
  update(id: number, item: any): Observable<any>;
  delete(id: number): Observable<void>;
  
  // Batch operations
  bulkCreate(items: any[]): Observable<any[]>;
  bulkDelete(ids: number[]): Observable<void>;
  
  // Export operations
  exportToCsv(): Observable<Blob>;
  exportToPdf(): Observable<Blob>;
}

// Read-only component forced to implement write methods!
class ReportViewer implements IDataSource {
  getAll() { /* actual impl */ }
  create() { throw new Error('Not supported'); } // 😱
  delete() { throw new Error('Not supported'); } // 😱
  // ... all other methods throwing errors
}
✅ AFTER Segregated Interfaces 
// Split into focused interfaces
interface IReadable<T> {
  getAll(): Observable<T[]>;
  getById(id: number): Observable<T>;
}

interface ISearchable<T> {
  search(query: string): Observable<T[]>;
}

interface IWritable<T> {
  create(item: T): Observable<T>;
  update(id: number, item: T): Observable<T>;
  delete(id: number): Observable<void>;
}

interface IExportable {
  exportToCsv(): Observable<Blob>;
  exportToPdf(): Observable<Blob>;
}

// Now implement only what you need!
class ReportViewer implements IReadable<Report>, IExportable {
  getAll() { /* ... */ }
  getById(id: number) { /* ... */ }
  exportToCsv() { /* ... */ }
  exportToPdf() { /* ... */ }
  // No unused methods! ✓
}
CORTEX Capability: System Refinement → Interface segregation
SOL-05 LSP HIGH TypeScript

Broken Inheritance: Square is NOT a Rectangle

LSP Violation — Classic example: a Square that extends Rectangle breaks when width/height are set independently. Subtypes must honor the contract of their base types.

❌ BEFORE shapes.ts 
class Rectangle {
  constructor(protected width: number, protected height: number) {}
  
  setWidth(w: number) { this.width = w; }
  setHeight(h: number) { this.height = h; }
  getArea(): number { return this.width * this.height; }
}

// LSP VIOLATION: Square can't be substituted for Rectangle
class Square extends Rectangle {
  constructor(size: number) { super(size, size); }
  
  // Must override to maintain square invariant
  setWidth(w: number) { this.width = this.height = w; }
  setHeight(h: number) { this.height = this.width = h; }
}

// This BREAKS with Square!
function doubleWidth(rect: Rectangle) {
  rect.setWidth(rect.getArea() / rect.getHeight() * 2);
  // Expected: area doubles
  // With Square: unexpected behavior!
}
✅ AFTER Composition over Inheritance 
// Use interfaces and composition instead
interface Shape {
  getArea(): number;
  getPerimeter(): number;
}

class Rectangle implements Shape {
  constructor(
    private readonly width: number,
    private readonly height: number
  ) {}
  
  getArea(): number { return this.width * this.height; }
  getPerimeter(): number { return 2 * (this.width + this.height); }
  
  // Factory method for scaling
  scale(factor: number): Rectangle {
    return new Rectangle(this.width * factor, this.height * factor);
  }
}

class Square implements Shape {
  constructor(private readonly size: number) {}
  
  getArea(): number { return this.size * this.size; }
  getPerimeter(): number { return 4 * this.size; }
  
  scale(factor: number): Square {
    return new Square(this.size * factor);
  }
}

// Now both work correctly with Shape interface
