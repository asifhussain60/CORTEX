7 Testing Anti-Patterns → Reliable Test Suites

🎓 Testing Concepts

T

Test-Driven Development (TDD)

"Red → Green → Refactor: Write failing test first, then make it pass."

🎯 Analogy: Writing the test questions before the textbook ensures you cover what matters.

A

Arrange-Act-Assert (AAA)

"Set up, perform action, verify result."

🧪 Structure: Given (setup) → When (action) → Then (assertion)

M

Mocking & Test Doubles

"Isolate the unit under test by replacing dependencies."

🎭 Analogy: A stunt double performs risky scenes so the actor doesn't have to.

TEST-01 HIGH C# xUnit

Integration Test Masquerading as Unit Test

Testing Anti-Pattern — This "unit test" actually hits a real database and sends real emails. It's slow, flaky, and tests too many things at once. Use mocks to isolate the unit under test.

❌ BEFORE OrderServiceTests.cs 
public class OrderServiceTests
{
    [Fact]
    public async Task CreateOrder_ShouldWork()
    {
        // NO MOCKING: Using real dependencies!
        var context = new AppDbContext(); // Real database
        var emailService = new SmtpEmailService(); // Real SMTP
        var service = new OrderService(context, emailService);
        
        var order = new Order { /* ... */ };
        
        // This test:
        // - Hits real database (slow, needs setup)
        // - Sends real emails (side effects!)
        // - Fails if DB is down (flaky)
        // - Can't run in parallel (shared state)
        var result = await service.CreateOrderAsync(order);
        
        Assert.NotNull(result);
    }
}
✅ AFTER Proper Unit Test with Mocks 
public class OrderServiceTests
{
    private readonly Mock<IOrderRepository> _repoMock;
    private readonly Mock<IEmailService> _emailMock;
    private readonly OrderService _sut; // System Under Test
    
    public OrderServiceTests()
    {
        _repoMock = new Mock<IOrderRepository>();
        _emailMock = new Mock<IEmailService>();
        _sut = new OrderService(_repoMock.Object, _emailMock.Object);
    }
    
    [Fact]
    public async Task CreateOrder_ValidOrder_SavesAndSendsEmail()
    {
        // Arrange
        var order = new Order { Id = 1, CustomerEmail = "test@test.com" };
        _repoMock.Setup(r => r.SaveAsync(order))
                 .ReturnsAsync(order);
        
        // Act
        var result = await _sut.CreateOrderAsync(order);
        
        // Assert
        Assert.Equal(1, result.Id);
        _repoMock.Verify(r => r.SaveAsync(order), Times.Once);
        _emailMock.Verify(e => e.SendAsync(
            "test@test.com", It.IsAny<string>(), It.IsAny<string>()), 
            Times.Once);
    }
}

TEST-02 HIGH Jest

Flaky Test: Timing-Dependent Assertions

Flaky Test — Tests that depend on real time or arbitrary delays pass sometimes and fail others. Use fake timers and proper async handling.

❌ BEFORE debounce.spec.ts 
describe('debounce', () => {
  it('should debounce calls', async () => {
    const fn = jest.fn();
    const debounced = debounce(fn, 100);
    
    debounced();
    debounced();
    debounced();
    
    // FLAKY: Real time delay - may fail on slow CI
    await new Promise(r => setTimeout(r, 150));
    
    expect(fn).toHaveBeenCalledTimes(1);
  });
  
  it('should handle async data', async () => {
    const result = await fetchData();
    
    // FLAKY: No wait for actual async completion
    // Sometimes data isn't ready yet
    expect(result.items.length).toBe(10);
  });
});
✅ AFTER Deterministic Tests 
describe('debounce', () => {
  beforeEach(() => {
    jest.useFakeTimers();
  });
  
  afterEach(() => {
    jest.useRealTimers();
  });
  
  it('should debounce calls', () => {
    const fn = jest.fn();
    const debounced = debounce(fn, 100);
    
    debounced();
    debounced();
    debounced();
    
    // Deterministic: advance fake timers
    jest.advanceTimersByTime(100);
    
    expect(fn).toHaveBeenCalledTimes(1);
  });
  
  it('should handle async data', async () => {
    // Use waitFor for async assertions
    const { result } = renderHook(() => useFetchData());
    
    await waitFor(() => {
      expect(result.current.items.length).toBe(10);
    });
  });
});

TEST-03 MEDIUM Jasmine

Testing Implementation Instead of Behavior

Brittle Tests — Testing internal implementation details breaks tests when refactoring, even if behavior is unchanged. Test what users see, not how it works inside.

❌ BEFORE login.component.spec.ts 
describe('LoginComponent', () => {
  it('should handle login', () => {
    // Testing internal state - BRITTLE
    expect(component.isLoading).toBeFalse();
    expect(component.errorMessage).toBe('');
    
    component.email = 'test@test.com';
    component.password = 'password';
    
    // Calling private method - BRITTLE
    (component as any).validateForm();
    
    // Checking internal flag - BRITTLE
    expect(component['formValid']).toBeTrue();
    
    // Rename internal variable? Test breaks!
    // Refactor validation logic? Test breaks!
  });
});
✅ AFTER Behavior-Based Testing 
describe('LoginComponent', () => {
  it('should show error for invalid email', async () => {
    // Test from USER's perspective
    const emailInput = fixture.debugElement.query(
      By.css('input[type="email"]'));
    const submitBtn = fixture.debugElement.query(
      By.css('button[type="submit"]'));
    
    // User types invalid email
    emailInput.nativeElement.value = 'invalid';
    emailInput.nativeElement.dispatchEvent(new Event('input'));
    submitBtn.nativeElement.click();
    fixture.detectChanges();
    
    // User sees error message
    const errorEl = fixture.debugElement.query(By.css('.error'));
    expect(errorEl.nativeElement.textContent)
      .toContain('Invalid email');
  });
  
  it('should navigate to dashboard on success', async () => {
    // Mock successful login
    authService.login.and.returnValue(of({ token: 'abc' }));
    
    // Fill form and submit
    fillLoginForm('test@test.com', 'password');
    clickSubmit();
    
    // Verify navigation (behavior, not implementation)
    expect(router.navigate).toHaveBeenCalledWith(['/dashboard']);
  });
});

TEST-04 MEDIUM C# xUnit

Happy Path Only: Missing Edge Cases

Incomplete Tests — Only testing the happy path misses bugs in error handling, boundary conditions, and edge cases. Use parameterized tests to cover more scenarios.

❌ BEFORE CalculatorTests.cs 
public class CalculatorTests
{
    [Fact]
    public void Divide_ShouldWork()
    {
        var calc = new Calculator();
        
        // Only happy path!
        var result = calc.Divide(10, 2);
        
        Assert.Equal(5, result);
        // What about:
        // - Divide by zero?
        // - Negative numbers?
        // - Very large numbers?
        // - Decimal precision?
    }
    
    [Fact]
    public void ValidateEmail_ShouldWork()
    {
        Assert.True(Validator.IsValidEmail("test@test.com"));
        // What about empty? null? unicode? very long?
    }
}
✅ AFTER Comprehensive Coverage 
public class CalculatorTests
{
    [Theory]
    [InlineData(10, 2, 5)]
    [InlineData(-10, 2, -5)]
    [InlineData(10, -2, -5)]
    [InlineData(0, 5, 0)]
    [InlineData(1, 3, 0.333333)]
    public void Divide_ValidInputs_ReturnsCorrectResult(
        double a, double b, double expected)
    {
        var result = new Calculator().Divide(a, b);
        Assert.Equal(expected, result, precision: 5);
    }
    
    [Fact]
    public void Divide_ByZero_ThrowsDivideByZeroException()
    {
        var calc = new Calculator();
        Assert.Throws<DivideByZeroException>(() => calc.Divide(10, 0));
    }
    
    [Theory]
    [InlineData("test@test.com", true)]
    [InlineData("user@domain.co.uk", true)]
    [InlineData("", false)]
    [InlineData(null, false)]
    [InlineData("invalid", false)]
    [InlineData("@no-local.com", false)]
    [InlineData("no-domain@", false)]
    public void IsValidEmail_VariousInputs(string email, bool expected)
    {
        Assert.Equal(expected, Validator.IsValidEmail(email));
    }
}
