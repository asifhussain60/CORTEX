Clean Code Philosophy

Clean code is code that is easy to understand and easy to change. It reads like well-written prose and makes the intent of the programmer clear. Based on Clean Code: A Handbook of Agile Software Craftsmanship by Robert C. Martin (2008).

Why Clean Code Matters

  • Readability: Code is read 10x more than written
  • Maintainability: Easy to modify without breaking
  • Team Productivity: New team members onboard faster
  • Fewer Bugs: Simpler code has fewer places to hide bugs
  • Lower Cost: Less time debugging and refactoring

1. Meaningful Names

Names should reveal intent without requiring comments.

Use Intention-Revealing Names

HIGH PRIORITY

Name should answer: why it exists, what it does, how it's used.

✅ Good: Intention-Revealing

# ✅ Clear intent
elapsed_time_in_days = 365
days_since_creation = 100
days_since_modification = 50

active_customers = get_active_customers()
total_revenue_this_quarter = calculate_quarterly_revenue()

# No comments needed - names explain everything

❌ Bad: Requires Mental Mapping

# ❌ What does 'd' mean?
d = 365  # elapsed time in days
elap = 100
t = 50

list1 = get_customers()  # What's in list1?
amt = calculate()        # Amount of what?

# Requires comments and mental effort

Avoid Disinformation

CRITICAL

Don't use names that mislead about what the code does.

✅ Good: Names Match Reality

# ✅ Names match types
account_group = []           # It's a list
customer_collection = {}     # It's a dict
user_set = set()             # It's a set

distance = calculate_distance()  # Clear what it calculates

❌ Bad: Misleading Names

# ❌ Misleading types
accountList = {}  # It's actually a dict, not a list!
customer_array = set()  # It's a set, not an array

# Misleading purpose
hp = calculate_distance()  # 'hp' suggests health points, not distance

Make Meaningful Distinctions

HIGH PRIORITY

If names must be different, they should mean something different.

✅ Good: Meaningful Differences

# ✅ Clear roles
def copy_chars(source: str, destination: str):
    """Source and destination have clear meaning."""
    for char in source:
        destination += char

def withdraw(account: Account, amount: Decimal):
    """Parameters have distinct, clear purposes."""
    if account.balance >= amount:
        account.balance -= amount

❌ Bad: Number-Series Naming

# ❌ Which is which?
def copy_chars(a1: str, a2: str):  # Which is source? destination?
    pass

# ❌ Noise words
customer_data = get_customer()
customer_info = get_customer()
customer_object = get_customer()
# These all mean the same thing!

Use Pronounceable Names

MEDIUM PRIORITY

Can you discuss the variable name with a colleague?

✅ Good: Pronounceable

# ✅ Easy to discuss
generation_timestamp = datetime.now()
modification_date = datetime(2025, 12, 22)

# "What's the generation timestamp?" - Natural conversation

❌ Bad: Unpronounceable

# ❌ How do you say this?
genymdhms = datetime.now()  # "jen-why-em-dee-aitch-em-ess"?
modymdhms = datetime(2025, 12, 22)

# Awkward in conversation

Use Searchable Names

MEDIUM PRIORITY

Constants and important values should be easy to find.

✅ Good: Searchable Constants

# ✅ Easy to find and change
MAX_STUDENTS_PER_CLASS = 30
WORK_DAYS_PER_WEEK = 5
NUMBER_OF_TASKS = 10

for i in range(NUMBER_OF_TASKS):
    process_task(i)

# Search for "MAX_STUDENTS_PER_CLASS" finds all uses

❌ Bad: Magic Numbers

# ❌ What does 30 mean? Where else is it used?
if len(students) > 30:  # Magic number
    split_class()

for i in range(10):  # What does 10 represent?
    process_task(i)

# Search for "30" finds hundreds of unrelated results

2. Functions

Small Functions

CRITICAL

Functions should be small. Really small. 5-10 lines ideal, rarely over 20.

✅ Good: Small, Focused Functions

# ✅ Each function does ONE thing
def is_valid_email(email: str) -> bool:
    """Check if email is valid."""
    return "@" in email and "." in email.split("@")[1]

def send_welcome_email(user: User) -> None:
    """Send welcome email to user."""
    email_service.send(
        to=user.email,
        subject="Welcome!",
        body=render_welcome_template(user)
    )

def create_user(username: str, email: str) -> User:
    """Create a new user."""
    if not is_valid_email(email):
        raise ValueError("Invalid email")
    
    user = User(username=username, email=email)
    user.save()
    send_welcome_email(user)
    return user

# Each function is 3-5 lines and does ONE thing

❌ Bad: Long, Multi-Purpose Function

# ❌ 50+ line function doing everything
def create_user(username, email, password, phone, address):
    # Validation (10 lines)
    if not username or len(username) < 3:
        raise ValueError("Invalid username")
    if not email or "@" not in email:
        raise ValueError("Invalid email")
    # ... more validation
    
    # Password hashing (5 lines)
    salt = generate_salt()
    hashed = hash_password(password, salt)
    # ...
    
    # Database insertion (10 lines)
    connection = db.connect()
    cursor = connection.cursor()
    cursor.execute("INSERT INTO...")
    # ...
    
    # Email sending (10 lines)
    smtp = smtplib.SMTP("smtp.gmail.com")
    smtp.login(username, password)
    # ...
    
    # Logging (5 lines)
    # ... continues for 50+ lines

Do One Thing

CRITICAL

Functions should do one thing. They should do it well. They should do it only.

✅ Good: Single Responsibility

# ✅ Each function has ONE purpose
def validate_user_input(username: str, email: str) -> None:
    """Only validation."""
    if not username or len(username) < 3:
        raise ValueError("Invalid username")
    if not email or "@" not in email:
        raise ValueError("Invalid email")

def hash_password(password: str) -> str:
    """Only password hashing."""
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt())

def save_user_to_database(user: User) -> None:
    """Only database persistence."""
    db.session.add(user)
    db.session.commit()

def send_welcome_notification(user: User) -> None:
    """Only notification sending."""
    email_service.send_welcome_email(user)

# Compose them
def create_user(username: str, email: str, password: str) -> User:
    """Orchestrate user creation."""
    validate_user_input(username, email)
    hashed_password = hash_password(password)
    user = User(username, email, hashed_password)
    save_user_to_database(user)
    send_welcome_notification(user)
    return user

One Level of Abstraction

HIGH PRIORITY

Statements in a function should all be at the same level of abstraction.

✅ Good: Consistent Abstraction Level

# ✅ High-level steps (same abstraction)
def render_page_with_setup():
    """All steps at high level."""
    setup_database_connection()
    load_user_preferences()
    render_html_content()
    cleanup_resources()

# Low-level implementation (same abstraction)
def calculate_checksum(data: bytes) -> int:
    """All steps at low level."""
    checksum = 0
    for byte in data:
        checksum ^= byte
    return checksum & 0xFF

❌ Bad: Mixed Abstraction Levels

# ❌ Mixes high-level and low-level
def render_page():
    # High-level
    setup_database()
    
    # Low-level (mixing!)
    buffer = []
    for char in html_content:
        if char == '<':
            buffer.append('<')
        else:
            buffer.append(char)
    
    # High-level again
    send_to_client()

Function Arguments

HIGH PRIORITY

Fewer arguments are better. Ideal: 0-2 arguments. Avoid more than 3.

✅ Good: Few Arguments

# ✅ 0-2 arguments (ideal)
def save() -> None: pass

def delete(entity_id: str) -> None: pass

def connect(username: str, password: str) -> Connection: pass

# If many arguments needed, use an object
class UserConfig:
    username: str
    email: str
    phone: str
    address: str

def create_user(config: UserConfig) -> User:
    """Single argument (object) replaces 4+ parameters."""
    return User(
        username=config.username,
        email=config.email,
        phone=config.phone,
        address=config.address
    )

❌ Bad: Too Many Arguments

# ❌ 6 arguments - hard to remember order
def create_user(username, email, password, phone, address, role):
    pass

# Did I pass them in the right order?
create_user("john", "john@example.com", "pass123", "555-1234", "123 Main St", "admin")
# Or was it: username, password, email, ...?

No Side Effects

CRITICAL

Function should not modify hidden state or have unexpected side effects.

✅ Good: Pure Functions

# ✅ No side effects - returns new value
def calculate_total(items: list[Item]) -> Decimal:
    """Pure function - no side effects."""
    return sum(item.price for item in items)

# Explicit side effects in name
def update_user_and_send_email(user: User) -> None:
    """Name reveals it does TWO things."""
    user.last_updated = datetime.now()
    user.save()  # Side effect 1
    email_service.send_update_notification(user)  # Side effect 2

❌ Bad: Hidden Side Effects

# ❌ Hidden side effect!
def check_password(username: str, password: str) -> bool:
    """Name suggests only checking, but..."""
    user = db.get_user(username)
    if user.password == hash(password):
        # HIDDEN SIDE EFFECT: Creates session!
        session.initialize(user)
        return True
    return False

# Caller doesn't expect a session to be created

3. Comments

Comments Are a Failure

MINDSET

Every comment represents a failure to express yourself in code. Code should be self-documenting.

✅ Good: Self-Documenting Code

# ✅ No comment needed - code is clear
if employee.is_eligible_for_full_benefits():
    process_full_benefits(employee)

# ✅ Function name explains what it does
def delete_inactive_users_older_than_90_days() -> int:
    cutoff_date = datetime.now() - timedelta(days=90)
    return User.query.filter(
        User.last_login < cutoff_date
    ).delete()

❌ Bad: Comments Explaining Bad Code

# ❌ Comment explains unclear code
# Check to see if the employee is eligible for full benefits
if (employee.flags & HOURLY_FLAG) and (employee.age > 65):
    pass

# ❌ Better: Make the code clear
if employee.is_eligible_for_full_benefits():
    pass

Good Comments

EXCEPTIONS

Some comments are necessary and beneficial.

Acceptable Comments:

  • Legal: Copyright, license
  • Informative: Explain regex, format
  • Warning: Warn about consequences
  • TODO: Track future work
  • Amplification: Emphasize importance

✅ Good Comments

# ✅ Legal comment
# Copyright 2025 Acme Corp. Licensed under MIT.

# ✅ Informative comment
# Format: YYYY-MM-DD HH:MM:SS
date_regex = r'\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}'

# ✅ Warning of consequences
# WARNING: This operation is expensive and locks the database
# for several seconds. Only run during maintenance windows.
def rebuild_search_index():
    pass

# ✅ TODO comment
# TODO: Replace with async version when Python 3.11 available
def fetch_data_sync():
    pass

4. Formatting

Vertical Formatting

READABILITY

Files should be small (200-500 lines). Use vertical space to separate concepts.

✅ Good: Vertical Spacing

# ✅ Blank lines separate concepts
class UserService:
    """User management service."""
    
    def __init__(self, repository):
        self.repository = repository
    
    # Blank line separates initialization from methods
    
    def create_user(self, username: str, email: str) -> User:
        """Create a new user."""
        user = User(username, email)
        self.repository.save(user)
        return user
    
    # Blank line between related methods
    
    def delete_user(self, user_id: str) -> None:
        """Delete a user."""
        self.repository.delete(user_id)

Horizontal Formatting

READABILITY

Keep lines short (80-120 characters). Use horizontal space for clarity.

✅ Good: Horizontal Spacing

# ✅ Spacing around operators
total = subtotal + tax + shipping

# ✅ Break long lines
user = User(
    username=username,
    email=email,
    created_at=datetime.now()
)

# ✅ Align related assignments
short_name  = 1
longer_name = 2
x           = 3

5. Error Handling

Use Exceptions, Not Return Codes

HIGH PRIORITY

Exceptions separate error handling from main logic.

✅ Good: Exceptions

# ✅ Clean separation
def delete_user(user_id: str) -> None:
    """Delete user (raises exception on error)."""
    user = repository.find(user_id)
    if not user:
        raise UserNotFoundError(f"User {user_id} not found")
    repository.delete(user)

# Usage: Try-except handles errors
try:
    delete_user("user123")
except UserNotFoundError as e:
    log.error(e)

❌ Bad: Return Codes

# ❌ Error handling mixed with logic
def delete_user(user_id: str) -> int:
    """Returns: 0=success, -1=not found, -2=db error."""
    user = repository.find(user_id)
    if not user:
        return -1
    try:
        repository.delete(user)
        return 0
    except:
        return -2

# Usage: Must check return code
result = delete_user("user123")
if result == -1:
    log.error("User not found")
elif result == -2:
    log.error("Database error")

Don't Return Null

HIGH PRIORITY

Returning null forces callers to check for null, leading to null pointer exceptions.

✅ Good: Return Empty Collection or Raise Exception

# ✅ Return empty list instead of None
def get_users() -> list[User]:
    """Always returns a list (possibly empty)."""
    users = repository.find_all()
    return users if users else []

# ✅ Or raise exception for not found
def get_user(user_id: str) -> User:
    """Returns user or raises exception."""
    user = repository.find(user_id)
    if not user:
        raise UserNotFoundError(f"User {user_id} not found")
    return user

# No null checks needed
for user in get_users():  # Always iterable
    process(user)

❌ Bad: Return None

# ❌ Returns None - forces null checks
def get_users() -> Optional[list[User]]:
    users = repository.find_all()
    return users if users else None

# Must check for None everywhere
users = get_users()
if users is not None:  # Null check
    for user in users:
        process(user)
