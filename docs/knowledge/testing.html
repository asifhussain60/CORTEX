Testing & Quality Assurance

TDD, testing pyramid, unit/integration/E2E testing, test doubles, and test automation strategies

🎯 Category Overview

Testing & Quality Assurance covers test-driven development (TDD), the testing pyramid strategy, unit/integration/E2E testing, test doubles (mocks, stubs, fakes), and automated testing best practices. This category ensures high-quality, maintainable, and reliable software.

Key Concepts

  • Test-Driven Development (TDD): RED-GREEN-REFACTOR cycle, writing tests before code
  • Testing Pyramid: Unit tests (70%), integration tests (20%), E2E tests (10%)
  • Unit Testing: Testing individual functions/classes in isolation
  • Integration Testing: Testing component interactions and database operations
  • End-to-End Testing: Testing complete user workflows through the UI
  • Test Doubles: Mocks, stubs, spies, fakes, and dummies for test isolation

Test-Driven Development (TDD)

TDD is a methodology where tests are written BEFORE implementation. Follow the RED-GREEN-REFACTOR cycle.

RED-GREEN-REFACTOR Cycle

graph LR RED["🔴 RED
Write Failing Test"] --> GREEN["🟢 GREEN
Write Minimal Code"] GREEN --> REFACTOR["♻️ REFACTOR
Improve Design"] REFACTOR --> RED style RED fill:#e53e3e style GREEN fill:#48bb78 style REFACTOR fill:#667eea

Three Laws of TDD (Uncle Bob)

Law Description Rationale
Law 1 You may not write production code until you have written a failing unit test Ensures test actually tests something
Law 2 You may not write more of a unit test than is sufficient to fail Keep tests small and focused
Law 3 You may not write more production code than is sufficient to pass the test Avoid speculative code (YAGNI)

TDD Example: Calculator

# STEP 1: RED - Write failing test
def test_add_positive_numbers():
    calculator = Calculator()
    assert calculator.add(2, 3) == 5  # FAILS - Calculator doesn't exist

# STEP 2: GREEN - Write minimal code to pass
class Calculator:
    def add(self, a, b):
        return a + b  # Simplest implementation

# STEP 3: REFACTOR - Improve (if needed)
# Code is already clean, move to next test

# STEP 1: RED - Write test for edge case
def test_add_with_zero():
    calculator = Calculator()
    assert calculator.add(0, 5) == 5  # Passes! No changes needed

# STEP 1: RED - Test negative numbers
def test_add_negative_numbers():
    calculator = Calculator()
    assert calculator.add(-2, -3) == -5  # Passes! Implementation is general enough

Unit Testing

Unit tests verify individual units (functions, classes, methods) in isolation. They are fast, deterministic, and form the foundation (70%) of your test suite.

Python Unit Test (pytest)

import pytest
from shopping_cart import ShoppingCart, Item

# AAA Pattern: Arrange, Act, Assert

def test_add_item_increments_count():
    # Arrange
    cart = ShoppingCart()
    item = Item("Laptop", 1000)
    
    # Act
    cart.add_item(item)
    
    # Assert
    assert cart.item_count() == 1

def test_calculate_total_sums_item_prices():
    # Arrange
    cart = ShoppingCart()
    cart.add_item(Item("Laptop", 1000))
    cart.add_item(Item("Mouse", 25))
    
    # Act
    total = cart.total()
    
    # Assert
    assert total == 1025

def test_apply_discount_reduces_total():
    # Arrange
    cart = ShoppingCart()
    cart.add_item(Item("Laptop", 1000))
    
    # Act
    cart.apply_discount(0.1)  # 10% discount
    
    # Assert
    assert cart.total() == 900

def test_remove_item_when_empty_raises_exception():
    # Arrange
    cart = ShoppingCart()
    
    # Act & Assert
    with pytest.raises(ValueError, match="Cart is empty"):
        cart.remove_item("Laptop")

JavaScript Unit Test (Jest)

const { UserService } = require('./user-service');

describe('UserService', () => {
  test('register creates user with hashed password', () => {
    // Arrange
    const service = new UserService();
    
    // Act
    const user = service.register('alice@example.com', 'password123');
    
    // Assert
    expect(user.email).toBe('alice@example.com');
    expect(user.password).not.toBe('password123'); // Should be hashed
    expect(user.password.length).toBeGreaterThan(20); // Hash is longer
  });

  test('register with duplicate email throws error', () => {
    // Arrange
    const service = new UserService();
    service.register('alice@example.com', 'password123');
    
    // Act & Assert
    expect(() => {
      service.register('alice@example.com', 'password456');
    }).toThrow('Email already registered');
  });

  test('authenticate with valid credentials returns true', () => {
    // Arrange
    const service = new UserService();
    service.register('alice@example.com', 'password123');
    
    // Act
    const result = service.authenticate('alice@example.com', 'password123');
    
    // Assert
    expect(result).toBe(true);
  });

  test('authenticate with invalid password returns false', () => {
    // Arrange
    const service = new UserService();
    service.register('alice@example.com', 'password123');
    
    // Act
    const result = service.authenticate('alice@example.com', 'wrong');
    
    // Assert
    expect(result).toBe(false);
  });
});

Integration Testing

Integration tests verify multiple components work together correctly. They test database operations, API endpoints, and service interactions. Make up 20% of test suite.

Python Integration Test (pytest + TestContainers)

import pytest
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="module")
def postgres_container():
    with PostgresContainer("postgres:15") as postgres:
        yield postgres

def test_user_repository_saves_and_retrieves(postgres_container):
    # Arrange
    connection_string = postgres_container.get_connection_url()
    repo = UserRepository(connection_string)
    user = User(name="Alice", email="alice@example.com")
    
    # Act
    user_id = repo.save(user)
    retrieved = repo.get_by_id(user_id)
    
    # Assert
    assert retrieved.name == "Alice"
    assert retrieved.email == "alice@example.com"

def test_user_repository_prevents_duplicate_emails(postgres_container):
    # Arrange
    connection_string = postgres_container.get_connection_url()
    repo = UserRepository(connection_string)
    
    # Act
    repo.save(User(name="Alice", email="alice@example.com"))
    
    # Assert
    with pytest.raises(IntegrityError):
        repo.save(User(name="Bob", email="alice@example.com"))  # Duplicate email

End-to-End (E2E) Testing

E2E tests verify complete user workflows through the UI. They are slow and brittle but catch integration issues. Should be only 10% of test suite.

Playwright E2E Test

const { test, expect } = require('@playwright/test');

test('user can complete checkout flow', async ({ page }) => {
  // Navigate to shop
  await page.goto('https://example.com/shop');
  
  // Add item to cart
  await page.click('button[data-product-id="1"]');
  await expect(page.locator('.cart-count')).toHaveText('1');
  
  // Go to cart
  await page.click('a[href="/cart"]');
  await expect(page.locator('.cart-total')).toContainText('$99.99');
  
  // Proceed to checkout
  await page.click('button:has-text("Checkout")');
  
  // Fill shipping information
  await page.fill('input[name="name"]', 'Alice Smith');
  await page.fill('input[name="address"]', '123 Main St');
  await page.fill('input[name="city"]', 'New York');
  await page.selectOption('select[name="state"]', 'NY');
  await page.fill('input[name="zip"]', '10001');
  
  // Fill payment information
  await page.fill('input[name="card_number"]', '4111111111111111');
  await page.fill('input[name="expiry"]', '12/25');
  await page.fill('input[name="cvv"]', '123');
  
  // Submit order
  await page.click('button[type="submit"]');
  
  // Verify success
  await expect(page).toHaveURL(/.*order-confirmation/);
  await expect(page.locator('h1')).toContainText('Order Confirmed');
  await expect(page.locator('.order-number')).toBeVisible();
});

test('user can login with valid credentials', async ({ page }) => {
  // Navigate to login
  await page.goto('https://example.com/login');
  
  // Fill credentials
  await page.fill('input[name="email"]', 'user@example.com');
  await page.fill('input[name="password"]', 'password123');
  
  // Submit
  await page.click('button[type="submit"]');
  
  // Verify redirect to dashboard
  await expect(page).toHaveURL(/.*dashboard/);
  await expect(page.locator('.welcome-message')).toContainText('Welcome back');
});

Test Doubles

Test doubles replace real dependencies in tests for isolation, speed, and determinism.

Types of Test Doubles

Type Purpose Verification Complexity
Dummy Passed but never used None Simple (null)
Stub Returns canned responses State verification Simple
Spy Records interactions Behavior (after execution) Medium
Mock Pre-programmed expectations Behavior (strict) Medium
Fake Working implementation State verification Complex

Stub Example

# Stub returns fixed responses
class StubPaymentGateway:
    def process_payment(self, amount):
        return {"success": True, "transaction_id": "STUB123"}

def test_checkout_with_successful_payment():
    # Arrange
    stub_gateway = StubPaymentGateway()
    service = CheckoutService(stub_gateway)
    
    # Act
    order = service.checkout(cart_total=100)
    
    # Assert
    assert order.status == "COMPLETED"

Mock Example

from unittest.mock import Mock

def test_order_service_sends_confirmation_email():

Fake Example

# Fake has working implementation
class FakeUserRepository:
    def __init__(self):
        self._users = {}  # In-memory storage
        self._next_id = 1
    
    def save(self, user):
        user.id = self._next_id
        self._users[user.id] = user
        self._next_id += 1
        return user.id
    
    def get_by_id(self, user_id):
        return self._users.get(user_id)

def test_user_service_prevents_duplicate_emails():
    # Arrange
    fake_repo = FakeUserRepository()
    service = UserService(fake_repo)
    
    # Act
    service.register("alice@example.com", "pass123")
    
    # Assert
    with pytest.raises(DuplicateEmailError):
        service.register("alice@example.com", "pass456")

Testing Best Practices

  • Follow AAA Pattern: Arrange (setup), Act (execute), Assert (verify)
  • One Assertion Per Test: Makes failures easier to diagnose
  • Descriptive Test Names: test_methodName_scenario_expectedBehavior()
  • Keep Tests Independent: No test order dependencies
  • Fast Tests: Unit tests < 100ms, integration tests < 10s
  • Test Behavior, Not Implementation: Tests should survive refactoring
  • Aim for 80%+ Coverage: But don't sacrifice quality for quantity
  • Test Edge Cases: Null, empty, negative, boundary values
  • Use Test Fixtures: Reusable setup for common scenarios
  • Clean Up After Tests: Transactions, temp files, containers

Category: Testing Strategy

Focus: Authoritative testing strategy for optimal test distribution

Pyramid Layers:

  • Unit Tests (70%): Fast (< 100ms), isolated, no external dependencies, test business logic
  • Integration Tests (20%): Medium speed (1-10s), test component interactions, database operations
  • E2E Tests (10%): Slow (10-60s), brittle, test critical user journeys through UI

Key Principles:

  • Test at the Lowest Level Possible: Lower-level tests are faster and more stable
  • Optimize Test Distribution: More unit tests, fewer integration/E2E tests
  • Fail Fast: Unit tests catch bugs in seconds vs minutes/hours for UI tests
  • Test Isolation: Each layer tests different concerns independently

Anti-Patterns:

  • Ice Cream Cone: Inverted pyramid with many UI tests, few unit tests (slow, brittle)
  • Manual Testing Trap: Over-reliance on manual testing instead of automation

Tools by Layer:

  • Unit: pytest, unittest, JUnit, xUnit, NUnit, Jest
  • Integration: TestContainers, WebApplicationFactory, pytest-docker, Supertest
  • E2E: Playwright, Cypress, Selenium WebDriver, Puppeteer

Category: Testing Techniques

Focus: Authoritative guide to test doubles for test isolation

Test Double Types:

  • Dummy: Passed but never used (simplest, often null)
  • Stub: Returns canned responses (state verification, no call checking)
  • Spy: Records interactions for later verification (flexible, verifies after execution)
  • Mock: Pre-programmed expectations (behavior verification, strict)
  • Fake: Working implementation with shortcuts (in-memory DB, reusable)

When to Use Each:

  • Dummy: Method requires parameter but test doesn't exercise that path
  • Stub: Control data returned by dependency, simulate slow/unavailable service
  • Spy: Verify method was called, inspect arguments, check call order
  • Mock: Test object collaboration, verify side effects, command pattern
  • Fake: Dependency is complex, need realistic behavior without overhead

Testing Styles:

  • Mockist (London School): Focus on object interactions, use mocks, test behavior
  • Classicist (Detroit School): Focus on final state, fewer mocks, test state

Category: Testing Tools

Focus: Migration guide from Selenium to Playwright for E2E testing

Why Migrate:

  • Playwright is faster (auto-waits, network interception)
  • Better debugging (traces, screenshots, video recording)
  • Multi-browser support (Chromium, Firefox, WebKit)
  • Built-in test runner with parallelization
  • Modern API design (async/await native)

Key Differences:

  • Locators: Playwright auto-waits, Selenium requires explicit waits
  • API: Playwright uses async/await, cleaner syntax
  • Performance: Playwright faster due to DevTools Protocol
  • Reliability: Playwright more stable (fewer flaky tests)

Example: TDD Orchestrator Unit Test

import pytest
from cortex_orchestrators.tdd_orchestrator import TDDOrchestrator

def test_tdd_orchestrator_generates_failing_test_first():
    # Arrange
    orchestrator = TDDOrchestrator()
    user_story = "As a user, I want to calculate 10% discount"
    
    # Act
    result = orchestrator.run_red_phase(user_story)
    
    # Assert
    assert result.phase == "RED"
    assert result.test_code is not None
    assert "def test_calculate_discount" in result.test_code
    assert result.test_status == "FAILING"

def test_tdd_orchestrator_generates_minimal_implementation():
    # Arrange
    orchestrator = TDDOrchestrator()
    failing_test = "def test_add(): assert add(2, 3) == 5"
    
    # Act
    result = orchestrator.run_green_phase(failing_test)
    
    # Assert
    assert result.phase == "GREEN"
    assert result.implementation is not None
    assert "def add" in result.implementation
    assert result.test_status == "PASSING"

def test_tdd_orchestrator_suggests_refactorings():
    # Arrange
    orchestrator = TDDOrchestrator()
    working_code = """
    def calculate_order_total(items):
        total = 0
        for item in items:
            total = total + item.price
        return total
    """
    
    # Act
    result = orchestrator.run_refactor_phase(working_code)
    
    # Assert
    assert result.phase == "REFACTOR"
    assert len(result.suggestions) > 0
    assert any("sum()" in s for s in result.suggestions)
