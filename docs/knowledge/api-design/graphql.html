Overview

GraphQL best practices for schema design, efficient queries, resolver optimization, and security to build flexible, performant APIs.

GraphQL Core Benefits:
Flexible Queries: Clients request exactly what they need
Single Endpoint: One URL for all operations
Strong Typing: Schema-driven development with validation
Introspection: Self-documenting API
Real-time: Built-in subscriptions for live data

Schema Design

Design Schema Around Business Domain, Not Database

HIGH

GraphQL schema should represent your business domain and use cases, not mirror your database structure. This allows flexibility in data sources and evolution.

✅ Good - Domain-Driven Schema

# Business domain focused
type User {
  id: ID!
  fullName: String!
  email: String!
  profile: UserProfile!
  orders(
    first: Int = 10
    status: OrderStatus
  ): OrderConnection!
  recommendations: [Product!]!
}

type UserProfile {
  avatarUrl: String
  bio: String
  location: Location
  joinedAt: DateTime!
}

type OrderConnection {
  edges: [OrderEdge!]!
  pageInfo: PageInfo!
  totalCount: Int!
}

type OrderEdge {
  node: Order!
  cursor: String!
}

❌ Bad - Database-Driven Schema

# Directly mirrors database tables
type User {
  user_id: Int!
  first_name: String
  last_name: String
  email_address: String
  profile_id: Int
  created_at: String
  updated_at: String
}

type UserProfile {
  profile_id: Int!
  user_id: Int!
  avatar_path: String
  # Exposes internal implementation details
Design Principle: Schema is your API contract. Abstract implementation details, use business terminology, design for client needs.

Use Nullable Fields by Default

MEDIUM

Make fields nullable unless you can guarantee they always have a value. Non-null (!) should be the exception, not the rule.

✅ Good - Conservative Nullability

type Product {
  id: ID!              # ID always exists
  name: String!        # Name required for product
  description: String  # May not have description
  price: Float         # May not have price yet
  category: Category   # May be uncategorized
  images: [String!]!   # List never null, but may be empty
}

type Query {
  product(id: ID!): Product  # Might not find product
  products: [Product!]!      # List never null
}

❌ Bad - Overly Strict Non-Null

type Product {
  id: ID!
  name: String!
  description: String!  # What if no description?
  price: Float!         # What if price not set?
  category: Category!   # Forces fake category
  images: [String!]!    # OK
}

# If any field is null, entire response fails!
# Breaks partial data delivery
Nullability Impact: Non-null fields that become null cause the entire parent object to be null. Be conservative - you can always make fields non-null later, but the reverse is a breaking change.

Use Enums for Fixed Sets of Values

MEDIUM

Define enums for fields with a fixed set of possible values. Provides type safety and auto-documentation.

✅ Good - Enum Types

enum OrderStatus {
  PENDING
  CONFIRMED
  PROCESSING
  SHIPPED
  DELIVERED
  CANCELLED
  REFUNDED
}

enum Currency {
  USD
  EUR
  GBP
  JPY
}

type Order {
  id: ID!
  status: OrderStatus!
  total: Float!
  currency: Currency!
}

type Query {
  orders(status: OrderStatus): [Order!]!
}

Queries & Mutations

Use Input Types for Complex Arguments

HIGH

For mutations and complex queries, use input types instead of many scalar arguments. Improves readability and reusability.

✅ Good - Input Types

input CreateUserInput {
  email: String!
  password: String!
  firstName: String!
  lastName: String!
  phoneNumber: String
  address: AddressInput
}

input AddressInput {
  street: String!
  city: String!
  state: String!
  zipCode: String!
  country: String!
}

type Mutation {
  createUser(input: CreateUserInput!): CreateUserPayload!
}

type CreateUserPayload {
  user: User
  errors: [UserError!]!
}

❌ Bad - Many Scalar Arguments

type Mutation {
  createUser(
    email: String!
    password: String!
    firstName: String!
    lastName: String!
    phoneNumber: String
    street: String
    city: String
    state: String
    zipCode: String
    country: String
  ): User
  # Hard to read, maintain, and reuse

Return Rich Mutation Payloads

HIGH

Mutation responses should include the modified object, errors, and any affected related data for client updates.

✅ Good - Rich Payload

type UpdateProductPayload {
  product: Product
  errors: [UserError!]!
  # Return related data for cache updates
  affectedCategories: [Category!]!
  userAction: UserAction!
}

type UserError {
  message: String!
  field: String
  code: ErrorCode!
}

enum ErrorCode {
  VALIDATION_ERROR
  NOT_FOUND
  UNAUTHORIZED
  RATE_LIMITED
}

type Mutation {
  updateProduct(
    id: ID!
    input: UpdateProductInput!
  ): UpdateProductPayload!
}

Resolver Optimization

Implement DataLoader to Prevent N+1 Queries

HIGH

Use DataLoader to batch and cache database queries within a single request, preventing the N+1 problem.

✅ Good - DataLoader

// Setup DataLoader
const DataLoader = require('dataloader');

const userLoader = new DataLoader(async (userIds) => {
  // Batch load all users in single query
  const users = await User.findAll({
    where: { id: userIds }
  });
  
  // Return in same order as keys
  const userMap = new Map(users.map(u => [u.id, u]));
  return userIds.map(id => userMap.get(id));
});

// Resolver using DataLoader
const resolvers = {
  Order: {
    customer: (order, args, { loaders }) => {
      // Automatically batched and cached
      return loaders.user.load(order.customerId);
    }
  },
  
  Query: {
    orders: async (parent, args, { loaders }) => {
      const orders = await Order.findAll();
      // Each order.customer call is batched
      return orders;
    }
  }
};

❌ Bad - N+1 Problem

const resolvers = {
  Order: {
    customer: async (order) => {
      // Separate query for EACH order
      return await User.findByPk(order.customerId);
    }
  },
  
  Query: {
    orders: async () => {
      const orders = await Order.findAll(); // 1 query
      // Then N queries for N orders!
      return orders;
    }
  }
};
// 100 orders = 101 database queries!

Use Field-Level Authorization

HIGH

Implement authorization checks at the field level, not just query level, to protect sensitive data granularly.

✅ Good - Field-Level Auth

const resolvers = {
  User: {
    email: (user, args, { currentUser }) => {
      // Only user themselves or admins can see email
      if (currentUser.id === user.id || currentUser.isAdmin) {
        return user.email;
      }
      return null;
    },
    
    ssn: (user, args, { currentUser }) => {
      // Only admins with special permission
      if (currentUser.isAdmin && currentUser.hasPermission('VIEW_PII')) {
        return user.ssn;
      }
      throw new AuthorizationError('Insufficient permissions');
    }
  },
  
  Query: {
    user: async (parent, { id }, { currentUser }) => {
      // Fetch user - field resolvers handle access
      return await User.findByPk(id);
    }
  }
};

Performance Optimization

Implement Query Complexity Analysis

HIGH

Limit query complexity to prevent malicious or accidental expensive queries from overwhelming your server.

✅ Good - Complexity Limits

const { createComplexityLimitRule } = require('graphql-validation-complexity');

const server = new ApolloServer({
  typeDefs,
  resolvers,
  validationRules: [
    createComplexityLimitRule(1000, {
      // Assign complexity costs
      scalarCost: 1,
      objectCost: 5,
      listFactor: 10,
      
      // Custom costs for expensive fields
      fieldCosts: {
        'User.orders': 50,
        'Product.recommendations': 100
      }
    })
  ],
  
  // Also limit query depth
  plugins: [
    {
      requestDidStart: () => ({
        didResolveOperation({ request, document }) {
          const depth = calculateDepth(document);
          if (depth > 10) {
            throw new Error('Query depth exceeds limit');
          }
        }
      })
    }
  ]
});
Attack Vector: Without complexity limits, attackers can craft deeply nested queries that cause exponential database queries and memory usage.

Use Pagination for Lists

HIGH

Implement cursor-based pagination (Relay spec) or offset pagination for all list fields to prevent loading thousands of records.

✅ Good - Cursor Pagination

# Relay-style cursor pagination
type Query {
  products(
    first: Int
    after: String
    last: Int
    before: String
    filter: ProductFilter
  ): ProductConnection!
}

type ProductConnection {
  edges: [ProductEdge!]!
  pageInfo: PageInfo!
  totalCount: Int!
}

type ProductEdge {
  node: Product!
  cursor: String!
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}

Security Best Practices

Disable Introspection in Production

MEDIUM

Disable GraphQL introspection queries in production to prevent attackers from discovering your entire schema.

✅ Good - Conditional Introspection

const { ApolloServer } = require('apollo-server');
const { NoIntrospection } = require('graphql-disable-introspection');

const server = new ApolloServer({
  typeDefs,
  resolvers,
  introspection: process.env.NODE_ENV !== 'production',
  validationRules: [
    process.env.NODE_ENV === 'production' 
      ? NoIntrospection 
      : null
  ].filter(Boolean),
  
  // Also disable playground in production
  playground: process.env.NODE_ENV !== 'production'
});

Implement Rate Limiting

HIGH

Apply rate limiting per user and per query complexity to prevent abuse and ensure fair resource usage.

✅ Good - GraphQL Rate Limiting

const { RateLimitDirective } = require('graphql-rate-limit-directive');

const typeDefs = `
  directive @rateLimit(
    limit: Int!
    duration: Int!
  ) on FIELD_DEFINITION

  type Query {
    user(id: ID!): User
    
    # Expensive query - strict limit
    searchProducts(query: String!): [Product!]!
      @rateLimit(limit: 10, duration: 60)
    
    # Public data - generous limit  
    products: [Product!]!
      @rateLimit(limit: 100, duration: 60)
  }
`;

const server = new ApolloServer({
  typeDefs,
  resolvers,
  schemaDirectives: {
    rateLimit: RateLimitDirective
  }
});
