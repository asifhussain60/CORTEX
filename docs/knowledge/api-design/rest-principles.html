🔗 HATEOAS: Hypermedia as the Engine of Application State

HATEOAS is the constraint that distinguishes a true REST API. Clients discover available actions through hypermedia links. 

sequenceDiagram
    participant Client
    participant API
    
    Client->>API: GET /users/123
    Note right of API: Server includes hypermedia links
    API-->>Client: {
  "id": 123,
  "name": "John",
  "_links": {
    "self": "/users/123",
    "orders": "/users/123/orders",
    "edit": "/users/123"
  }
}
    
    Note left of Client: Client discovers available actions
    Client->>API: GET /users/123/orders
    API-->>Client: [Order objects with links]
    
    Note left of Client: No hardcoded URLs needed

💡 Key Benefits of HATEOAS

  • Decoupling: Clients don't need to hardcode URLs
  • Discoverability: Available actions are self-documented
  • Evolvability: Server can change URLs without breaking clients
  • State Transitions: Links guide clients through workflows

🏛️ Six REST Constraints

1. Client-Server

Separation of concerns between UI and data storage

2. Stateless

Each request contains all necessary information

3. Cacheable

Responses explicitly indicate cacheability

4. Uniform Interface

Consistent resource identification and manipulation

5. Layered System

Client cannot tell if connected directly to end server

6. Code-On-Demand (Optional)

Server can extend client functionality with code

🏆 Progressive Challenge

Design a complete order management API with HATEOAS that supports:

  • Order creation with hypermedia links to payment and shipping
  • State transitions (pending → paid → shipped → delivered)
  • Dynamic links based on current order state
  • Proper HTTP status codes for each operation

💡 Hint

Start with defining the Order resource with id, status, items, and total. Then add conditional _links based on status (e.g., only show "cancel" link if status is "pending").
