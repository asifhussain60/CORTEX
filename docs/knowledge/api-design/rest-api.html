Overview

REST (Representational State Transfer) API best practices for designing scalable, maintainable, and developer-friendly APIs following HTTP standards.

REST Principles:
Resource-Based: APIs expose resources (nouns), not actions (verbs)
HTTP Methods: Use standard methods (GET, POST, PUT, DELETE, PATCH)
Stateless: Each request contains all necessary information
Cacheable: Responses indicate if they can be cached
Uniform Interface: Consistent patterns across all endpoints

Resource Design

Use Nouns for Resource Names, Not Verbs

HIGH

REST APIs expose resources (things) via URIs. Use HTTP methods to express actions on resources.

✅ Good - Resource-Based URIs

GET    /api/users              # List users
GET    /api/users/123          # Get user by ID
POST   /api/users              # Create user
PUT    /api/users/123          # Update user
PATCH  /api/users/123          # Partial update
DELETE /api/users/123          # Delete user

GET    /api/users/123/orders   # User's orders
POST   /api/orders             # Create order
GET    /api/products/456       # Get product

❌ Bad - Verb-Based URIs

GET  /api/getUser?id=123
POST /api/createUser
POST /api/updateUser
POST /api/deleteUser
GET  /api/getUserOrders?userId=123

# HTTP methods ignored
# Inconsistent patterns
# Not RESTful

Use Plural Nouns for Collections

MEDIUM

Use plural nouns for collection resources for consistency. Single item is accessed via collection with ID.

✅ Good - Plural Collections

GET  /api/users           # Collection
GET  /api/users/123       # Item in collection
GET  /api/orders          # Collection
GET  /api/orders/789      # Item

# Consistent pattern:
# /{collection}
# /{collection}/{id}
# /{collection}/{id}/{sub-collection}

❌ Bad - Mixed Singular/Plural

GET /api/user/123         # Singular
GET /api/users            # Plural
GET /api/order/789        # Singular
GET /api/products         # Plural

# Inconsistent, confusing

Model Resource Relationships in URIs

MEDIUM

Express resource relationships through nested URIs when there's a clear parent-child relationship.

✅ Good - Nested Resources

# User's orders (parent-child relationship)
GET    /api/users/123/orders
POST   /api/users/123/orders
GET    /api/users/123/orders/456

# Product reviews
GET    /api/products/789/reviews
POST   /api/products/789/reviews
DELETE /api/products/789/reviews/101

# Also provide direct access for non-hierarchical queries
GET    /api/orders?userId=123
GET    /api/orders/456

HTTP Methods

Use HTTP Methods Correctly

HIGH

Each HTTP method has specific semantics. GET is safe, PUT/DELETE are idempotent, POST is neither.

✅ Good - Correct Method Usage

// GET - Safe, idempotent, cacheable
app.get('/api/users/:id', async (req, res) => {
  const user = await db.users.findById(req.params.id);
  res.json(user);
  // No side effects, can be cached
});

// POST - Create new resource, not idempotent
app.post('/api/users', async (req, res) => {
  const newUser = await db.users.create(req.body);
  res.status(201)
     .location(`/api/users/${newUser.id}`)
     .json(newUser);
  // Each call creates new user
});

// PUT - Replace entire resource, idempotent
app.put('/api/users/:id', async (req, res) => {
  const updated = await db.users.replace(req.params.id, req.body);
  res.json(updated);
  // Multiple identical calls = same result
});

// PATCH - Partial update, idempotent
app.patch('/api/users/:id', async (req, res) => {
  const updated = await db.users.update(req.params.id, req.body);
  res.json(updated);
});

// DELETE - Remove resource, idempotent
app.delete('/api/users/:id', async (req, res) => {
  await db.users.delete(req.params.id);
  res.status(204).send();
  // Multiple calls = same result (resource deleted)
});
Method Properties:
Safe: No side effects (GET, HEAD, OPTIONS)
Idempotent: Multiple identical requests = same result (GET, PUT, DELETE, HEAD, OPTIONS)
POST: Not safe, not idempotent - creates new resources

Use PATCH for Partial Updates

MEDIUM

Use PATCH to update specific fields without sending entire resource. More efficient than PUT for partial updates.

✅ Good - PATCH for Partial Update

PATCH /api/users/123
Content-Type: application/json

{
  "email": "newemail@example.com"
}

# Only sends changed fields
# Server merges with existing data

❌ Bad - PUT with Partial Data

PUT /api/users/123
Content-Type: application/json

{
  "email": "newemail@example.com"
}

# PUT should replace entire resource
# Missing fields would be deleted
# Client must send all fields

HTTP Status Codes

Return Appropriate Status Codes

HIGH

Use standard HTTP status codes to communicate result. Don't return 200 OK for errors.

✅ Good - Correct Status Codes

// Success responses
app.post('/api/users', async (req, res) => {
  const user = await createUser(req.body);
  res.status(201).json(user);  // 201 Created
});

app.delete('/api/users/:id', async (req, res) => {
  await deleteUser(req.params.id);
  res.status(204).send();      // 204 No Content
});

app.get('/api/users', async (req, res) => {
  const users = await getUsers();
  res.status(200).json(users); // 200 OK
});

// Client errors (4xx)
app.get('/api/users/:id', async (req, res) => {
  const user = await findUser(req.params.id);
  if (!user) {
    return res.status(404).json({
      error: 'User not found'
    });
  }
  res.json(user);
});

app.post('/api/users', async (req, res) => {
  const errors = validateUser(req.body);
  if (errors) {
    return res.status(400).json({
      error: 'Validation failed',
      details: errors
    });
  }
  // ...
});

app.put('/api/orders/:id', async (req, res) => {
  if (!req.user) {
    return res.status(401).json({
      error: 'Authentication required'
    });
  }
  
  if (!canEditOrder(req.user, req.params.id)) {
    return res.status(403).json({
      error: 'Insufficient permissions'
    });
  }
  // ...
});

// Server errors (5xx)
app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({
    error: 'Internal server error'
  });
});
Common Status Codes:
200 OK: Success
201 Created: Resource created (include Location header)
204 No Content: Success with no response body
400 Bad Request: Invalid input
401 Unauthorized: Authentication required
403 Forbidden: Authenticated but no permission
404 Not Found: Resource doesn't exist
409 Conflict: Request conflicts with current state
429 Too Many Requests: Rate limit exceeded
500 Internal Server Error: Server error

API Versioning

Version Your API

HIGH

Use versioning to maintain backward compatibility while evolving the API. Common approaches: URI versioning, header versioning.

✅ Good - URI Versioning

# Version in URI (most common, explicit)
GET /api/v1/users
GET /api/v2/users

# Header versioning (cleaner URIs)
GET /api/users
Accept: application/vnd.myapi.v1+json

GET /api/users
Accept: application/vnd.myapi.v2+json

# Query parameter versioning
GET /api/users?version=1
GET /api/users?version=2

✅ Good - Implementation

// Express with URI versioning
const v1Router = express.Router();
const v2Router = express.Router();

// v1 API
v1Router.get('/users', (req, res) => {
  res.json({
    users: [
      { id: 1, name: 'Alice' }
    ]
  });
});

// v2 API with breaking changes
v2Router.get('/users', (req, res) => {
  res.json({
    data: [
      { 
        id: 1, 
        fullName: 'Alice Smith',  // Changed field name
        email: 'alice@example.com' // New field
      }
    ],
    meta: {
      total: 1,
      page: 1
    }
  });
});

app.use('/api/v1', v1Router);
app.use('/api/v2', v2Router);

Pagination & Filtering

Implement Pagination for Collections

HIGH

Always paginate collection responses to prevent performance issues. Include metadata about pagination.

✅ Good - Pagination Response

GET /api/products?page=2&limit=20

HTTP/1.1 200 OK
Content-Type: application/json
Link: ; rel="first",
      ; rel="next",
      ; rel="last"

{
  "data": [
    { "id": 21, "name": "Product 21" },
    { "id": 22, "name": "Product 22" }
  ],
  "meta": {
    "currentPage": 2,
    "perPage": 20,
    "total": 200,
    "totalPages": 10
  },
  "links": {
    "first": "/api/products?page=1&limit=20",
    "prev": "/api/products?page=1&limit=20",
    "next": "/api/products?page=3&limit=20",
    "last": "/api/products?page=10&limit=20"
  }
}

Support Filtering, Sorting, and Field Selection

MEDIUM

Allow clients to filter, sort, and select specific fields via query parameters for efficient data retrieval.

✅ Good - Query Parameters

# Filtering
GET /api/products?category=electronics&price_min=100&price_max=500

# Sorting
GET /api/products?sort=-price,name
# - prefix for descending, comma-separated

# Field selection (sparse fieldsets)
GET /api/users?fields=id,name,email
# Only return specified fields

# Combined
GET /api/products?category=electronics&sort=-price&fields=id,name,price&page=1&limit=10

✅ Implementation Example

app.get('/api/products', async (req, res) => {
  const { 
    category, 
    price_min, 
    price_max,
    sort = 'name',
    fields,
    page = 1,
    limit = 20
  } = req.query;
  
  const query = db.products.find();
  
  // Filtering
  if (category) query.where('category', category);
  if (price_min) query.where('price', '>=', price_min);
  if (price_max) query.where('price', '<=', price_max);
  
  // Sorting
  const sortFields = sort.split(',');
  sortFields.forEach(field => {
    const order = field.startsWith('-') ? 'desc' : 'asc';
    const fieldName = field.replace('-', '');
    query.orderBy(fieldName, order);
  });
  
  // Field selection
  if (fields) {
    const selectedFields = fields.split(',');
    query.select(selectedFields);
  }
  
  // Pagination
  const offset = (page - 1) * limit;
  query.limit(limit).offset(offset);
  
  const products = await query;
  const total = await db.products.count(/* same filters */);
  
  res.json({
    data: products,
    meta: {
      currentPage: page,
      perPage: limit,
      total,
      totalPages: Math.ceil(total / limit)
    }
  });
});
