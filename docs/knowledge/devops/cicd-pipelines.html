What is CI/CD?

Continuous Integration/Continuous Deployment (CI/CD) automates software delivery from code commit to production. CI ensures code changes are automatically built and tested. CD ensures deployments are automated, reliable, and repeatable.

Key Benefits

Faster Time to Market: 60-90% reduction in release cycle time
Reduced Risk: Small, frequent releases easier to troubleshoot
Improved Quality: Automated testing catches bugs before production
Consistent Deployments: Eliminates human error (95% success rate)
Rapid Feedback: 10x faster feedback loop for developers
💡 CI vs CD vs Continuous Deployment:
CI: Automatically build and test on every commit
CD (Delivery): Always deployable, manual approval for production
CD (Deployment): Every passing build automatically deploys to production

Pipeline Stages

A typical CI/CD pipeline consists of these sequential stages.

Stage 1: Source

HIGH PRIORITY

Trigger pipeline on code changes and clone repository.

✅ GitHub Actions Example

name: CI Pipeline
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Full history for analysis

Best Practices

Use webhooks for instant triggering (not polling)
Shallow clone to reduce clone time
Cache dependencies between runs

Stage 2: Build

HIGH PRIORITY

Compile code, resolve dependencies, create artifacts.

✅ Multi-Language Build

# .NET Build
- name: Setup .NET
  uses: actions/setup-dotnet@v3
  with:
    dotnet-version: '8.0.x'

- name: Restore dependencies
  run: dotnet restore

- name: Build
  run: dotnet build --configuration Release --no-restore

- name: Publish
  run: dotnet publish -c Release -o ./publish

✅ Node.js Build

# Node.js Build
- name: Setup Node.js
  uses: actions/setup-node@v4
  with:
    node-version: '20'
    cache: 'npm'

- name: Install dependencies
  run: npm ci

- name: Build
  run: npm run build

Best Practices

Keep build time under 10 minutes
Fail fast on build errors
Cache dependencies (npm, NuGet, Maven)
Use specific tool versions (not "latest")

Stage 3: Test

HIGH PRIORITY

Run automated tests to validate code quality.

✅ Multi-Level Testing

- name: Unit Tests
  run: dotnet test --configuration Release --no-build --verbosity normal --logger trx

- name: Integration Tests
  run: dotnet test tests/IntegrationTests --no-build
  env:
    ConnectionString: ${{ secrets.TEST_DB_CONNECTION }}

- name: Code Coverage
  run: |
    dotnet test /p:CollectCoverage=true /p:CoverletOutputFormat=lcov
    bash <(curl -s https://codecov.io/bash)

- name: Publish Test Results
  uses: dorny/test-reporter@v1
  if: always()
  with:
    name: Test Results
    path: '**/*.trx'
    reporter: dotnet-trx

Test Categories

Unit Tests: Fast, isolated tests (seconds)
Integration Tests: Test component interactions (minutes)
E2E Tests: Full user workflows (minutes to hours)
Performance Tests: Load/stress testing

Stage 4: Security Scanning

HIGH PRIORITY

Scan for vulnerabilities, secrets, and code quality issues.

✅ Security Checks

- name: Dependency Vulnerability Scan
  run: dotnet list package --vulnerable --include-transitive

- name: Secret Scanning
  uses: trufflesecurity/trufflehog@main
  with:
    path: ./
    base: main

- name: SAST (Static Analysis)
  uses: github/codeql-action/analyze@v2

- name: SonarQube Analysis
  uses: sonarsource/sonarqube-scan-action@master
  env:
    SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

Stage 5: Artifact Storage

MEDIUM PRIORITY

Package and store build artifacts for deployment.

✅ Docker Image

- name: Build Docker Image
  run: |
    docker build -t myapp:${{ github.sha }} .
    docker tag myapp:${{ github.sha }} myapp:latest

- name: Push to Container Registry
  run: |
    echo ${{ secrets.DOCKER_PASSWORD }} | docker login -u ${{ secrets.DOCKER_USERNAME }} --password-stdin
    docker push myapp:${{ github.sha }}
    docker push myapp:latest

✅ NuGet Package

- name: Pack NuGet Package
  run: dotnet pack --configuration Release --output ./nupkgs

- name: Push to NuGet.org
  run: dotnet nuget push ./nupkgs/*.nupkg --api-key ${{ secrets.NUGET_API_KEY }} --source https://api.nuget.org/v3/index.json

Automated Testing Strategy

Comprehensive testing ensures code quality and prevents regressions.

Test Pyramid

HIGH PRIORITY

Balance fast unit tests with slower integration and E2E tests.

Recommended Distribution

         /\
        /E2E\       10% - Slow, brittle, expensive
       /------\
      /  Intg  \    20% - Medium speed, test interactions
     /----------\
    /   Unit     \  70% - Fast, cheap, reliable
   /--------------\

UNIT TESTS (70%):
- Test single function/class
- Fast execution (< 1 second each)
- No external dependencies (mocked)
- High coverage (80%+)

INTEGRATION TESTS (20%):
- Test component interactions
- Database, API, file system
- Medium speed (seconds to minutes)
- Focus on critical paths

E2E TESTS (10%):
- Test complete user workflows
- Browser automation (Selenium, Playwright)
- Slow (minutes)
- Cover happy paths only

Test Quality Gates

HIGH PRIORITY

Define thresholds that must pass before deployment.

✅ Quality Gate Configuration

# Fail pipeline if quality gates not met
- name: Check Code Coverage
  run: |
    COVERAGE=$(grep -Po 'Line coverage: \K[0-9.]+' coverage.txt)
    if (( $(echo "$COVERAGE < 80" | bc -l) )); then
      echo "Code coverage $COVERAGE% is below 80% threshold"
      exit 1
    fi

- name: Check Test Pass Rate
  run: |
    PASS_RATE=$(grep -Po 'Test pass rate: \K[0-9.]+' test-results.txt)
    if (( $(echo "$PASS_RATE < 95" | bc -l) )); then
      echo "Test pass rate $PASS_RATE% is below 95% threshold"
      exit 1
    fi

Common Quality Gates

Code Coverage: ≥ 80% line coverage
Test Pass Rate: 100% tests passing
Security Vulnerabilities: Zero critical/high vulnerabilities
Code Smells: SonarQube rating ≥ A
Build Time: < 10 minutes

Deployment Strategies

Choose the right deployment strategy based on risk tolerance and downtime requirements.

Blue-Green Deployment

HIGH PRIORITY

Maintain two identical environments. Switch traffic instantly, instant rollback.

✅ Blue-Green Strategy

# Deploy to Green (inactive) environment
- name: Deploy to Green
  run: |
    kubectl apply -f k8s/green-deployment.yaml
    kubectl rollout status deployment/myapp-green

# Run smoke tests on Green
- name: Smoke Test Green
  run: |
    curl https://green.myapp.com/health
    ./run-smoke-tests.sh green.myapp.com

# Switch traffic from Blue to Green
- name: Switch Traffic
  run: |
    kubectl patch service myapp -p '{"spec":{"selector":{"version":"green"}}}'
    
# Monitor for 5 minutes
- name: Monitor
  run: sleep 300

# Rollback if issues detected
- name: Rollback if Needed
  if: failure()
  run: |
    kubectl patch service myapp -p '{"spec":{"selector":{"version":"blue"}}}'

Pros & Cons

✅ Instant rollback (just switch traffic back)
✅ Zero downtime
✅ Full production testing before cutover
❌ Requires double infrastructure (expensive)
❌ Database migration challenges

Canary Deployment

HIGH PRIORITY

Gradually roll out to small percentage of users, monitor, then expand.

✅ Canary Strategy

# Deploy canary (5% traffic)
- name: Deploy Canary
  run: |
    kubectl apply -f k8s/canary-deployment.yaml
    kubectl set image deployment/myapp-canary myapp=myapp:${{ github.sha }}
    
# Route 5% traffic to canary
- name: Configure Traffic Split
  run: |
    kubectl apply -f - <<EOF
    apiVersion: v1
    kind: Service
    metadata:
      name: myapp
    spec:
      trafficPolicy:
        canary:
          weight: 5  # 5% to canary, 95% to stable
    EOF

# Monitor canary metrics for 30 minutes
- name: Monitor Canary
  run: |
    ./monitor-canary.sh --duration 30m --error-rate-threshold 1%
    
# If successful, increase to 50%
- name: Increase Canary
  run: kubectl patch service myapp -p '{"spec":{"trafficPolicy":{"canary":{"weight":50}}}}'

# Monitor again
- name: Monitor 50%
  run: ./monitor-canary.sh --duration 30m

# Promote canary to 100%
- name: Promote Canary
  run: |
    kubectl patch service myapp -p '{"spec":{"trafficPolicy":{"canary":{"weight":100}}}}'
    kubectl delete deployment myapp-stable
    kubectl rename deployment myapp-canary myapp-stable

Pros & Cons

✅ Limits blast radius (only affects small % of users)
✅ Real production testing with real users
✅ Gradual rollout reduces risk
❌ Complex traffic routing
❌ Requires monitoring/alerting

Rolling Deployment

MEDIUM PRIORITY

Update instances one by one. Simple but limited rollback.

✅ Kubernetes Rolling Update

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1  # Max 1 pod down at a time
      maxSurge: 2        # Max 2 extra pods during update
  template:
    spec:
      containers:
      - name: myapp
        image: myapp:${{ github.sha }}
        readinessProbe:  # Critical for rolling updates
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5

Pipeline Security

Secure your CI/CD pipeline to prevent supply chain attacks.

Secrets Management

HIGH PRIORITY

Never hardcode secrets. Use secret managers.

✅ GitHub Secrets

- name: Deploy to Production
  run: |
    az login --service-principal \
      --username ${{ secrets.AZURE_CLIENT_ID }} \
      --password ${{ secrets.AZURE_CLIENT_SECRET }} \
      --tenant ${{ secrets.AZURE_TENANT_ID }}
    
    az webapp deploy --name myapp --resource-group prod

❌ Avoid - Hardcoded Secrets

# NEVER DO THIS!
- name: Deploy
  run: |
    export API_KEY="sk-1234567890abcdef"  # Exposed in logs!
    ./deploy.sh

Least Privilege Access

HIGH PRIORITY

Grant minimum permissions needed for each pipeline stage.

✅ Scoped Permissions

permissions:
  contents: read        # Read repository
  packages: write       # Publish packages
  deployments: write    # Create deployments
  # Do NOT grant:
  # - admin (too broad)
  # - write to main branch

Pipeline Optimization

Improve build speed and resource efficiency.

Caching Dependencies

MEDIUM PRIORITY

Cache dependencies to avoid re-downloading on every build.

✅ Multi-Language Caching

# Node.js
- uses: actions/setup-node@v4
  with:
    node-version: '20'
    cache: 'npm'  # Automatic caching

# .NET
- uses: actions/setup-dotnet@v3
  with:
    dotnet-version: '8.0.x'
- uses: actions/cache@v3
  with:
    path: ~/.nuget/packages
    key: ${{ runner.os }}-nuget-${{ hashFiles('**/*.csproj') }}

# Python
- uses: actions/setup-python@v4
  with:
    python-version: '3.11'
    cache: 'pip'

✅ Reduces build time by 50-80%

Parallel Jobs

MEDIUM PRIORITY

Run independent jobs in parallel to reduce total pipeline time.

✅ Matrix Strategy

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [18, 20, 22]
        os: [ubuntu-latest, windows-latest, macos-latest]
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm test

# Runs 9 jobs in parallel (3 versions × 3 OSes)
