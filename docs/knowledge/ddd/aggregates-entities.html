Tactical DDD Building Blocks

Tactical Domain-Driven Design provides building blocks for implementing domain models within bounded contexts. These patterns ensure data consistency, enforce business invariants, and create maintainable domain logic.

💡 Key Benefit: Aggregates define consistency boundaries, ensuring all business rules are enforced atomically within transaction boundaries.

Core Building Blocks

  • Entities: Objects with unique identity that persists over time
  • Value Objects: Immutable objects defined by attributes, not identity
  • Aggregates: Cluster of entities/value objects with consistency boundary
  • Domain Events: Record of something significant that happened
  • Repositories: Abstraction for accessing aggregates
  • Domain Services: Stateless operations not belonging to entities
  • Factories: Complex object creation logic

Entities

Entities are objects with unique identity and lifecycle. Equality is based on ID, not attributes. Identity remains constant throughout the entity's lifecycle.

Entity Identity Patterns

HIGH PRIORITY

Choose appropriate identity strategy based on your domain and infrastructure needs.

Strategy 1: GUID/UUID (Recommended for Distributed Systems)

✅ Recommended

public class Order : Entity
{
    public Guid Id { get; private set; }
    public DateTime OrderDate { get; private set; }
    
    public Order()
    {
        Id = Guid.NewGuid();  // Generated in code
        OrderDate = DateTime.UtcNow;
    }
}

// Benefits:
// 1. No database round-trip needed
// 2. Portable across systems
// 3. No collision risk in distributed scenarios

Strategy 2: Database-Generated ID

-- SQL Server IDENTITY
CREATE TABLE Orders (
    OrderId INT IDENTITY(1,1) PRIMARY KEY,
    CustomerId INT,
    OrderDate DATETIME
);

-- Pros: Simple, guaranteed unique, sequential
-- Cons: Requires DB round-trip, not portable

Strategy 3: Natural Key

public class Product : Entity
{
    public string SKU { get; private set; }  // Stock Keeping Unit
    
    public Product(string sku)
    {
        if (string.IsNullOrEmpty(sku))
            throw new ArgumentException("SKU required");
        SKU = sku;
    }
}

// Pros: Human-readable, business meaningful
// Cons: May change over time, uniqueness not guaranteed

Entity Base Class Pattern

HIGH PRIORITY

Implement a base Entity class with identity-based equality comparison.

✅ Recommended

public abstract class Entity
{
    public Guid Id { get; protected set; }
    
    // Equality based on ID
    public override bool Equals(object obj)
    {
        if (obj is not Entity other)
            return false;
        
        if (ReferenceEquals(this, other))
            return true;
        
        if (GetType() != other.GetType())
            return false;
        
        // Entities with default ID (not persisted) are not equal
        if (Id == default || other.Id == default)
            return false;
        
        return Id == other.Id;
    }
    
    public override int GetHashCode()
    {
        return Id.GetHashCode();
    }
    
    public static bool operator ==(Entity left, Entity right)
    {
        if (left is null && right is null)
            return true;
        if (left is null || right is null)
            return false;
        return left.Equals(right);
    }
    
    public static bool operator !=(Entity left, Entity right)
    {
        return !(left == right);
    }
}

Value Objects

Value Objects are immutable objects defined by their attributes, not identity. Two value objects with the same attributes are considered equal.

Value Object Characteristics

HIGH PRIORITY

Value Objects must be immutable, have no identity, and implement value-based equality.

✅ Recommended - Money Value Object

public sealed class Money : IEquatable<Money>
{
    public decimal Amount { get; }
    public string Currency { get; }
    
    private Money(decimal amount, string currency)
    {
        if (string.IsNullOrEmpty(currency))
            throw new ArgumentException("Currency required");
        
        Amount = amount;
        Currency = currency.ToUpperInvariant();
    }
    
    public static Money Create(decimal amount, string currency)
    {
        return new Money(amount, currency);
    }
    
    // Value-based equality
    public bool Equals(Money other)
    {
        if (other is null) return false;
        return Amount == other.Amount && Currency == other.Currency;
    }
    
    public override bool Equals(object obj)
    {
        return obj is Money other && Equals(other);
    }
    
    public override int GetHashCode()
    {
        return HashCode.Combine(Amount, Currency);
    }
    
    // Immutable operations return new instances
    public Money Add(Money other)
    {
        if (Currency != other.Currency)
            throw new InvalidOperationException("Cannot add different currencies");
        
        return new Money(Amount + other.Amount, Currency);
    }
}

// Usage
var price = Money.Create(99.99m, "USD");
var discount = Money.Create(10.00m, "USD");
var finalPrice = price.Add(discount.Negate());

When to Use Value Objects vs Entities

MEDIUM PRIORITY

Use value objects for concepts that have no meaningful identity.

Examples

// VALUE OBJECTS (no identity needed)
public class Address
{
    public string Street { get; }
    public string City { get; }
    public string PostalCode { get; }
    // Immutable, value-based equality
}

public class DateRange
{
    public DateTime Start { get; }
    public DateTime End { get; }
    // Immutable, value-based equality
}

// ENTITIES (need identity)
public class Customer : Entity
{
    public Guid Id { get; private set; }
    public string Name { get; private set; }
    public Address ShippingAddress { get; private set; }  // Value object
}

Aggregates

An Aggregate is a cluster of entities and value objects with a consistency boundary. The Aggregate Root is the only entry point for external access.

Aggregate Rules

HIGH PRIORITY

Follow these rules to design effective aggregates that maintain consistency.

  • Rule 1: Protect business invariants inside aggregate boundaries
  • Rule 2: Design small aggregates for better performance
  • Rule 3: Reference other aggregates by ID only
  • Rule 4: Update one aggregate per transaction
  • Rule 5: Use eventual consistency between aggregates

✅ Recommended - Order Aggregate

public class Order : Entity, IAggregateRoot
{
    // Aggregate root properties
    public Guid Id { get; private set; }
    public Guid CustomerId { get; private set; }  // Reference by ID
    public DateTime OrderDate { get; private set; }
    
    // Aggregate contains children
    private readonly List<OrderItem> _items = new();
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();
    
    public Money TotalAmount { get; private set; }
    public OrderStatus Status { get; private set; }
    
    // Private constructor - use factory method
    private Order() { }
    
    // Factory method enforces invariants
    public static Order Create(Guid customerId)
    {
        var order = new Order
        {
            Id = Guid.NewGuid(),
            CustomerId = customerId,
            OrderDate = DateTime.UtcNow,
            Status = OrderStatus.Draft,
            TotalAmount = Money.Create(0, "USD")
        };
        
        return order;
    }
    
    // Aggregate root controls all changes
    public void AddItem(Guid productId, int quantity, Money unitPrice)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Cannot modify submitted order");
        
        if (quantity <= 0)
            throw new ArgumentException("Quantity must be positive");
        
        var item = new OrderItem(productId, quantity, unitPrice);
        _items.Add(item);
        
        RecalculateTotal();  // Maintain invariant
    }
    
    public void RemoveItem(Guid itemId)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Cannot modify submitted order");
        
        var item = _items.FirstOrDefault(i => i.Id == itemId);
        if (item != null)
        {
            _items.Remove(item);
            RecalculateTotal();
        }
    }
    
    public void Submit()
    {
        if (_items.Count == 0)
            throw new InvalidOperationException("Cannot submit empty order");
        
        Status = OrderStatus.Submitted;
        
        // Raise domain event
        AddDomainEvent(new OrderSubmittedEvent(Id, CustomerId, TotalAmount));
    }
    
    // Private method ensures invariant
    private void RecalculateTotal()
    {
        var total = _items.Sum(i => i.LineTotal.Amount);
        TotalAmount = Money.Create(total, "USD");
    }
}

// OrderItem is NOT an aggregate root - only accessible through Order
public class OrderItem : Entity
{
    public Guid Id { get; private set; }
    public Guid ProductId { get; private set; }
    public int Quantity { get; private set; }
    public Money UnitPrice { get; private set; }
    public Money LineTotal { get; private set; }
    
    internal OrderItem(Guid productId, int quantity, Money unitPrice)
    {
        Id = Guid.NewGuid();
        ProductId = productId;
        Quantity = quantity;
        UnitPrice = unitPrice;
        LineTotal = Money.Create(quantity * unitPrice.Amount, unitPrice.Currency);
    }
}

Aggregate Size Guidelines

MEDIUM PRIORITY

Keep aggregates small to avoid performance and concurrency issues.

❌ Avoid - Aggregate Too Large

// BAD: Customer aggregate contains too much
public class Customer : IAggregateRoot
{
    public List<Order> Orders { get; set; }          // 1000s of orders
    public List<Payment> Payments { get; set; }      // 1000s of payments
    public List<Address> Addresses { get; set; }     // Many addresses
    public List<Review> Reviews { get; set; }        // 1000s of reviews
    
    // Loading this aggregate is expensive!
    // Concurrency conflicts are common!
}

✅ Recommended - Right-Sized Aggregates

// GOOD: Separate aggregates with references by ID
public class Customer : IAggregateRoot
{
    public Guid Id { get; private set; }
    public string Name { get; private set; }
    // Small, focused aggregate
}

public class Order : IAggregateRoot
{
    public Guid Id { get; private set; }
    public Guid CustomerId { get; private set; }  // Reference by ID
    public List<OrderItem> Items { get; private set; }
}

// Each aggregate can be loaded/updated independently

Repositories

Repositories provide abstraction for accessing aggregates, hiding data access complexity and providing collection-like interface.

Repository Pattern

HIGH PRIORITY

Create one repository per aggregate root. Repositories work with complete aggregates, not fragments.

✅ Recommended

// Repository interface (in domain layer)
public interface IOrderRepository
{
    Task<Order> GetByIdAsync(Guid orderId);
    Task<List<Order>> GetByCustomerIdAsync(Guid customerId);
    Task AddAsync(Order order);
    Task UpdateAsync(Order order);
    Task DeleteAsync(Guid orderId);
}

// Repository implementation (in infrastructure layer)
public class OrderRepository : IOrderRepository
{
    private readonly AppDbContext _context;
    
    public OrderRepository(AppDbContext context)
    {
        _context = context;
    }
    
    public async Task<Order> GetByIdAsync(Guid orderId)
    {
        // Load complete aggregate (root + children)
        return await _context.Orders
            .Include(o => o.Items)  // Load order items
            .FirstOrDefaultAsync(o => o.Id == orderId);
    }
    
    public async Task AddAsync(Order order)
    {
        await _context.Orders.AddAsync(order);
        await _context.SaveChangesAsync();
    }
}

// Usage in application service
public class OrderService
{
    private readonly IOrderRepository _orderRepository;
    
    public async Task SubmitOrder(Guid orderId)
    {
        var order = await _orderRepository.GetByIdAsync(orderId);
        order.Submit();  // Business logic in domain
        await _orderRepository.UpdateAsync(order);
    }
}

Domain Events

Domain Events capture significant business occurrences and enable decoupled communication between aggregates using eventual consistency.

Domain Event Pattern

MEDIUM PRIORITY

Use domain events to maintain consistency across aggregate boundaries.

✅ Recommended

// Domain event
public class OrderSubmittedEvent : IDomainEvent
{
    public Guid OrderId { get; }
    public Guid CustomerId { get; }
    public Money TotalAmount { get; }
    public DateTime OccurredOn { get; }
    
    public OrderSubmittedEvent(Guid orderId, Guid customerId, Money totalAmount)
    {
        OrderId = orderId;
        CustomerId = customerId;
        TotalAmount = totalAmount;
        OccurredOn = DateTime.UtcNow;
    }
}

// Aggregate raises event
public class Order : IAggregateRoot
{
    private readonly List<IDomainEvent> _domainEvents = new();
    public IReadOnlyList<IDomainEvent> DomainEvents => _domainEvents;
    
    public void Submit()
    {
        Status = OrderStatus.Submitted;
        _domainEvents.Add(new OrderSubmittedEvent(Id, CustomerId, TotalAmount));
    }
    
    public void ClearDomainEvents() => _domainEvents.Clear();
}

// Event handler (separate aggregate)
public class InventoryService : IDomainEventHandler<OrderSubmittedEvent>
{
    public async Task Handle(OrderSubmittedEvent @event)
    {
        // Reserve inventory for submitted order
        // This happens in separate transaction (eventual consistency)
    }
}
