What are Domain Events?

"Use a domain event to capture an occurrence of something that happened in the domain." — Eric Evans

Domain Events are records of significant occurrences in your domain. They enable decoupled communication between aggregates and bounded contexts, support eventual consistency, and provide an audit trail of system behavior.

Characteristics

Past Tense Naming: OrderPlaced (not PlaceOrder) - describes what happened
Immutable: What happened cannot change after the fact
Contains Relevant Data: Information needed by event consumers
Published After Persistence: Only after aggregate state is saved
Triggers Side Effects: Can cause actions in other parts of system

Types of Events

Internal Domain Events: Within same bounded context (OrderConfirmed → EmailSent)
Integration Events: Across bounded contexts (OrderPlaced → Fulfillment notified)
Event Sourcing Events: Complete state representation for rebuilding aggregates
💡 Benefits: Decouples components, enables eventual consistency, provides audit trail, supports temporal queries, makes implicit processes explicit.

Event Design

How to structure domain events for maximum clarity and maintainability.

Event Structure Components

HIGH PRIORITY

Every domain event should contain these key components.

✅ Recommended - Well-Designed Event

// Base domain event class
public abstract class DomainEvent
{
    public Guid EventId { get; }          // Unique event identifier
    public DateTime OccurredOn { get; }    // When it happened
    
    protected DomainEvent()
    {
        EventId = Guid.NewGuid();
        OccurredOn = DateTime.UtcNow;
    }
}

// Specific domain event
public class OrderPlacedEvent : DomainEvent
{
    // Aggregate information
    public Guid OrderId { get; }           // What aggregate
    public Guid CustomerId { get; }        // Who caused it
    
    // Event-specific data
    public Money TotalAmount { get; }      // Relevant information
    public DateTime OrderDate { get; }
    public List<OrderItemDto> Items { get; }
    
    // Metadata
    public string CorrelationId { get; }   // For distributed tracing
    
    public OrderPlacedEvent(
        Guid orderId,
        Guid customerId,
        Money totalAmount,
        DateTime orderDate,
        List<OrderItemDto> items,
        string correlationId)
    {
        OrderId = orderId;
        CustomerId = customerId;
        TotalAmount = totalAmount;
        OrderDate = orderDate;
        Items = items ?? new List<OrderItemDto>();
        CorrelationId = correlationId;
    }
}

// DTO for event data (avoid exposing domain entities)
public class OrderItemDto
{
    public Guid ProductId { get; set; }
    public int Quantity { get; set; }
    public Money UnitPrice { get; set; }
}

Event Naming Convention

HIGH PRIORITY

Use past tense to describe what happened. Be specific and business-focused.

✅ Good Event Names

// E-commerce
OrderPlacedEvent
OrderShippedEvent
PaymentProcessedEvent
InventoryReservedEvent

// Banking
AccountOpenedEvent
FundsTransferredEvent
LoanApprovedEvent
InterestAccruedEvent

// Healthcare
AppointmentScheduledEvent
PrescriptionIssuedEvent
TestResultsPublishedEvent

❌ Poor Event Names

// Avoid command-style names (not past tense)
PlaceOrderEvent          // Use: OrderPlacedEvent
ProcessPaymentEvent      // Use: PaymentProcessedEvent

// Avoid generic names (not specific)
DataChangedEvent         // What data? What changed?
UpdatedEvent             // What was updated?

// Avoid technical names (not business-focused)
DatabaseWrittenEvent     // Use business concept instead
CacheInvalidatedEvent    // Implementation detail, not domain event

Publishing Events

How and when to publish domain events from aggregates.

In-Memory Event Publishing Pattern

HIGH PRIORITY

Collect events in aggregate, publish after successful persistence.

✅ Recommended

// Aggregate collects events
public class Order : Entity, IAggregateRoot
{
    private readonly List<DomainEvent> _domainEvents = new();
    public IReadOnlyList<DomainEvent> DomainEvents => _domainEvents;
    
    public void Submit()
    {
        if (Items.Count == 0)
            throw new InvalidOperationException("Cannot submit empty order");
        
        // Change state
        Status = OrderStatus.Submitted;
        
        // Raise event (not published yet)
        _domainEvents.Add(new OrderSubmittedEvent(
            Id, 
            CustomerId, 
            TotalAmount,
            DateTime.UtcNow
        ));
    }
    
    public void ClearDomainEvents() => _domainEvents.Clear();
}

// Repository publishes events after save
public class OrderRepository : IOrderRepository
{
    private readonly DbContext _context;
    private readonly IEventBus _eventBus;
    
    public async Task UpdateAsync(Order order)
    {
        _context.Orders.Update(order);
        
        // Save changes first
        await _context.SaveChangesAsync();
        
        // Then publish events (only if save succeeds)
        foreach (var @event in order.DomainEvents)
        {
            await _eventBus.PublishAsync(@event);
        }
        
        order.ClearDomainEvents();
    }
}

// Application service coordinates
public class OrderService
{
    private readonly IOrderRepository _repository;
    
    public async Task SubmitOrder(Guid orderId)
    {
        var order = await _repository.GetByIdAsync(orderId);
        
        order.Submit();  // Raises event
        
        await _repository.UpdateAsync(order);  // Saves + publishes
    }
}

✅ Events only published after successful database save.

Outbox Pattern for Reliability

MEDIUM PRIORITY

Store events in database table, publish asynchronously for guaranteed delivery.

✅ Recommended for Distributed Systems

// Outbox table stores unpublished events
public class OutboxMessage
{
    public Guid Id { get; set; }
    public string EventType { get; set; }
    public string EventData { get; set; }  // JSON serialized
    public DateTime OccurredOn { get; set; }
    public bool Published { get; set; }
    public DateTime? PublishedOn { get; set; }
}

// Save event to outbox in same transaction as aggregate
public async Task UpdateAsync(Order order)
{
    using var transaction = await _context.Database.BeginTransactionAsync();
    
    try
    {
        // Save aggregate
        _context.Orders.Update(order);
        
        // Save events to outbox (same transaction)
        foreach (var @event in order.DomainEvents)
        {
            var outboxMessage = new OutboxMessage
            {
                Id = Guid.NewGuid(),
                EventType = @event.GetType().Name,
                EventData = JsonSerializer.Serialize(@event),
                OccurredOn = @event.OccurredOn,
                Published = false
            };
            
            _context.OutboxMessages.Add(outboxMessage);
        }
        
        await _context.SaveChangesAsync();
        await transaction.CommitAsync();
        
        order.ClearDomainEvents();
    }
    catch
    {
        await transaction.RollbackAsync();
        throw;
    }
}

// Background worker publishes events from outbox
public class OutboxProcessor : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var unpublishedEvents = await _context.OutboxMessages
                .Where(m => !m.Published)
                .OrderBy(m => m.OccurredOn)
                .Take(100)
                .ToListAsync();
            
            foreach (var message in unpublishedEvents)
            {
                try
                {
                    // Publish to message bus
                    await _eventBus.PublishAsync(
                        DeserializeEvent(message.EventType, message.EventData)
                    );
                    
                    // Mark as published
                    message.Published = true;
                    message.PublishedOn = DateTime.UtcNow;
                }
                catch (Exception ex)
                {
                    // Log error, retry later
                    _logger.LogError(ex, "Failed to publish event {EventId}", message.Id);
                }
            }
            
            await _context.SaveChangesAsync();
            await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
        }
    }
}

✅ Guarantees event delivery even if message bus is temporarily unavailable.

Event Handlers

How to subscribe to and handle domain events.

Event Handler Pattern

HIGH PRIORITY

Implement handlers for specific event types. Handlers should be idempotent.

✅ Recommended

// Event handler interface
public interface IEventHandler<TEvent> where TEvent : DomainEvent
{
    Task HandleAsync(TEvent @event);
}

// Specific event handler
public class OrderSubmittedEventHandler : IEventHandler<OrderSubmittedEvent>
{
    private readonly IInventoryService _inventoryService;
    private readonly IEmailService _emailService;
    private readonly ILogger _logger;
    
    public async Task HandleAsync(OrderSubmittedEvent @event)
    {
        _logger.LogInformation(
            "Handling OrderSubmitted event for order {OrderId}", 
            @event.OrderId
        );
        
        try
        {
            // Reserve inventory
            await _inventoryService.ReserveInventoryAsync(
                @event.OrderId, 
                @event.Items
            );
            
            // Send confirmation email
            await _emailService.SendOrderConfirmationAsync(
                @event.CustomerId,
                @event.OrderId,
                @event.TotalAmount
            );
            
            _logger.LogInformation(
                "Successfully handled OrderSubmitted event for order {OrderId}", 
                @event.OrderId
            );
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex, 
                "Error handling OrderSubmitted event for order {OrderId}", 
                @event.OrderId
            );
            throw;  // Let infrastructure retry
        }
    }
}

// Event bus dispatches to handlers
public class EventBus : IEventBus
{
    private readonly IServiceProvider _serviceProvider;
    
    public async Task PublishAsync<TEvent>(TEvent @event) where TEvent : DomainEvent
    {
        var handlers = _serviceProvider
            .GetServices<IEventHandler<TEvent>>();
        
        foreach (var handler in handlers)
        {
            await handler.HandleAsync(@event);
        }
    }
}

Idempotent Event Handling

HIGH PRIORITY

Handlers must be idempotent - processing same event multiple times has same result.

✅ Recommended - Idempotency Check

// Track processed events
public class ProcessedEventTracker
{
    private readonly DbContext _context;
    
    public async Task<bool> HasBeenProcessedAsync(Guid eventId)
    {
        return await _context.ProcessedEvents
            .AnyAsync(e => e.EventId == eventId);
    }
    
    public async Task MarkAsProcessedAsync(Guid eventId)
    {
        _context.ProcessedEvents.Add(new ProcessedEvent
        {
            EventId = eventId,
            ProcessedOn = DateTime.UtcNow
        });
        await _context.SaveChangesAsync();
    }
}

// Handler checks idempotency
public class PaymentProcessedEventHandler : IEventHandler<PaymentProcessedEvent>
{
    private readonly ProcessedEventTracker _tracker;
    private readonly IInvoiceService _invoiceService;
    
    public async Task HandleAsync(PaymentProcessedEvent @event)
    {
        // Check if already processed
        if (await _tracker.HasBeenProcessedAsync(@event.EventId))
        {
            _logger.LogInformation(
                "Event {EventId} already processed, skipping", 
                @event.EventId
            );
            return;
        }
        
        // Process event
        await _invoiceService.MarkAsPaidAsync(@event.InvoiceId);
        
        // Mark as processed
        await _tracker.MarkAsProcessedAsync(@event.EventId);
    }
}

✅ Prevents duplicate processing if event is delivered multiple times.

Event Sourcing

Store all changes as sequence of events. Aggregate state is derived by replaying events. Provides complete audit trail and enables temporal queries.

Event Sourcing Pattern

MEDIUM PRIORITY

Store events as primary source of truth, rebuild state by replaying events.

✅ Recommended

// Event-sourced aggregate
public class BankAccount
{
    public Guid Id { get; private set; }
    public decimal Balance { get; private set; }
    
    private List<DomainEvent> _changes = new();
    
    // Replay events to rebuild state
    public static BankAccount LoadFromHistory(Guid id, IEnumerable<DomainEvent> history)
    {
        var account = new BankAccount { Id = id };
        
        foreach (var @event in history)
        {
            account.Apply(@event);
        }
        
        return account;
    }
    
    // Apply event to state
    private void Apply(DomainEvent @event)
    {
        switch (@event)
        {
            case AccountOpenedEvent e:
                Id = e.AccountId;
                Balance = e.InitialDeposit;
                break;
            
            case FundsDepositedEvent e:
                Balance += e.Amount;
                break;
            
            case FundsWithdrawnEvent e:
                Balance -= e.Amount;
                break;
        }
    }
    
    // Public methods raise events
    public void Deposit(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentException("Amount must be positive");
        
        var @event = new FundsDepositedEvent(Id, amount, DateTime.UtcNow);
        Apply(@event);
        _changes.Add(@event);
    }
}

// Event store repository
public class EventStore
{
    public async Task<BankAccount> GetByIdAsync(Guid accountId)
    {
        var events = await _context.Events
            .Where(e => e.AggregateId == accountId)
            .OrderBy(e => e.Version)
            .ToListAsync();
        
        return BankAccount.LoadFromHistory(accountId, events);
    }
    
    public async Task SaveAsync(BankAccount account)
    {
        foreach (var @event in account.GetChanges())
        {
            await _context.Events.AddAsync(new StoredEvent
            {
                EventId = @event.EventId,
                AggregateId = account.Id,
                EventType = @event.GetType().Name,
                EventData = JsonSerializer.Serialize(@event),
                OccurredOn = @event.OccurredOn
            });
        }
        
        await _context.SaveChangesAsync();
    }
}

CQRS (Command Query Responsibility Segregation)

Separate read and write models. Commands change state, queries return data. Often combined with event sourcing.

CQRS Pattern

MEDIUM PRIORITY

Split command (write) operations from query (read) operations.

✅ Recommended

// COMMAND SIDE (Write Model)
public class PlaceOrderCommand
{
    public Guid CustomerId { get; set; }
    public List<OrderItemDto> Items { get; set; }
}

public class PlaceOrderCommandHandler
{
    private readonly IOrderRepository _repository;
    
    public async Task<Guid> Handle(PlaceOrderCommand command)
    {
        var order = Order.Create(command.CustomerId);
        
        foreach (var item in command.Items)
        {
            order.AddItem(item.ProductId, item.Quantity, item.UnitPrice);
        }
        
        await _repository.AddAsync(order);
        
        return order.Id;
    }
}

// QUERY SIDE (Read Model)
public class OrderSummaryQuery
{
    public Guid OrderId { get; set; }
}

public class OrderSummaryQueryHandler
{
    private readonly IReadOnlyDbContext _queryDb;
    
    public async Task<OrderSummaryDto> Handle(OrderSummaryQuery query)
    {
        // Query optimized read model
        return await _queryDb.OrderSummaries
            .Where(o => o.OrderId == query.OrderId)
            .Select(o => new OrderSummaryDto
            {
                OrderId = o.OrderId,
                CustomerName = o.CustomerName,
                TotalAmount = o.TotalAmount,
                Status = o.Status
            })
            .FirstOrDefaultAsync();
    }
}
