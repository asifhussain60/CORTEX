What is a Bounded Context?

"A Bounded Context delimits the applicability of a particular model so that team members have a clear and shared understanding of what has to be consistent and what can develop independently." — Eric Evans

A Bounded Context is an explicit boundary within which a domain model is defined and applicable. It prevents model pollution and ambiguity by clearly separating different models that may use the same terms with different meanings.

Key Concepts

Ubiquitous Language: Common language shared by domain experts and developers within the context
Context Boundary: Explicit boundary marked by separate database, team ownership, or deployment
Model Integrity: Within the boundary, the model must be internally consistent
💡 Example: In an e-commerce system, "Order" has different meanings:
Sales Context: Purchase request with items and payment
Fulfillment Context: Shipment instructions and tracking
Billing Context: Invoice record for accounting
Each context has its own Order model optimized for its specific needs.

Identifying Bounded Contexts

Use these heuristics to discover and define bounded context boundaries in your system.

Heuristic 1: Linguistic Boundaries

HIGH PRIORITY

Different meanings of the same term indicate separate contexts.

Example: Customer Concept

// SALES CONTEXT - Customer is a lead/opportunity
public class Customer
{
    public Guid Id { get; set; }
    public string CompanyName { get; set; }
    public LeadStatus Status { get; set; }  // Lead, Qualified, Closed
    public decimal PotentialRevenue { get; set; }
}

// SUPPORT CONTEXT - Customer is a service recipient
public class Customer
{
    public Guid Id { get; set; }
    public string AccountNumber { get; set; }
    public SupportTier Tier { get; set; }  // Basic, Premium, Enterprise
    public List<Ticket> OpenTickets { get; set; }
}

// BILLING CONTEXT - Customer is a payment source
public class Customer
{
    public Guid Id { get; set; }
    public string TaxId { get; set; }
    public PaymentMethod DefaultPayment { get; set; }
    public List<Invoice> Invoices { get; set; }
}

Each context has its own Customer model with different attributes and behaviors.

Heuristic 2: Team Boundaries

HIGH PRIORITY

Different teams managing different parts of the system (Conway's Law).

Team-Aligned Contexts

// E-commerce Organization Structure
┌─────────────────────────────────────────────────┐
│ Marketing Team → CATALOG CONTEXT                │
│   - Product listings, search, recommendations   │
├─────────────────────────────────────────────────┤
│ Sales Team → CHECKOUT CONTEXT                   │
│   - Shopping cart, payment processing           │
├─────────────────────────────────────────────────┤
│ Operations Team → FULFILLMENT CONTEXT           │
│   - Order picking, packing, shipping            │
├─────────────────────────────────────────────────┤
│ Support Team → CUSTOMER SERVICE CONTEXT         │
│   - Tickets, returns, refunds                   │
└─────────────────────────────────────────────────┘

Each team owns its bounded context and can evolve it independently.

Heuristic 3: Business Capabilities

MEDIUM PRIORITY

Distinct business functions often map to separate bounded contexts.

Banking System Contexts

// Banking Application
┌─────────────────────────────────────────┐
│ ACCOUNT MANAGEMENT CONTEXT              │
│ - Account opening, closure, maintenance │
├─────────────────────────────────────────┤
│ PAYMENT PROCESSING CONTEXT              │
│ - Transfers, bill payments, ACH         │
├─────────────────────────────────────────┤
│ LOAN ORIGINATION CONTEXT                │
│ - Applications, underwriting, approval  │
├─────────────────────────────────────────┤
│ INVESTMENT MANAGEMENT CONTEXT           │
│ - Portfolio management, trading         │
└─────────────────────────────────────────┘

Heuristic 4: Change Rate Analysis

MEDIUM PRIORITY

Parts that change together should be in the same context.

Example

✅ SAME CONTEXT (change together):
- Order processing + Inventory management
  → When order is placed, inventory is reserved
  → Both change frequently during promotions

✅ SEPARATE CONTEXTS (change independently):
- Product catalog + Order fulfillment
  → Catalog changes daily (new products, prices)
  → Fulfillment process stable (shipping, tracking)

Context Mapping

A Context Map documents relationships between bounded contexts and integration patterns. It helps visualize dependencies and communication strategies.

Context Map Relationships

HIGH PRIORITY

Document how bounded contexts relate and integrate with each other.

Partnership

Definition: Two contexts in mutual success-failure relationship, teams coordinate closely.

Example: Order Processing ↔ Payment Processing
- Both contexts must succeed or fail together
- Changes coordinated between teams
- Shared success criteria

Shared Kernel

Definition: Subset of domain model shared between contexts (use sparingly).

// Shared Kernel - Common types used by multiple contexts
namespace CompanyName.SharedKernel
{
    public class Money
    {
        public decimal Amount { get; }
        public string Currency { get; }
    }
    
    public class Address
    {
        public string Street { get; }
        public string City { get; }
        public string PostalCode { get; }
    }
}

// Both contexts use the shared kernel
using CompanyName.SharedKernel;

// Warning: Changes to shared kernel affect all contexts!

⚠️ Minimize shared kernel - it creates coupling between contexts.

Customer-Supplier

Definition: Downstream context depends on upstream context. Upstream prioritizes downstream needs.

Example: Catalog (Upstream) → Shopping Cart (Downstream)
- Shopping cart depends on product catalog
- Catalog team provides APIs for cart team
- Contract defined and versioned
- Automated tests validate integration

Conformist

Definition: Downstream conforms to upstream model without negotiation (e.g., external API).

// External Payment Gateway (Upstream)
// We conform to their model
public class StripePaymentGateway
{
    public async Task<PaymentResult> ProcessPayment(
        StripePaymentRequest request)  // Their model
    {
        // Conform to Stripe's API structure
        var charge = await _stripeClient.Charges.CreateAsync(
            new ChargeCreateOptions
            {
                Amount = request.Amount,
                Currency = request.Currency,
                Source = request.Token
            });
        
        return MapToOurModel(charge);  // Translate to our domain
    }
}

Anti-Corruption Layer (ACL)

Definition: Translation layer prevents external models from polluting your domain.

// Anti-Corruption Layer for legacy system
public class LegacyOrderAdapter
{
    private readonly LegacyOrderService _legacyService;
    
    public async Task<Order> GetOrder(Guid orderId)
    {
        // Get data from legacy system (their model)
        var legacyOrder = await _legacyService.FetchOrder(orderId.ToString());
        
        // Translate to our domain model
        return new Order
        {
            Id = Guid.Parse(legacyOrder.OrderNumber),
            CustomerId = Guid.Parse(legacyOrder.CustomerCode),
            OrderDate = DateTime.Parse(legacyOrder.OrderDt),
            TotalAmount = Money.Create(
                decimal.Parse(legacyOrder.TotalAmt),
                legacyOrder.CurrencyCode
            )
        };
    }
}

// Our domain model stays clean, unaffected by legacy complexity

Integration Patterns

How bounded contexts communicate with each other.

API-Based Integration

HIGH PRIORITY

Synchronous HTTP/gRPC APIs for request-response communication.

✅ Recommended - REST API

// Catalog Context exposes API
[ApiController]
[Route("api/products")]
public class ProductsController : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<ProductDto> GetProduct(Guid id)
    {
        var product = await _productRepository.GetByIdAsync(id);
        return _mapper.Map<ProductDto>(product);
    }
}

// Shopping Cart Context consumes API
public class ProductClient
{
    private readonly HttpClient _httpClient;
    
    public async Task<ProductDto> GetProductAsync(Guid productId)
    {
        var response = await _httpClient.GetAsync($"/api/products/{productId}");
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<ProductDto>();
    }
}

Event-Driven Integration

HIGH PRIORITY

Asynchronous messaging for loose coupling and eventual consistency.

✅ Recommended - Domain Events

// Order Context publishes event
public class Order
{
    public void Submit()
    {
        Status = OrderStatus.Submitted;
        
        // Publish event
        _eventBus.Publish(new OrderSubmittedEvent
        {
            OrderId = Id,
            CustomerId = CustomerId,
            TotalAmount = TotalAmount
        });
    }
}

// Inventory Context subscribes to event
public class InventoryService : IEventHandler<OrderSubmittedEvent>
{
    public async Task Handle(OrderSubmittedEvent @event)
    {
        // Reserve inventory (separate transaction)
        await _inventoryManager.ReserveForOrder(@event.OrderId);
    }
}

// Billing Context also subscribes
public class BillingService : IEventHandler<OrderSubmittedEvent>
{
    public async Task Handle(OrderSubmittedEvent @event)
    {
        // Create invoice (separate transaction)
        await _invoiceGenerator.CreateInvoice(@event.OrderId);
    }
}

✅ Benefits: Loose coupling, multiple subscribers, fault tolerance.

Anti-Patterns to Avoid

Shared Database

CRITICAL

❌ Avoid - Direct Database Access

// BAD: Shopping Cart directly queries Product database
public class CartService
{
    public async Task AddToCart(Guid productId)
    {
        // Direct database access violates context boundary!
        var product = await _productDbContext.Products
            .FirstOrDefaultAsync(p => p.Id == productId);
        
        // Now two contexts are tightly coupled via database
    }
}

❌ Problems: Tight coupling, schema changes break multiple contexts.

✅ Use APIs Instead

// GOOD: Shopping Cart uses Catalog API
public class CartService
{
    private readonly IProductClient _productClient;
    
    public async Task AddToCart(Guid productId)
    {
        var product = await _productClient.GetProductAsync(productId);
        // Use API - respects context boundary
    }
}

Big Ball of Mud

CRITICAL

Failing to define any bounded contexts results in tangled, unmaintainable code.

❌ Avoid

// BAD: One giant "Customer" class used everywhere
public class Customer
{
    // Sales properties
    public LeadStatus LeadStatus { get; set; }
    public decimal PotentialRevenue { get; set; }
    
    // Support properties
    public List<Ticket> Tickets { get; set; }
    public SupportTier SupportTier { get; set; }
    
    // Billing properties
    public List<Invoice> Invoices { get; set; }
    public PaymentMethod PaymentMethod { get; set; }
    
    // Marketing properties
    public List<Campaign> Campaigns { get; set; }
    public bool OptInEmail { get; set; }
    
    // This class means different things in different contexts!
}
