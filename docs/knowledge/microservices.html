🏗️ Microservices Architecture

Distributed Systems, Resilience Patterns, and Service Design

🔧 Architecture 🌐 Distributed Systems 📅 Updated: Dec 2025

📋 Overview

Microservices architecture structures applications as collections of loosely coupled, independently deployable services. Each service owns its domain logic and data, communicating through well-defined APIs. This architecture enables scalability, fault isolation, and technology diversity.

Key Principles:
  • Single Responsibility: Each service handles one business capability
  • Independence: Deploy, scale, and fail independently
  • Decentralization: Distributed data management and governance
  • Resilience: Design for failure with circuit breakers and retries

🎯 Service Design Principles

Core Concepts

📐

Domain-Driven Design

Strategic Design

  • Bounded Contexts: Explicit boundaries around models
  • Ubiquitous Language: Shared team vocabulary
  • Context Mapping: Define relationships between contexts
  • Aggregates: Consistency boundaries within domain
🔲

Service Boundaries

Decomposition Strategies

  • Business Capability: Service per capability
  • Subdomain: DDD subdomain alignment
  • Team Ownership: Conway's Law consideration
  • Data Cohesion: High cohesion within service
📦

Service Size

Right-Sizing Guidelines

  • Not Too Small: Avoid nano-services
  • Not Too Large: Avoid distributed monoliths
  • Team Ownership: 2-pizza team can maintain
  • Deployment Unit: Independent release cycle

🔄 Communication Patterns

Synchronous Communication

🌐

REST APIs

HTTP-based Communication

Characteristics

  • Request-response pattern
  • Simple and widely adopted
  • Text-based (JSON)
  • HTTP status codes

Best For

  • CRUD operations
  • Public APIs
  • Browser clients
⚡

gRPC

High-Performance RPC

Characteristics

  • HTTP/2 based
  • Binary protocol (Protobuf)
  • Bidirectional streaming
  • Code generation

Best For

  • Internal service-to-service
  • High throughput
  • Polyglot environments
🔗

Service Mesh

Infrastructure Layer

Capabilities

  • Load balancing
  • Service discovery
  • Mutual TLS
  • Traffic management

Popular Options

  • Istio
  • Linkerd
  • Consul Connect

Asynchronous Communication

📨

Event-Driven

Publish-Subscribe Pattern

Implementation

  • Event producers publish to topics
  • Multiple consumers subscribe
  • Decoupled services
  • Eventual consistency
📬

Message Queues

Point-to-Point Pattern

Implementation

  • Single consumer per message
  • Work distribution
  • Guaranteed delivery
  • Dead letter queues
🎭

Saga Pattern

Distributed Transactions

Approaches

  • Choreography: Event-based coordination
  • Orchestration: Central coordinator
  • Compensating transactions
  • Eventual consistency

💾 Data Management

Database Patterns

🗄️

Database per Service

Benefits

  • Independence: Deploy and scale separately
  • Technology Choice: Right DB for the job
  • Fault Isolation: Database failures contained
  • Clear Ownership: Service owns its data

Challenges

  • Distributed queries
  • Data consistency
  • Transaction management
🔄

CQRS

Command Query Responsibility Segregation

Pattern

  • Write Model: Commands for updates
  • Read Model: Optimized queries
  • Separation: Different models for reads/writes
  • Scalability: Scale reads independently
📜

Event Sourcing

Immutable Event Log

Pattern

  • Events: Store state changes as events
  • Replay: Rebuild state from events
  • Audit Trail: Complete history
  • Time Travel: Query past states

🛡️ Resilience Patterns

Failure Handling

⚡

Circuit Breaker

Prevent Cascading Failures

States

  • Closed: Normal operation, requests pass through
  • Open: Failures exceeded threshold, fail fast
  • Half-Open: Test if service recovered

Configuration

  • Failure threshold (e.g., 50% errors)
  • Timeout duration (e.g., 30s)
  • Half-open retry count
🔄

Retry Pattern

Handle Transient Failures

Strategies

  • Exponential Backoff: Increase delay between retries
  • Jitter: Random delay to prevent thundering herd
  • Max Attempts: Limit retry count (e.g., 3)
  • Idempotency: Safe to retry operations
⏱️

Timeout Pattern

Prevent Resource Blocking

Best Practices

  • Set Deadlines: Every external call
  • Context Propagation: Pass deadlines downstream
  • Aggressive Timeouts: Fail fast, retry quickly
  • Monitoring: Track timeout occurrences

Additional Resilience Patterns

🚢

Bulkhead Pattern

Resource Isolation

  • Separate thread pools per service
  • Connection pool limits
  • Prevent resource exhaustion
  • Failure isolation
🔙

Fallback Pattern

Graceful Degradation

  • Return cached data
  • Default values
  • Alternative service
  • Partial response
📊

Health Checks

Service Monitoring

  • Liveness probes
  • Readiness probes
  • Dependency checks
  • Graceful shutdown
Resilience Best Practices:
  • Design for Failure: Assume every call can fail
  • Fail Fast: Use timeouts and circuit breakers
  • Isolate Failures: Bulkheads prevent cascade
  • Monitor Everything: Metrics, logs, traces
  • Test Chaos: Inject failures in production
  • Gradual Rollout: Canary and blue-green deployments

👁️ Observability

Three Pillars

📊

Metrics

Key Metrics

  • RED Method: Rate, Errors, Duration
  • USE Method: Utilization, Saturation, Errors
  • Business Metrics: Orders, revenue, signups
  • Tools: Prometheus, Grafana
📝

Logs

Structured Logging

  • JSON Format: Machine-readable
  • Correlation IDs: Trace across services
  • Log Levels: ERROR, WARN, INFO, DEBUG
  • Tools: ELK Stack, Loki
🔍

Distributed Tracing

Request Flow

  • Trace ID: Unique per request
  • Span ID: Per operation
  • Context Propagation: Headers across services
  • Tools: Jaeger, Zipkin, OpenTelemetry
