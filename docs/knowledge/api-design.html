API Design Excellence

REST, GraphQL, and API versioning strategies for building robust, scalable APIs

🎯 Category Overview

API Design Excellence encompasses the principles, patterns, and practices for designing robust, scalable, and maintainable APIs. This category covers REST API design, GraphQL best practices, and API versioning strategies for backward compatibility.

Key Concepts

  • REST Architecture: RESTful API design following architectural constraints (statelessness, client-server separation, uniform interface)
  • GraphQL: Query language and runtime for APIs with strongly-typed schemas and client-specified queries
  • API Versioning: Strategies for evolving APIs while maintaining backward compatibility
  • HTTP Semantics: Proper use of HTTP methods, status codes, headers, and content negotiation
  • Performance: Pagination, filtering, caching, and optimization techniques
  • Security: Authentication, authorization, rate limiting, and input validation

REST API Design Principles

REST (Representational State Transfer) is an architectural style for building scalable web services. Key principles include:

Resource Naming Best Practices

# ✅ GOOD: Use nouns, plural, lowercase with hyphens
GET    /users                    # List all users
GET    /users/123                # Get specific user
POST   /users                    # Create user
PUT    /users/123                # Replace user
PATCH  /users/123                # Update user
DELETE /users/123                # Delete user

# Nested resources for relationships
GET    /users/123/orders         # User's orders
GET    /orders/456/items         # Order items

# Query parameters for filtering/sorting
GET    /users?role=admin&sort=created_at
GET    /orders?status=pending&limit=20&page=2

# ❌ BAD: RPC-style, verbs, inconsistent naming
POST   /getUserOrders            # Don't use verbs
GET    /user/123                 # Use plural
GET    /OrderItems               # Use lowercase
GET    /users_by_role?role=admin # Use query params

HTTP Methods and Status Codes

// GET - Retrieve resources (Safe, Idempotent)
GET /users/123
Response: 200 OK + user data
         404 Not Found

// POST - Create new resource (Not Safe, Not Idempotent)
POST /users
Body: { "email": "user@example.com", "name": "John" }
Response: 201 Created + Location header + created resource
         400 Bad Request (validation error)
         409 Conflict (duplicate)

// PUT - Replace entire resource (Not Safe, Idempotent)
PUT /users/123
Body: { "email": "...", "name": "..." } // All fields
Response: 200 OK + updated resource
         404 Not Found

// PATCH - Partial update (Not Safe, Idempotent)
PATCH /users/123
Body: { "name": "Jane" } // Only changed fields
Response: 200 OK + updated resource
         400 Bad Request

// DELETE - Remove resource (Not Safe, Idempotent)
DELETE /users/123
Response: 204 No Content
         404 Not Found

Pagination Patterns

# Offset-based pagination
@app.get("/users")
def get_users(page: int = 1, limit: int = 20):
    offset = (page - 1) * limit
    users = db.query(User).offset(offset).limit(limit).all()
    total = db.query(User).count()
    
    return {
        "data": users,
        "pagination": {
            "page": page,
            "limit": limit,
            "total_pages": math.ceil(total / limit),
            "total_items": total,
            "has_more": page < math.ceil(total / limit)
        }
    }

# Cursor-based pagination (recommended for large datasets)
@app.get("/users")
def get_users(cursor: Optional[str] = None, limit: int = 20):
    if cursor:
        decoded_cursor = decode_cursor(cursor)
        users = db.query(User).filter(
            User.id > decoded_cursor['id']
        ).limit(limit).all()
    else:
        users = db.query(User).limit(limit).all()
    
    next_cursor = encode_cursor({'id': users[-1].id}) if users else None
    
    return {
        "data": users,
        "pagination": {
            "next_cursor": next_cursor,
            "has_more": len(users) == limit
        }
    }

GraphQL Design Principles

GraphQL is a query language for APIs with strongly-typed schemas where clients request exactly what they need.

Schema Design Best Practices

# Use PascalCase for types, camelCase for fields
type User {
  id: ID!                          # Non-null ID
  email: String!                   # Non-null required field
  firstName: String!               # Use camelCase
  lastName: String!
  phoneNumber: String              # Nullable optional field
  isActive: Boolean!               # Prefix booleans with is/has
  role: UserRole!                  # Enum for fixed values
  profile: UserProfile             # Nested type
  orders(first: Int, after: String): OrderConnection!
}

# Input types for mutations
input CreateUserInput {
  email: String!
  firstName: String!
  lastName: String!
  phoneNumber: String
}

input UpdateUserInput {
  firstName: String
  lastName: String
  phoneNumber: String
}

# Enum for status fields
enum UserRole {
  USER
  ADMIN
  MODERATOR
}

# Interfaces for shared fields
interface Node {
  id: ID!
}

type Product implements Node {
  id: ID!
  title: String!
  price: Float!
}

# Unions for polymorphic responses
union SearchResult = User | Product | Article

type Query {
  search(query: String!): [SearchResult!]!
}

// Resolver with DataLoader (prevents N+1 queries)
const resolvers = {
  Query: {
    users: async (_, { first = 10, after }, { dataSources }) => {
      const users = await dataSources.userAPI.getUsers({ first, after });
      return users;
    }
  },
  User: {
    orders: async (user, _, { loaders }) => {
      // DataLoader batches requests
      return loaders.orderLoader.load(user.id);
    }
  }
};

// DataLoader setup (batching and caching)
const orderLoader = new DataLoader(async (userIds) => {
  const orders = await db.orders.findAll({
    where: { userId: { in: userIds } }
  });
  
  // Map results back to user IDs
  return userIds.map(id => 
    orders.filter(order => order.userId === id)
  );
});

Mutation Patterns with Error Handling

# Mutation with payload type (recommended)
type Mutation {
  createUser(input: CreateUserInput!): CreateUserPayload!
  updateUser(id: ID!, input: UpdateUserInput!): UpdateUserPayload!
  deleteUser(id: ID!): DeleteUserPayload!
}

# Payload types include errors
type CreateUserPayload {
  user: User
  errors: [UserError!]
  clientMutationId: String
}

type UserError {
  field: String!
  message: String!
  code: ErrorCode!
}

enum ErrorCode {
  VALIDATION_ERROR
  DUPLICATE_EMAIL
  INSUFFICIENT_PERMISSIONS
}

# Usage in client
mutation CreateUser($input: CreateUserInput!) {
  createUser(input: $input) {
    user {
      id
      email
    }
    errors {
      field
      message
      code
    }
  }
}

API Versioning Strategies

API versioning enables safe evolution while maintaining backward compatibility. Choose the right strategy for your use case.

Strategy Pattern Pros Cons When to Use
URI Versioning /v1/users Highly visible, easy to test, cache-friendly Pollutes URI space, entire API versioned Public APIs, many external clients
Header Versioning X-API-Version: 1 Clean URLs, per-resource versioning Not visible in URL, harder to test Internal APIs, RESTful purists
Content Negotiation Accept: application/vnd.api.v1+json Most RESTful, standards-compliant Complex, less common Mature REST APIs, hypermedia
Query Parameter /users?version=1 Simple, easy to test Easily forgotten, caching issues Quick prototyping (not recommended)
No Versioning Backward compatible only No overhead, clean Impossible for breaking changes Internal APIs, stable requirements

URI Versioning Implementation

# FastAPI with URI versioning
from fastapi import APIRouter

# Version 1 router
v1_router = APIRouter(prefix="/v1")

@v1_router.get("/users/{user_id}")
def get_user_v1(user_id: int):
    user = db.get_user(user_id)
    # V1 format: single name field
    return {
        "id": user.id,
        "name": f"{user.first_name} {user.last_name}",
        "email": user.email
    }

# Version 2 router
v2_router = APIRouter(prefix="/v2")

@v2_router.get("/users/{user_id}")
def get_user_v2(user_id: int):
    user = db.get_user(user_id)
    # V2 format: separate first/last name
    return {
        "id": user.id,
        "firstName": user.first_name,
        "lastName": user.last_name,
        "email": user.email,
        "createdAt": user.created_at  # New field in V2
    }

# Register routers
app.include_router(v1_router)
app.include_router(v2_router)

Deprecation Workflow

// Express.js deprecation middleware
const deprecationMiddleware = (version, sunsetDate, migrationUrl) => {
  return (req, res, next) => {
    // Add deprecation headers
    res.set('Deprecation', 'true');
    res.set('Sunset', sunsetDate);
    res.set('Link', `<${migrationUrl}>; rel="deprecation"`);
    
    // Add warning to response body
    const originalJson = res.json.bind(res);
    res.json = (body) => {
      return originalJson({
        ...body,
        _warnings: [{
          code: 'DEPRECATED_VERSION',
          message: `API version ${version} is deprecated`,
          sunset_date: sunsetDate,
          migration_guide: migrationUrl
        }]
      });
    };
    
    next();
  };
};

// Apply to v1 routes
app.use('/v1', deprecationMiddleware(
  'v1',
  'Sat, 31 Dec 2025 23:59:59 GMT',
  'https://api.example.com/docs/v1-to-v2-migration'
));

// GraphQL deprecation (built-in)
const typeDefs = gql`
  type User {
    id: ID!
    legacyId: String @deprecated(reason: "Use 'id' instead")
    name: String @deprecated(reason: "Use 'firstName' and 'lastName'")
    firstName: String
    lastName: String
  }
`;

Security Best Practices

Authentication & Authorization

# JWT Authentication with FastAPI
from fastapi import Depends, HTTPException, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
import jwt

security = HTTPBearer()

def verify_token(credentials: HTTPAuthorizationCredentials = Depends(security)):
    try:
        payload = jwt.decode(
            credentials.credentials,
            SECRET_KEY,
            algorithms=["HS256"]
        )
        return payload
    except jwt.ExpiredSignatureError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Token has expired"
        )
    except jwt.InvalidTokenError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Invalid token"
        )

# Role-based authorization
def require_role(required_role: str):
    def role_checker(token_payload: dict = Depends(verify_token)):
        user_role = token_payload.get("role")
        if user_role != required_role:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="Insufficient permissions"
            )
        return token_payload
    return role_checker

# Protected endpoints
@app.get("/users", dependencies=[Depends(require_role("admin"))])
def list_users():
    return db.get_all_users()

@app.get("/users/me", dependencies=[Depends(verify_token)])
def get_current_user(token_payload: dict = Depends(verify_token)):
    return db.get_user(token_payload["user_id"])

Rate Limiting

// Express rate limiting with Redis
const rateLimit = require('express-rate-limit');
const RedisStore = require('rate-limit-redis');

const limiter = rateLimit({
  store: new RedisStore({
    client: redisClient
  }),
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100, // Limit each IP to 100 requests per window
  standardHeaders: true, // Return rate limit info in headers
  legacyHeaders: false,
  handler: (req, res) => {
    res.status(429).json({
      error: {
        code: 'RATE_LIMIT_EXCEEDED',
        message: 'Too many requests, please try again later',
        retry_after: req.rateLimit.resetTime
      }
    });
  },
  // Custom key generator (e.g., by user ID)
  keyGenerator: (req) => {
    return req.user?.id || req.ip;
  }
});

app.use('/api', limiter);

Performance Optimization

HTTP Caching with ETags

# FastAPI with ETag support
from fastapi import Response, Request
import hashlib
import json

@app.get("/users/{user_id}")
def get_user(user_id: int, request: Request, response: Response):
    user = db.get_user(user_id)
    user_json = json.dumps(user.__dict__, sort_keys=True)
    
    # Generate ETag
    etag = hashlib.md5(user_json.encode()).hexdigest()
    
    # Check If-None-Match header
    if request.headers.get("If-None-Match") == etag:
        response.status_code = 304  # Not Modified
        return None
    
    # Set caching headers
    response.headers["ETag"] = etag
    response.headers["Cache-Control"] = "private, max-age=300"  # 5 minutes
    
    return user

  • Use REST: Simple CRUD, heavy caching needs, file uploads, third-party integrations

Category: API Design Excellence

Focus: API versioning strategies for backward compatibility and evolution

Key Topics:

  • Why Version: Safe API evolution, backward compatibility, clear migration paths, measurable deprecation
  • Breaking Changes: Removing endpoints/fields, renaming, changing types, changing structure, authentication changes
  • Non-Breaking Changes: Adding endpoints, optional fields, response fields, enum values, deprecating (not removing)
  • Versioning Strategies:
    • URI Versioning (/v1/users) - Best for public APIs
    • Header Versioning (X-API-Version) - Clean URLs, per-resource
    • Content Negotiation (Accept header) - Most RESTful
    • Query Parameter (?version=1) - Not recommended
    • No Versioning - Backward compatible only
  • Semantic Versioning: MAJOR.MINOR.PATCH for API versions
  • Deprecation Lifecycle: Announcement → Grace period (6-12 months) → Sunset warning (3 months) → Removal
  • Deprecation Headers: Sunset header (RFC 8594), Deprecation header, Link header to migration guide
  • Migration Strategies: Documentation, SDK updates, sandbox testing, dedicated support, monitoring
  • Version Lifecycle: Current (full support) → Previous (maintenance) → Deprecated (security only) → Removed (410 Gone)

Implementation Patterns:

  • Shared service layer with version-specific controllers
  • Request/response transformers between versions
  • Feature flags for gradual rollout

Anti-Patterns to Avoid:

  • Supporting too many versions (5+)
  • No deprecation process
  • Micro-versioning for every small change
  • Inconsistent versioning strategy
  • Not monitoring version usage
  • Breaking changes without version bump
