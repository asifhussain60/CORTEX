🎯 Domain-Driven Design

Bounded Contexts, Aggregates, and Strategic Patterns

📐 Architecture 🏗️ Patterns 📅 Updated: Dec 2025

📋 Overview

Domain-Driven Design (DDD) is an approach to software development that centers the design on the business domain and domain logic. Through collaboration between technical and domain experts, DDD creates a shared understanding expressed in code through strategic and tactical patterns.

Core Concepts:
Ubiquitous Language: Shared vocabulary between developers and domain experts
Bounded Context: Explicit boundaries around domain models
Strategic Design: High-level patterns for system architecture
Tactical Design: Building blocks for domain models

🏗️ Tactical Patterns

Building Blocks

🎯

Entity

Characteristics

Has unique identity
Identity persists over time
Mutable state
Equality by ID

Examples

User (by ID)
Order (by order number)
Account (by account ID)
💎

Value Object

Characteristics

No identity
Immutable
Equality by value
Can be shared

Examples

Money (amount + currency)
Address
Date range
📦

Aggregate

Characteristics

Cluster of entities/value objects
Consistency boundary
One aggregate root
External access via root

Guidelines

Keep aggregates small
Reference by ID
Transactional boundary

🗄️

Repository

Purpose

Abstract data access
Collection-like interface
One per aggregate root
Persistence ignorance
⚙️

Domain Service

When to Use

Operation doesn't fit in entity
Involves multiple aggregates
Stateless operation
Domain logic, not infrastructure

Factory

Purpose

Complex object creation
Encapsulate construction logic

Pattern

💡 Best Practices

DDD Guidelines:
Start with Exploration: Event storming sessions with domain experts
Small Aggregates: Keep aggregates focused and small
Consistency Boundaries: One transaction per aggregate
Reference by ID: Don't hold references to other aggregates
Eventual Consistency: Use domain events between aggregates
Protect Invariants: Enforce business rules in domain model
Common Pitfalls:
Anemic Domain Model: Domain objects with no behavior
Large Aggregates: Performance and complexity issues
Over-Engineering: DDD not needed for simple CRUD
Ignoring Business: Technical solutions without domain input
