Domain-Driven Design (DDD)

Strategic & tactical patterns for modeling complex business domains

🎯 Category Overview

Domain-Driven Design (DDD) is an approach to software development that emphasizes collaboration between technical and domain experts to create software that reflects complex business realities. Introduced by Eric Evans in his seminal 2003 book, DDD provides both strategic patterns for system architecture and tactical patterns for domain modeling.

Key Concepts

  • Ubiquitous Language: Shared vocabulary between developers and domain experts used consistently in code and conversation
  • Bounded Contexts: Explicit boundaries within which a domain model is defined and applicable
  • Aggregates: Clusters of domain objects treated as a unit for data consistency
  • Entities: Objects with unique identity that persists over time
  • Value Objects: Immutable objects defined by their attributes, not identity
  • Domain Events: Records of significant occurrences in the domain
  • Context Mapping: Patterns for integrating multiple bounded contexts

Strategic vs Tactical DDD

Strategic Design (Architecture)

Focuses on the big picture - how to organize large systems:

  • Bounded Contexts: Define clear model boundaries (often microservices)
  • Context Mapping: Relationships between contexts (upstream/downstream, partnerships)
  • Subdomains: Core (competitive advantage), Supporting (necessary), Generic (commodity)
  • Team Organization: Align teams with bounded contexts

Tactical Design (Implementation)

Focuses on the details - how to model the domain:

  • Aggregates: Transaction and consistency boundaries
  • Entities vs Value Objects: When identity matters vs when it doesn't
  • Domain Events: Capture business occurrences for eventual consistency
  • Repositories: Abstract persistence concerns
  • Domain Services: Operations that don't belong to entities

When to Use DDD

DDD is most valuable for:

  • Complex Business Logic: Rich domain rules, workflows, and invariants
  • Long-Lived Systems: Software that will evolve over years
  • Collaborative Teams: Domain experts and developers working together
  • Microservices Architecture: Bounded contexts map naturally to services

Not recommended for:

  • Simple CRUD applications with minimal business logic
  • Short-lived prototypes or MVPs
  • Data-centric systems without complex domain rules

Bounded Context is the central strategic pattern in DDD. It defines explicit boundaries within which a domain model is defined and applicable, preventing model pollution and enabling autonomous teams.

What is a Bounded Context?

"A Bounded Context delimits the applicability of a particular model so that team members have a clear and shared understanding of what has to be consistent and what can develop independently." - Eric Evans

Key Insight: The same term can mean different things in different contexts. "Customer" in Sales means "potential buyer," in Support means "service recipient," in Billing means "payment source."

Context Mapping Patterns

1. Partnership

Two contexts in mutual dependence with coordinated development.

# Order Management ↔ Inventory Management (Partnership)
# Both contexts must evolve together

class OrderService:
    def __init__(self, inventory_service):
        self.inventory = inventory_service
    
    def place_order(self, customer_id, items):
        # Check inventory in real-time (tight integration)
        if not self.inventory.check_availability(items):
            raise InsufficientInventoryError()
        
        # Reserve inventory immediately
        self.inventory.reserve_items(items)
        
        order = Order(customer_id, items)
        order.status = OrderStatus.CONFIRMED
        return order
2. Customer-Supplier

Upstream context provides services to downstream context.

// Payment Processing (upstream) → Order Management (downstream)
// Upstream defines API, downstream consumes

// Upstream Payment Context
public interface IPaymentService
{
    PaymentResult ProcessPayment(string orderId, decimal amount);
}

// Downstream Order Context
public class OrderCheckoutService
{
    private readonly IPaymentService _paymentService;
    
    public OrderCheckoutService(IPaymentService paymentService)
    {
        _paymentService = paymentService;
    }
    
    public void Checkout(Order order)
    {
        var result = _paymentService.ProcessPayment(
            order.Id.ToString(), 
            order.Total
        );
        
        if (result.IsSuccess)
            order.MarkAsPaid();
    }
}
3. Anti-Corruption Layer (ACL)

Protect domain model from external systems with translation layer.

// Modern E-commerce (our context) ← Legacy ERP System
// ACL translates between models

class LegacyERPAdapter {
    constructor(legacyClient) {
        this.legacyClient = legacyClient;
    }
    
    // Translate from our domain model to legacy format
    async syncOrder(order) {
        const legacyFormat = {
            ORDERNO: order.id,
            CUSTID: order.customerId,
            TOTAMT: order.total,
            ITEMS: order.items.map(item => ({
                PARTNO: item.sku,
                QTY: item.quantity,
                PRICE: item.unitPrice
            }))
        };
        
        await this.legacyClient.createOrder(legacyFormat);
    }
    
    // Translate from legacy format to our domain model
    async getOrder(orderId) {
        const legacyOrder = await this.legacyClient.getOrder(orderId);
        
        return new Order({
            id: legacyOrder.ORDERNO,
            customerId: legacyOrder.CUSTID,
            total: legacyOrder.TOTAMT,
            items: legacyOrder.ITEMS.map(item => new OrderItem({
                sku: item.PARTNO,
                quantity: item.QTY,
                unitPrice: item.PRICE
            }))
        });
    }
}

Tactical DDD provides building blocks for implementing domain models within bounded contexts.

Entities

Objects with unique identity that persists over time.

✅ Rich Entity with Behavior
from dataclasses import dataclass, field
from uuid import UUID, uuid4
from typing import List

@dataclass
class Order:
    """Order entity with identity and business logic"""
    id: UUID = field(default_factory=uuid4)
    customer_id: UUID = field(default=None)
    _items: List['OrderItem'] = field(default_factory=list, repr=False)
    status: str = 'DRAFT'
    
    @property
    def items(self) -> List['OrderItem']:
        """Read-only access to items"""
        return self._items.copy()
    
    @property
    def total(self) -> float:
        """Calculated property"""
        return sum(item.subtotal for item in self._items)
    
    def add_item(self, product_id: UUID, quantity: int, price: float):
        """Encapsulated business logic"""
        if quantity <= 0:
            raise ValueError("Quantity must be positive")
        
        # Check if product already in order
        existing = next(
            (item for item in self._items if item.product_id == product_id),
            None
        )
        
        if existing:
            existing.increase_quantity(quantity)
        else:
            self._items.append(OrderItem(product_id, quantity, price))
    
    def submit(self):
        """State transition with validation"""
        if not self._items:
            raise ValueError("Cannot submit empty order")
        if self.status != 'DRAFT':
            raise ValueError("Only draft orders can be submitted")
        
        self.status = 'SUBMITTED'
    
    def __eq__(self, other):
        """Equality based on ID"""
        if not isinstance(other, Order):
            return False
        return self.id == other.id
    
    def __hash__(self):
        return hash(self.id)

Value Objects

Immutable objects defined by their attributes, not identity.

✅ Value Object Examples
// Money Value Object
public class Money : ValueObject
{
    public decimal Amount { get; }
    public string Currency { get; }
    
    public Money(decimal amount, string currency)
    {
        if (amount < 0)
            throw new ArgumentException("Amount cannot be negative");
        if (string.IsNullOrEmpty(currency))
            throw new ArgumentException("Currency required");
        
        Amount = amount;
        Currency = currency;
    }
    
    // Value objects should have business operations
    public Money Add(Money other)
    {
        if (Currency != other.Currency)
            throw new InvalidOperationException("Cannot add different currencies");
        
        return new Money(Amount + other.Amount, Currency);
    }
