GraphQL Best Practices

Design Efficient, Secure, and Scalable GraphQL APIs

API Design Excellence v1.0.0 Production-Ready

What is GraphQL?

GraphQL is a query language and runtime for APIs. Unlike REST, GraphQL lets clients request exactly the data they need in a single request. The strongly-typed schema serves as a contract between client and server, enabling powerful tooling and validation.

GraphQL Core Principles

Strongly Typed Schema

Schema defines complete API contract with types

Type safety at development time
Auto-generated documentation
Client code generation
Query validation before execution

Client-Specified Queries

Clients request exactly what they need

No over-fetching or under-fetching
Single request for complex data
Reduced network overhead

Introspection

Schema is queryable by clients

Auto-generated documentation
GraphQL Playground/IDE support
Runtime schema validation

Single Endpoint

All queries go to /graphql

Simplified routing
Easier caching strategies
Unified authentication

Schema Design Best Practices

✅ Use PascalCase for Types

Good: type UserProfile { ... }

Bad: type user_profile { ... }

✅ Use camelCase for Fields

Good: firstName: String

Bad: first_name: String

✅ Prefix Boolean Fields

Good: isActive: Boolean, hasPermission: Boolean

Bad: active: Boolean, permission: Boolean

✅ Use Verbs for Mutations

Good: createUser, updateProfile, deleteOrder

Bad: user, profile, order

GraphQL Type System

Object Types

Primary building blocks defining entities

Keep types focused and cohesive
Use interfaces for shared fields
Avoid deeply nested types (>3-4 levels)
Make fields nullable by default

Interfaces

Abstract types for polymorphism

Use for polymorphic responses (SearchResult)
Define shared fields (Node interface with id)
Enable type-safe union alternatives

Unions

Return one of multiple types

Search results with different types
Mutation results (success/error types)
Use when no shared fields needed

Enums

Fixed set of values

Use UPPER_SNAKE_CASE for values
Never remove enum values (deprecate)
Perfect for status, roles, categories

Input Types

Complex mutation arguments

Separate from output types
Use nullable fields for partial updates
Name with Input suffix

Field Nullability Patterns

[Type!]!

Non-null list of non-null items

Required collection (e.g., permissions)

[Type!]

Nullable list of non-null items

Optional collection

[Type]!

Non-null list with nullable items

Rare - usually avoid

Type!

Non-null field

IDs, required business fields

Pagination Strategies

Cursor-Based Pagination (Relay-Style)

Recommended for production GraphQL APIs

type Query {
  users(first: Int, after: String, last: Int, before: String): UserConnection!
}

type UserConnection {
  edges: [UserEdge!]!
  pageInfo: PageInfo!
  totalCount: Int
}

type UserEdge {
  node: User!
  cursor: String!
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}
✅ Handles inserts/deletes consistently
✅ Works with infinite scroll
✅ Standardized across industry (Relay spec)

Offset-Based Pagination

Simple page-based approach

type Query {
  users(page: Int = 1, perPage: Int = 10): UserPage!
}

type UserPage {
  items: [User!]!
  page: Int!
  perPage: Int!
  total: Int!
  hasMore: Boolean!
}
✅ Simple to implement
✅ Familiar to developers
❌ Performance issues with large offsets
❌ Inconsistent with concurrent changes

Query Optimization with DataLoader

DataLoader solves the N+1 query problem by batching and caching data requests within a single GraphQL request.

N+1 Problem

Without DataLoader, resolving a list of users and their orders results in 1 query for users + N queries for orders (one per user).

DataLoader Solution

Batch multiple requests for the same resource
Execute single query for all needed items
Cache results within request context
Automatically deduplicate requests

DataLoader Best Practices

Create one DataLoader per resource type
Instantiate DataLoaders per-request (not globally)
Use DataLoader for associations (user.orders)
Profile queries to identify N+1 problems

      }
    }
  ]

Error Handling Strategies

Field Errors: Return null for field, add error to errors array
Union Types: Return success or error type in union
Error Extensions: Add custom error codes and metadata
Partial Success: Return partial data when some fields fail

Error Best Practices

Use custom error codes (NOT_FOUND, VALIDATION_ERROR, etc.)
Include helpful context in extensions
Never expose internal errors to clients
Log full error details server-side
Consider union types for expected errors

Security Best Practices

Query Depth Limiting

Prevent deeply nested queries that could overload server:

// Limit query depth to 5 levels
const depthLimit = require('graphql-depth-limit');
app.use('/graphql', graphqlHTTP({
  validationRules: [depthLimit(5)]
}));

Query Complexity Analysis

Assign complexity costs to fields and limit total query complexity:

type Query {
  users(first: Int!): [User!]! # Complexity: first * 10
  user(id: ID!): User           # Complexity: 1
}

Rate Limiting

Implement per-user rate limits
Use query complexity for adaptive rate limiting
Monitor expensive queries
Consider GraphQL-specific rate limiting (not just HTTP)

Authentication & Authorization

Authenticate at HTTP layer (before GraphQL)
Authorize at field level in resolvers
Use directive-based authorization (@auth, @hasRole)
Never expose unauthorized data (return null)
Disable introspection in production

Schema Evolution

Deprecation Over Breaking Changes

type User {
  # Deprecated field
  name: String @deprecated(reason: "Use firstName and lastName instead")
  
  # New fields
  firstName: String
  lastName: String
}

Versioning Strategies

Deprecation (Recommended): Mark old fields @deprecated, add new fields
Versioned Endpoints: /graphql/v1, /graphql/v2 (avoid if possible)
Field Aliases: Resolve same data with different field names

Schema Evolution Best Practices

Never remove fields (deprecate instead)
Add new fields as nullable
Use @deprecated directive with reason
Monitor deprecated field usage
Communicate changes to clients early
Maintain schema changelog

Schema Design Example

Complete User Schema

type Query {
  user(id: ID!): User
  users(first: Int, after: String): UserConnection!
}

type Mutation {
  createUser(input: CreateUserInput!): CreateUserPayload!
  updateUser(id: ID!, input: UpdateUserInput!): UpdateUserPayload!
  deleteUser(id: ID!): DeleteUserPayload!
}

type User implements Node {
  id: ID!
  email: String!
  firstName: String!
  lastName: String!
  fullName: String!  # Computed field
  isActive: Boolean!
  role: UserRole!
  createdAt: DateTime!
  updatedAt: DateTime!
  
  # Associations with pagination
  orders(first: Int, after: String): OrderConnection!
  profile: UserProfile
}

interface Node {
  id: ID!
}

enum UserRole {
  USER
  ADMIN
  MODERATOR
}

input CreateUserInput {
  email: String!
  firstName: String!
  lastName: String!
  password: String!
}

input UpdateUserInput {
  firstName: String
  lastName: String
  isActive: Boolean
}

type CreateUserPayload {
  user: User
  errors: [UserError!]
}

type UpdateUserPayload {
  user: User
  errors: [UserError!]
}

type DeleteUserPayload {
  success: Boolean!
  errors: [UserError!]
}

type UserError {
  field: String
  message: String!
  code: ErrorCode!
}

enum ErrorCode {
  VALIDATION_ERROR
  NOT_FOUND
  UNAUTHORIZED
  FORBIDDEN
}

DataLoader Implementation - Python

Batch Loading Function

from aiodataloader import DataLoader

class UserLoader(DataLoader):
    async def batch_load_fn(self, user_ids):
        # Single query for all user_ids
        users = await db.query(User).filter(User.id.in_(user_ids)).all()
        
        # Return users in same order as user_ids
        user_map = {user.id: user for user in users}
        return [user_map.get(user_id) for user_id in user_ids]

# Usage in resolver
async def resolve_user(parent, info, id):
    return await info.context['user_loader'].load(id)

GraphQL Schema Validation in CORTEX

CORTEX includes intelligent agents that validate GraphQL schemas against best practices and detect anti-patterns.

Schema Validator

# CORTEX GraphQL Schema Validator
class GraphQLSchemaValidator:
    def validate_schema(self, schema: str) -> List[Violation]:
        violations = []
        parsed_schema = parse_schema(schema)
        
        # Check naming conventions
        for type_def in parsed_schema.types:
            if not self.is_pascal_case(type_def.name):
                violations.append(Violation(
                    rule="Use PascalCase for types",
                    severity="MEDIUM",
                    location=f"Type: {type_def.name}",
                    suggestion=f"Change to: {self.to_pascal_case(type_def.name)}"
                ))
            
            for field in type_def.fields:
                if not self.is_camel_case(field.name):
                    violations.append(Violation(
                        rule="Use camelCase for fields",
                        severity="MEDIUM",
                        location=f"{type_def.name}.{field.name}",
                        suggestion=f"Change to: {self.to_camel_case(field.name)}"
                    ))
        
        # Check for N+1 risks
        for type_def in parsed_schema.types:
            for field in type_def.fields:
                if self.is_list_field(field) and not field.has_pagination:
                    violations.append(Violation(
                        rule="List fields should have pagination",
                        severity="HIGH",
                        location=f"{type_def.name}.{field.name}",
                        suggestion="Add cursor-based pagination (first, after, last, before)"
                    ))
        
        # Check deprecation usage
        for type_def in parsed_schema.types:
            for field in type_def.fields:
                if field.is_deprecated and not field.deprecation_reason:
                    violations.append(Violation(
                        rule="Deprecated fields need reason",
                        severity="LOW",
                        location=f"{type_def.name}.{field.name}",
                        suggestion="Add @deprecated(reason: '...')"
                    ))
        
        return violations

Query Complexity Analyzer

# CORTEX Query Complexity Analyzer
class QueryComplexityAnalyzer:
    def analyze_complexity(self, query: str, schema: str) -> ComplexityReport:
        parsed_query = parse_query(query)
        complexity = 0
        
        # Calculate complexity
        for selection in parsed_query.selections:
            field_complexity = self.calculate_field_complexity(selection, schema)
            complexity += field_complexity
        
        # Calculate query depth
        depth = self.calculate_query_depth(parsed_query)
        
        # Check limits
        violations = []
        if complexity > MAX_QUERY_COMPLEXITY:
            violations.append(f"Query complexity {complexity} exceeds limit {MAX_QUERY_COMPLEXITY}")
        
        if depth > MAX_QUERY_DEPTH:
            violations.append(f"Query depth {depth} exceeds limit {MAX_QUERY_DEPTH}")
        
        return ComplexityReport(
            complexity=complexity,
            depth=depth,
            violations=violations,
            suggestions=self.generate_optimization_suggestions(parsed_query)
        )
    
    def calculate_field_complexity(self, selection, schema):
        field = schema.get_field(selection.name)
        base_complexity = field.complexity_cost or 1
        
        # Lists multiply complexity by 'first' argument
        if field.is_list and 'first' in selection.arguments:
            multiplier = selection.arguments['first']
            return base_complexity * multiplier
        
        return base_complexity
