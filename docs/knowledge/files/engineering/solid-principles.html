SOLID Principles

Five Principles of Object-Oriented Design

Robert C. Martin (Uncle Bob) Software Engineering v1.0.0

What are SOLID Principles?

SOLID is an acronym representing five fundamental principles of object-oriented design that, when applied together, make software designs more understandable, flexible, and maintainable. Coined by Robert C. Martin (Uncle Bob) in the early 2000s, these principles have become the cornerstone of professional software engineering.

Each principle addresses a specific aspect of software design, from managing dependencies to ensuring classes have well-defined responsibilities. When followed, SOLID principles lead to code that is easier to test, modify, and extend over time, significantly reducing technical debt and maintenance costs.

These principles are language-agnostic and apply to any object-oriented programming language, including Python, C#, Java, JavaScript, and TypeScript. They form the foundation for many modern design patterns and architectural styles.

The Five Principles

S

Single Responsibility

A class should have one, and only one, reason to change

O

Open/Closed

Software entities should be open for extension but closed for modification

L

Liskov Substitution

Derived classes must be substitutable for their base classes

I

Interface Segregation

Many client-specific interfaces are better than one general-purpose interface

D

Dependency Inversion

Depend upon abstractions, not concretions

Key Benefits

Maintainability: Easier to understand and modify code without fear of breaking existing functionality
Testability: Classes with single responsibilities and clear dependencies are straightforward to test
Flexibility: Changes can be made by extending code rather than modifying existing implementations
Reusability: Well-designed classes can be reused across different contexts
Reduced Coupling: Dependencies are minimized and managed through abstractions
Increased Cohesion: Related functionality is grouped together in focused classes

When to Use

✅ Use When

Building enterprise applications expected to evolve over years
Working on team projects with multiple developers
Creating reusable libraries or frameworks
Maintaining legacy codebases that need refactoring
Implementing complex business logic with many moving parts
Designing systems that require high testability

❌ Consider Alternatives When

Building simple scripts or one-off utilities
Creating prototypes or proof-of-concept projects
Working under extreme time constraints (technical debt trade-off)
Dealing with very simple domains (over-engineering risk)
Team lacks OOP experience (training required first)

Single Responsibility Principle (SRP)

Definition: A class should have one, and only one, reason to change.

"Reason to change" refers to different stakeholders or actors who might request changes. If multiple actors need different things from the same class, those are multiple responsibilities. Each class should serve a single actor.

Common Violations

God Objects: Classes that know too much or do too much (>20 methods, >500 lines)
Divergent Change: Having to change the same class for unrelated feature requests
Multiple Concerns: Class handles business logic AND persistence AND validation
Generic Names: Classes named Manager, Controller, Handler, Util often violate SRP

Detection Heuristics

More than 20 methods → likely multiple responsibilities
More than 300 lines of code → probably doing too much
More than 10 dependencies → interacting with too many other classes
Class description contains "and" or "or" → suggests multiple responsibilities

Refactoring Strategies

Extract Class: Create new classes for each distinct responsibility
Move Method: Move methods to classes they depend on most
Extract Interface: Separate interface from implementation

Open/Closed Principle (OCP)

Definition: Software entities should be open for extension but closed for modification.

You should be able to add new functionality without changing existing code. This is achieved through abstraction, polymorphism, and dependency injection. The goal is to change behavior by adding new code, not by modifying existing working code.

Key Techniques

Inheritance: Extend base classes to add new behavior
Interfaces: Define contracts that can be implemented in multiple ways
Strategy Pattern: Encapsulate algorithms and make them interchangeable
Template Method: Define skeleton algorithms with customizable steps

Benefits

Minimizes risk of breaking existing functionality
Easier to add new features
Better separation of concerns
Supports plugin architectures

Liskov Substitution Principle (LSP)

Definition: Derived classes must be substitutable for their base classes without altering correctness.

If class B is a subclass of class A, we should be able to replace A with B without disrupting the behavior of the program. Subtypes must strengthen, not weaken, the contract defined by the base type.

Contract Rules

Preconditions cannot be strengthened in subtype
Postconditions cannot be weakened in subtype
Invariants must be preserved in subtype
No new exceptions should be thrown by subtype

Common Violations

Rectangle/Square problem (mutable dimensions)
Empty implementations that throw NotImplementedException
Subtypes that strengthen preconditions
Subtypes that weaken postconditions

Interface Segregation Principle (ISP)

Definition: Many client-specific interfaces are better than one general-purpose interface.

No client should be forced to depend on methods it does not use. Instead of one fat interface, create multiple smaller, cohesive interfaces. This prevents clients from depending on functionality they don't need.

Interface Design Guidelines

Keep interfaces small and focused (2-5 methods)
Group related methods together
Segregate by client needs, not by implementation
Use role interfaces (e.g., Readable, Writable, Closeable)

Benefits

Reduced coupling between clients and implementations
Easier to understand and implement
Better testability with focused mocks
Supports composition over inheritance

Dependency Inversion Principle (DIP)

Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions.

Abstractions should not depend on details. Details should depend on abstractions. This inverts the typical dependency structure where high-level business logic depends on low-level implementation details.

Key Concepts

Inversion of Control (IoC): Framework controls flow, not your code
Dependency Injection (DI): Dependencies provided externally, not created internally
Abstract Dependencies: Depend on interfaces/abstract classes, not concrete classes
Plugin Architecture: Core depends on abstractions, plugins provide implementations

Implementation Techniques

Constructor injection (preferred)
Property injection
Method injection
Service locator pattern
IoC containers (e.g., dependency_injector, Spring, Unity)

Single Responsibility Principle - Python Example

❌ Violation: Multiple Responsibilities

# ❌ Violates SRP - Multiple responsibilities
class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email
    
    # Responsibility 1: User data management
    def update_profile(self, name, email):
        self.name = name
        self.email = email
    
    # Responsibility 2: Persistence
    def save_to_database(self):
        db.execute("INSERT INTO users...")
    
    # Responsibility 3: Email notifications
    def send_welcome_email(self):
        smtp.send(self.email, "Welcome!")
    
    # Responsibility 4: Validation
    def validate_email(self):
        return '@' in self.email

✅ Compliant: Separated Responsibilities

# ✅ Follows SRP - Separated responsibilities
class User:
    """Domain model - single responsibility: represent user data"""
    def __init__(self, name, email):
        self.name = name
        self.email = email

class UserRepository:
    """Single responsibility: persist users"""
    def save(self, user: User):
        db.execute("INSERT INTO users VALUES (?, ?)", 
                  user.name, user.email)

class EmailService:
    """Single responsibility: send emails"""
    def send_welcome_email(self, user: User):
        smtp.send(user.email, "Welcome!")

class EmailValidator:
    """Single responsibility: validate emails"""
    def is_valid(self, email: str) -> bool:
        return '@' in email and '.' in email

Open/Closed Principle - Example

❌ Violation: Modification Required

# ❌ Violates OCP - Must modify to add new shapes
class AreaCalculator:
    def calculate_area(self, shape):
        if shape.type == "circle":
            return 3.14 * shape.radius ** 2
        elif shape.type == "rectangle":
            return shape.width * shape.height
        elif shape.type == "triangle":  # Must modify for new shape!
            return 0.5 * shape.base * shape.height

✅ Compliant: Extension Through Inheritance

# ✅ Follows OCP - Extend without modification
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float:
        pass

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius
    
    def area(self) -> float:
        return 3.14 * self.radius ** 2

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height
    
    def area(self) -> float:
        return self.width * self.height

class Triangle(Shape):  # New shape added without modifying existing code
    def __init__(self, base, height):
        self.base = base
        self.height = height
    
    def area(self) -> float:
        return 0.5 * self.base * self.height

class AreaCalculator:
    def calculate_area(self, shape: Shape) -> float:
        return shape.area()  # Polymorphism!

Dependency Inversion Principle - Example

❌ Violation: Depends on Concrete Implementation

# ❌ Violates DIP - High-level depends on low-level
class EmailSender:
    def send(self, message):
        # SMTP implementation
        pass

class UserNotificationService:
    def __init__(self):
        self.email_sender = EmailSender()  # Concrete dependency!
    
    def notify_user(self, user, message):
        self.email_sender.send(message)

✅ Compliant: Depends on Abstraction

# ✅ Follows DIP - Depends on abstraction
from abc import ABC, abstractmethod

class MessageSender(ABC):
    @abstractmethod
    def send(self, message: str) -> None:
        pass

class EmailSender(MessageSender):
    def send(self, message: str) -> None:
        # SMTP implementation
        pass

class SmsSender(MessageSender):
    def send(self, message: str) -> None:
        # SMS API implementation
        pass

class UserNotificationService:
    def __init__(self, sender: MessageSender):  # Abstraction dependency!
        self.sender = sender
    
    def notify_user(self, user, message):
        self.sender.send(message)

# Usage with dependency injection
email_sender = EmailSender()
notification_service = UserNotificationService(email_sender)

# Can easily switch to SMS without changing UserNotificationService
sms_sender = SmsSender()
notification_service = UserNotificationService(sms_sender)

Interface Segregation in CORTEX

Focused Role Interfaces

# Instead of one fat interface:
# class Agent(ABC):
#     def analyze() ...
#     def generate() ...
#     def review() ...
#     def refactor() ...  # Not all agents need all methods!

# CORTEX uses focused interfaces:
class Analyzable(ABC):
    @abstractmethod
    def analyze(self, code: str) -> Analysis:
        pass

class Generatable(ABC):
    @abstractmethod
    def generate(self, spec: Specification) -> GeneratedCode:
        pass

class Reviewable(ABC):
    @abstractmethod
    def review(self, code: str) -> ReviewResult:
        pass

# Agents implement only what they need
class CodeReviewer(Analyzable, Reviewable):  # Not forced to implement generate
    pass

class TestGenerator(Generatable):  # Only needs generate capability
    pass

Dependency Inversion in CORTEX

Brain Storage Abstraction

# High-level orchestrators depend on abstraction
class BrainStorage(ABC):
    @abstractmethod
    def store(self, key: str, value: Any) -> None:
        pass
    
    @abstractmethod
    def retrieve(self, key: str) -> Any:
        pass

# Low-level implementations
class SQLiteBrainStorage(BrainStorage):
    def store(self, key: str, value: Any) -> None:
        # SQLite implementation
        pass

class PostgresBrainStorage(BrainStorage):
    def store(self, key: str, value: Any) -> None:
        # PostgreSQL implementation
        pass

# High-level orchestrator depends on abstraction
class MaintenanceOrchestrator:
    def __init__(self, brain: BrainStorage):  # Abstraction, not concrete
        self.brain = brain
    
    def run_maintenance(self):
        data = self.brain.retrieve("health_metrics")  # Works with any implementation
