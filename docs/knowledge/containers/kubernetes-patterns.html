Overview

Kubernetes patterns for container orchestration covering deployments, service discovery, configuration management, storage, and security best practices.

Kubernetes Core Concepts:
  • Pods: Smallest deployable units containing one or more containers
  • Deployments: Declarative updates for Pods and ReplicaSets
  • Services: Stable network endpoints for Pod groups
  • ConfigMaps/Secrets: Configuration and sensitive data management
  • StatefulSets: Ordered, stable deployments for stateful apps

Deployment Patterns

Define Resource Requests and Limits

HIGH

Always specify CPU and memory requests/limits to ensure proper scheduling and prevent resource exhaustion.

✅ Good - Resource Management

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web
        image: myapp:1.0.0
        resources:
          requests:
            memory: "256Mi"    # Guaranteed minimum
            cpu: "250m"        # 0.25 CPU cores
          limits:
            memory: "512Mi"    # Maximum allowed
            cpu: "500m"        # 0.5 CPU cores
        livenessProbe:
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5

❌ Bad - No Resource Limits

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: web
        image: myapp:1.0.0
        # No resources defined
        # Can consume unlimited memory/CPU
        # Causes unpredictable scheduling
        # One pod can starve others
Resource Guidelines: Requests ensure scheduling, limits prevent runaway consumption. Set requests to typical usage, limits to maximum tolerable spike. Monitor actual usage and adjust.

Use Rolling Updates with Health Checks

HIGH

Configure rolling update strategy with proper health checks to ensure zero-downtime deployments.

✅ Good - Rolling Update Strategy

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
spec:
  replicas: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # Create 1 extra pod during update
      maxUnavailable: 1  # Allow 1 pod down during update
  template:
    spec:
      containers:
      - name: api
        image: api-server:2.0.0
        readinessProbe:
          httpGet:
            path: /health/ready
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5
          failureThreshold: 3
        livenessProbe:
          httpGet:
            path: /health/live
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
          failureThreshold: 3
        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 10"]
          # Graceful shutdown: wait for connections to drain

Service Patterns

Use Appropriate Service Types

HIGH

Choose service type based on access requirements: ClusterIP (internal), NodePort (external via node), LoadBalancer (cloud LB).

✅ Good - Service Type Selection

---
# ClusterIP - Internal microservice communication
apiVersion: v1
kind: Service
metadata:
  name: database
spec:
  type: ClusterIP
  selector:
    app: postgres
  ports:
  - port: 5432
    targetPort: 5432
---
# LoadBalancer - External web traffic
apiVersion: v1
kind: Service
metadata:
  name: web-frontend
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 8080
  sessionAffinity: ClientIP  # Sticky sessions
---
# Headless - StatefulSet direct pod access
apiVersion: v1
kind: Service
metadata:
  name: cassandra
spec:
  clusterIP: None  # Headless
  selector:
    app: cassandra
  ports:
  - port: 9042

Use Ingress for HTTP/HTTPS Routing

MEDIUM

For HTTP(S) traffic, use Ingress controller for path-based routing, TLS termination, and single load balancer.

✅ Good - Ingress Configuration

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  tls:
  - hosts:
    - api.example.com
    - web.example.com
    secretName: tls-secret
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /v1
        pathType: Prefix
        backend:
          service:
            name: api-v1
            port:
              number: 8080
      - path: /v2
        pathType: Prefix
        backend:
          service:
            name: api-v2
            port:
              number: 8080
  - host: web.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-frontend
            port:
              number: 80

Configuration Management

Use ConfigMaps for Configuration, Secrets for Sensitive Data

HIGH

Separate configuration from code. Use ConfigMaps for non-sensitive config, Secrets for passwords, tokens, keys.

✅ Good - ConfigMap & Secret

---
# ConfigMap for app configuration
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: "production"
  LOG_LEVEL: "info"
  FEATURE_FLAGS: "feature1,feature2"
  app.properties: |
    server.port=8080
    cache.ttl=300
---
# Secret for sensitive data
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
type: Opaque
stringData:
  DATABASE_PASSWORD: "secure_password"
  API_KEY: "secret_api_key"
---
# Deployment using ConfigMap and Secret
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  template:
    spec:
      containers:
      - name: app
        image: myapp:1.0.0
        envFrom:
        - configMapRef:
            name: app-config
        - secretRef:
            name: app-secrets
        volumeMounts:
        - name: config-volume
          mountPath: /etc/config
      volumes:
      - name: config-volume
        configMap:
          name: app-config

❌ Bad - Hardcoded Config

apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  template:
    spec:
      containers:
      - name: app
        image: myapp:1.0.0
        env:
        # Hardcoded in manifest
        - name: DATABASE_PASSWORD
          value: "mypassword123"
        # Can't change without redeploying
        # Password visible in Git

Persistent Storage

Use PersistentVolumeClaims for Stateful Apps

HIGH

For databases and stateful applications, use PersistentVolumeClaims with appropriate storage classes.

✅ Good - StatefulSet with PVC

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:15
        ports:
        - containerPort: 5432
        env:
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef:
              name: postgres-secret
              key: password
        volumeMounts:
        - name: postgres-data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
  - metadata:
      name: postgres-data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: fast-ssd
      resources:
        requests:
          storage: 50Gi

Security Best Practices

Run Containers as Non-Root

HIGH

Never run containers as root user. Use securityContext to enforce non-root execution and drop capabilities.

✅ Good - Security Context

apiVersion: apps/v1
kind: Deployment
metadata:
  name: secure-app
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: app
        image: myapp:1.0.0
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          runAsNonRoot: true
          runAsUser: 1000
          capabilities:
            drop:
            - ALL
        volumeMounts:
        - name: tmp
          mountPath: /tmp
      volumes:
      - name: tmp
        emptyDir: {}

Use Network Policies for Pod Isolation

MEDIUM

Implement network policies to control pod-to-pod communication and enforce zero-trust networking.

✅ Good - Network Policy

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-network-policy
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
  - Ingress
  - Egress
  ingress:
  # Only allow traffic from frontend
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
  egress:
  # Allow traffic to database only
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
  # Allow DNS
  - to:
    - namespaceSelector:
        matchLabels:
          name: kube-system
    ports:
    - protocol: UDP
      port: 53
