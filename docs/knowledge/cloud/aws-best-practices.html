Well-Architected Framework

Design for Failure

HIGH

Assume everything fails. Design applications to handle failures gracefully using multiple Availability Zones, auto-recovery, and health checks.

✅ Good - Multi-AZ Deployment

# CloudFormation - Multi-AZ Auto Scaling Group
Resources:
  WebServerASG:
    Type: AWS::AutoScaling::AutoScalingGroup
    Properties:
      VPCZoneIdentifier:
        - !Ref SubnetAZ1
        - !Ref SubnetAZ2
        - !Ref SubnetAZ3
      MinSize: 3
      MaxSize: 10
      DesiredCapacity: 3
      HealthCheckType: ELB
      HealthCheckGracePeriod: 300
      TargetGroupARNs:
        - !Ref TargetGroup
      LaunchTemplate:
        LaunchTemplateId: !Ref LaunchTemplate
        Version: !GetAtt LaunchTemplate.LatestVersionNumber
Best Practice: Deploy across at least 3 Availability Zones for high availability. Each AZ is an isolated data center.

Implement Security in Depth

HIGH

Apply security at every layer: VPC, subnet, security group, IAM, and application level.

✅ Good - Layered Security

// IAM Policy - Least Privilege
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"

      "Condition": {
        "IpAddress": {
          "aws:SourceIp": "203.0.113.0/24"
        }
      }
    }
  ]
}

Compute (EC2 & Lambda)

Right-Size EC2 Instances

HIGH

Choose instance types based on workload requirements. Use CloudWatch metrics to monitor and adjust sizing.

✅ Good - Right-Sized Instance

# For CPU-intensive workloads
InstanceType: c6i.2xlarge  # 8 vCPU, 16 GB RAM
# Compute Optimized

# For memory-intensive workloads  
InstanceType: r6i.2xlarge  # 8 vCPU, 64 GB RAM
# Memory Optimized

# For general purpose
InstanceType: t3.medium    # 2 vCPU, 4 GB RAM
# Burstable with baseline

❌ Bad - Over-Provisioned

# Using large instance for small workload
InstanceType: m5.16xlarge  # 64 vCPU, 256 GB RAM
# For a simple web server with low traffic
# Wastes resources and increases costs

Use Lambda for Event-Driven Workloads

MEDIUM

Lambda is ideal for event-driven, short-duration tasks. No server management, automatic scaling, pay only for execution time.

✅ Good - Lambda Function

# Lambda function for S3 image processing
import boto3
import os
from PIL import Image

s3 = boto3.client('s3')

def lambda_handler(event, context):
    # Triggered when image uploaded to S3
    bucket = event['Records'][0]['s3']['bucket']['name']
    key = event['Records'][0]['s3']['object']['key']
    
    # Download image
    download_path = f'/tmp/{key}'
    s3.download_file(bucket, key, download_path)
    
    # Create thumbnail
    img = Image.open(download_path)
    img.thumbnail((200, 200))
    
    # Upload thumbnail
    thumbnail_key = f'thumbnails/{key}'
    thumbnail_path = f'/tmp/thumb_{key}'
    img.save(thumbnail_path)
    s3.upload_file(thumbnail_path, bucket, thumbnail_key)
    
    return {
        'statusCode': 200,
        'body': f'Thumbnail created: {thumbnail_key}'
    }

Storage (S3)

Use S3 Storage Classes

HIGH

Choose the right S3 storage class based on access patterns to optimize costs.

✅ Good - Lifecycle Policy

{
  "Rules": [
    {
      "Id": "MoveToIA",
      "Status": "Enabled",
      "Transitions": [
        {
          "Days": 30,
          "StorageClass": "STANDARD_IA"
        },
        {
          "Days": 90,
          "StorageClass": "GLACIER_IR"
        },
        {
          "Days": 180,
          "StorageClass": "DEEP_ARCHIVE"
        }
      ],
      "NoncurrentVersionTransitions": [
        {
          "NoncurrentDays": 30,
          "StorageClass": "STANDARD_IA"
        }
      ]
    }
  ]
}
Storage Class Comparison:
S3 Standard: Frequent access, millisecond latency
S3 Standard-IA: Infrequent access, lower cost
S3 Glacier Instant Retrieval: Archive with instant access
S3 Glacier Deep Archive: Lowest cost, 12hr retrieval

Enable S3 Versioning and Replication

HIGH

Enable versioning to protect against accidental deletion. Use cross-region replication for disaster recovery.

✅ Good - S3 Bucket Configuration

Resources:
  S3Bucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: my-production-bucket
      VersioningConfiguration:
        Status: Enabled
      ReplicationConfiguration:
        Role: !GetAtt ReplicationRole.Arn
        Rules:
          - Id: ReplicateAll
            Status: Enabled
            Priority: 1
            Destination:
              Bucket: !GetAtt BackupBucket.Arn
              ReplicationTime:
                Status: Enabled
                Time:
                  Minutes: 15
      PublicAccessBlockConfiguration:
        BlockPublicAcls: true
        BlockPublicPolicy: true
        IgnorePublicAcls: true
        RestrictPublicBuckets: true

Networking (VPC)

Use Private Subnets for Resources

HIGH

Place application servers and databases in private subnets. Only load balancers and NAT gateways should be in public subnets.

✅ Good - VPC Architecture

Resources:
  VPC:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: 10.0.0.0/16
      EnableDnsHostnames: true
      EnableDnsSupport: true

  PublicSubnet1:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref VPC
      CidrBlock: 10.0.1.0/24
      AvailabilityZone: !Select [0, !GetAZs '']
      MapPublicIpOnLaunch: true

  PrivateSubnet1:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref VPC
      CidrBlock: 10.0.10.0/24
      AvailabilityZone: !Select [0, !GetAZs '']
      # No public IP mapping

  # NAT Gateway for private subnet internet access
  NATGateway:
    Type: AWS::EC2::NatGateway
    Properties:
      AllocationId: !GetAtt EIP.AllocationId
      SubnetId: !Ref PublicSubnet1

Implement Security Groups as Stateful Firewalls

HIGH

Use security groups to control inbound and outbound traffic. Follow principle of least privilege.

✅ Good - Restrictive Security Group

WebServerSecurityGroup:
  Type: AWS::EC2::SecurityGroup
  Properties:
    GroupDescription: Web server security group
    VpcId: !Ref VPC
    SecurityGroupIngress:
      # Only allow HTTPS from Load Balancer
      - IpProtocol: tcp
        FromPort: 443
        ToPort: 443
        SourceSecurityGroupId: !Ref LoadBalancerSG
    SecurityGroupEgress:
      # Allow outbound to database only
      - IpProtocol: tcp
        FromPort: 5432
        ToPort: 5432
        DestinationSecurityGroupId: !Ref DatabaseSG

Cost Optimization

Use Reserved Instances and Savings Plans

MEDIUM

For predictable workloads, commit to 1 or 3-year terms for up to 72% savings compared to On-Demand.

Cost Optimization Strategies:
Reserved Instances: 1-3 year commitment, 40-72% savings
Savings Plans: Flexible commitment, 40-66% savings
Spot Instances: Bid on spare capacity, up to 90% savings
Auto Scaling: Scale resources based on demand

Tag Resources for Cost Allocation

MEDIUM

Tag all resources with environment, project, and owner for detailed cost tracking and chargeback.

✅ Good - Resource Tagging

Resources:
  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: t3.medium
      Tags:
        - Key: Environment
          Value: Production
        - Key: Project
          Value: ECommerce
        - Key: Owner
          Value: TeamAlpha
        - Key: CostCenter
          Value: Engineering
        - Key: Application
          Value: WebFrontend
