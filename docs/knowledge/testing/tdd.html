Overview

Test-Driven Development (TDD) is a software development approach where tests are written before the implementation code, following the Red-Green-Refactor cycle.

TDD Benefits:
  • Better Design: Writing tests first forces modular, testable code
  • Documentation: Tests serve as living documentation
  • Confidence: Safe refactoring with comprehensive test suite
  • Fewer Bugs: Catch issues early in development
  • Focus: Clear goal for each implementation step

Red-Green-Refactor Cycle

Follow the Three-Step Cycle

HIGH

TDD follows a strict cycle: Red (write failing test), Green (make it pass), Refactor (improve code quality). Never skip steps.

✅ Example - TDD Cycle

# STEP 1: RED - Write failing test
import pytest
from calculator import Calculator

def test_add_two_numbers():
    calc = Calculator()
    result = calc.add(2, 3)
    assert result == 5
    # Run: test fails (Calculator doesn't exist yet)

# STEP 2: GREEN - Minimal code to pass
class Calculator:
    def add(self, a, b):
        return 5  # Hardcoded to pass test
    # Run: test passes

# STEP 3: REFACTOR - Proper implementation
class Calculator:
    def add(self, a, b):
        return a + b
    # Run: test still passes

# Continue cycle: Add more tests, implement, refactor
Common Mistake: Writing implementation before tests, or skipping the Red phase. Always see the test fail first to ensure it's actually testing something.

Write the Simplest Test First

HIGH

Start with the simplest possible test case. Build complexity incrementally through additional tests.

✅ Good - Incremental Test Progression

// Test 1: Simplest case - empty list
describe('ShoppingCart', () => {
  it('should start with zero total', () => {
    const cart = new ShoppingCart();
    expect(cart.getTotal()).toBe(0);
  });

  // Test 2: Single item
  it('should calculate total for one item', () => {
    const cart = new ShoppingCart();
    cart.addItem({ name: 'Book', price: 10 });
    expect(cart.getTotal()).toBe(10);
  });

  // Test 3: Multiple items
  it('should calculate total for multiple items', () => {
    const cart = new ShoppingCart();
    cart.addItem({ name: 'Book', price: 10 });
    cart.addItem({ name: 'Pen', price: 2 });
    expect(cart.getTotal()).toBe(12);
  });

  // Test 4: Edge case - discount
  it('should apply discount correctly', () => {
    const cart = new ShoppingCart();
    cart.addItem({ name: 'Book', price: 100 });
    cart.applyDiscount(0.1); // 10% discount
    expect(cart.getTotal()).toBe(90);
  });
});

Take Baby Steps

MEDIUM

Make small, incremental changes. Each test should require minimal code to pass. Don't write multiple tests before implementing.

✅ Good - Small Iterations

// Iteration 1: Test empty string
[Test]
public void ReverseString_EmptyString_ReturnsEmpty()
{
    var reverser = new StringReverser();
    Assert.AreEqual("", reverser.Reverse(""));
}

// Implementation 1
public string Reverse(string input)
{
    return ""; // Simplest passing code
}

// Iteration 2: Test single character
[Test]
public void ReverseString_SingleChar_ReturnsSameChar()
{
    var reverser = new StringReverser();
    Assert.AreEqual("a", reverser.Reverse("a"));
}

// Implementation 2
public string Reverse(string input)
{
    if (input.Length <= 1) return input;
    return ""; // Still hardcoded for multi-char
}

// Iteration 3: Test two characters
[Test]
public void ReverseString_TwoChars_ReversesOrder()
{
    var reverser = new StringReverser();
    Assert.AreEqual("ba", reverser.Reverse("ab"));
}

// Implementation 3 (final)
public string Reverse(string input)
{
    return new string(input.Reverse().ToArray());
}

Writing Effective Tests

Follow AAA Pattern: Arrange-Act-Assert

HIGH

Structure tests with three clear sections: Arrange (setup), Act (execute), Assert (verify). Improves readability and maintainability.

✅ Good - AAA Pattern

describe('UserService', () => {
  it('should create user with hashed password', async () => {
    // Arrange
    const userService = new UserService();
    const userData = {
      email: 'test@example.com',
      password: 'SecurePass123'
    };
    
    // Act
    const user = await userService.createUser(userData);
    
    // Assert
    expect(user.email).toBe('test@example.com');
    expect(user.password).not.toBe('SecurePass123');
    expect(user.password.length).toBeGreaterThan(20);
  });
});

❌ Bad - Mixed Sections

it('should create user', async () => {
  const userService = new UserService();
  const user = await userService.createUser({
    email: 'test@example.com',
    password: 'SecurePass123'
  });
  expect(user.email).toBe('test@example.com');
  const anotherUser = await userService.createUser({
    email: 'test2@example.com',
    password: 'Pass456'
  });
  expect(user.password).not.toBe('SecurePass123');
  // Confusing, hard to follow

One Assert Per Test (Guideline)

MEDIUM

Prefer single assertions per test for clear failure messages. Multiple related assertions are acceptable for same behavior.

✅ Good - Focused Tests

def test_user_registration_creates_user():
    user = register_user("alice@example.com", "password123")
    assert user is not None

def test_user_registration_sets_email():
    user = register_user("alice@example.com", "password123")
    assert user.email == "alice@example.com"

def test_user_registration_hashes_password():
    user = register_user("alice@example.com", "password123")
    assert user.password != "password123"
    assert len(user.password) > 20

# Clear failure messages: knows exactly what failed

❌ Bad - Testing Multiple Behaviors

def test_user_registration():
    user = register_user("alice@example.com", "password123")
    assert user is not None
    assert user.email == "alice@example.com"
    assert user.password != "password123"
    assert user.is_active == True
    assert user.role == "user"
    assert user.created_at is not None
    # If second assert fails, others don't run
    # Unclear which behavior failed

Test Behavior, Not Implementation

HIGH

Focus on what the code does (public API), not how it does it (private methods). Tests should survive refactoring.

✅ Good - Testing Behavior

// Test public behavior
describe('EmailService', () => {
  it('should send welcome email after user signup', async () => {
    const emailService = new EmailService();
    const mockMailer = createMockMailer();
    emailService.setMailer(mockMailer);
    
    await emailService.sendWelcomeEmail('user@example.com');
    
    expect(mockMailer.sentEmails).toHaveLength(1);
    expect(mockMailer.sentEmails[0].to).toBe('user@example.com');
    expect(mockMailer.sentEmails[0].subject).toContain('Welcome');
  });
});

❌ Bad - Testing Implementation

// Testing private methods
describe('EmailService', () => {
  it('should call _formatEmailBody', () => {
    const emailService = new EmailService();
    const spy = jest.spyOn(emailService, '_formatEmailBody');
    
    emailService.sendWelcomeEmail('user@example.com');
    
    expect(spy).toHaveBeenCalled();
    // Breaks if refactor changes method name
    // Doesn't test actual behavior

Mocking & Test Doubles

Use Dependency Injection for Testability

HIGH

Inject dependencies through constructor or method parameters to enable easy mocking in tests.

✅ Good - Dependency Injection

# Production code with DI
class OrderService:
    def __init__(self, payment_gateway, email_service):
        self.payment_gateway = payment_gateway
        self.email_service = email_service
    
    def process_order(self, order):
        payment_result = self.payment_gateway.charge(order.total)
        if payment_result.success:
            self.email_service.send_confirmation(order)
            return True
        return False

# Test with mocks
def test_order_processing_sends_confirmation():
    # Arrange
    mock_gateway = Mock()
    mock_gateway.charge.return_value = PaymentResult(success=True)
    mock_email = Mock()
    
    service = OrderService(mock_gateway, mock_email)
    order = Order(total=100)
    
    # Act
    result = service.process_order(order)
    
    # Assert
    assert result is True
    mock_email.send_confirmation.assert_called_once_with(order)

❌ Bad - Hard Dependencies

# Hard to test
class OrderService:
    def process_order(self, order):
        # Creates dependencies internally
        gateway = StripePaymentGateway()  # Hard-coded
        email = SendGridEmailService()    # Hard-coded
        
        payment_result = gateway.charge(order.total)
        if payment_result.success:
            email.send_confirmation(order)
            return True
        return False

# Test requires actual Stripe/SendGrid connections
# Slow, brittle, requires credentials

Prefer Fakes Over Mocks for Complex Dependencies

MEDIUM

For complex external systems (databases, APIs), use fake implementations instead of mocking every interaction.

✅ Good - Fake Implementation

// Fake repository for testing
class FakeUserRepository implements IUserRepository {
  private users: Map = new Map();
  
  async findById(id: string): Promise {
    return this.users.get(id) || null;
  }
  
  async save(user: User): Promise {
    this.users.set(user.id, user);
  }
  
  async delete(id: string): Promise {
    this.users.delete(id);
  }
}

// Test using fake
describe('UserService', () => {
  it('should update user profile', async () => {
    const fakeRepo = new FakeUserRepository();
    const service = new UserService(fakeRepo);
    
    // Create test user
    await fakeRepo.save({ id: '1', name: 'Alice' });
    
    // Test update
    await service.updateProfile('1', { name: 'Alice Smith' });
    
    const updated = await fakeRepo.findById('1');
    expect(updated.name).toBe('Alice Smith');
  });
});

TDD Patterns & Tips

Test Edge Cases and Error Conditions

HIGH

Don't just test happy path. Cover edge cases, boundaries, and error conditions.

✅ Good - Comprehensive Test Coverage

// Happy path
[Test]
public void Divide_ValidNumbers_ReturnsQuotient()
{
    Assert.AreEqual(4, Calculator.Divide(8, 2));
}

// Edge case: Zero dividend
[Test]
public void Divide_ZeroDividend_ReturnsZero()
{
    Assert.AreEqual(0, Calculator.Divide(0, 5));
}

// Error condition: Division by zero
[Test]
public void Divide_ZeroDivisor_ThrowsException()
{
    Assert.Throws(() => 
        Calculator.Divide(10, 0)
    );
}

// Edge case: Negative numbers
[Test]
public void Divide_NegativeNumbers_ReturnsNegativeQuotient()
{
    Assert.AreEqual(-2, Calculator.Divide(-8, 4));
    Assert.AreEqual(-2, Calculator.Divide(8, -4));
}

// Boundary: Very large numbers
[Test]
public void Divide_LargeNumbers_HandlesCorrectly()
{
    Assert.AreEqual(1000000, Calculator.Divide(1000000000, 1000));
}

Keep Tests Fast

HIGH

Unit tests should run in milliseconds. Fast tests enable frequent execution during development.

Speed Guidelines:
  • Unit Tests: < 100ms per test, full suite < 10s
  • Integration Tests: < 1s per test
  • E2E Tests: < 10s per test
  • Avoid: Database calls, file I/O, network requests, Thread.Sleep
  • Use: In-memory fakes, mocks, test-specific lightweight implementations
