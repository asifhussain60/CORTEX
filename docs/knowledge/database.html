🎯 Category Overview

Database Design & Management covers relational (SQL) and non-relational (NoSQL) database systems, schema design, query optimization, transaction management, and database migration strategies. This category includes Oracle-specific best practices and general database patterns.

Key Concepts

  • Relational Databases (SQL): ACID transactions, normalization, indexes, query optimization
  • NoSQL Databases: Document stores, key-value stores, column-family, graph databases
  • Oracle Best Practices: Connection pooling, bind variables, transaction management, security
  • Schema Design: Entity relationships, normalization forms, denormalization strategies
  • Query Optimization: Indexes, execution plans, join strategies, performance tuning
  • Database Migrations: Version control, schema changes, data migrations, zero-downtime deployments

Criteria SQL (Relational) NoSQL
Data Structure Structured, fixed schema Flexible, schema-less or dynamic
Transactions ACID guarantees, multi-row transactions Eventual consistency (most), limited transactions
Scaling Vertical scaling (scale up) Horizontal scaling (scale out)
Relationships Complex joins, foreign keys Denormalized, embedded documents

Oracle Best Practices

Critical patterns for Oracle database development following industry standards.

Connection Pooling

Always use connection pools to reuse connections efficiently. Dramatically improves performance by avoiding expensive connection creation.

import oracledb

# ✅ GOOD: Create connection pool (recommended)
pool = oracledb.create_pool(
    user="app_user",
    password="secure_password",
    dsn="mydb.example.com:1521/ORCLPDB1",
    min=2,
    max=10,
    increment=1,
    threaded=True
)

# Acquire connection from pool
with pool.acquire() as connection:
    with connection.cursor() as cursor:
        cursor.execute("SELECT * FROM employees WHERE dept_id = :dept", dept=10)
        results = cursor.fetchall()

# ❌ BAD: Creating new connection for each operation (inefficient)
connection = oracledb.connect(
    user="app_user",
    password="secure_password",
    dsn="mydb.example.com:1521/ORCLPDB1"
)
cursor = connection.cursor()
cursor.execute("SELECT * FROM employees")
connection.close()  # Expensive to create/destroy connections

Bind Variables (SQL Injection Prevention)

Always use bind variables to prevent SQL injection and enable statement caching.

# ✅ GOOD: Named bind variables (recommended)
cursor.execute("""
    SELECT employee_id, first_name, last_name
    FROM employees
    WHERE department_id = :dept_id
    AND salary > :min_salary
""", dept_id=10, min_salary=50000)

# ✅ GOOD: Positional bind variables
cursor.execute("""
    SELECT * FROM employees
    WHERE department_id = :1 AND salary > :2
""", [10, 50000])

# ❌ BAD: String concatenation (DANGEROUS - SQL injection risk!)
dept_id = request.get("dept_id")
cursor.execute(f"SELECT * FROM employees WHERE department_id = {dept_id}")

# ❌ BAD: String formatting (also dangerous)
cursor.execute("SELECT * FROM employees WHERE dept_id = %s" % dept_id)

Efficient Data Fetching

Use arraysize and appropriate fetch methods for optimal data retrieval.

# ✅ GOOD: Set arraysize for bulk fetching
cursor.arraysize = 1000  # Fetch 1000 rows at a time
cursor.execute("SELECT * FROM large_table WHERE status = :status", status='ACTIVE')

# Fetch in batches
while True:
    rows = cursor.fetchmany()
    if not rows:
        break
    process_batch(rows)

# ❌ BAD: Fetching one row at a time (inefficient)
cursor.execute("SELECT * FROM large_table")
while True:
    row = cursor.fetchone()
    if not row:
        break
    process(row)  # Multiple round trips - very slow!

Transaction Management

Use explicit transactions for atomicity of related operations.

connection.autocommit = False  # Explicit transaction control

try:
    # Transfer money between accounts (atomic operation)
    cursor.execute(
        "UPDATE accounts SET balance = balance - :amt WHERE id = :id",
        amt=100, id=1
    )
    cursor.execute(
        "UPDATE accounts SET balance = balance + :amt WHERE id = :id",
        amt=100, id=2
    )
    connection.commit()  # Commit both operations
except Exception as e:
    connection.rollback()  # Rollback on error
    raise

Bulk Operations

Use executemany() for batch inserts/updates - much faster than loops.

# ✅ GOOD: Bulk insert (much faster)
data = [
    (1, 'John', 'Doe', 50000),
    (2, 'Jane', 'Smith', 60000),
    (3, 'Bob', 'Johnson', 55000)
]

cursor.executemany("""
    INSERT INTO employees (id, first_name, last_name, salary)
    VALUES (:1, :2, :3, :4)
""", data)

connection.commit()

# ❌ BAD: Individual inserts (slow)
for emp in employees:
    cursor.execute("""
        INSERT INTO employees (id, first_name, last_name, salary)
        VALUES (:1, :2, :3, :4)
    """, (emp['id'], emp['first_name'], emp['last_name'], emp['salary']))

connection.commit()  # Multiple round trips - very slow!

Query Optimization

Indexes for Performance

-- Single-column index for frequently searched columns
CREATE INDEX idx_emp_dept ON employees(department_id);

-- Composite index for multi-column searches
CREATE INDEX idx_emp_dept_sal ON employees(department_id, salary);

-- Function-based index for computed searches
CREATE INDEX idx_emp_upper_name ON employees(UPPER(last_name));

-- Unique index for primary/unique keys
CREATE UNIQUE INDEX idx_emp_email ON employees(email);

-- Check index usage
SELECT * FROM v$object_usage WHERE index_name = 'IDX_EMP_DEPT';

Execution Plan Analysis

-- Generate execution plan
EXPLAIN PLAN FOR
SELECT e.employee_id, e.first_name, d.department_name
FROM employees e
JOIN departments d ON e.department_id = d.department_id
WHERE e.salary > :min_salary;

-- View execution plan
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

-- Look for:
-- - TABLE ACCESS FULL (full table scans - add indexes)
-- - High COST values
-- - Missing indexes on join/filter columns

Query Best Practices

-- ✅ GOOD: Select only required columns
SELECT employee_id, first_name, last_name, salary
FROM employees
WHERE department_id = :dept_id;

-- ❌ BAD: SELECT * (wasteful)
SELECT *
FROM employees
WHERE department_id = :dept_id;

-- ✅ GOOD: Use appropriate JOIN types
SELECT e.employee_id, e.first_name, d.department_name
FROM employees e
INNER JOIN departments d ON e.department_id = d.department_id
WHERE e.salary > :min_salary;

-- ❌ BAD: Cartesian product (missing JOIN condition)
SELECT e.first_name, d.department_name
FROM employees e, departments d
WHERE e.salary > 50000;

MongoDB Document Design

// Embedded documents (denormalized - fast reads)
{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "name": "John Doe",
  "email": "john@example.com",
  "address": {
    "street": "123 Main St",
    "city": "New York",
    "state": "NY",
    "zip": "10001"
  },
  "orders": [
    {
      "order_id": "ORD-001",
      "date": ISODate("2025-01-15"),
      "total": 99.99,
      "items": [
        { "product": "Widget", "quantity": 2, "price": 49.99 }
      ]
    }
  ]
}

// Reference pattern (normalized - flexible)
// Users collection
{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "name": "John Doe",
  "email": "john@example.com"
}

// Orders collection (references user)
{
  "_id": ObjectId("507f191e810c19729de860ea"),
  "user_id": ObjectId("507f1f77bcf86cd799439011"),
  "date": ISODate("2025-01-15"),
  "total": 99.99
}

MongoDB Query Optimization

// Create indexes
db.users.createIndex({ "email": 1 }, { unique: true })
db.orders.createIndex({ "user_id": 1, "date": -1 })
db.products.createIndex({ "category": 1, "price": 1 })

// Query with indexes
db.orders.find({
  user_id: ObjectId("507f1f77bcf86cd799439011"),
  date: { $gte: ISODate("2025-01-01") }
}).sort({ date: -1 }).limit(10)

// Aggregation pipeline (efficient for complex queries)
db.orders.aggregate([
  { $match: { status: "completed" } },
  { $group: {
      _id: "$user_id",
      total_spent: { $sum: "$total" },
      order_count: { $sum: 1 }
  }},
  { $sort: { total_spent: -1 } },
  { $limit: 10 }
])

Zero-Downtime Migrations

-- Step 1: Add new column (nullable initially)
ALTER TABLE users ADD phone_number VARCHAR2(20);

-- Step 2: Deploy code that writes to both old and new columns
-- (Application code deployment)

-- Step 3: Backfill existing data
UPDATE users SET phone_number = legacy_phone WHERE phone_number IS NULL;
COMMIT;

-- Step 4: Make column NOT NULL (after backfill complete)
ALTER TABLE users MODIFY phone_number NOT NULL;

-- Step 5: Deploy code that only uses new column
-- (Application code deployment)

-- Step 6: Drop old column
ALTER TABLE users DROP COLUMN legacy_phone;

Security Best Practices

  • Least Privilege: Grant only necessary permissions to application users
  • Bind Variables: Always use bind variables to prevent SQL injection
  • Secure Credentials: Never hardcode credentials; use environment variables or secrets managers
  • Encrypted Connections: Enable TLS/SSL for network traffic
  • Audit Critical Operations: Enable auditing for sensitive data access
  • Row-Level Security: Implement row-level security policies for multi-tenant systems

Key Topics:

  • Connection Management: Connection pooling (min/max/increment), proper resource closing, timeout configuration
  • SQL Query Optimization: Bind variables (SQL injection prevention), efficient fetching (arraysize), column selection, indexes, JOIN optimization
  • Transaction Management: Explicit transactions (commit/rollback), short transaction duration, savepoints for complex operations
  • Security Best Practices: Least privilege principle, secure credential storage (environment variables, Oracle Wallet), encrypted connections (TLS/SSL), auditing
  • Performance Tuning: Execution plan analysis (EXPLAIN PLAN), bulk operations (executemany), table partitioning, statistics gathering, result caching
  • Error Handling: Specific exception handling (IntegrityError, DatabaseError), detailed logging, retry logic for transient errors
  • Data Types: Appropriate type selection (NUMBER, VARCHAR2, DATE, TIMESTAMP, CLOB, BLOB), character encoding (UTF-8), LOBs for large data
  • Monitoring: Connection pool health, query performance tracking (v$sql), database health metrics

Critical Practices:

  • Always use bind variables (prevents SQL injection, enables caching)
  • Use connection pooling (dramatically improves performance)
  • Close resources properly with context managers
  • Never hardcode credentials (security fundamental)
  • Use explicit transactions for data consistency
  • Grant least privileges (limits security exposure)

Common Pitfalls:

  • String concatenation in SQL (SQL injection risk)
  • Not closing connections (resource leaks)
  • Fetching rows one at a time (performance issue)
  • Using SELECT * (inefficient data transfer)
  • Long-running transactions (lock contention)
  • Over-privileged database users (security risk)

🧠 CORTEX Usage

How CORTEX could leverage database best practices for its knowledge storage and operations.

CORTEX Database Architecture

CORTEX could use a hybrid approach combining SQL and NoSQL:

  • PostgreSQL: Structured data (orchestration state, user sessions, configuration)
  • MongoDB: Knowledge files, conversation history, flexible schemas
  • Redis: Caching, session state, rate limiting
  • Elasticsearch: Full-text search across knowledge base

Oracle Best Practices Applied to CORTEX

  • Connection Pooling: Pool size 10-50 for orchestrator database connections
  • Bind Variables: All queries use bind variables to prevent SQL injection
  • Transactions: Atomic operations for orchestration state updates
  • Bulk Operations: executemany() for batch knowledge file indexing
  • Indexes: Indexes on knowledge_file_id, category, tags for fast queries
  • Security: Separate users for read-only (queries) vs read-write (orchestrators)

Knowledge Base Schema Design

-- Knowledge files table
CREATE TABLE knowledge_files (
    id VARCHAR2(100) PRIMARY KEY,
    category VARCHAR2(50) NOT NULL,
    file_path VARCHAR2(500) NOT NULL,
    content CLOB NOT NULL,
    metadata JSON,
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP,
    updated_at TIMESTAMP DEFAULT SYSTIMESTAMP
);

CREATE INDEX idx_kf_category ON knowledge_files(category);
CREATE INDEX idx_kf_updated ON knowledge_files(updated_at);

-- Knowledge tags (many-to-many)
CREATE TABLE knowledge_tags (
    file_id VARCHAR2(100),
    tag VARCHAR2(50),
    PRIMARY KEY (file_id, tag),
    FOREIGN KEY (file_id) REFERENCES knowledge_files(id) ON DELETE CASCADE
);

CREATE INDEX idx_kt_tag ON knowledge_tags(tag);

-- Orchestration history
CREATE TABLE orchestration_runs (
    run_id VARCHAR2(50) PRIMARY KEY,
    orchestrator VARCHAR2(100) NOT NULL,
    status VARCHAR2(20) NOT NULL,
    started_at TIMESTAMP NOT NULL,
    completed_at TIMESTAMP,
    input_data JSON,
    output_data JSON,
    error_message CLOB
);

CREATE INDEX idx_or_status ON orchestration_runs(status, started_at);
