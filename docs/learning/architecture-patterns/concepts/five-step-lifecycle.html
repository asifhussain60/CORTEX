The Five-Step Lifecycle.

Every CORTEX orchestrator — regardless of domain or specialisation — follows the same five phases: Prepare → Govern → Execute → Validate → Close. This consistency is what makes every operation auditable, predictable, and safe to roll back.

~14 min read 5 phases 8 primitives
Real-World Analogy

Think of a Surgical Procedure

No surgeon walks into an operating theatre and starts cutting. There is a mandated sequence: pre-op checks, ethical sign-off, the operation, recovery monitoring, and formal discharge. Skip any step and patient safety is at risk. CORTEX applies the same discipline to every code-touching operation.

What Happens in Each Phase

Each phase is implemented via declarative YAML primitive templates — not inline procedural code in the orchestrator itself.

Phase 1
Prepare

Emits AC_START — the audit trail begins. Creates a git checkpoint for safe rollback. Displays the Definition of Ready (DoR) card so the operator sees exactly what work is scoped.

primitives/execution/ac-marker-emit.yaml primitives/execution/git-checkpoint.yaml primitives/governance/dor-display.yaml
AC_START("AC-IMPL-001") # timestamp + orchestrator + operation git_checkpoint("before-implement-user-auth") display_dor(scope, acceptance_criteria)
Phase 2
Govern

Runs the Holistic Validation Gate (CORE-048) — checks all 60 governance YAMLs for existing P0/P1 violations before a single line of code is touched. If violations exist, execution is blocked. Also opens the Sweep Catalogue to track every issue found this session.

primitives/governance/holistic-validation-gate.yaml primitives/governance/challenge-gate.yaml primitives/governance/sweep-catalogue-open.yaml
# CORE-048 Holistic Validation Gate violations = scan_all_governance_rules() if violations.p0_count > 0: raise GovernanceBlockError( f"❌ {violations.p0_count} P0 violations — fix before proceeding" )
Phase 3
Execute

The orchestrator performs its specialised work — TDD cycle, code implementation, audit scan, or refactor sweep. For IMPLEMENT/FIX/REFACTOR, this is the TDD red-green-refactor loop. The work is driven by declarative workflow YAML templates, not inline orchestrator logic.

sdlc/implement-workflow.yaml tdd/tdd-workflow.yaml audit/audit-fix-pipeline.yaml
# TDD inner loop (CORE-008 — tests before implementation) write_failing_test(acceptance_criteria) # RED implement_minimal_code(to_pass_test) # GREEN refactor(maintain_green) # REFACTOR
Phase 4
Validate

Runs the Convergence Loop (CORE-068): detect → fix → rescan until p0_count == 0 AND p1_count == 0. Maximum 3 cycles before escalation. This is not a single pass — it loops until the workspace is provably clean.

primitives/validation/detect-fix-rescan-loop.yaml
# CORE-068 Universal Convergence Gate cycle = 0 while cycle < 3: violations = detect() if violations.p0 == 0 and violations.p1 == 0: break # ✅ clean fix(violations) cycle += 1 else: raise ConvergenceError("Max cycles reached")
Phase 5
Close

Emits AC_COMPLETE with timing and success/failure status. Closes the Sweep Catalogue — verifying CORE-064 (every issue catalogued at Govern has been resolved). Emits a URS reinforcement signal for the learning system.

primitives/execution/ac-marker-emit.yaml primitives/governance/sweep-catalogue-close.yaml
sweep_catalogue_close(assert_all_closed=True) # CORE-064 AC_COMPLETE("AC-IMPL-001", status="✅", ms=1247) urs_emit(signal_type="MILD_REWARD", scope="implement")
AC Marker Format Standard

The Audit Trail

Every operation generates a pair of AC markers persisted to SQLite. No orphaned AC_START without a matching AC_COMPLETE is allowed — EnforcementOrchestrator blocks the commit.

Marker Anatomy
# Format: AC-{DOMAIN}-{SEQUENCE} AC-P89-001 # Phase 89, operation 1 AC-IMPL-042 # IMPLEMENT domain, op 42 AC-CORE-007 # CORE domain, op 7 AC-AUDIT-001 # AUDIT domain, op 1 # Domain is the phase or module identifier # Sequence is zero-padded 3-digit counter
