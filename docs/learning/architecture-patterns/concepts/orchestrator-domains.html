The 14 Orchestrator
Domains.

CORTEX organises 296 orchestrator files into 14 specialised domains — each with a clearly bounded responsibility, zero cross-domain direct coupling, and a unified protocol contract that makes any orchestrator discoverable and testable in isolation.

~12 min read 296 orchestrators 14 domains
Real-World Analogy

Think of a Modern Hospital

A hospital doesn't have one doctor who does everything. It has departments — each with a clear speciality, its own team, but all coordinated through the same patient record system. CORTEX works the same way.

🏥
Hospital ER
core domain

Emergency intake, routing, and triage. In CORTEX this is core/ — 132 files handling IntentRouter, MasterOrchestrator, and TDDOrchestrator. Every request starts here.

🔬
Diagnostic Lab
intelligence domain

Runs tests, produces results, feeds back to clinicians. CORTEX's intelligence/ — 16 files — runs LENS analysis, RCA Engine, and URS learning signals.

📋
Administration
governance domain

Records, compliance, policies. CORTEX's validation/ — 12 files — enforces CORE rules, pre-commit gates, and governance YAMLs at every stage.

💊
Pharmacy & Support
support domain

Fulfils prescriptions from clinicians. CORTEX's support/ — 54 files — runs the debugger, RCA engine, and multi-stack debug pipeline on demand.

🫀
ICU / Monitoring
health domain

Continuous patient monitoring with 22 endpoints. CORTEX's health/ — 27 files — runs HealthOrchestrator and VacuumOrchestrator to keep the system clean.

🧬
Specialist Wards
domain orchestrators

Cardiology, oncology, neurology — each ward handles specific conditions. CORTEX's domain/ — 29 files — handles Git, C#, TypeScript, and frontend stacks.

The hospital coordinator (MasterOrchestrator) knows which department to send you to — but never does their job for them.

Directory Structure

Every domain maps to a subdirectory under cortex/orchestrators/. Drop a file in the right folder — CORTEX discovers it at startup via the IOrchestrator protocol.

cortex/orchestrators/ ├─ core/ 132 files ← IntentRouter, MasterOrch, TDDOrch, EnforcementOrch ├─ support/ 54 files ← DebuggerOrch, MarkerInjectionEngine, AutoCleanup ├─ health/ 27 files ← HealthOrchestrator, VacuumOrchestrator (8-stage) ├─ domain/ 29 files ← GitOrch, C# refactor/security, TypeScript, Frontend ├─ intelligence/ 16 files ← LENS, IntelligenceFacade, RCA Engine, KAL ├─ validation/ 12 files ← GovernanceChecker, ContractValidator, SweepCatalogue ├─ persona/ 6 files ← Role-based response adapters ├─ workflow/ 6 files ← WorkflowComposer, template execution engine ├─ response/ 5 files ← ResponseFormatter, ProgressRenderer ├─ git/ 4 files ← GitOrchestrator, CheckpointInjector, RollbackManager ├─ synthesis/ 1 file ← KnowledgeSynthesisOrchestrator ├─ registry/ 1 file ← OrchestratorRegistry (auto-discover at boot) ├─ tools/ 1 file ← MCP tool bridge orchestrator └─ _top_level/ 2 files ← Bootstrap, session init orchestrators
Protocol Contract

The IOrchestrator Protocol

Every orchestrator across all 14 domains satisfies the same protocol. Declare your intent keywords, place your file in the right domain folder, and CORTEX's registry auto-discovers it at startup — no manual wiring required.

Minimal Implementation
from cortex.core import OrchestratorProtocolMixin class MyOrchestrator(OrchestratorProtocolMixin): @property def intent_keywords(self) -> list[str]: return ["implement", "build", "create"] async def execute(self, ctx) -> OrchestratorResult: AC_START("AC-MY-001") # ... do specialised work ... return AC_COMPLETE("✅")
What the Registry Does at Boot
# cortex/orchestrators/registry/ # orchestrator_registry.py for module in glob("orchestrators/**/*.py"): cls = import_class(module) if isinstance(cls, OrchestratorProtocolMixin): for kw in cls.intent_keywords: registry[kw] = cls # IntentRouter queries registry at runtime: handler = registry.get(intent_type) await handler.execute(context)

How Domains Communicate

Domains never call each other directly. All inter-domain communication routes through MasterOrchestrator — the single coordination point that enforces the five-step lifecycle for every request.

# ✅ CORRECT — routed through MasterOrchestrator class TDDOrchestrator(OrchestratorProtocolMixin): async def execute(self, ctx): # Needs health check — asks MasterOrch to route it health = await self.master.route(IntentType.HEALTH, ctx) if health.passed: return await self.run_tdd_cycle(ctx) # ❌ FORBIDDEN — direct domain coupling class TDDOrchestrator: def __init__(self): self.health = HealthOrchestrator() # 🚫 creates direct coupling
Why

Enables every orchestrator to be tested in isolation with a mock MasterOrchestrator — no test dependency on 295 other files.

How it's enforced

EnforcementOrchestrator runs a pre-commit import graph scan. Any direct cross-domain import is a P0 governance violation — commit is blocked.

Benefit

You can add an entirely new domain without touching any existing orchestrator. The registry auto-discovers it at next boot.
