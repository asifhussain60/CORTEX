At their core, most language models rely on prediction. Imagine if it's a model, the fragment. The weather today is very, and then leave a blank. The model will look at all the text it saw during training and calculate which next word is most likely. In our example, sunny often has the highest probability. When we talk about probabilities, we're talking about numbers. For the model, each possible word or piece of a word carries a score. That score comes from a pattern it learned in its training data. And here is a key term. In the world of language models, we call each word or sometimes just a part of a word a token. What makes language models really impressive is their ability to adjust based on context. Now imagine we add some extra context. I live in Antarctica. Suddenly the whole prediction shifts. Now over the past decade, these models have evolved dramatically, leading to what we now call large language models, or LLMs. But what exactly makes the language model large? You can train a small language model on a laptop or a single GPU, but training an LLM, that requires a fleet of GPUs running in parallel across compute clusters and sometimes weeks of continuous processing. Then there is the question of capability. Small language models are great at narrow tasks like sentiment analysis or spam filtering, but LLMs go much further. They can perform complex reasoning, generate human‑like text, summarize long documents or even write functioning code. Finally, there is scope. Traditional models are often task‑specific. You build one model for one job, but LLMs are general purpose. With the right prompt, the same model can do hundreds of different things and do them well. Agentic AI

By now, we're all pretty familiar with AI systems like ChatGPT or Claude. They're pretty straightforward. You type in a prompt, and they give you a response. It's a one‑shot interaction, input in, answer out, simple and useful. The next step in the evolution of AI systems was the idea of workflows. This is great when you want to chain multiple actions together, like summarizing a document, translating it, and generating a response, all in one go. But now, we've arrived at something even more powerful, AI agents. Agents work differently. Just like before, everything starts with an input to a language model. But instead of just giving you an answer, the model can actually take actions in the environment. Once the action is taken, the agent receives feedback from the environment, and here is where things get interesting. The agent has to decide what to do next. It might ask you for a clarifying question. It might hit an error and stop, or it might determine that the task is done. But if the job's not finished, it doesn't just quit. It uses the feedback to refine its strategy and tries again. This loop continues until the agent reaches the desired state or goal. Think of agents as smart workers who first perceive their environment, gathering all necessary information. The reason through this data using LLMs, making informed decisions about what needs to be done. Then they act, executing their tasks independently. Finally, they learn from the results, improving their performance over time. These characteristics are sometimes simplified into three core actions, plan, act, and adapt. This means that once the agent is given a task, it can perform it on its own without constant human input. Then they are proactive. Agents don't just wait around for instructions. They can take initiative and decide when to act. Next, AI agents are goal‑oriented. They're not just completing steps. They're working towards a specific outcome. And finally, AI agents should be designed to collaborate. That means they can interact with humans, other agents or systems to coordinate and solve problems more effectively. Now, most AI agents are built using the three main components. First, there is the reasoning engine, usually powered by a large language model. This is the brain of the agent. It interprets input, makes decisions, and determines the next step. Second, we have memory. Agents need to remember things, not just within a single conversation, but across multiple interactions and actions. And third, we have tools. Tools are the actions the agent is allowed to perform, like making an API call, running a function, sending an email or querying a database.

MCP
Let's explore something called the MCP. It might sound a bit technical, but don't worry, we'll break it down step by step. The best way to understand MCP is to start with something we've already seen, tools. In the last video, we talked about how LLMs use tools to take action. Let's take file management as an example. It could have one tool that creates a file, another that updates it, and another that deletes it. Same goes for directory. Maybe you've got tools to create, list or remove folders. Now here's the catch. Tools are usually built for a specific agent. That means they are not very reusable. You can just plug in them into another system and expect everything to work. This is where Model Context Protocol, or MCP for short, starts to shine. MCP is an open protocol designed to standardize how applications provide context and tools to LLMs. In other words, it gives us a consistent structured way to tell the LLM what action it can take and how to take them regardless of the underlying system. So how does this help with our tool problem? Well, instead of managing individual tools for every little task, we can group them by type and wrap them inside an MCP server. Think of the MCP server as an interface between the LLM and a data source. In our file management example, the file system itself becomes the data source, and the MCP server provides a unified set of actions that the LLM can use to interact with. And it doesn't stop there. We can have different MCP servers for different types of data sources. One might expose a PostgreSQL database. Another might give access to a Git repository. The LLM doesn't have to know the low‑level details. It just talks to the MCP server and picks the right tool for the job based on what it's trying to accomplish. Now, I have a small confession to make. Earlier, I said the LLM talks directly to the MCP server, but that's not exactly true. In reality, the LLM doesn't call the server on its own. It needs something in between the MCP client. The MCP client is the PC responsible for calling MCP servers on behalf of the LLM. It acts as a bridge between the model and the environment. And where does this client live? Well, it runs inside what we call an MCP host. An MCP host is essentially the environment that houses the client library. It could be anything, an application like Claude for Desktop, your favorite IDE or even an instance of an agentic framework you're working with. The host uses the MCP client to pull in relevant context from one or more MCP servers and then feeds that context into the LLM. If you're curious to learn more about MCP, the best place to start is modelcontextprotocol.io. You'll find all the specs, documentation, and even guides on how to build your own MCP server. And here is the cool part. Chances are someone in the community has already built an MCP server for your use case. So definitely check out the GitHub repo shared by the community. It's a gold mine of inspiration and practical code.
RAG
If you've ever hit the context limit of an LLM or needed to give it access to fresh or private data, RAG is your new best friend. It's a clever method that combines the reasoning power of language model with external knowledge. Here's the thing, every language model is trained on a specific dataset, and that training only goes up to a certain point in time. This point is called the cutoff time. Anything that happens after that, the model has no idea. You could ask it about events from last week, and it will just shrug. This is exactly where retrieval‑augmented generation, or RAG, comes in. RAG is a technique that allows LLMs to pull in new or external information at runtime. This helps reduce hallucinations, improve accuracy, and makes the model far more useful in real‑world scenarios. Let's look at an example using Claude. If we ask it something like, who are the top 5 players in the WTA rankings right now?, Claude tries to help, but it admits it doesn't know. Its training cutoff was January 2025. So it can only give us the rankings from back then. Helpful, but not exactly current. Now let's try the same prompt again, but this time we enable RAG using web search. There are many forms of RAG, some systems retrieved from files, other from private databases, and in this case, we're using the web. We hit Send, and Claude starts browsing online resources for updated information. After a few seconds, we get a response. This time, Claude was able to retrieve the name of the current #1 WTA player. It didn't get the full top 5, and it's clearly making progress by pulling in external knowledge. With a few more follow‑ups or refined prompts, we could probably complete the list. So, what exactly happened behind the scenes? Well, we started by sending a prompt to the LLM, but the model couldn't answer it on its own because it didn't have access to the latest data. It was trained up to its cutoff time, and anything beyond that is outside its knowledge. So, it told us it didn't know and signaled the need to look elsewhere. That's when the RAG mechanism kicked in. It detected that the LLM needed external information, and it went out to query additional data sources, in this case, the web. Depending on the setup, RAG could also search files, documents, databases or APIs. Once it gathered the relevant data, the system passed that information back into the model, usually by injecting it into the prompt in a structured way. The LLM then uses the fresh context to generate a more accurate, relevant response, and that's what we finally saw as the output. However, RAG isn't completely worry‑free. As powerful as it is, it does come with a few challenges you'll need to keep in mind. One major issue is the risk of retrieving irrelevant data. Just because the system finds something doesn't mean it's the right something. If the retrieval step pulls in unrelated or low‑quality content, the LLM might generate an answer that sounds confident, but is actually off topic or incorrect. Another challenge comes from long and complex documents. Parsing dense PDFs, legal contracts or technical reports isn't easy. Chunking the information properly, keeping context intact, and choosing the most relevant parts to fit into the model, that's all part of the RAG design puzzle. And finally, there is the issue of security and access control. When the RAG system are retrieving data from internal sources like databases, document stores or APIs, we need to make sure that the agent respects permissions. Just because a user asks for something doesn't mean they should have access to it. Managing roles, authentication, and data sensitivity becomes critical when you're mixing AI with private or proprietary content. Before we wrap up this video, there is one more concept we need to cover, and that's vector databases. This plays a big role in most RAG systems. And chances are, you've already used one without even realizing it. Many vendors today are indexing data into vector databases to power search, retrieval, and context injection for LLMs. So, how do they work? Let's simplify it with an example. Imagine you have three images, each representing a medal, a gold medal, a silver medal, and a bronze medal. Now to a human, we can easily tell them apart by shape, color, shininess, material or weight. Vector databases operate in a similar way. They store and compare data based on dimensions like this. Each item, in this case, each image is converted into a vector embedding. A vector is just an array of numbers, and then embedding is a mathematical representation of that item across various dimensions. These embeddings are generated using machine learning models, and they can help capture the essence of the content, whether it's an image, a sentence or an entire document. So for our medals, the gold one might score high on yellow, shiny, and weight, while the bronze one scores differently. Now if we ask an LLM to find something that's round, yellow, and shiny, it will search the vector database for the closest match and retrieve the gold medal. Of course, this is a very, very simplified version. In real‑world use, embeddings have often hundreds or thousands of dimensions. And instead of medals, we're dealing with chunks of text, code, images or documents. But the core idea is the same, store meaning in numbers and find the closest match based on the meaning.
Data Security and Compliance
As exciting as AI is, we can't ignore the responsibilities that comes with using it, especially when dealing with sensitive information. Whether you're building with LLMs, deploying AI agents or integrating RAG systems, protecting data and respecting compliance standards isn't optional, it's mandatory. When working with AI agents, there are two major risks we need to keep in mind. The first one is autonomous access. This new world of agentic AI has also opened the world to an entirely new class of exploits. Because agents can now take actions and operate autonomously across systems, they become a tempting target for attackers. For example, shortly after the GitHub MCP server was developed, researchers from Invariant Labs discovered a serious vulnerability. The exploit allowed an agent to access private repositories, inject malicious code, and even leak sensitive data, all without any direct user command. Just imagine an agent that's been given too much power and not enough oversight. It becomes a security incident waiting to happen. These kinds of threats aren't theoretical anymore. The second major risk is the non‑compliant behavior. As impressive as AI agents can be, they don't always behave predictably. There have been numerous reports of agents going off script performing actions where they never explicitly told to do. In some cases, agents have deleted important project files. In more extreme cases, they even attempted to wipe entire directories or critical parts of the operating system. One interesting development we're starting to see is the rise of AI regulations. As AI systems become more capable and more integrated into critical workflows, governments and institutions are stepping in to define clear boundaries. A great example of this is the EU AI Act. It's already been adopted and will be fully enforced by August 2026. This law categorizes AI systems based on the risk level, and each level comes with different obligations and restrictions. At the bottom of the scale, we have minimal risk systems. These are considered safe and don't require regulation, things like spam filters or basic recommendation engines. One step up, we have limited risk systems where some transparency is required, like making sure users know they are interacting with an AI. Then we get to the high‑risk systems. These are heavily regulated because they operate in sensitive domains like healthcare, finance or law enforcement. Developers of these systems must meet strict requirements around safety, data governance, and human oversight. And finally, there are unacceptable risk systems. These are AI systems that are outright forbidden. For example, systems that involve social scoring or manipulative behavioral tracking are banned under the EU AI Act.

Multi-agent Systems
Up until now, we've mostly focused on single‑agent scenarios where one agent handles everything from reasoning to execution. But as tasks grow in complexity, coordination becomes the most important thing. That's where multi‑agent systems come in. They allow agents to collaborate, communicate, and divide work just like human teams do in real‑world projects. There are a few common conversational patterns we encounter when designing multi‑agent systems. The first and simplest pattern is the two‑agent chat. This is where two agents engage in a back‑and‑forth conversation to solve a task together. It's straightforward and works well for simple scenarios where just a bit of coordination is needed. Next, we have sequential chats. Think of this like a content publishing pipeline. First, a content writer agent creates the initial draft. Then the output is passed to an SEO optimizer agent. After that, it moves on to an image generator and finally to a publisher agent. Each agent completes each specific task before handing off to the next one, maintaining a clear and controlled workflow. Then, there is the group chat pattern, which is great for handling parallel tasks. Imagine a project management scenario. You could have a timeline‑planning agent, a budget agent, a resource management agent, and the risk assessment agent all working at the same time focusing on their specific areas. A group chat manager agent acts as the orchestrator, collecting input from everyone and ensuring that all perspectives are considered before moving forward. Finally, there's the nested chat pattern, which is perfect for hierarchical tasks. Let's take a social media campaign as an example. At the top, there is a campaign manager agent overseeing two separate teams. The production team includes a content creator agent and a hashtag optimizer agent, while the strategy team might have a trend analyzer agent and an audience insights agent. Each team works independently to their part of the campaign, but everything rolls up to the campaign manager for final coordination. Each of these patterns has its own strengths. Two‑agent chats are great for simple interactions. Sequential chats maintain clear task order. Group chats allow for parallel processing, and nested chats are ideal for managing complex, layered projects.
Agent Observability and Evaluation
Building AI agents is exciting, but once they're running in production, you need to know what they're doing, how they're performing, and whether they're making good decisions. Without proper observability and evaluation, you're basically flying blind. Before we dive deeper, I want to quickly make a distinction between two terms that often come up when analyzing AI agents, testing and evaluation. Let's start with testing. Testing is all about checking the output. For example, let's say we have a prompt that asks an AI agent to generate some code. By testing the agent, we're simply verifying whether the output is correct. Does the code compile? Does it meet the requirements? And is it what we actually asked for? Testing focuses on the final result, and while that's useful, it doesn't always tell the whole story. That brings us to evaluation. Evaluation goes much deeper than looking at the output. It's about assessing the entire thinking process the agent went through to produce that output. This includes looking at internal prompts, analyzing how many tokens were consumed, and checking whether the agent used memory effectively or called the right tools at the right time. There are a few key ways we can evaluate an AI agent. The simplest is human‑in‑the‑loop evaluation. Here, we pause the agent after each step or after every few steps and checking if it's on the right track. It's a hands‑on way to guide and monitor the agent during execution. Another option is to use another LLM‑as‑a‑judge. This lets a separate model evaluate the agent's output or reasoning, giving you scalable feedback without constant human involvement. Then, there is task completion evaluation where we look at metrics across many runs like success rate, execution time, and tool usage to see how the agent performs over time. And for deeper insights, we have observability frameworks. One popular open‑source option is Opik from Comet, which focuses on tracing the reasoning process step by step. Another powerful framework is Langfuse, which provides detailed analytics, prompts tracking, and decision flow visualizations, all essentials for debugging and improving your AI agents.
