Root Cause Analysis Engine

Four structured methodologies — auto-selected by failure category. Each completed analysis generates an ADVISORY prevention rule persisted in SQLite.

Five-Whys
Category: TECHNOLOGY
Iterative questioning — peel back layers until the root cause emerges. Best for technical failures with clear causal chains. Generates a why-chain of 5 levels with the root cause at the terminal node.
Fishbone (Ishikawa)
Category: PROCESS / PEOPLE
6-category cause analysis — Method, Machine, Material, Measurement, Man, Environment. Best for systemic issues with multiple contributing factors.
Fault Tree
Manual override
Boolean logic tree — AND/OR gates model how combinations of failures lead to the top event. Best for complex systems where multiple conditions must coincide.
Causal Chain
Category: DATA
Linear cause-effect sequence from initiating event to final impact. Best for data pipeline failures and cascading errors across boundaries.
# RCA via cortex_learning MCP tool cortex_learning op=rca rca_action=analyze \ failure_id="PROD-2026-0342" \ symptom="API P99 latency spike to 800ms" \ category=TECHNOLOGY # → Five-Whys auto-selected # → PreventionRule(ADVISORY) persisted to rca_store.db cortex_learning op=rca rca_action=query # → Surfaces matching prevention rules before next fix

OpenTelemetry Distributed Tracing

Request-scoped trace context propagated across orchestrator chains, MCP tool calls, and agent collaborations. OTLP export to Jaeger/Tempo/Honeycomb.

Span Attributes

  • ✦ intent.mode — IMPLEMENT, FIX, AUDIT, etc.
  • ✦ router.decision — orchestrator routing path
  • ✦ mcp.tool — MCP tool name + result status
  • ✦ agent.name — health agent identifier
  • ✦ ac.marker — AC_START / AC_COMPLETE

Trace Features

  • ✦ Parent-child span relationships for agent chains
  • ✦ Performance overhead tracking (<10ms per request)
  • ✦ OTLP/HTTP export via OTEL_EXPORTER_OTLP_ENDPOINT
  • ✦ Jaeger, Zipkin, Tempo, Honeycomb compatible
  • ✦ Fire-and-forget — never raises into caller code

Self-Managing Infrastructure

CORTEX Operates Itself.
SREs Operate What Matters.

Seven SQLite databases with automatic 30-day retention and VACUUM cycles. Twenty-two health endpoints wired to structured probes. WAL mode enforced by governance rule, not convention. The platform's own reliability requirements are met continuously by the platform itself — without a runbook, a cron job, or an SRE on call for framework maintenance.

Data Hygiene Without Intervention

30-day retention enforced, orphaned records pruned, all 7 databases VACUUMed on a single command: refresh_prompt_suite.py --db-cleanup. No custom scripts. No scheduled tasks to maintain.

22 Health Endpoints, Zero Manual Checks

Every orchestrator domain exposes structured health probes. One command — /health — surfaces pass/fail status across the entire framework. Prometheus scrape config is included. Grafana dashboards ship with the repo.

Extensions Register Themselves

New orchestrators added by the engineering team auto-register their health probes via the IOrchestrator protocol. SREs don't update dashboards for new services — the observability surface grows with the system.
