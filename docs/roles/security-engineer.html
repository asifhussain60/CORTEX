Secure Coding Practices

Comprehensive best practices enforced at code review and pre-commit — covering input validation, authentication, authorization, secrets management, and API security.

🛡️

Input Validation

  • ✦ Validate & sanitize all external inputs
  • ✦ Whitelist approach — reject unrecognized
  • ✦ Parameterized queries — never f-strings
🔐

Authentication

  • ✦ Hash with bcrypt/argon2 — never SHA256
  • ✦ OAuth2 + PKCE + MFA for privileged ops
  • ✦ Short-lived JWTs (15min access, 7d refresh)
🔒

Authorization

  • ✦ RBAC + principle of least privilege
  • ✦ Authorize every request server-side
  • ✦ PCI-DSS scope isolation for card data
🔑

Secrets Management

  • ✦ Never hardcode secrets or API keys
  • ✦ Environment variables or Vault/SSM
  • ✦ Rotate credentials quarterly
⚠️

Error Handling

  • ✦ Never expose stack traces to users
  • ✦ Log with correlation IDs — no PII
  • ✦ Generic error messages to clients
🌐

API Security

  • ✦ Rate limiting — 100 req/min unauthed
  • ✦ Strict CORS — whitelist known origins
  • ✦ API versioning with 6-month deprecation

Continuous Security Posture

Security Rules Self-Enforce.
No Scheduling Required.

OWASP gates don't wait for a scheduled audit. Secret detection doesn't wait for a policy review cycle. STRIDE/DREAD threat modelling runs as code touches the pipeline. Your security posture is a continuous invariant maintained by the framework — not a periodic exercise owned by a single engineer.

Controls That Never Clock Off

5-layer defence — pre-commit secrets, SAST, OWASP gate, supply chain validation, compliance audit — runs on every change, every time. Controls don't degrade between security reviews because they aren't owned by the review cycle.

Tamper-Evident by Architecture

Every orchestrator action writes to a tamper-evident audit chain in SQLite — WAL mode enforced by governance rule. Security Engineers don't configure log integrity; it's a non-negotiable structural property of the framework.

Threats Get Remembered

The RCA Memory Engine classifies security findings, generates prevention rules, and surfaces prior threat patterns before each code-modifying operation. Vulnerability classes that appeared once don't silently re-emerge — CORTEX has already seen them.
