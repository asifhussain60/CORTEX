The Three Laws of TDD

Kent Beck's three laws are not guidelines in CORTEX — they are governance rules enforced by CORE-008 at every stage.

🔴
RED
Write a failing test first. No production code until you have a test that fails.
🟢
GREEN
Write only enough production code to make the failing test pass. Nothing more.
🔵
REFACTOR
Improve code structure. Tests must stay green. Commit on green via GitOrchestrator.
# CORTEX TDD Workflow (CORE-008 enforced) AC_START("AC-TDD-001") 1. write_failing_test() # RED — test MUST fail 2. implement_minimum() # GREEN — just enough code 3. refactor_safely() # REFACTOR — tests stay green 4. git_checkpoint() # GitOrchestrator auto-commit AC_COMPLETE("✅ 3 tests GREEN")

Test Strategy by Scenario

Every change type has a prescribed test strategy — from new features to security patches. No guesswork.

🚀

New Feature

  • ✦ Unit tests for every public method
  • ✦ Integration test for each API + DB interaction
  • ✦ Golden test after 2 consecutive green CI runs
  • ✦ Auth boundary test (401 for unauthenticated)
🐛

Bug Fix

  • ✦ Failing test reproducing exact bug FIRST
  • ✦ Regression test — never delete
  • ✦ CORE-064: sweep entire codebase for same pattern
♻️

Refactoring

  • ✦ Freeze existing tests as contract BEFORE changes
  • ✦ Add property-based tests for boundaries
  • ✦ Coverage must not drop below entry baseline
🌐

API Endpoint

  • ✦ OpenAPI schema test (request/response shape)
  • ✦ 401 + 403 + 200 auth tests
  • ✦ All error code paths tested
  • ✦ P99 latency: <200ms read, <500ms write
🗄️

Database

  • ✦ Transaction isolation (rolled back per test)
  • ✦ Migration forward AND rollback paths
  • ✦ No full-scan queries on large tables
🔒

Security Patch

  • ✦ Injection tests — SQL/NoSQL mandatory
  • ✦ Auth bypass with expired/forged/missing JWT
  • ✦ No secrets in logs, responses, or errors

Automated Code Review Gates

The Code Review Orchestrator runs five automated review passes — structural, security, governance, test-coverage, and style. P0 blocks merge. P1 must be fixed in the PR. P2 recommended. P3 tracked as tech debt. Enforced by ruff, mypy, bandit, and pytest.

P0 — BLOCKING
✦ No hardcoded secrets (CORE-028)
✦ All user input sanitized
✦ SQL/command injection impossible
✦ Auth enforced on every protected route
✦ Transactions atomic — no partial writes
P1 — REQUIRED
✦ No functions > 50 lines (SOLID)
✦ No class > 300 lines (SRP)
✦ Cyclomatic complexity ≤ 10
✦ Type hints + docstrings on public APIs
✦ No bare except — catch specific exceptions
P2 — RECOMMENDED
✦ No N+1 query patterns
✦ No blocking I/O in async context
✦ Variable names describe intent
✦ Magic numbers → named constants
P3 — ADVISORY
✦ README updated if behaviour changes
✦ Architecture decisions recorded (ADR)
✦ Runbook updated if ops behaviour changes

Autonomous Quality Governance

Quality Gates Enforce Themselves.
You Set the Standard.

CORTEX enforces quality continuously — no manual check-ins, no process championing, no reminders. TDD laws block non-compliant code before it merges. The 8-dimension quality scorer runs on every diff. Convergence loops rescan until P0 and P1 counts hit zero. QEs define what quality means; CORTEX enforces it without being asked.

Tests Exist Before Code Does

CORE-008 is not a team agreement — it's an architectural constraint. TDD enforcement blocks work that skips the test-first contract. The gate doesn't need a QE present to fire; it fires on every save.

Issues Resolve Until Zero Remain

The detect→fix→rescan convergence loop (CORE-068) doesn't stop after one pass. It cycles until P0 and P1 counts are zero. Quality assurance is a guarantee, not a best-effort.

Defects Don't Repeat

The RCA Memory Engine records root causes and generates prevention rules after every significant failure. The same bug class doesn't require a QE retrospective the second time — CORTEX already knows why it happened.
