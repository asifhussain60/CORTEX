Executive Summary

Holistic Code Discovery is CORTEX's search-before-create system that prevents code duplication at creation time. The HOLISTIC_CODE_DISCOVERY_ENFORCEMENT SKULL rule blocks any new implementation until the entire codebase has been searched for existing solutions. This eliminates the common problem of duplicate functions with different names (e.g., parse_config, load_config, read_config) that plague large codebases.

The Problem: Accidental Duplication

Without discovery enforcement, this happens: 

# Developer A creates:
def load_yaml_config(path):
    with open(path) as f:
        return yaml.safe_load(f)

# Developer B creates (same functionality, different name):
def parse_config_file(filepath):
    return yaml.safe_load(open(filepath))

# Developer C creates (same again!):
def read_configuration(config_path):
    with open(config_path) as file:
        return yaml.load(file)

Result: Three functions doing the same thing. Which one should new code use? Which is the "correct" implementation? Code reviewers catch this too late. Technical debt grows.

How Holistic Discovery Works

🧠 Step 1: Semantic Search (Intent-Based)

▼

Purpose: Find similar functionality regardless of naming

How it works:

  • Natural Language Query: Describe what you want to implement
  • Semantic Matching: AI finds code with similar intent/purpose
  • Cross-File Search: Searches entire codebase, not just current module
  • Context-Aware: Understands synonyms and related concepts

Example queries:

semantic_search("parse configuration file yaml")
semantic_search("authenticate user with token")
semantic_search("validate email address format")
semantic_search("convert markdown to html")

What it finds:

  • Functions with similar behavior
  • Classes providing related functionality
  • Utility modules with overlapping purpose
  • Documentation comments describing similar goals

🔎 Step 2: Grep Search (Pattern-Based)

▼

Purpose: Find functions/classes with similar keywords in names

How it works:

  • Regex Patterns: Search for naming patterns across codebase
  • Fast & Precise: Text-based matching for exact keyword hits
  • Case-Insensitive: Finds PascalCase, camelCase, snake_case variations
  • Multi-Language: Works across Python, C#, JavaScript, etc.

Example patterns:

grep_search("def.*config|class.*Config", isRegexp=true)
grep_search("authenticate|verify.*token", isRegexp=true)
grep_search("parse|load|read.*yaml", isRegexp=true)
grep_search("validate.*email", isRegexp=true)

What it finds:

  • Functions with keywords in names (e.g., parse_config, load_config)
  • Classes with related names (e.g., ConfigParser, ConfigLoader)
  • Variables and constants with similar naming
  • Import statements for related modules

📊 Step 3: Usage Analysis (Dependency-Based)

▼

Purpose: Understand how existing implementations are used

How it works:

  • Call Site Analysis: Finds all locations where function is called
  • Usage Patterns: Shows how callers use the function (parameters, return values)
  • Dependency Graph: Maps what depends on what
  • Impact Assessment: Helps decide reuse vs enhance vs create new

Example queries:

list_code_usages("ConfigParser")
list_code_usages("authenticate_user")
list_code_usages("parse_yaml")

What it reveals:

  • How many call sites exist (usage frequency)
  • What parameters are commonly passed
  • What modules depend on this function
  • Whether it's safe to modify (impact radius)

⚖️ Step 4: Decision Matrix

▼

Based on discovery results, CORTEX decides:

Found Exact Match → Reuse It

Existing function does exactly what you need. Link your caller to the existing implementation. No new code needed.

Found Similar → Enhance It

Existing function almost works but needs additional features. Add parameters, extend functionality, update tests. Better than creating duplicate.

Found None → Create New (Document Why)

Genuinely unique functionality. Create new function with clear documentation explaining why it's different from similar-sounding functions.

Real-World Example: Configuration Parsing

Scenario: Developer wants to implement configuration file parsing

Discovery Phase:

# Semantic search
semantic_search("parse configuration yaml file")

# Results found:
- src/config_loader.py: load_yaml_config()
- src/utils/yaml_parser.py: parse_yaml_file()
- src/core/settings.py: read_config()

# Grep search
grep_search("def.*config.*yaml|load.*yaml", isRegexp=true)

# Usage analysis
list_code_usages("load_yaml_config")
# 14 call sites found across 8 files

Decision:

load_yaml_config() in src/config_loader.py does exactly what's needed. 14 existing callers prove it's battle-tested. REUSE IT. No new function created.

✅ Result: Zero duplication. Cleaner codebase. Faster development.

SKULL Protection Rule

HOLISTIC_CODE_DISCOVERY_ENFORCEMENT

Zero-tolerance policy: Before implementing any new functionality, CORTEX MUST search the entire codebase for existing implementations. Brain Protector blocks implementation until discovery is complete.

Enforcement triggers:

  • Keywords: "implement", "create function", "add method", "new class"
  • Scope: Intent analysis, implementation phase detection
  • Validation: Semantic search + grep search + usage analysis must run
