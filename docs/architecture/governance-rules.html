Governance Rules

The 4-Tier Hierarchy Protecting CORTEX Integrity

CORTEX 6.0 uses a hierarchical governance system where rules from higher tiers override lower tiers. Tier 0 (SKULL rules) are immutable and protect core operational boundaries. These 23 rules ensure production-grade reliability, security, and maintainability.

4-Tier Governance Architecture

0
CORTEX_CORE
HIGHEST PRECEDENCE
23 SKULL rules (immutable). Core brain protection rules that define operational boundaries. These rules ALWAYS win conflicts.
1
BUSINESS_TIER_0
HIGH PRECEDENCE
Active epic requirements, business constraints, project-specific rules. Dynamic and changes per epic.
2
COMPANY_PRACTICES
MEDIUM PRECEDENCE
Engineering standards, code style guidelines, quality gates, contracts. Organization-wide practices.
3
KNOWLEDGE_PRACTICES
LOW PRECEDENCE
Learned patterns, insights, optimizations. Suggestions that improve over time.

CORE-001 BLOCKED

Incremental Autonomous Execution

ALL orchestrators MUST work in small, meaningful increments to prevent token limit errors and server failures (HTTP 502). Large monolithic operations cause catastrophic failures.

  • Operations split into <500 line increments per execution
  • Each increment independently executable
  • State persisted between increments (continuation support)
  • Token usage monitored and capped at 80% of limit
  • Autonomous mode enabled (no user prompts mid-execution)
Category orchestration_lifecycle
Priority 8
Hook pre_execution
CORE-006 BLOCKED

Setup Verification Mandatory

ALL orchestrators MUST run Phase -2 setup verification before execution. This prevents false positives and ensures dependencies are ACTUALLY complete, not just file existence.

  • Dependencies pass implementation tests
  • False positive detection runs
  • VSCode cache state checked
  • Governance compliance validated
Priority 1 (Highest)
Middleware SetupVerifier
CORE-007 BLOCKED

Teardown + REFACTOR + Commit Mandatory

ALL orchestrators MUST run Phase N+1 teardown after execution. Ensures code cleanup and atomic git commits following /cortex-git-commit pattern.

  • Whole-file REFACTOR runs (remove unused imports, orphaned code)
  • All modified files refactored
  • Git commit follows /cortex-git-commit pattern
  • Commit message includes orchestrator name + phase summary

Development Workflow

Rules enforcing test-driven development, code quality, and proper development practices. These ensure reliable, tested code enters the codebase.

CORE-008 BLOCKED

Test-Driven Development Mandatory

Tests MUST be written BEFORE implementation (RED → GREEN → REFACTOR). This prevents untested code from entering the codebase.

  • Test file exists before implementation file
  • Test fails initially (RED phase)
  • Implementation makes test pass (GREEN phase)
  • REFACTOR phase removes code smells
TDD Workflow:
✓ PASS
1. Write test_audit_logger.py → fails
2. Implement audit_logger.py → test passes
3. Refactor both files → clean code
✗ FAIL
1. Implement audit_logger.py
2. Write tests later (blocked by CORE-008)
CORE-019 BLOCKED

TDD-Master Required for All Development

ALL implementation work (planned and unplanned) MUST route through TDD-Master orchestrator. Direct coding without TDD workflow is prohibited.

  • TDD-Master invoked for all code changes
  • Evidence bundle created automatically
  • Tests written before implementation
  • Governance enforcement logged
CORE-011 BLOCKED

Python Type Hints Required

ALL Python functions and methods MUST have complete type hints for parameters and return values. Critical for autonomous code generation safety.

  • All function parameters have type hints (except self, cls)
  • All functions have return type hints (use None if no return)
  • Complex types use typing module (List, Dict, Optional, Union)
✓ PASS
def log(message: str, level: int) -> None:
✗ FAIL
def log(message, level): # Missing type hints

Architecture Integrity

Rules protecting CORTEX architecture, file organization, and structural integrity. These prevent clutter and maintain clean, navigable codebase.

CORE-009 BLOCKED

Plan Files in Designated Folders

ALL files related to epics, plans, features MUST be housed within plan folder structure. Root-level file creation DISCOURAGED unless absolutely necessary.

  • Plan artifacts in plan_folder/artifacts/
  • Analysis documents in plan_folder/analysis/
  • Progress reports in plan_folder/reports/
  • Context documents in plan_folder/context/
  • Scripts in plan_folder/scripts/
  • Tracking data in plan_folder/tracking/
  • No plan-related files in workspace root
CORE-020 BLOCKED

No Markdown in cortex-brain/

ALL knowledge files in cortex-brain/ MUST be machine-readable (YAML/JSON). Markdown is for documentation, not structured brain data.

  • Use YAML for structured data
  • Use JSON for runtime state
  • Markdown only in docs/ folder
  • Machine-parseable formats only
CORE-022 BLOCKED

Kebab-Case File Naming

Enforce kebab-case file naming with max 20 characters (excluding extension). Improves readability and cross-platform compatibility.

  • Use kebab-case: governance-rules.yaml
  • Max 20 characters (without extension)
  • No spaces, underscores, or camelCase
  • Lowercase only
✓ PASS
governance-rules.yaml
master-orchestrator.py
✗ FAIL
GovernanceRules.yaml
master_orchestrator.py

Response Formatting

Rules governing how orchestrators format output, preventing workspace clutter and ensuring concise, visual progress reporting.

CORE-002 BLOCKED

No Summary File Generation

Orchestrators MUST NOT create markdown summary files (*-summary.md, *-report.md). Executive summaries provided in chat, NOT as files.

  • No files matching: *-summary.md, *-report.md, completion-*.md
  • No root-level summary files
  • Exception: Required reports in plan_folder/reports/
  • Exception: Analysis in plan_folder/analysis/
CORE-003 BLOCKED

Visual Progress Response Format

ALL orchestrator responses MUST provide executive summaries without code snippets, using visual progress bars (█████░░░░░ style).

  • Contains executive summary section
  • NO code snippets in summary
  • Visual progress bars present
  • Shows phase completion percentage
  • Response length ≤40 lines (concise)

Portability & Security

Rules ensuring cross-platform compatibility and protecting against security vulnerabilities. Critical for production deployment.

CORE-005 BLOCKED

Path Portability Required

NEVER use hardcoded absolute paths. ALWAYS use relative paths or dynamic detection. CORTEX must work across Windows, macOS, Linux installations.

  • No hardcoded paths: /Users/username/ or C:\Users\
  • Use get_project_root() for dynamic detection
  • Use Path(__file__).resolve() for relative resolution
  • Config files use relative paths only
✓ PASS
from src.utils.project_root import get_project_root
path = get_project_root() / "cortex-brain"
✗ FAIL
path = "D:\\PROJECTS\\CORTEX\\cortex-brain"
CORE-017 BLOCKED

Governance Enforcement

ALL operations MUST enforce governance rules. Bypass attempts trigger security alerts and operation blocking. Audit trails required.

  • GovernanceMerger validates all operations
  • Bypass attempts logged as violations
  • Tier 0 rules ALWAYS enforced
  • Security team notified on violations

Quality Gates

Rules enforcing code quality validation before commit. Prevents low-quality code from entering production.

CORE-023 BLOCKED

File Type-Specific Validation

Pre-commit validation MUST check file-specific quality gates: HTML5 validation, WCAG AA compliance, YAML schema, Python linting.

  • HTML: W3C HTML5 validator, WCAG 2.1 Level AA
  • YAML: Schema validation, no duplicate keys
  • Python: Pylint, Black, isort, type checking
  • JSON: JSON schema validation, no trailing commas
