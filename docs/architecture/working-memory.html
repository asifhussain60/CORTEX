Working Memory (Tier 1)

Short-term, high-velocity state management for active orchestration

Overview

Tier 1: Working Memory is CORTEX's consciousness—what it's actively thinking about right now. This tier stores ephemeral state that changes rapidly during orchestration: active plans, current phase progress, conversation context, and agent handoff coordination.

Unlike Tier 0 (immutable rules) and Tier 2 (long-term knowledge), Tier 1 is read-write intensive with a 30-day rolling retention window. It's implemented using SQLite databases for ACID transactions and JSONL logs for append-only event streams. This enables stateful orchestration where users can say "continue" and CORTEX resumes exactly where it left off.

Storage Components

PlanningStateDB

Type: SQLite database
Location: cortex-brain/tier1/working_memory.db
Schema: plans, phases, tasks, acceptance_criteria, checkpoints
Purpose: Track plan execution state, current phase, progress bars
Retention: 30 days

ConversationDB

Type: SQLite database
Location: cortex-brain/tier1/conversations.db
Schema: sessions, messages, user_preferences, intent_history
Purpose: Enable "continue" command, track conversation context
Retention: 30 days

Event Log (JSONL)

Type: Append-only JSONL
Location: cortex-brain/tier1/event_log.jsonl
Schema: timestamp, event_type, orchestrator, metadata
Purpose: Audit trail, debugging, performance analysis
Retention: 90 days

Performance Cache

Type: In-memory dict + pickle backup
Location: cortex-brain/tier1/cache.pkl
Data: Token usage, hot paths, frequently queried knowledge
Purpose: Speed up repeated queries, reduce Tier 2 reads
Retention: Session-based

PlanningStateDB Schema

The core database for stateful plan orchestration:

plans Table

plan_id (TEXT PRIMARY KEY)
Unique identifier (UUID)
title (TEXT)
User-facing plan name
status (TEXT)
active | paused | completed | failed
current_phase (INTEGER)
0-17 (Phase -1 to Phase 15)
created_at (TIMESTAMP)
Plan creation time
plan_document_path (TEXT)
Link to markdown plan file

phases Table

Links to plans.plan_id (foreign key). Stores per-phase state:
phase_id, plan_id, phase_number, phase_name, status, tasks_total, tasks_completed, started_at, completed_at

tasks Table

Links to phases.phase_id (foreign key). Granular task tracking:
task_id, phase_id, task_description, status, assigned_agent, completed_at

Agent Coordination via Tier 1

Tier 1 acts as the message bus for agent handoffs. When Planning Agent finishes creating a plan, it writes the plan to Tier 1 with status='active'. Execution Agent polls Tier 1 for active plans, reads the current phase, and begins implementation. Progress updates flow back to Tier 1 in real-time.

Handoff Protocol

  1. Planning Agent: Write plan to PlanningStateDB with status='active', current_phase=0
  2. Master Orchestrator: Detect plan creation event, invoke Execution Agent
  3. Execution Agent: Query SELECT * FROM plans WHERE status='active' ORDER BY created_at DESC LIMIT 1
  4. Execution Agent: Read phase 1 tasks from phases table
  5. Execution Agent: Implement task 1, update UPDATE tasks SET status='completed' WHERE task_id=?
  6. Execution Agent: Repeat for remaining tasks, update phase status when all complete
  7. Learning Agent: Query completed phases, extract patterns, write to Tier 2

The "Continue" Command

One of CORTEX's most powerful features is stateful resumption. Users can close VS Code, come back hours later, type continue, and CORTEX picks up exactly where it left off.

Implementation

User Input: continue or resume

Master Orchestrator Logic:

  1. Query ConversationDB: SELECT * FROM sessions ORDER BY last_activity DESC LIMIT 1
  2. Extract last_orchestrator from session metadata (e.g., "Planning", "TDD", "Execution")
  3. Query PlanningStateDB: SELECT * FROM plans WHERE status='active' LIMIT 1
  4. Load plan metadata: current_phase, tasks_completed, tasks_total
  5. Display to user: "Resuming [orchestrator] - Phase [X]: [Y/Z tasks complete]"
  6. Invoke appropriate agent with loaded state

Example Interaction

Session 1 (Friday 3pm):
User: /CORTEX plan user authentication
CORTEX: Phase 0 complete, 17 phases planned. Phase 1 starting...
(User closes VS Code)

Session 2 (Monday 9am):
User: continue
CORTEX: Resuming Planning v5 - Phase 1: Implementation (2/8 tasks complete). Starting task 3: Add JWT token validation...

Performance Characteristics

Write Latency
<5ms for plan updates (SQLite ACID transactions)
Query Speed
<2ms for active plan lookup (indexed by status + created_at)
Database Size
~10MB per 100 plans (with 30-day auto-cleanup)
Concurrent Access
SQLite WAL mode enables concurrent readers + single writer
Auto-Cleanup
Daily cron job removes plans >30 days old, logs >90 days
Backup Strategy
Daily SQLite backup to cortex-brain/backups/ (7-day retention)
