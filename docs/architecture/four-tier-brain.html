Overview

The 4-Tier Brain is CORTEX's hierarchical memory architecture that enables intelligent, context-aware orchestration. Each tier serves a distinct purpose in the cognitive pipeline, from rigid governance rules to dynamic execution context.

Unlike traditional AI systems with flat memory models, CORTEX's tiered approach creates a memory hierarchy that mirrors human cognition: immutable rules (instinct), working memory (consciousness), long-term knowledge (experience), and environmental context (perception).

Tier 0 Governance Layer

Purpose: Immutable brain protection rules that enforce quality, safety, and architectural integrity.

Tier 0 contains the SKULL (Safeguards for Knowledge, Understanding, Learning & Logic) rules—61 non-negotiable constraints that the Master Orchestrator must obey. These act as CORTEX's "instincts," preventing harmful or architecturally unsound actions.

Key Rules

TDD_ENFORCEMENT
Tests must fail before implementation (RED→GREEN→REFACTOR)
HOLISTIC_DISCOVERY
Search before create to prevent duplication
GIT_ISOLATION
CORTEX code never commits to user repos
PLANNING_ISOLATION
Planning commands create plans only, never implement
REFACTOR_CLEANUP
Remove orphaned code, deduplicate, optimize
HAND_OFF_PROTOCOL
Autonomous orchestrators execute independently

Storage: cortex-brain/brain-protection-rules.yaml (61 rules)
Access: Read-only by Master Orchestrator
Update Frequency: Rarely (architectural changes only)

Tier 1 Working Memory

Purpose: Short-term, high-velocity storage for active plans, conversation state, and orchestrator coordination.

Tier 1 is CORTEX's "consciousness"—what it's currently thinking about. When you create a plan, start a TDD session, or continue a previous task, Tier 1 tracks the state. This enables stateful orchestration where agents can resume work across sessions.

Data Stored

Active Plans
Current phase, progress, acceptance criteria, git checkpoints
Conversation Context
Last 3 sessions, user preferences, intent history
State Coordination
PlanningStateDB, orchestrator status, agent handoffs
Performance Cache
Token usage, execution metrics, hot paths

Storage: cortex-brain/tier1/ (JSONL, SQLite)
Access: Read/write by all orchestrators
Retention: 30 days (rolling window)

Tier 2 Knowledge Graph

Purpose: Long-term, structured knowledge capturing lessons learned, relationships, and patterns.

Tier 2 is CORTEX's "experience memory." Every successful pattern, failure mode, and architectural decision is captured as nodes in a knowledge graph with typed relationships. This enables continuous learning—CORTEX gets smarter with every project.

Knowledge Structure

Lessons Learned
What worked, what failed, why, context, impact
Relationships
Dependencies, conflicts, alternatives, compositions
Patterns
Architectural patterns, anti-patterns, idioms
Phase -1 Knowledge
80 modules across 17 domains (API design, testing, security...)

Storage: cortex-brain/tier2/knowledge-graph.yaml, Neo4j-style graph
Access: Read by all, write by Learning Agent
Retention: Permanent (with version history)

Tier 3 Development Context

Purpose: Real-time workspace awareness including files, git state, dependencies, and execution environment.

Tier 3 is CORTEX's "perception"—what it sees in your project right now. This tier is dynamically loaded from the workspace and provides the concrete context for executing plans. Unlike the other tiers, Tier 3 is ephemeral and project-specific.

Context Sources

Project Files
Source code, configs, schemas, documentation
Git State
Current branch, commit history, diffs, remote status
Dependencies
package.json, requirements.txt, .csproj, lock files
Execution Env
Python/Node versions, virtual envs, PATH, shells
Errors & Warnings
Compiler errors, linter warnings, test failures
Build Config
tasks.json, scripts, Makefiles, CI/CD pipelines

Storage: Live workspace + cortex-brain/tier3/development-context.yaml
Access: Read-only (writes go to workspace, not Tier 3)
Retention: Session-based (cleared on workspace close)

Inter-Tier Communication

The tiers don't operate in isolation—they form a cognitive pipeline where data flows up and down the hierarchy based on the task at hand.

Downward Flow (Enforcement)

Tier 0 → Tier 1 → Tier 2 → Tier 3
When you issue a command, the Master Orchestrator checks Tier 0 constraints, loads Tier 1 state, queries Tier 2 for relevant patterns, and applies to Tier 3 context. This ensures every action is compliant, stateful, informed, and contextual.

Upward Flow (Learning)

Tier 3 → Tier 2 → Tier 1
After execution, results from Tier 3 (did the tests pass? was the refactor successful?) feed back to Tier 1 (update plan progress) and Tier 2 (capture lesson learned). Tier 0 never changes—rules are immutable.

Real-World Examples

Example 1: Creating a Plan

User: /CORTEX plan user authentication

  1. Tier 0: Enforce PLANNING_ISOLATION (plan only, don't implement)
  2. Tier 1: Create new plan entry, set status = "active", phase = 0
  3. Tier 2: Query for authentication patterns, best practices, security considerations
  4. Tier 3: Scan project for existing auth code, identify integration points
  5. Output: 17-phase plan document with knowledge-enriched steps

Example 2: TDD Session

User: tdd login function

  1. Tier 0: Enforce TDD_ENFORCEMENT (RED→GREEN→REFACTOR mandatory)
  2. Tier 1: Check for active TDD session, resume if exists
  3. Tier 2: Load testing patterns for login functions
  4. Tier 3: Identify test framework, locate test files, check coverage
  5. Output: Failing test first, then minimal implementation, then refactor

Example 3: Resuming Work

User: continue

  1. Tier 1: Query last 3 sessions, find most recent orchestrator
  2. Tier 1: Load plan state (current phase, completed tasks)
  3. Tier 2: Recall context from previous session
  4. Tier 3: Re-scan workspace for changes since last session
  5. Output: "Resuming Phase 5: Implementation (3/8 tasks complete)"

Advantages of Tiered Architecture

Safety
Tier 0 prevents harmful actions before execution
Statefulness
Tier 1 enables resuming work across sessions
Learning
Tier 2 captures lessons, improving over time
Context Awareness
Tier 3 grounds actions in current workspace reality
Separation of Concerns
Each tier has a single, well-defined responsibility
Scalability
Add/modify tiers without affecting others
