Executive Summary

CORTEX's Git Operations system provides automated version control with strict isolation between CORTEX internal code and user application code. Three SKULL rules enforce git integrity: GIT_ISOLATION_ENFORCEMENT prevents CORTEX code from touching user repos, GIT_CHECKPOINT_ENFORCEMENT creates safety checkpoints before risky operations, and PREVENT_DIRTY_STATE_WORK blocks development on uncommitted changes.

Core Git Operations

🛡️ Git Isolation Enforcement

▼

Purpose: Absolute separation between CORTEX internal code and user application code

How it works:

  • CORTEX Repository: All CORTEX code lives in /PROJECTS/CORTEX/
  • User Repositories: Application code lives in separate repos (e.g., /PROJECTS/MyApp/)
  • Zero Cross-Contamination: CORTEX never commits to user repos, users never commit to CORTEX
  • Brain Protector Validation: All git operations validated against isolation rules

Protected paths:

CORTEX Critical Paths (never touch user code):
├── src/tier0/ (governance)
├── cortex-brain/ (memory, knowledge, context)
├── .github/prompts/ (prompt files)
└── cortex-operations.yaml (operation registry)

User Application Paths (CORTEX never commits here):
├── SPA/ (Single Page Applications)
├── blazor/ (Blazor apps)
├── signalr/ (SignalR hubs)
└── Any user-created project folders

🔖 Automatic Checkpointing

▼

Purpose: Safety net for rollback before high-risk operations

When checkpoints are created:

  • Before System Maintenance: Checkpoint before cleanup phase
  • Before Refactoring: Checkpoint before code restructuring
  • Before Major Changes: Architecture updates, migrations
  • Before Pull Operations: Safety net before merging remote changes

Checkpoint format:

git commit -m "checkpoint: Pre-cleanup safety checkpoint"
git tag checkpoint-20251210-143000

Rollback capability:

# If something goes wrong, rollback to checkpoint
git reset --hard checkpoint-20251210-143000

# Or just view the checkpoint
git show checkpoint-20251210-143000

🚫 Dirty State Prevention

▼

Purpose: Block development work when uncommitted changes exist

What's blocked:

  • New Feature Development: Can't start planning with dirty state
  • System Maintenance: Maintenance requires clean working tree
  • Refactoring: Can't refactor with uncommitted changes
  • Major Operations: Migrations, deployments require clean state

Brain Protector response:

🚨 BLOCKED: PREVENT_DIRTY_STATE_WORK

Cannot start development work with uncommitted changes.

Current State:
  Modified: 3 files
  Untracked: 2 files

Required Action:
  1. Review changes: git status
  2. Commit changes: git add . && git commit -m "..."
  3. Or stash: git stash save "WIP: description"
  
Then retry your request.

Why this matters:

Prevents work-in-progress from being lost or accidentally mixed with new changes. Ensures clean rollback capability and clear change history.

SKULL Protection Rules

Git Operations are governed by 3 core SKULL rules:

GIT_ISOLATION_ENFORCEMENT

Zero-tolerance policy: CORTEX code never touches user repos. User code never touches CORTEX repo. Brain Protector validates every git operation against isolation rules.

GIT_CHECKPOINT_ENFORCEMENT

Mandatory checkpoints: Before high-risk operations (cleanup, refactoring, migrations), CORTEX creates git checkpoint (commit + tag) for rollback capability.

PREVENT_DIRTY_STATE_WORK

Clean state required: Development work blocked when uncommitted changes exist. Prevents WIP loss and ensures clean rollback.

How It Works

Git operations are automatic: CORTEX handles checkpointing, isolation validation, and commit message generation without user intervention.

User actions that trigger git operations:

  • system maintenance - Creates checkpoint before cleanup
  • plan [feature] - Validates clean state, creates feature branch
  • execute all phases autonomously - Commits after each phase
  • deploy - Creates deployment tag

All git operations are logged and validated by Brain Protector for compliance.
