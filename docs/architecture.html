Current Implementation View

CORTEX Today — The Control Plane Behind the Metaphor

The sections below explain the current repository-backed architecture directly. They complement the page’s established visual language with clearer descriptions of the execution surfaces that matter in practice today.

Control Plane

The current system is a layered control plane, not a single monolithic brain.

The most useful way to understand modern CORTEX is to start with its layered operating model. The prompt surface provides policy, tone, and routing contracts; the Python control plane in cortex/ handles orchestration and execution decisions; the registry in cortex-registry/ holds canonical workflow, governance, and planning artifacts; and the supporting prompt, agent, and skill surfaces in .github/ and .claude/ define how that system behaves across host environments. This matters because the older shorthand of “brain” can be helpful as metaphor, but it is no longer sufficient as an architectural explanation. The real implementation separates orchestration, reusable guidance, runtime tools, and evidence stores so the platform can route work, apply policy, delegate specialized tasks, and return a traceable result. That separation is what makes CORTEX maintainable, auditable, and adaptable as more commands, agents, workflows, and runtime surfaces are added over time.

Execution Boundaries

Orchestration, Claude agents, subagents, and skills are different layers with different jobs.

One of the biggest sources of confusion in AI-engineering systems is treating every control artifact as if it were the same thing. CORTEX has moved beyond that. Orchestration is the traffic-control layer: it classifies the request, loads the right execution route, opens governance gates, and decides when work is complete. Claude-facing agents are specialist operating profiles: they define how audit, planning, documentation, debugging, or readiness work should behave when loaded. Subagents are narrower delegated workers that execute scoped tasks and then hand control back to the parent route. Skills are not runtime engines at all; they are reusable capability packs that describe domain knowledge, workflow expectations, and command semantics that prompts and agents can reuse. Shared infrastructure then ties all of this together through tools, registries, trace stores, and learning services. When those boundaries are clear, the system is easier to reason about, easier to document, and much less likely to drift into duplicated logic or contradictory behavior across Copilot and Claude execution surfaces.

Shared Runtime and Return Flow

Requests only make sense when you can see what crosses a boundary and how control returns.

A practical architecture page has to explain more than the names of components; it has to explain movement. In CORTEX, a request begins as user intent at the host surface, is classified by orchestration, enriched with repository and registry context, and then passed into a route that may load agents, skills, workflow templates, and tool calls. If delegation is needed, the parent route passes scoped work to a subagent and later receives a condensed result back rather than surrendering end-to-end ownership. Meanwhile, shared infrastructure keeps the whole system coherent: MCP tools execute actions, validation scripts confirm gates, the intelligence facade provides a unified entry point for analysis and registry access, and trace databases capture AC markers, RCA history, and reinforcement signals. The important architectural fact is that control always returns to the orchestrating path. That is how the platform keeps completion logic centralized, preserves auditability, and prevents delegated workers from becoming untracked side channels.

Cognitive Architecture

The CORTEX Brain

The Brain is the decision-making centre between the LENS sensory layer and the execution engine. It receives workspace signals, identifies patterns, selects the right strategy depth, and builds a step-by-step plan — before a single line of code is written or changed.

Unlike a language model that generates responses, the CORTEX Brain routes through structured cognitive tiers — each with defined inputs, rules, and outputs — making every decision traceable and auditable.

Cognitive Stack

Three Tiers — Perception · Reasoning · Action

Each tier is a distinct processing stage with its own inputs, algorithms, and outputs. Data flows top-down; feedback flows bottom-up through the Unified Reinforcement Signal.

Tier 1 — Reads LENS signals

Perception

Receives the structured output of the LENS scan and maps workspace signals to canonical design patterns. Each pattern receives a confidence score between 0.0 and 1.0 using a weighted signal model. Patterns scoring above 0.75 are promoted to the Reasoning tier as high-confidence candidates.

Nine canonical patterns are evaluated on every scan — regardless of intent type — so the Brain always has a fresh context map before strategy selection begins.

Tier 2 — Selects strategy

Reasoning

Takes high-confidence patterns from Tier 1 and selects the appropriate execution mode — Quick (cached rules), Targeted (LENS-scoped), or Full (all 9 analyzers). This decision determines which orchestrators are engaged and what governance gates are applied.

Before strategy selection, the Brain consults the RCA Memory Engine (PLIP-001). If a prior failure pattern with confidence ≥ 0.4 matches the current context, it is surfaced as a warning — preventing the same mistake from recurring.

Tier 3 — Builds execution plan

Action

Converts the Reasoning tier's selected strategy into a concrete, step-by-step execution plan — routed through the MasterOrchestrator. Every step includes a mandatory test checkpoint, a rollback point, and a governance gate.

Every entry and exit point emits an AC_START / AC_COMPLETE marker, persisted to SQLite — making every Brain decision auditable and replayable.

SQLite Audit Trail

URS — Closed-Loop Learning

Unified Reinforcement Signal

After every Action tier execution, the Brain emits a reward or penalty signal. These signals update confidence scores for patterns and strategies — making the Brain measurably smarter about your codebase over time.

🏆
MILD_REWARD (+1.0)

Emitted when an execution completes without governance violations, test failures, or regressions. The pattern's confidence score increases, making it more likely to be selected on similar future contexts.

⚠️
MILD_PUNISHMENT (−1.0)

Emitted when an execution produces P0/P1 violations, test failures, or regressions. Confidence decreases. After 3 failures, the pattern is demoted. After 5, it is quarantined from recommendations.

Cross-Team Signal Propagation

URS signals are stored in cortex_learning MCP tool with scope-isolated domains. When Team A discovers a root cause, the generated PreventionRule is immediately available to all other teams — without post-mortems or knowledge-base updates.

# Emit after success cortex_learning( op="emit", signal_type="MILD_REWARD", pattern_id="implement", source_orchestrator="TDDOrchestrator" )

Root Cause Analysis

Four RCA Methodologies — Failures Never Repeat

Every root cause analysis generates a SQLite-backed PreventionRule that surfaces automatically the next time a similar pattern appears.

Five-Whys

Linear root cause tracing — best for technology failures with clear sequential cause chains.

Fishbone

Multi-factor analysis across People, Process, Technology, and Data failure axes.

Fault Tree

AND/OR gate analysis surfacing the minimum set of conditions for failure.

Causal Chain

Temporal event correlation — reveals triggering events that precede the visible symptom.

Prevention Escalation

Three Escalation Levels

Prevention rules escalate based on recurrence count. Chronic failures get harder to ignore.

⚠️

Advisory

Default level. Shows warning in analysis but does not block. Generated on first RCA completion.

🚫

Blocking

Promoted after 3+ recurrences. Requires explicit acknowledgment to proceed past the gate.

🔒

Hard Block

Promoted after 5+ recurrences. Cannot be bypassed — the operation is refused outright.

The TDD Cycle — Red · Green · Refactor

CORTEX enforces Test-Driven Development as an immutable contract. No implementation proceeds without a failing test. There is no flag to skip it.

Define expected behaviour. The test MUST fail before any production code is written.

🟢
GREEN — Minimum Passing Code

♻️

Improve structure while keeping tests green. Convergence gate rescans until zero violations.
