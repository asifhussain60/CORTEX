What is SKULL Protection?

SKULL (Strategic Knowledge & Universal Logic Layer) is CORTEX's Tier 0 governance system—22 immutable rules enforced by the Brain Protector that prevent common development anti-patterns. These rules are never bypassed, operating as fundamental instincts that protect code quality, maintain TDD discipline, prevent duplication, and enforce Git isolation.

When a developer attempts an action that would violate a SKULL rule, the Brain Protector intervenes with evidence-based reasoning, explaining why the action is problematic and suggesting the correct approach.

The 22 SKULL Rules

🎯 TDD Enforcement (6 rules)

1. TDD_ENFORCEMENT

▼

Rule: RED→GREEN→REFACTOR cycle is mandatory. Implementation blocked until failing tests exist.

Why: Prevents "implementation-first" development that leads to untestable code.

Enforcement: Brain Protector alerts if implementation starts without failing tests.

2. RED_PHASE_VALIDATION

▼

Rule: Tests must fail before implementation begins. Prevents false-positive passing tests.

Why: Validates tests actually check the functionality (not just passing due to bugs).

Enforcement: CORTEX runs tests and confirms failures before GREEN phase.

3. TDD_TEST_FILE_VALIDATION

▼

Rule: All production code must have corresponding test files.

Why: Ensures complete test coverage infrastructure exists.

Enforcement: Automated validation checks for matching test files.

4. TDD_EMPTY_TEST_DETECTION

▼

Rule: No placeholder or empty test files allowed.

Why: Prevents false sense of test coverage with stub tests.

Enforcement: Scans test files for actual assertions and logic.

5. TDD_LAYER_COVERAGE_VALIDATION

▼

Rule: Tests must cover all 4 layers: unit, integration, system, acceptance.

Why: Ensures comprehensive testing from micro to macro level.

Enforcement: Per-layer coverage validation with specific targets.

6. TEST_LOCATION_SEPARATION

▼

Rule: Application tests in user repo, CORTEX tests in tests/.

Why: Maintains clean separation between CORTEX internal tests and user app tests.

Enforcement: File path validation during test creation.

🔍 Code Discovery & Duplication Prevention (4 rules)

7. HOLISTIC_CODE_DISCOVERY_ENFORCEMENT

▼

Rule: Search entire codebase before creating new code. Prevents duplication.

Why: Reduces code bloat and maintenance burden from duplicate implementations.

Enforcement: Brain Protector requires search evidence before creation.

8. REFACTOR_CODE_CLEANUP_ENFORCEMENT

▼

Rule: Remove orphaned and duplicate code during refactoring phase.

Why: Keeps codebase clean and maintainable over time.

Enforcement: Automated dead code detection during refactoring.

9. DUPLICATE_DETECTION

▼

Rule: Alert on similar code patterns across codebase.

Why: Identifies opportunities for abstraction and reuse.

Enforcement: Similarity analysis on new code contributions.

10. SEMANTIC_SEARCH_FIRST

▼

Rule: Use semantic search to find existing implementations before creating new ones.

Why: Leverages AI-powered search to find conceptually similar code.

Enforcement: Semantic search results must be reviewed first.

🔀 Git Isolation & Repository Management (4 rules)

11. GIT_ISOLATION_ENFORCEMENT

▼

Rule: CORTEX code never committed to user repositories.

Why: Prevents CORTEX internals from polluting user projects.

Enforcement: Git pre-commit hooks validate commit scope.

12. CHECKPOINT_VALIDATION

▼

Rule: Automated checkpoints only on clean working directory.

Why: Ensures checkpoints represent stable states.

Enforcement: Git status check before checkpoint creation.

13. BRANCH_PROTECTION

▼

Rule: Protected branches require specific permissions for modifications.

Why: Prevents accidental changes to stable branches.

Enforcement: Branch validation before operations.

14. COMMIT_MESSAGE_QUALITY

▼

Rule: Commit messages must follow conventional format with context.

Why: Maintains readable git history for team collaboration.

Enforcement: Commit message validation before acceptance.

📚 Documentation & Knowledge Management (4 rules)

15. DOCUMENT_ORGANIZATION_ENFORCEMENT

▼

Rule: All docs in cortex-brain/documents/{category}/, never at root.

Why: Maintains organized, discoverable documentation structure.

Enforcement: File path validation during document creation.

16. RESPONSE_FORMAT_COMPLIANCE

▼

Rule: All responses use mandatory 5-part format (v3.0).

Why: Ensures consistent, professional communication.

Enforcement: Template validation before response delivery.

17. KNOWLEDGE_GRAPH_VALIDATION

▼

Rule: All captured knowledge must link to existing nodes or create valid new ones.

Why: Maintains graph integrity and prevents orphaned knowledge.

Enforcement: Graph validation during Tier 2 updates.

18. CONTEXT_FRESHNESS

▼

Rule: Working memory (Tier 1) maintains 70-conversation FIFO with timestamps.

Why: Balances context depth with query performance (<100ms).

Enforcement: Automated FIFO cleanup and timestamp tracking.

🗺️ Planning & Execution (4 rules)

19. DOR_DOD_COMPLIANCE

▼

Rule: All plans must include Definition of Ready and Definition of Done.

Why: Ensures clear acceptance criteria before execution starts.

Enforcement: Plan validation rejects plans without DoR/DoD.

20. TDD_IN_PLANS

▼

Rule: TDD automatically included in all feature plans.

Why: Makes test-driven development the default, not an afterthought.

Enforcement: Planning System 2.0 auto-adds TDD phases.

21. COMPLEXITY_ROUTING

▼

Rule: Automatic complexity detection routes to appropriate planning strategy.

Why: High-complexity features get incremental planning; low-complexity get skeleton.

Enforcement: Complexity analyzer determines routing automatically.

22. PHASE_GATE_VALIDATION

▼

Rule: Each phase must pass validation gates before next phase starts.

Why: Prevents cascading failures from incomplete phases.

Enforcement: Automated gate checks between phases.

How SKULL Protection Works

Brain Protector: The Enforcement Engine

The Brain Protector is CORTEX's enforcement engine that monitors all operations against the 22 SKULL rules. When a violation is detected, it intervenes immediately with evidence-based reasoning.

Intervention Example:

⚠️ SKULL Rule Violation Detected

Rule: TDD_ENFORCEMENT

Issue: Implementation started without failing tests

Evidence: No test files found for new_feature.py

Recommended Action: Create failing tests in RED phase before implementing new_feature.py

Zero Tolerance Policy:

  • SKULL rules are never bypassed or overridden
  • No "just this once" exceptions
  • 100% enforcement across all operations
  • Rules operate as fundamental instincts, not suggestions
