The Core Concept

No inline logic. Pure declaration.

Before the Workflow Composer existed, each orchestrator contained its own execution logic — creating drift, duplication, and governance gaps. The Composer solved this by moving all execution into YAML workflow templates. Orchestrators now declare what to do; the Composer decides how to do it.

Think of it as the difference between a script and a playbook. A script is brittle. A playbook is reproducible, auditable, and learnable.

1

Intent arrives via MCP or Copilot Chat

The IntentRouter classifies your request into one of 31 intent types — IMPLEMENT, FIX, REFACTOR, DEBUG, AUDIT, and more.

2

Workflow template is selected

Each intent maps to a YAML template in cortex-registry/workflows/templates/. No ambiguity, no guessing.

3

Universal primitives inject governance

Eight atomic steps — git checkpoints, TDD gates, sweep catalogues, convergence loops — wrap every execution automatically.

4

AC markers trace every milestone

AC_START and AC_COMPLETE are emitted at every orchestrator boundary, written to SQLite, and auditable on demand.

MCP-First Architecture

Pylance-style. Zero setup.

CORTEX's MCP server starts automatically when you open the workspace in VS Code — exactly like Pylance starts automatically for Python. There is no server to launch, no port to remember. The 36+ registered tools are available the moment Copilot Chat opens.

Every Workflow Composer execution is exposed as an MCP tool call. You can trigger the entire implement-workflow pipeline with a single tool invocation — or compose workflows programmatically.

Auto-start configuration

// .vscode/settings.json { "github.copilot.chat.mcpServers": { "cortex": { "command": "python3", "args": ["-m", "cortex.mcp"], "transport": "stdio" } } }

Universal Primitives

Governance by construction.

Eight atomic workflow primitives inject governance into every code-modifying execution. You never need to remember to add them — the Workflow Composer wraps every pipeline automatically.

🏁

AC Markers

Emit AC_START and AC_COMPLETE at every orchestrator boundary — written to SQLite.

🔀

Git Checkpoint

Creates a safe rollback point before any file change. Every execution is reversible.

📋

DOR Display

Definition of Ready rendered before execution begins — sets explicit acceptance criteria.

🔍

Holistic Validation

CORE-048 pre-execution gate — scans codebase state before any change is made.

⚡

Challenge Gate

Risk-based alternative presentation — surfaces trade-offs before committing.

📂

Sweep Catalogue

CORE-064 open/close tracking — no partial sweeps, every issue catalogued and closed.

🔄

Convergence Loop

CORE-068 detect→fix→rescan until zero P0/P1 violations remain (max 3 cycles).

🧪

TDD Gate

CORE-008 enforced — failing test written before implementation on every code-modifying intent.

Live Execution Walkthrough

What happens when you say proceed.

Follow a single /implement command through its complete lifecycle — from intent classification to a verified, audited result stored in SQLite.

①

IntentRouter classifies → IMPLEMENT

Your message is parsed by the IntentRouter. Keywords, context, and prior patterns route to the correct intent type. This takes <50ms.

②

LENS analyses the codebase (9 parallel analyzers)

Structure, history, security, complexity, patterns, dependencies, test coverage, style, and semantics — read in parallel before any plan is formed.

③

Holistic Validation Gate runs (CORE-048)

Pre-execution scan. If P0 violations exist in the target area, CORTEX flags them before touching code. No surprises mid-execution.

④

Failing test written first (CORE-008)

TDD is not optional. Before a single line of implementation is touched, a red test is committed — creating an explicit success criterion.

⑤

Implementation → convergence loop (CORE-068)

Code is written, tests run, violations detected. The loop repeats until zero P0/P1 remain — never stops at first pass.

⑥

AC_COMPLETE emitted → SQLite persisted

Every execution leaves a durable trace. Timing, phase, violations, resolution — all written to orchestrator-traces.db for audit.
