Phase 1 · Modules 1–5

Skills — Packaging Expertise Once

Every Claude session starts with no memory of how your team works. Skills solve this permanently. A SKILL.md file packages a domain of knowledge — coding conventions, testing workflows, deployment rules — into a named unit that Claude loads on demand based on intent signals in your request. Write it once; every future session benefits automatically.

Analogy — The Specialist's Handbook

When a new specialist joins your team, you don't explain the entire company from scratch. You hand them the handbook for their domain: a security specialist gets the security rules; a frontend developer gets the UI conventions guide. Claude's skills work identically — the right handbook, loaded at the right moment, without you repeating it every session.

SKILL.md anatomy

A SKILL.md has two parts: YAML frontmatter controlling how Claude discovers and loads it, and a Markdown body with the actual instructions. The description field is the most critical element — Claude pattern-matches request keywords against it to decide which skill to load automatically.

📋 Skill Match Flow — How "implement recurring tasks" Loads the TDD Skill
SKILL.md.claude/skills/taskflow-tdd/SKILL.md
--- name: taskflow-tdd description: TDD workflow for TaskFlow — triggered by "implement", "add feature", "build" argument-hint: "Describe the feature to implement" --- # TaskFlow TDD Workflow ## Rules (always follow) - Write the failing test BEFORE any implementation code - Run npm test -- --testPathPattern {file} after each step - Commit only when full suite passes: npm test - Models → src/models/ · Services → src/services/ ## Workflow 1. RED: Write a failing test in tests/ mirroring the src/ path 2. GREEN: Write minimum code in src/ to make the test pass 3. REFACTOR: Clean up while keeping tests green 4. VERIFY: npm test — full suite must pass before committing

Three skill patterns

PatternPurposeTaskFlow example
ProceduralStep-by-step workflows — TDD, deployments, PR creationtaskflow-tdd/SKILL.md — ordered RED → GREEN → REFACTOR steps
ReferenceKnowledge domains — API conventions, naming rules, architecture decisionstaskflow-conventions/SKILL.md — naming patterns, import rules
GatewayTop-level skill that routes requests to the right domain skill via intent signalstaskflow/SKILL.md — maps "implement" → TDD skill, "review" → conventions skill
🧪
Module 1 in practice Create .claude/skills/taskflow-tdd/SKILL.md with the code above. In your next session, say "implement a recurring task feature" — Claude matches "implement" and "feature" against the skill's description and loads it automatically. No explicit invocation needed.

Phase 2 · Modules 6–9

Agents — Scoped Assistants

An agent is a Claude instance with a defined role, limited tools, and targeted instructions. Instead of one Claude doing everything, you build a team: a read-only reviewer that physically cannot edit files, a scoped deployer that cannot touch production data, a security auditor with exactly the access its role requires — and not one tool more.

Analogy — Security Clearance Levels

Think of a large facility: the HVAC contractor has access to mechanical rooms but not the server room. The network engineer has server room access but not the executive suite. Nobody gets more access than their job requires. Your Claude agents work identically — each one has exactly the tools its role needs and is physically incapable of using anything beyond those bounds.

Agent anatomy

Every agent lives in .claude/agents/ as a Markdown file with YAML frontmatter that controls tools, loaded skills, and permission mode. The Markdown body defines how the agent behaves when invoked.

.claude/ ├── CLAUDE.md # global rules + routing └── agents/ ├── taskflow-reviewer.md # [Read, Grep, Glob] — reads only ├── taskflow-builder.md # [Read, Write, Bash(npm test:*)] └── taskflow-deployer.md # [Bash(npm run deploy:*)] only
Agent definition.claude/agents/taskflow-reviewer.md
--- name: taskflow-reviewer description: Code quality reviewer — invoked for review, PR, quality check requests tools: [Read, Grep, Glob] skills: [taskflow-conventions] # No Write or Bash — this agent can only read. Restriction is framework-enforced. --- # TaskFlow Code Reviewer Review all code changes in this order: 1. Structure: File organization, import paths, naming conventions 2. Logic: Correctness, edge cases, null/undefined handling 3. Security: No hardcoded secrets, all inputs validated, no injection risk 4. Tests: Coverage present, edge cases covered, assertions meaningful Standards (from loaded taskflow-conventions skill): - Models: singular PascalCase in src/models/ - Services: camelCase + plural in src/services/ - Never catch-and-swallow errors — log them or rethrow

Phase 3 · Modules 10–13

Hooks — Automated Quality Gates

Hooks are event-triggered interceptors that fire at defined moments in the Claude tool-use lifecycle. They run tests after every file edit, block dangerous commands before they execute, send alerts when Claude needs attention — all without interrupting workflow or requiring you to remind Claude to verify its own work.

Analogy — Airport Security Checkpoints

Each hook activates at a specific point in the journey: check-in (PreToolUse), boarding gate (PostToolUse), arrival (Stop). The checkpoint doesn't stop the journey — it verifies the passenger is safe to proceed. A PreToolUse hook that blocks a destructive git push --force is exactly a boarding agent checking your ticket before you step on the plane.

The five hook events

⏱️ Hook Event Timeline — When Each Hook Fires in the Claude Lifecycle
Hook eventFires whenTypical TaskFlow use
PreToolUseBefore any tool executesBlock git push --force, validate inputs before writes
PostToolUseAfter each tool completesRun tests after every file edit, log all changes
NotificationWhen Claude needs your attentionDesktop alert, Slack notification via webhook
StopWhen the session endsGenerate session summary, cleanup temp files
SubagentStopWhen a subagent finishesCollect and merge results from parallel agents

Building the TaskFlow quality gate

The highest-value hook: automatically run the related tests after every source file edit. Claude detects failures immediately at each change — not after building three more things on a broken foundation.

Hook configAdd to CLAUDE.md
## Hooks hooks: - event: PostToolUse matcher: tool: Write path: "src/**/*.ts" # Only fires on TaskFlow source edits action: type: command command: npm test -- --testPathPattern "$CLAUDE_TOOL_FILE" timeout: 30 blocking: true # Pause Claude if tests fail — lets it self-correct
💡
Blocking vs non-blocking blocking: true pauses Claude until the hook exits with code 0. Use this for quality gates. blocking: false (default) fires in the background — use for notifications and logging. A failing blocking hook sends its stdout back to Claude as context so it can self-correct automatically.
🧪
Module 13 in practice Add the PostToolUse hook above to your TaskFlow CLAUDE.md. Ask Claude to implement a feature without TDD discipline. The hook fires after each file write, runs the affected tests, and if a test fails, Claude receives the error and corrects the code before continuing — automatically enforcing TDD without you policing it.

Phase 4 · Modules 14–17

Context & Prompting

The context window is your most finite resource — every file Claude reads, every message in the conversation, every tool output consumes tokens. Expert developers don't just know what to ask; they know how to ask it efficiently, in the right session structure, using patterns that extract maximum value with minimum waste.

Analogy — The Working Whiteboard

The context window is a shared whiteboard at the start of a working session. It begins clean and everything fits clearly. As the session progresses, it fills with notes, diagrams, and code. When nearly full, you can erase it (/clear) or ask someone to summarize the key points before erasing (/compact). The discipline is noticing the whiteboard getting cluttered and acting before it's too late to think clearly.

📊 Where Tokens Go — Typical TaskFlow Feature Session

Five prompting principles

#PrincipleTaskFlow application
1Verify Work — always tell Claude to check its output"Add recurring tasks and run npm test to verify before finishing"
2Explore First — read context before writing code"Read src/models/task.ts carefully before making any changes to it"
3Be Specific — scope beats vagueness every time"Update only src/commands/add.ts — touch no other files"
4Provide Context — paste errors, reference specific files"Fix the error in @src/services/taskService.ts:47: TypeError…"
5Iterate Small — one focused task per session beats marathonsOne feature per session; use /clear between unrelated tasks

Four prompting patterns

I

Interview — let Claude surface the questions

"Before implementing recurring tasks, ask me 3 clarifying questions about requirements." Use this when requirements are unclear or to discover hidden complexity before any code is written.

C

Constraint — define explicit limits upfront

"Implement recurring tasks. Constraint: don't change the database schema — add a scheduler service only." Prevents scope-creep and protects critical parts of the codebase from unintended changes.

T

Teaching — explain before you execute

"Explain how you'd structure the recurring task scheduler before writing any code." Forces Claude to articulate a plan first, surfacing flawed assumptions before they become bugs in production.

Co

Comparison — evaluate before committing to an approach

"Compare cron-based vs. event-driven scheduling for TaskFlow recurring tasks. Then implement the better option and explain your reasoning." Gets Claude to reason about trade-offs before writing a single line.

Phase 5 · Modules 18–23

Mastery — The Complete Customisation Stack

Mastery is not about knowing individual features — it's about composing them into a coherent, self-managing system: a gateway skill that routes intent automatically, a library of domain skills, agents with precisely scoped tool access, and hooks that enforce quality without human intervention. Together they transform Claude from a helpful assistant into a project-aware development partner.

Analogy — A Well-Run Hospital

A hospital doesn't have one doctor who does everything. It has departments (domain skills), a reception desk (gateway skill) that routes each patient to the right department, qualified staff (agents with tool allowlists), and safety protocols (hooks) that fire automatically at defined checkpoints. Nobody has to know everything. The system routes, delegates, and verifies on its own.

The gateway skill pattern

Instead of one large overloaded SKILL.md, create a lightweight gateway that reads intent signals and routes to the appropriate domain skill. Each domain skill stays focused, minimal, and easy to update independently.

Gateway skill.claude/skills/taskflow/SKILL.md
--- name: taskflow description: TaskFlow project gateway — routes all requests to domain skills --- # TaskFlow Gateway Skill ## Intent routing | Signal words | Load this skill | |---------------------------------------|---------------------------| | implement, add feature, build | taskflow-tdd | | review, PR, check quality | taskflow-conventions | | deploy, release, publish | taskflow-deploy | | security, vuln, OWASP | taskflow-security | | bug, broken, test failing | taskflow-debug | When a signal word matches, load the domain skill and follow its workflow exactly.
