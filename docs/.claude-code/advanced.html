Phase 1 · Modules 1–4

Agent Teams — Divide & Conquer

A single Claude instance eventually hits limits: context saturates, responsibilities tangle, and mistakes compound. Agent teams solve this. A lead agent orchestrates work; specialists execute in their domain. Context stays clean, failures are isolated, and quality improves through enforced separation of concerns.

Analogy — The Aircraft Carrier Battle Group

An aircraft carrier doesn't operate alone — it leads a battle group: destroyers for perimeter defense, submarines for stealth, support ships for logistics. Each unit has a single defined role, communicates via strict protocols, and cannot take on another unit's job. Your agent team is exactly this — the lead agent is the carrier, specialists are the escorts, and the mailbox protocol is radio communications.

The 4-agent TaskFlow team

Start with the smallest team that solves the real problem. For TaskFlow feature work, four roles cover everything: a Lead that reads requirements and delegates, a Builder that writes TDD-first code, a Reviewer that enforces quality, and a Tester that validates integration.

👥 TaskFlow Team — Fan-Out Delegation Architecture

The mailbox protocol

Inter-agent communication uses file-based mailboxes — the simplest reliable channel. The lead writes task instructions to .claude/mailboxes/builder.md; the builder executes and returns results to .claude/mailboxes/results/builder.md. No shared state, no race conditions, and a full audit trail.

Phase 2 · Modules 5–6

Automation — Claude in the Pipeline

Moving Claude from interactive sessions into automated pipelines multiplies its value. Every pull request gets reviewed, every commit gets tested, every release gets validated — automatically, without a human triggering it manually each time.

Analogy — The Factory Assembly Line

A car factory doesn't rely on humans manually checking every bolt. Automated quality stations verify each stage — body alignment, paint thickness, engine torque — before the line advances. If a station fails, it stops automatically and flags the fault. Your CI/CD pipeline with Claude is identical: automated quality checks at each stage that stop and flag without requiring a human to notice.

Headless mode — the automation bridge

Claude Code's --print flag (-p) enables non-interactive operation: pipe input in, capture structured output out. This is the bridge from interactive sessions to pipelines where no human is present during execution.

⚙️ CI/CD Pipeline — Claude Code GitHub Action Flow
GitHub Actions.github/workflows/claude-review.yml
name: Claude Code PR Review on: [pull_request] jobs: review: runs-on: ubuntu-latest if: github.event.pull_request.draft == false steps: - uses: actions/checkout@v4 with: {fetch-depth: 0} - name: Claude reviews PR changes run: | DIFF=$(git diff origin/main --name-only) claude --print "Review these TaskFlow changes: 1. Naming conventions (PascalCase models, camelCase services) 2. TDD discipline (tests must precede implementation) 3. No hardcoded credentials, paths, or secrets Changed files: $DIFF Output: structured PASS/FAIL with file citations." \ --context "$(git diff origin/main)" env: ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
⚠️
Cost control in CI/CD Gate actions with if: github.event.pull_request.draft == false and limit context to changed files only (git diff --name-only). Set a token budget limit in the prompt and test the workflow on a branch before enabling on main.

Phase 3 · Modules 7–10

Patterns & Plugins

Advanced practitioners apply named design patterns to keep complex agent systems maintainable and predictable. Fan-out/fan-in handles parallelism elegantly. Writer/reviewer enforces quality through healthy separation. Plugins extend Claude Code itself via MCP — creating custom slash commands that feel native.

Analogy — Railroad Switching Stations

A well-designed rail network uses switches and signals to route trains. Fan-out is a diverging switch (one train → many tracks). Fan-in is a merging switch (many tracks → one). A gate pattern is the signal that holds a train until the track ahead is clear. You don't redesign the train for each destination — you design the network infrastructure that routes it correctly every time.

Plugin architecture — MCP

A plugin is an MCP server that exposes custom slash commands. It has three parts: a manifest (available commands), handlers (what each command does), and a registration entry in Claude's MCP config. Once registered, /taskflow scaffold model RecurringTask works exactly like any built-in command.

Phase 4 · Modules 11–16

Orchestration — The 5-Layer Model

Production agent systems need an architecture that is reasoned about, debugged, and extended by rational decomposition. The 5-layer orchestration model provides this: Intent → Classification → Routing → Execution → Verification. Every operation in your TaskFlow agent system maps to one of these layers. Which means you only need to understand the layer you're debugging — not the whole system.

Analogy — Emergency Services Dispatch

When you call 999, your call transits through layers before help arrives: Intent (you describe the emergency) → Classification (fire, police, or ambulance?) → Routing (which station is closest?) → Execution (units dispatched) → Verification (units confirm on-scene). Each layer has one job. Each can fail and be fixed independently. The system works because the layers are defined and respected.

The architecture

🏗️ The 5-Layer Orchestration Stack — TaskFlow Mapped

Five orchestration patterns

1

Intent Router

Classify requests at entry. Map signal words (implement, fix, review, deploy) to agents or skills. Fail fast with "I can't handle that" rather than attempting to hallucinate a path.

2

Pipeline

Chain processing stages: Analyse → Plan → Implement → Test → Review. Each stage is an agent invocation. Output becomes context for the next stage via file handoff. Stages are independently replaceable.

3

Gate / Guardian

Quality checkpoints between pipeline stages. A Gate blocks until defined criteria are met. A Guardian enforces invariants across the entire session. Implement with blocking: true PostToolUse hooks so enforcement is automatic, not advisory.

4

Convergence Loop

Execute → evaluate → retry until a quality threshold is reached. Always set a max iteration count (3 is a sensible default). Track iteration count in a context file — never rely on conversation history to count loop iterations reliably.

5

Specialist Delegation

Route domain sub-tasks to specialists with the right tools and constraints. The lead agent identifies the domain (security, performance, UI) and delegates — keeping the lead's context clean and each specialist focused.

Phase 5 · Modules 17–23

CORTEX Patterns — Production at Scale

The CORTEX Framework operationalises everything in this path at production scale: 314 orchestrators, 36 MCP tools, 61 governance YAMLs, ~21,000 tests — all wired together using the same patterns you've learned here. Studying CORTEX gives you battle-tested blueprints for running agent systems in real teams on real codebases.

Analogy — Building Codes & Site Inspectors

Building codes don't trust builders to self-report compliance. Site inspectors verify at each stage — foundation, framing, electrical, plumbing — before the next stage is approved. CORTEX works identically: governance YAMLs define the rules; hooks are the inspectors that verify every change against those rules at runtime, before anything is committed or deployed. The rules are readable; the enforcement is automatic.

Governance → hooks translation

The key CORTEX insight: translate human-readable governance rules into enforceable automated checks. CORE-008: tests before implementation becomes a PostToolUse hook verifying a test file exists before any source file is written. Rules become reality through hooks.
