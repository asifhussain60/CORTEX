DOC-01

Missing Code Documentation

Functions without documentation force reading implementation details

TypeScript TSDoc

How This Was Refactored

Undocumented functions were annotated with comprehensive TSDoc comments. Each function now includes @param descriptions, @returns documentation, @throws for exceptions, and @example blocks showing usage. IDEs display this documentation on hover, eliminating the need to read source code.

Why this matters: Well-documented code is 10x faster to use. Developers shouldn't need to read implementation details to understand how to call a function.
Before CORTEX
export class UserService {
    private cache = new Map<string, User>();

    async getUser(id: string, includeDeleted?: boolean) {
        if (this.cache.has(id)) {
            return this.cache.get(id)!;
        }
        const user = await this.repo.findById(id);
        if (!user || (user.deletedAt && !includeDeleted)) {
            return null;
        }
        this.cache.set(id, user);
        return user;
    }

    async updateUser(id: string, data: Partial<User>) {
        const user = await this.getUser(id);
        if (!user) throw new Error('Not found');
        const updated = { ...user, ...data };
        await this.repo.save(updated);
        this.cache.delete(id);
        return updated;
    }
}
CORTEX
After CORTEX

     */
    async getUser(
        id: string,

    ): Promise<User | null> {

     * Updates user data and invalidates cache.

Key Improvements

  • @param: Document every parameter with type and purpose
  • @returns: Describe what the function returns
  • @throws: List all exceptions that can be thrown
  • @example: Provide usage examples
DOC-02

Missing API Documentation

REST endpoints without Swagger/OpenAPI documentation

C# Swagger

How This Was Refactored

Bare controllers were annotated with Swagger attributes and XML documentation. Each endpoint now declares its response types with [ProducesResponseType], parameters are documented, and the Swagger UI provides interactive "Try it out" functionality. Clients can generate typed SDKs from the OpenAPI specification.

Why this matters: API consumers shouldn't guess what endpoints return. Self-documenting APIs reduce support burden and enable client code generation.
Before CORTEX
[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> CreateOrder(
        CreateOrderRequest request)
    {
        var order = await _orderService.CreateAsync(request);
        return CreatedAtAction(nameof(GetOrder), 
            new { id = order.Id }, order);
    }

    [HttpGet("{id}")]
    public async Task<IActionResult> GetOrder(Guid id)
    {
        var order = await _orderService.GetByIdAsync(id);
        if (order == null) return NotFound();
        return Ok(order);
    }
}
CORTEX
After CORTEX
/// <summary>Manages order lifecycle.</summary>
[ApiController]
[Route("api/[controller]")]
[Produces("application/json")]
[Tags("Orders")]
public class OrdersController : ControllerBase
{
    /// <summary>Creates a new order.</summary>
    /// <param name="request">Order details</param>
    /// <response code="201">Order created</response>
    /// <response code="400">Invalid request</response>
    [HttpPost]
    [ProducesResponseType(typeof(OrderResponse), 201)]
    [ProducesResponseType(typeof(ProblemDetails), 400)]
    public async Task<IActionResult> CreateOrder(
        [FromBody] CreateOrderRequest request) { }

    /// <summary>Gets order by ID.</summary>
    /// <param name="id">Order identifier</param>
    /// <response code="200">Order found</response>
    /// <response code="404">Order not found</response>
    [HttpGet("{id:guid}")]
    [ProducesResponseType(typeof(OrderResponse), 200)]
    [ProducesResponseType(404)]
    public async Task<IActionResult> GetOrder(Guid id) { }
}

Key Improvements

  • ProducesResponseType: Documents all response codes
  • XML comments: Appear in Swagger UI
  • Client generation: OpenAPI spec enables typed clients
DOC-03

Undocumented Angular Components

Inputs and outputs without descriptions or usage examples

Angular

How This Was Refactored

Component inputs and outputs were documented with TSDoc comments including @usageNotes with template examples, @default values, and @see references to related types. Storybook stories were added for visual documentation. The component is now self-documenting in IDEs and component libraries.

Why this matters: Reusable components need clear contracts. Without documentation, developers copy-paste code instead of reusing existing components.
Before CORTEX
@Component({
    selector: 'app-data-table',
    templateUrl: './data-table.html'
})
export class DataTableComponent<T> {
    @Input() data: T[] = [];
    @Input() columns: ColumnDef[] = [];
    @Input() pageSize = 10;
    @Input() sortable = true;
    @Input() selectable = false;
    
    @Output() rowClick = new EventEmitter<T>();
    @Output() selectionChange = new EventEmitter<T[]>();
    @Output() sortChange = new EventEmitter<SortEvent>();
    
    // No documentation - what does each input do?
    // How do I use this component?
}
CORTEX
After CORTEX
/**
 * Generic data table with sorting and selection.
 * @usageNotes
 * ```html
 * <app-data-table
 *   [data]="users"
 *   [columns]="cols"
 *   (rowClick)="onSelect($event)">
 * </app-data-table>
 * ```
 */
@Component({ selector: 'app-data-table' })
export class DataTableComponent<T> {
    /** Array of items to display. */
    @Input() data: T[] = [];
    
    /** Column definitions. @see ColumnDef */
    @Input() columns: ColumnDef[] = [];
    
    /** Rows per page. @default 10 */
    @Input() pageSize = 10;
    
    /** Enable column sorting. @default true */
    @Input() sortable = true;
    
    /** Emitted when a row is clicked. */
    @Output() rowClick = new EventEmitter<T>();
    
    /** Emitted when selection changes. */
    @Output() selectionChange = new EventEmitter<T[]>();
}

Key Improvements

  • @usageNotes: HTML template examples
  • @default: Document default values
  • Input/Output docs: Each binding explained
