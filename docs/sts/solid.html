What are SOLID Principles?

SOLID is an acronym for five design principles that make software designs more understandable, flexible, and maintainable. Created by Robert C. Martin (Uncle Bob), these principles are foundational to object-oriented design.

S - Single Responsibility

A class should have only one reason to change. One class = one job.

O - Open/Closed

Open for extension, closed for modification. Add new features without changing existing code.

L - Liskov Substitution

Subtypes must be substitutable for their base types without breaking the program.

I - Interface Segregation

Many specific interfaces are better than one general-purpose interface.

D - Dependency Inversion

Depend on abstractions, not concrete implementations.

SRP-01

God Class Violation

Single class handling multiple unrelated responsibilities

C#

How This Was Refactored

The monolithic OrderManager class was split into focused, single-purpose services. Each service now owns exactly one responsibility: validation logic moved to OrderValidator, pricing calculations to PricingService, database operations to OrderRepository, and notifications to NotificationService. The main OrderService becomes an orchestrator that coordinates these services through dependency injection.

Why this matters: Each service can now be tested, modified, and deployed independently. A change to email templates won't risk breaking price calculations.
Before CORTEX 
public class OrderManager
{
    private readonly string _connectionString;
    private readonly SmtpClient _smtp;
    
    // Does EVERYTHING - SRP violation!
    public Order CreateOrder(OrderRequest request)
    {
        // 1. Validate order
        if (string.IsNullOrEmpty(request.CustomerEmail))
            throw new Exception("Email required");
        if (request.Items.Count == 0)
            throw new Exception("No items");
            
        // 2. Calculate pricing
        decimal total = 0;
        foreach (var item in request.Items)
        {
            var price = GetProductPrice(item.ProductId);
            var discount = CalculateDiscount(item, request.CustomerId);
            total += (price - discount) * item.Quantity;
        }
        total += CalculateShipping(request.Address);
        total += total * 0.08m; // Tax
        
        // 3. Save to database
        using var conn = new SqlConnection(_connectionString);
        conn.Open();
        var cmd = new SqlCommand("INSERT INTO Orders...", conn);
        cmd.ExecuteNonQuery();
        
        // 4. Send confirmation email
        var message = new MailMessage();
        message.To.Add(request.CustomerEmail);
        message.Subject = "Order Confirmation";
        message.Body = GenerateEmailBody(request);
        _smtp.Send(message);
        
        // 5. Update inventory
        foreach (var item in request.Items)
            UpdateInventory(item.ProductId, -item.Quantity);
        
        return new Order { Total = total };
    }
    
    // ... 500 more lines of mixed responsibilities
}

After CORTEX 
// Each class has ONE responsibility
public class OrderService : IOrderService
{
    private readonly IOrderValidator _validator;
    private readonly IPricingService _pricing;
    private readonly IOrderRepository _repository;
    private readonly INotificationService _notifications;
    
    public OrderService(
        IOrderValidator validator,
        IPricingService pricing,
        IOrderRepository repository,
        INotificationService notifications)
    {
        _validator = validator;
        _pricing = pricing;
        _repository = repository;
        _notifications = notifications;
    }
    
    public async Task<Order> CreateOrderAsync(OrderRequest request)
    {
        // Orchestrates single-responsibility services
        await _validator.ValidateAsync(request);
        var pricing = await _pricing.CalculateAsync(request);
        var order = new Order(request, pricing);
        
        await _repository.SaveAsync(order);
        await _notifications.SendConfirmationAsync(order);
        
        return order;
    }
}

// Single Responsibility: Validation only
public class OrderValidator : IOrderValidator
{
    public Task ValidateAsync(OrderRequest request)
    {
        var errors = new List<ValidationError>();
        if (string.IsNullOrEmpty(request.CustomerEmail))
            errors.Add(new("Email is required"));
        if (!request.Items.Any())
            errors.Add(new("Order must have items"));
        if (errors.Any())
            throw new ValidationException(errors);
        return Task.CompletedTask;
    }
}

Key Improvements

  • Separated concerns: Validation, pricing, persistence, notification are now separate services
  • Dependency injection: All dependencies injected via constructor
  • Interface abstractions: Each service implements an interface for testability
OCP-01

Open/Closed Violation

Modifying existing code for every new payment type

TypeScript

How This Was Refactored

The giant if/else chain was replaced with the Strategy Pattern. We defined a PaymentStrategy interface that all payment methods implement. The PaymentProcessor now maintains a registry of strategies and delegates to the appropriate one at runtime. Adding a new payment method means creating a new class—no existing code needs to change.

Why this matters: You can add Venmo, Crypto, or any future payment method by simply registering a new strategy class. The core processor remains untouched and stable.
Before CORTEX 
class PaymentProcessor {
    processPayment(
        amount: number, 
        method: string, 
        details: any
    ): PaymentResult {
        // Must modify this class for every new payment type!
        if (method === 'credit_card') {
            return this.processCreditCard(amount, details);
        } else if (method === 'paypal') {
            return this.processPayPal(amount, details);
        } else if (method === 'stripe') {
            return this.processStripe(amount, details);
        } else if (method === 'apple_pay') {
            // Added later - had to modify existing code
            return this.processApplePay(amount, details);
        } else if (method === 'google_pay') {
            // Added even later - more modifications
            return this.processGooglePay(amount, details);
        }
        throw new Error(`Unknown payment method: ${method}`);
    }
    
    private processCreditCard(amount: number, details: any) {
        // Credit card specific logic
    }
    
    private processPayPal(amount: number, details: any) {
        // PayPal specific logic  
    }
}
CORTEX
After CORTEX 
// Strategy interface - open for extension
interface PaymentStrategy {
    readonly methodType: string;
    processPayment(amount: number, details: PaymentDetails): 
        Promise<PaymentResult>;
    validateDetails(details: PaymentDetails): ValidationResult;
}

// Closed for modification - never changes
class PaymentProcessor {
    private strategies = new Map<string, PaymentStrategy>();
    
    registerStrategy(strategy: PaymentStrategy): void {
        this.strategies.set(strategy.methodType, strategy);
    }
    
    async processPayment(
        amount: number,
        method: string,
        details: PaymentDetails
    ): Promise<PaymentResult> {
        const strategy = this.strategies.get(method);
        if (!strategy) {
            throw new PaymentError(`Unknown: ${method}`);
        }
        return strategy.processPayment(amount, details);
    }
}

// New payment types = new classes, no modifications
class StripeStrategy implements PaymentStrategy {
    readonly methodType = 'stripe';
    async processPayment(amount: number, details: PaymentDetails) {
        // Stripe-specific implementation
    }
}

Key Improvements

  • Strategy Pattern: Each payment method is a separate, pluggable class
  • Registry approach: New methods registered without modifying core code
  • Type safety: Interface ensures all strategies implement required methods
ISP-01

Interface Segregation Violation

Fat interface forcing implementations of unused methods

Angular

How This Was Refactored

The bloated IDataService interface was split into focused, role-specific interfaces: Readable, Writable, Deletable, and Searchable. Angular components now depend only on the capabilities they actually need. A read-only dashboard injects Readable<T>, while an admin panel might inject both Readable and Writable.

Why this matters: Components declare their exact requirements. Mock implementations for testing become trivial—just implement the one or two methods you need.
Before CORTEX 
// Fat interface - forces implementation of everything
interface IDataService<T> {
    getAll(): Observable<T[]>;
    getById(id: string): Observable<T>;
    create(item: T): Observable<T>;
    update(id: string, item: T): Observable<T>;
    delete(id: string): Observable<void>;
    search(query: string): Observable<T[]>;
    export(): Observable<Blob>;
    import(file: File): Observable<T[]>;
    validate(item: T): boolean;
    getHistory(id: string): Observable<History[]>;
}

// ReadOnly component forced to implement write methods!
@Injectable()
class ReadOnlyUserService implements IDataService<User> {
    getAll() { return this.http.get<User[]>('/api/users'); }
    getById(id: string) { return this.http.get<User>(`/api/users/${id}`); }
    
    // Forced to implement methods we don't need!
    create() { throw new Error('Not supported'); }
    update() { throw new Error('Not supported'); }
    delete() { throw new Error('Not supported'); }
    search() { throw new Error('Not supported'); }
    export() { throw new Error('Not supported'); }
    import() { throw new Error('Not supported'); }
    validate() { throw new Error('Not supported'); }
    getHistory() { throw new Error('Not supported'); }
}

After CORTEX 
// Segregated interfaces - implement only what you need
interface Readable<T> {
    getAll(): Observable<T[]>;
    getById(id: string): Observable<T>;
}

interface Writable<T> {
    create(item: T): Observable<T>;
    update(id: string, item: T): Observable<T>;
}

interface Deletable {
    delete(id: string): Observable<void>;
}

interface Searchable<T> {
    search(query: string): Observable<T[]>;
}

// Clean implementation - only what's needed
@Injectable({ providedIn: 'root' })
class UserQueryService implements Readable<User> {
    constructor(private http: HttpClient) {}
    
    getAll(): Observable<User[]> {
        return this.http.get<User[]>('/api/users');
    }
    
    getById(id: string): Observable<User> {
        return this.http.get<User>(`/api/users/${id}`);
    }
}

// Component declares exactly what it needs
@Component({ selector: 'app-user-list' })
class UserListComponent {
    constructor(private users: Readable<User>) {}
}

Key Improvements

  • Focused interfaces: Each interface represents one capability
  • Composition: Services can implement multiple interfaces as needed
  • Explicit dependencies: Components declare exactly what they need
DIP-01

Dependency Inversion Violation

High-level module depends on low-level database implementation

C# SQL

How This Was Refactored

Direct SQL queries embedded in business logic were extracted behind an IReportRepository interface. The ReportService (high-level policy) now depends on an abstraction, not the concrete SqlConnection. The actual database implementation is injected at runtime, making it possible to swap SQL Server for PostgreSQL, or use an in-memory store for testing.

Why this matters: Business logic is insulated from database changes. You can test report generation without a database, and migrate storage backends without touching business rules.
Before CORTEX 
// High-level module directly depends on low-level SQL
public class ReportService
{
    private readonly string _connectionString;
    
    public ReportService(string connectionString)
    {
        _connectionString = connectionString;
    }
    
    public SalesReport GenerateSalesReport(DateTime from, DateTime to)
    {
        // Tightly coupled to SQL Server implementation
        using var conn = new SqlConnection(_connectionString);
        conn.Open();
        
        var cmd = new SqlCommand(@"
            SELECT 
                p.Category,
                SUM(oi.Quantity) as TotalSold,
                SUM(oi.Quantity * oi.UnitPrice) as Revenue
            FROM OrderItems oi
            JOIN Products p ON oi.ProductId = p.Id
            JOIN Orders o ON oi.OrderId = o.Id
            WHERE o.OrderDate BETWEEN @from AND @to
            GROUP BY p.Category", conn);
            
        cmd.Parameters.AddWithValue("@from", from);
        cmd.Parameters.AddWithValue("@to", to);
        
        using var reader = cmd.ExecuteReader();
        var report = new SalesReport();
        while (reader.Read())
        {
            report.AddCategory(
                reader.GetString(0),
                reader.GetInt32(1),
                reader.GetDecimal(2));
        }
        return report;
    }
}

After CORTEX 
// Abstraction owned by high-level module
public interface IReportRepository
{
    Task<IEnumerable<CategorySales>> GetSalesByCategory(
        DateTime from, DateTime to);
}

// High-level module depends on abstraction
public class ReportService
{
    private readonly IReportRepository _repository;
    
    public ReportService(IReportRepository repository)
    {
        _repository = repository;
    }
    
    public async Task<SalesReport> GenerateSalesReport(
        DateTime from, DateTime to)
    {
        var sales = await _repository.GetSalesByCategory(from, to);
        return SalesReport.FromCategorySales(sales);
    }
}

// Low-level implementation depends on abstraction
public class SqlReportRepository : IReportRepository
{
    private readonly IDbConnection _connection;
    
    public async Task<IEnumerable<CategorySales>> GetSalesByCategory(
        DateTime from, DateTime to)
    {
        const string sql = @"
            SELECT Category, SUM(Quantity), SUM(Revenue)
            FROM vw_SalesByCategory
            WHERE OrderDate BETWEEN @from AND @to
            GROUP BY Category";
            
        return await _connection.QueryAsync<CategorySales>(
            sql, new { from, to });
    }
}

Key Improvements

  • Abstraction layer: Interface defines contract, not implementation
  • Dependency injection: Repository injected, not created internally
  • Testability: Can test business logic with mock repository
  • Flexibility: Easy to swap SQL Server for another database
LSP-01

Liskov Substitution Violation

Square class breaks Rectangle behavior expectations

TypeScript

How This Was Refactored

The classic Rectangle/Square inheritance was replaced with a composition-based approach. Instead of Square extends Rectangle (which violates LSP because setting width also changes height), we use a common Shape interface. Both Rectangle and Square implement Shape independently, each with appropriate behavior for their invariants.

Why this matters: Code that works with Shape won't break when you pass a Square instead of a Rectangle. The principle: subtypes must be substitutable for their base types.
Before CORTEX 
class Rectangle {
    constructor(
        protected _width: number, 
        protected _height: number
    ) {}
    
    get width() { return this._width; }
    set width(value: number) { this._width = value; }
    
    get height() { return this._height; }
    set height(value: number) { this._height = value; }
    
    getArea(): number {
        return this._width * this._height;
    }
}

// LSP Violation: Square changes Rectangle's behavior!
class Square extends Rectangle {
    constructor(side: number) {
        super(side, side);
    }
    
    // Breaks expected Rectangle behavior
    set width(value: number) {
        this._width = value;
        this._height = value; // Unexpected side effect!
    }
    
    set height(value: number) {
        this._width = value;  // Unexpected side effect!
        this._height = value;
    }
}

// This code breaks with Square!
function doubleWidth(rect: Rectangle) {
    const expectedArea = rect.width * 2 * rect.height;
    rect.width = rect.width * 2;
    console.log(rect.getArea() === expectedArea); // false for Square!
}
CORTEX
After CORTEX 
// Common abstraction without inheritance issues
interface Shape {
    getArea(): number;
    getPerimeter(): number;
}

// Immutable Rectangle - no setters, no surprises
class Rectangle implements Shape {
    constructor(
        readonly width: number, 
        readonly height: number
    ) {}
    
    getArea(): number {
        return this.width * this.height;
    }
    
    getPerimeter(): number {
        return 2 * (this.width + this.height);
    }
    
    withWidth(width: number): Rectangle {
        return new Rectangle(width, this.height);
    }
    
    withHeight(height: number): Rectangle {
        return new Rectangle(this.width, height);
    }
}

// Square is independent, not a subtype of Rectangle
class Square implements Shape {
    constructor(readonly side: number) {}
    
    getArea(): number {
        return this.side * this.side;
    }
    
    getPerimeter(): number {
        return 4 * this.side;
    }
    
    withSide(side: number): Square {
        return new Square(side);
    }
}

// Works correctly with any Shape
function printArea(shape: Shape) {
    console.log(`Area: ${shape.getArea()}`);
}

Key Improvements

  • Composition over inheritance: Both implement Shape, neither extends the other
  • Immutable design: No setters = no unexpected behavior changes
  • LSP compliant: Any Shape can be substituted without breaking code
