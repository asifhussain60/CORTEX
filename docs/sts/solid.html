🎓 What is SOLID?

SOLID is an acronym for five design principles that make software easier to understand, maintain, and extend. Think of them as "rules of thumb" that prevent code from becoming a tangled mess over time.

S

Single Responsibility Principle (SRP)

"A class should have only one reason to change."

🍳 Analogy: A chef shouldn't also be the accountant, waiter, and dishwasher. Each role should be separate.

O

Open/Closed Principle (OCP)

"Software should be open for extension, but closed for modification."

🔌 Analogy: A power strip lets you add new devices without rewiring your house.

L

Liskov Substitution Principle (LSP)

"Subtypes must be substitutable for their base types."

🦆 Analogy: If it walks like a duck and quacks like a duck, your code should work with any duck.

I

Interface Segregation Principle (ISP)

"Clients shouldn't be forced to depend on methods they don't use."

📱 Analogy: A TV remote shouldn't have buttons for a washing machine.

D

Dependency Inversion Principle (DIP)

"Depend on abstractions, not concretions."

🔌 Analogy: Your laptop uses a standard USB port, not a wire soldered directly to one specific mouse.

SOL-04 OCP HIGH

If/Else Chain: Adding Payment Methods Requires Code Changes

OCP Violation — Every time we add a new payment type (Apple Pay, Google Pay, etc.), we must modify this function. The Strategy Pattern lets us add new payment methods without touching existing code.

❌ BEFORE src/business/payment.py:17

✅ AFTER Strategy Pattern 
from abc import ABC, abstractmethod

class PaymentStrategy(ABC):
    """Base class - new payments extend this"""
    @abstractmethod
    def process(self, amount: float) -> dict: ...

class CreditCardPayment(PaymentStrategy):
    def process(self, amount): ...

class PayPalPayment(PaymentStrategy):
    def process(self, amount): ...

# Adding Apple Pay? Just create a new class!
class ApplePayPayment(PaymentStrategy):
    def process(self, amount): ...

class PaymentProcessor:
    def __init__(self):
        self.strategies: dict[str, PaymentStrategy] = {}
    
    def register(self, name: str, strategy: PaymentStrategy):
        self.strategies[name] = strategy
    
    def process(self, payment_type: str, amount: float):
        strategy = self.strategies.get(payment_type)
        return strategy.process(amount) if strategy else None

SOL-09 DIP HIGH

Tight Coupling: Can't Swap Database Without Rewriting

DIP Violation — The application creates a specific Database class directly. Want to switch from SQLite to PostgreSQL? You'd have to rewrite the entire app. Dependency Injection solves this by depending on an interface, not a concrete class.

❌ BEFORE src/app.py:37

    # TIGHT COUPLING: App is married to SQLite Database
    # Want PostgreSQL? Rewrite everything.
    # Want to test with mock DB? Can't.

    user_api = UserAPI(db)
    product_api = ProductAPI(db)
    order_api = OrderAPI(db)

✅ AFTER Dependency Injection 
from abc import ABC, abstractmethod

# Define an INTERFACE (abstraction)
class DatabaseInterface(ABC):
    @abstractmethod
    def execute(self, query: str, params: tuple): ...
    @abstractmethod
    def get_one(self, query: str, params: tuple): ...

# Concrete implementations
class SQLiteDatabase(DatabaseInterface): ...
class PostgresDatabase(DatabaseInterface): ...
class MockDatabase(DatabaseInterface): ...  # For testing!

def create_app(db: DatabaseInterface):  # Inject dependency
    """App depends on abstraction, not concrete class"""
    app = Flask(__name__)
    
    # Now we can swap databases easily!
    user_api = UserAPI(db)
    product_api = ProductAPI(db)
    
    return app

# Production: create_app(PostgresDatabase())
# Testing:    create_app(MockDatabase())

SOLID Transformation Summary

Why SOLID Matters

  • Maintainability: Small, focused classes are easier to understand and modify
  • Testability: Single-responsibility classes can be unit tested in isolation
  • Flexibility: Strategy pattern and DI make swapping implementations trivial
  • Reduced Risk: Changes to one area don't accidentally break unrelated features
  • Team Productivity: Multiple developers can work on different classes without conflicts
