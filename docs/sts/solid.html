Single Responsibility Principle

C#

How This Was Refactored

Problem: One class handling user data, validation, email, and database operations
Fix: Extract each responsibility into focused, single-purpose classes
Result: Each class has one reason to change, improving maintainability
Before: Multiple Responsibilities
public class UserManager
{
    public void CreateUser(string name, string email)
    {
        // Validation
        if (string.IsNullOrEmpty(name)) throw new Exception("Invalid");
        if (!email.Contains("@")) throw new Exception("Invalid email");
        
        // Database
        var conn = new SqlConnection(connectionString);
        conn.Open();
        // ... save user
        
        // Email
        var smtp = new SmtpClient();
        smtp.Send(new MailMessage("noreply@app.com", email));
    }
}
After: Single Responsibility
public class UserService
{
    private readonly IUserValidator _validator;
    private readonly IUserRepository _repository;
    private readonly IEmailService _emailService;
    
    public UserService(IUserValidator v, IUserRepository r, IEmailService e)
    {
        _validator = v; _repository = r; _emailService = e;
    }
    
    public async Task CreateUserAsync(CreateUserRequest request)
    {
        _validator.Validate(request);
        var user = await _repository.CreateAsync(request);
        await _emailService.SendWelcomeAsync(user);
    }
}

Open/Closed Principle

TypeScript

How This Was Refactored

Problem: Adding new payment types requires modifying existing code
Fix: Use strategy pattern with interface - extend via new classes
Result: Open for extension (new payment types), closed for modification
Before: Modification Required
class PaymentProcessor {
  process(type: string, amount: number): void {
    if (type === 'credit') {
      // Credit card logic
      console.log(\`Credit: $\${amount}\`);
    } else if (type === 'paypal') {
      // PayPal logic  
      console.log(\`PayPal: $\${amount}\`);
    } else if (type === 'crypto') {
      // Must modify this class for each new type!
      console.log(\`Crypto: $\${amount}\`);
    }
  }
}
After: Extension Only
interface PaymentStrategy {
  process(amount: number): Promise<PaymentResult>;
}

class CreditCardPayment implements PaymentStrategy { /*...*/ }
class PayPalPayment implements PaymentStrategy { /*...*/ }
class CryptoPayment implements PaymentStrategy { /*...*/ }

class PaymentProcessor {
  constructor(private strategies: Map<string, PaymentStrategy>) {}
  
  async process(type: string, amount: number): Promise<PaymentResult> {
    const strategy = this.strategies.get(type);
    if (!strategy) throw new Error(\`Unknown: \${type}\`);
    return strategy.process(amount);
  }
}

Interface Segregation Principle

Angular

How This Was Refactored

Problem: Fat interface forces classes to implement unused methods
Fix: Split into focused interfaces that clients actually need
Result: Components only depend on interfaces they use
Before: Fat Interface
interface IWorker {
  work(): void;
  eat(): void;
  sleep(): void;
  attendMeeting(): void;
  writeReport(): void;
}

// Robot must implement eat() and sleep()!
class Robot implements IWorker {
  work() { /* OK */ }
  eat() { throw new Error('Robots dont eat'); }
  sleep() { throw new Error('Robots dont sleep'); }
  attendMeeting() { /* OK */ }
  writeReport() { /* OK */ }
}
After: Segregated Interfaces
interface Workable { work(): void; }
interface Feedable { eat(): void; }
interface Restable { sleep(): void; }
interface Meetable { attendMeeting(): void; }

class Human implements Workable, Feedable, Restable, Meetable {
  work() { /* ... */ }
  eat() { /* ... */ }
  sleep() { /* ... */ }
  attendMeeting() { /* ... */ }
}

class Robot implements Workable, Meetable {
  work() { /* ... */ }
  attendMeeting() { /* ... */ }
  // No unused methods!
}

Dependency Inversion Principle

C#

How This Was Refactored

Problem: High-level module directly depends on low-level implementation
Fix: Both depend on abstractions; inject dependencies via constructor
Result: Loose coupling enables testing and swapping implementations
Before: Direct Dependency
public class OrderService
{
    private SqlDatabase _database = new SqlDatabase();
    private SmtpEmailer _emailer = new SmtpEmailer();
    
    public void PlaceOrder(Order order)
    {
        // Tightly coupled to concrete implementations
        _database.Save(order);
        _emailer.Send(order.CustomerEmail, "Order confirmed");
    }
}
After: Abstraction Dependency
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly INotificationService _notifier;
    
    public OrderService(IOrderRepository repo, INotificationService notifier)
    {
        _repository = repo;
        _notifier = notifier;
    }
    
    public async Task PlaceOrderAsync(Order order)
    {
        await _repository.SaveAsync(order);
        await _notifier.NotifyOrderConfirmedAsync(order);
    }
}
