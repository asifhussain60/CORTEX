What are SOLID Principles?

SOLID is an acronym for five design principles that make software designs more understandable, flexible, and maintainable. Created by Robert C. Martin (Uncle Bob), these principles are foundational to object-oriented design.

S - Single Responsibility

A class should have only one reason to change. One class = one job.

O - Open/Closed

Open for extension, closed for modification. Add new features without changing existing code.

L - Liskov Substitution

Subtypes must be substitutable for their base types without breaking the program.

I - Interface Segregation

Many specific interfaces are better than one general-purpose interface.

D - Dependency Inversion

Depend on abstractions, not concrete implementations.

        var discount = await _discounts.ApplyAsync(request);

CORTEX
After CORTEX 
// Strategy interface - open for extension
interface PaymentStrategy {
    readonly methodType: string;
    processPayment(amount: number, details: PaymentDetails): 
        Promise<PaymentResult>;
    validateDetails(details: PaymentDetails): ValidationResult;
}

// Closed for modification - never changes
class PaymentProcessor {
    private strategies = new Map<string, PaymentStrategy>();
    
    registerStrategy(strategy: PaymentStrategy): void {
        this.strategies.set(strategy.methodType, strategy);
    }
    
    async processPayment(
        amount: number,
        method: string,
        details: PaymentDetails
    ): Promise<PaymentResult> {
        const strategy = this.strategies.get(method);
        if (!strategy) {
            throw new PaymentError(`Unknown method: ${method}`);
        }
        
        const validation = strategy.validateDetails(details);
        if (!validation.isValid) {
            throw new ValidationError(validation.errors);
        }
        
        return strategy.processPayment(amount, details);
    }
}

// New payment types - just add new classes!
class CreditCardStrategy implements PaymentStrategy {
    readonly methodType = 'credit_card';
    
    async processPayment(amount: number, details: PaymentDetails) {
        // Credit card specific logic
        return { success: true, transactionId: '...' };
    }
    
    validateDetails(details: PaymentDetails) {
        // Validate card number, CVV, expiry
    }
}

class ApplePayStrategy implements PaymentStrategy {
    readonly methodType = 'apple_pay';
    
    async processPayment(amount: number, details: PaymentDetails) {
        // Apple Pay specific logic - no existing code modified!
        return { success: true, transactionId: '...' };
    }
}

// Registration - typically in DI container setup
const processor = new PaymentProcessor();
processor.registerStrategy(new CreditCardStrategy());
processor.registerStrategy(new PayPalStrategy());
processor.registerStrategy(new ApplePayStrategy());
// Add new strategies without touching PaymentProcessor!

What CORTEX Fixed

  • Strategy pattern: Each payment method is its own class
  • Open for extension: Add new payment methods without modifying PaymentProcessor
  • Closed for modification: Core processor code never changes
  • Registration system: New strategies registered at startup
LSP-01

Liskov Substitution Violation

Subclass that breaks base class contract

C#
Before CORTEX 
public class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
    
    public int CalculateArea() => Width * Height;
}

// LSP Violation: Square changes Rectangle behavior!
public class Square : Rectangle
{
    private int _side;
    
    public override int Width
    {
        get => _side;
        set => _side = value; // Also changes height!
    }
    
    public override int Height
    {
        get => _side;
        set => _side = value; // Also changes width!
    }
}

// This breaks when substituting Square for Rectangle
public class AreaCalculator
{
    public void ProcessRectangle(Rectangle rect)
    {
        rect.Width = 5;
        rect.Height = 10;
        
        // Expected: 50, but with Square: 100!
        var area = rect.CalculateArea();
        
        if (area != 50) // Breaks with Square
            throw new Exception("Unexpected area!");
    }
}
CORTEX
After CORTEX 
// Common interface for all shapes
public interface IShape
{
    double CalculateArea();
    double CalculatePerimeter();
}

// Immutable Rectangle - no inheritance issues
public sealed class Rectangle : IShape
{
    public int Width { get; }
    public int Height { get; }
    
    public Rectangle(int width, int height)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(width);
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(height);
        
        Width = width;
        Height = height;
    }
    
    public double CalculateArea() => Width * Height;
    public double CalculatePerimeter() => 2 * (Width + Height);
}

// Square is NOT a Rectangle - separate implementation
public sealed class Square : IShape
{
    public int Side { get; }
    
    public Square(int side)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(side);
        Side = side;
    }
    
    public double CalculateArea() => Side * Side;
    public double CalculatePerimeter() => 4 * Side;
}

// Works with any shape without assumptions
public class AreaCalculator
{
    public double CalculateTotalArea(IEnumerable<IShape> shapes)
    {
        return shapes.Sum(s => s.CalculateArea());
    }
}

// Factory for creating shapes
public static class ShapeFactory
{
    public static IShape CreateRectangle(int w, int h) => 
        new Rectangle(w, h);
    
    public static IShape CreateSquare(int side) => 
        new Square(side);
}

What CORTEX Fixed

  • Composition over inheritance: Square and Rectangle both implement IShape
  • Immutable objects: Properties set via constructor, no setters
  • Sealed classes: Prevents problematic inheritance chains
  • Factory pattern: Centralized shape creation

SOLID Best Practices

Single Responsibility

If describing a class requires "and", it probably does too much. Split it.

OrderValidator, OrderPricer, OrderSaver

Open/Closed

Use strategy, decorator, or factory patterns to extend without modifying.

interface IPaymentStrategy

Liskov Substitution

Prefer composition over inheritance. Use interfaces for polymorphism.

interface IShape { Area(); }

Dependency Inversion

Program to interfaces. Let DI containers wire implementations.

services.AddScoped<IRepo, SqlRepo>()
