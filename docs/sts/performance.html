🎓 Performance Concepts Explained

Performance isn't just about speed—it's about scalability, resource efficiency, and user experience. A function that works fine with 100 records might crash with 100,000.

N+1

N+1 Query Problem

"Making 1 query to get N records, then N more queries to get related data."

🛒 Analogy: Instead of getting all groceries in one trip, you drive to the store once per item.

O(n)

Big O Notation

"A way to describe how performance scales with input size."

📈 O(1) = constant (instant lookup)
O(n) = linear (twice the data = twice the time)
O(n²) = quadratic (twice the data = 4x the time)

💾

Caching

"Storing expensive computation results for reuse."

📒 Analogy: Writing down a phone number instead of looking it up every time you call.

🔄

Connection Pooling

"Reusing database connections instead of creating new ones for each request."

🚗 Analogy: Car sharing instead of buying a new car for every trip.

PERF-01 N+1 Queries CRITICAL

N+1 Query Problem: 1001 Queries for 1000 Orders

Performance Killer: To display 1000 orders with customer names, this code makes 1 query to get orders + 1000 queries to get each customer. That's 1001 database round-trips instead of 1 or 2!

❌ BEFORE src/data/database.py 
def get_orders_with_customers():
    """N+1 Query Problem - 1001 queries for 1000 orders!"""
    
    # Query 1: Get all orders
    orders = db.execute("SELECT * FROM orders")  # 1 query
    
    result = []
    for order in orders:  # 1000 iterations
        # Query 2-1001: Get customer for EACH order
        customer = db.get_one(
            f"SELECT * FROM customers WHERE id = {order['customer_id']}"
        )  # 1000 more queries!
        
        result.append({
            "order": order,
            "customer": customer
        })
    
    return result  # Total: 1001 queries 😱
✅ AFTER JOIN Query 
def get_orders_with_customers():
    """Single JOIN query - O(1) queries regardless of size!"""
    
    # One query with JOIN - gets everything at once
    query = """
        SELECT 
            o.id as order_id,
            o.total,
            o.created_at,
            c.id as customer_id,
            c.name as customer_name,
            c.email as customer_email
        FROM orders o
        INNER JOIN customers c ON o.customer_id = c.id
        ORDER BY o.created_at DESC
    """
    
    rows = db.execute(query)  # 1 query total! 🚀
    
    return [
        {
            "order": {"id": r["order_id"], "total": r["total"]},
            "customer": {"name": r["customer_name"], "email": r["customer_email"]}
        }
        for r in rows
    ]

PERF-02 No Pagination HIGH

Memory Bomb: Loading 1 Million Products at Once

Scalability Failure: Loading all records into memory works fine with 100 products. With 1 million? Your server runs out of memory and crashes. Pagination loads data in small chunks (e.g., 20 at a time).

❌ BEFORE src/api/products.py 
@app.route('/products')
def get_products():
    """Loads ALL products into memory - crashes at scale!"""
    
    # No LIMIT = load everything
    # 1 million products = 1 million objects in memory
    # Memory usage: potentially gigabytes!
    products = db.execute("SELECT * FROM products")
    
    return jsonify(products)  # Timeout or OOM crash
✅ AFTER Cursor Pagination 
@app.route('/products')
def get_products():
    """Paginated - constant memory regardless of total size"""
    
    page = request.args.get('page', 1, type=int)
    per_page = request.args.get('per_page', 20, type=int)
    per_page = min(per_page, 100)  # Cap at 100 max
    
    offset = (page - 1) * per_page
    
    products = db.execute(
        "SELECT * FROM products ORDER BY id LIMIT ? OFFSET ?",
        (per_page, offset)
    )
    
    total = db.get_one("SELECT COUNT(*) as count FROM products")
    
    return jsonify({
        "data": products,
        "pagination": {
            "page": page,
            "per_page": per_page,
            "total": total["count"],
            "pages": (total["count"] + per_page - 1) // per_page
        }
    })
CORTEX Capability: Architectural Review → Pagination patterns
PERF-04 No Pooling HIGH

Connection Overhead: New Connection Per Request

Resource Waste: Creating a database connection takes 50-100ms. If every request creates a new connection, you add 50-100ms latency to every request. Connection pooling keeps connections open and reuses them.

❌ BEFORE src/data/database.py:18 
class Database:
    def __init__(self, db_path: str):
        # New connection created in constructor
        # Each request = new Database() = new connection
        # 100ms overhead per request!
        self.connection = sqlite3.connect(db_path)
    
    def execute(self, query: str):
        # Uses single connection, but it's created fresh
        cursor = self.connection.cursor()
        return cursor.execute(query).fetchall()
    
    def close(self):
        self.connection.close()

# In request handler:
def handle_request():
    db = Database("app.db")  # 100ms to connect
    result = db.execute("SELECT * FROM users")
    db.close()  # Connection thrown away
    return result
✅ AFTER Connection Pool 
from sqlalchemy import create_engine
from sqlalchemy.pool import QueuePool

# Create engine with connection pool (once at startup)
engine = create_engine(
    "sqlite:///app.db",
    poolclass=QueuePool,
    pool_size=5,           # Keep 5 connections ready
    max_overflow=10,       # Allow 10 more under load
    pool_pre_ping=True,    # Verify connections are alive
    pool_recycle=3600      # Refresh connections hourly
)

class Database:
    def execute(self, query: str):
        # Get connection from pool (instant!)
        with engine.connect() as conn:
            result = conn.execute(text(query))
            return result.fetchall()
        # Connection returned to pool, not closed

# In request handler:
def handle_request():
    # No connection overhead - reuses pooled connection
    return db.execute("SELECT * FROM users")  # ~0ms connect

Performance Transformation Summary

Key Optimizations

  • N+1 Eliminated: 1001 queries → 1 query with JOIN
  • Pagination Added: Constant memory usage at any scale
  • Connection Pooling: 100ms → ~0ms connection overhead
  • Caching: Expensive computations stored for reuse
  • Async Operations: Non-blocking I/O for better throughput
