PERF-01

N+1 Query Problem

Executing separate database queries for each item in a collection

C# EF Core SQL

How This Was Refactored

The loop executing N additional queries was replaced with eager loading using .Include(). Entity Framework Core now generates a single SQL query with JOINs to fetch orders and their related items in one database round-trip. For 100 orders, this reduces 101 queries to just 1.

Why this matters: N+1 is a silent performance killer. With 1000 orders, you're making 1001 database calls instead of 1—that's 1000x more network latency.
Before CORTEX
public List<OrderDto> GetOrders()
{
    // Query 1: Get all orders
    var orders = _context.Orders.ToList();
    
    var result = new List<OrderDto>();
    foreach (var order in orders)
    {
        // Query N: For EACH order, hit DB again!
        var items = _context.OrderItems
            .Where(i => i.OrderId == order.Id)
            .ToList();
            
        result.Add(new OrderDto {
            Order = order,
            Items = items  // N+1 problem!
        });
    }
    return result;
}
// 100 orders = 101 database queries!
CORTEX
After CORTEX
public async Task<List<OrderDto>> GetOrdersAsync()
{
    // Single query with eager loading
    var orders = await _context.Orders
        .Include(o => o.Items)      // JOIN in SQL
        .Include(o => o.Customer)   // Another JOIN
        .AsNoTracking()              // Read-only = faster
        .ToListAsync();
    
    return orders.Select(o => new OrderDto {
        Order = o,
        Items = o.Items,
        CustomerName = o.Customer.Name
    }).ToList();
}
// 100 orders = 1 database query with JOINs!

Key Improvements

  • Eager loading: .Include() loads related data in one query
  • AsNoTracking: Disables change tracking for read-only scenarios
  • Async: Non-blocking database operations
PERF-02

Blocking Synchronous I/O

Sequential API calls blocking the event loop

TypeScript

How This Was Refactored

Sequential await calls were parallelized using Promise.all(). Independent API calls now execute concurrently instead of waiting for each other. Three 100ms calls complete in ~100ms total instead of 300ms. For dependent calls, we batch where possible.

Why this matters: Users wait for the sum of all sequential calls. Parallel execution reduces wait time to the longest single call.
Before CORTEX
async function loadDashboard(userId: string) {
    // Sequential: Each waits for previous!
    const user = await fetchUser(userId);      // 100ms
    const orders = await fetchOrders(userId);  // 150ms
    const reviews = await fetchReviews(userId); // 80ms
    const recommendations = await fetchRecs(userId);
    
    // Total: 100 + 150 + 80 + 120 = 450ms!
    return { user, orders, reviews, recommendations };
}

// Even worse: sequential in a loop
async function loadAllUsers(ids: string[]) {
    const users = [];
    for (const id of ids) {
        users.push(await fetchUser(id)); // One at a time!
    }
    return users;
}
CORTEX
After CORTEX
async function loadDashboard(userId: string) {
    // Parallel: All requests fire simultaneously!
    const [user, orders, reviews, recs] = await Promise.all([
        fetchUser(userId),
        fetchOrders(userId),
        fetchReviews(userId),
        fetchRecommendations(userId)
    ]);
    
    // Total: max(100, 150, 80, 120) = 150ms!
    return { user, orders, reviews, recommendations: recs };
}

// Parallel with error handling
async function loadAllUsers(ids: string[]) {
    const results = await Promise.allSettled(
        ids.map(id => fetchUser(id))
    );
    return results
        .filter(r => r.status === 'fulfilled')
        .map(r => r.value);
}

Key Improvements

  • Promise.all: Executes independent promises in parallel
  • Promise.allSettled: Handles partial failures gracefully
  • 3x faster: 450ms → 150ms for this dashboard
PERF-03

Memory Leak - Unsubscribed Observables

Subscriptions not cleaned up on component destroy

Angular

How This Was Refactored

Manual subscriptions were replaced with the async pipe and takeUntilDestroyed(). The async pipe automatically subscribes in the template and unsubscribes when the component is destroyed. For imperative subscriptions, we use Angular's DestroyRef to clean up automatically.

Why this matters: Leaked subscriptions keep components alive in memory, accumulating with each navigation. After 50 route changes, you have 50 zombie components.
Before CORTEX
@Component({ selector: 'app-dashboard' })
export class DashboardComponent implements OnInit {
    users: User[] = [];
    
    ngOnInit() {
        // LEAK: Never unsubscribed!
        this.userService.getUsers().subscribe(
            users => this.users = users
        );
        
        // LEAK: Interval keeps firing after destroy!
        interval(5000).subscribe(() => {
            this.refreshData();
        });
        
        // LEAK: Route params subscription
        this.route.params.subscribe(params => {
            this.loadUser(params['id']);
        });
    }
    // No ngOnDestroy = memory leaks!
}
CORTEX
After CORTEX
@Component({ selector: 'app-dashboard' })
export class DashboardComponent {
    // Option 1: Async pipe (preferred)
    users$ = this.userService.getUsers();
    
    private destroyRef = inject(DestroyRef);
    
    constructor() {
        // Option 2: takeUntilDestroyed for imperative
        interval(5000).pipe(
            takeUntilDestroyed(this.destroyRef)
        ).subscribe(() => this.refreshData());
        
        // Auto-cleanup with takeUntilDestroyed
        this.route.params.pipe(
            takeUntilDestroyed(this.destroyRef)
        ).subscribe(p => this.loadUser(p['id']));
    }
}
// Template: <div *ngFor="let u of users$ | async">

Key Improvements

  • Async pipe: Auto-subscribes and unsubscribes in template
  • takeUntilDestroyed: Angular 16+ automatic cleanup
  • No manual tracking: Framework handles lifecycle
PERF-04

O(n²) Algorithm

Nested loops for lookups that should use hash-based structures

C#

How This Was Refactored

The nested loop with O(n²) complexity was replaced with a Dictionary lookup achieving O(n). We build a hash map of products once, then look up each order item in O(1). For 10,000 items, this changes from 100,000,000 operations to ~20,000 operations.

Why this matters: O(n²) algorithms work fine with 100 items but become unusable with 10,000. The Dictionary approach scales linearly.
Before CORTEX
public decimal CalculateTotal(
    List<OrderItem> items, 
    List<Product> products)
{
    decimal total = 0;
    
    // O(n²) - nested loops!
    foreach (var item in items)  // n iterations
    {
        foreach (var product in products)  // × n iterations
        {
            if (product.Id == item.ProductId)
            {
                total += product.Price * item.Quantity;
                break;
            }
        }
    }
    return total;
}
// 10,000 items × 10,000 products = 100M comparisons!
CORTEX
After CORTEX
public decimal CalculateTotal(
    List<OrderItem> items, 
    List<Product> products)
{
    // O(n) - build dictionary once
    var productLookup = products.ToDictionary(
        p => p.Id, 
        p => p.Price);
    
    // O(n) - single pass with O(1) lookups
    return items.Sum(item => 
        productLookup.TryGetValue(item.ProductId, out var price)
            ? price * item.Quantity
            : 0m);
}
// 10,000 items + 10,000 products = ~20K operations!

Key Improvements

  • Dictionary lookup: O(1) instead of O(n) per lookup
  • LINQ Sum: Clean, readable aggregation
  • 5000x faster: For 10K items, 100M → 20K operations
