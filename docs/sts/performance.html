N+1 Query Problem

C#

How This Was Refactored

  • Problem: Lazy loading triggers N+1 database queries
  • Fix: Use eager loading with Include() to batch queries
  • Result: Reduced from 101 queries to 1 query
Before: N+1 Queries
public List<OrderDto> GetOrders()
{
    var orders = _context.Orders.ToList(); // 1 query
    
    return orders.Select(o => new OrderDto
    {
        Id = o.Id,
        // Each access triggers a query!
        CustomerName = o.Customer.Name, // N queries
        Items = o.Items.Select(i => i.Name).ToList()
    }).ToList();
}
// Total: 1 + N + N = potentially 201 queries!
After: Eager Loading
public List<OrderDto> GetOrders()
{
    var orders = _context.Orders
        .Include(o => o.Customer)      // Join customer
        .Include(o => o.Items)         // Join items
        .AsNoTracking()                 // Read-only optimization
        .ToList();                      // 1 query total!
    
    return orders.Select(o => new OrderDto
    {
        Id = o.Id,
        CustomerName = o.Customer.Name,
        Items = o.Items.Select(i => i.Name).ToList()
    }).ToList();
}

Sequential vs Parallel Async

TypeScript

How This Was Refactored

  • Problem: Sequential awaits block unnecessarily
  • Fix: Use Promise.all() for independent operations
  • Result: 3 seconds reduced to 1 second (parallel)
Before: Sequential (3s)
async function loadDashboard(userId: string) {
  // Each await blocks the next - total 3 seconds!
  const user = await fetchUser(userId);      // 1 sec
  const orders = await fetchOrders(userId);  // 1 sec  
  const stats = await fetchStats(userId);    // 1 sec
  
  return { user, orders, stats };
}
After: Parallel (1s)
async function loadDashboard(userId: string) {
  // All requests fire simultaneously!
  const [user, orders, stats] = await Promise.all([
    fetchUser(userId),
    fetchOrders(userId),
    fetchStats(userId)
  ]);
  // Total time = slowest request only (1 sec)
  
  return { user, orders, stats };
}

Angular Change Detection

Angular

How This Was Refactored

  • Problem: Default change detection checks entire tree
  • Fix: OnPush strategy + immutable data patterns
  • Result: Component only re-renders when inputs change
Before: Check Always
@Component({
  selector: 'app-user-list',
  template: `
    <div *ngFor="let user of users">
      {{ user.name }} - {{ getStatus(user) }}
    </div>
  `
  // Default: checks on EVERY change detection cycle
})
export class UserListComponent {
  @Input() users: User[];
  
  getStatus(user: User): string {
    console.log('Called every cycle!');
    return user.active ? 'Active' : 'Inactive';
  }
}
After: OnPush + Pure Pipe
@Component({
  selector: 'app-user-list',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <div *ngFor="let user of users; trackBy: trackById">
      {{ user.name }} - {{ user | userStatus }}
    </div>
  `
})
export class UserListComponent {
  @Input() users: User[];
  trackById = (i: number, user: User) => user.id;
}

@Pipe({ name: 'userStatus', pure: true })
export class UserStatusPipe implements PipeTransform {
  transform(user: User): string {
    return user.active ? 'Active' : 'Inactive';
  }
}

Database Indexing

SQL

How This Was Refactored

  • Problem: Full table scan on every query
  • Fix: Add covering index for common query patterns
  • Result: Query time from 5s to 10ms
Before: Full Table Scan
-- No index on Status or CreatedAt
-- Full table scan: 5+ seconds on 10M rows

SELECT OrderId, CustomerId, Total, Status
FROM Orders
WHERE Status = 'Pending'
  AND CreatedAt > DATEADD(day, -7, GETDATE())
ORDER BY CreatedAt DESC;

-- Execution plan shows: Table Scan (100% cost)
After: Covering Index
-- Create covering index for this query pattern
CREATE NONCLUSTERED INDEX IX_Orders_Status_Date
ON Orders (Status, CreatedAt DESC)
INCLUDE (OrderId, CustomerId, Total);

-- Same query now uses Index Seek: 10ms
SELECT OrderId, CustomerId, Total, Status
FROM Orders
WHERE Status = 'Pending'
  AND CreatedAt > DATEADD(day, -7, GETDATE())
ORDER BY CreatedAt DESC;

-- Execution plan: Index Seek (0.01% cost)

Cache-Aside Pattern (Lazy Loading)

C#

How This Was Refactored

  • Problem: Every request hits database (3 network round trips per call)
  • Fix: Implement cache-aside with TTL and miss handling
  • Result: 66% latency reduction (200ms → 68ms)
Before: No Caching (3 Calls)
public async Task<User> GetUserAsync(int userId)
{
    // Always hits database
    var user = await _db.Users
        .Include(u => u.Profile)
        .Include(u => u.Preferences)
        .FirstOrDefaultAsync(u => u.Id == userId);
    
    return user;
}

// Every call = 3 network round trips:
// 1. Query database
// 2. Load Profile (JOIN)
// 3. Load Preferences (JOIN)
// Total latency: ~200ms per request
After: Cache-Aside Pattern
public async Task<User> GetUserAsync(int userId)
{
    string cacheKey = $"user:{userId}";
    
    // Check cache first
    var cachedUser = await _cache.GetAsync<User>(cacheKey);
    if (cachedUser != null)
    {
        return cachedUser; // Cache hit: ~2ms
    }
    
    // Cache miss: Load from database
    var user = await _db.Users
        .Include(u => u.Profile)
        .Include(u => u.Preferences)
        .AsNoTracking() // Read-only optimization
        .FirstOrDefaultAsync(u => u.Id == userId);
    
    // Populate cache with 5-minute TTL
    await _cache.SetAsync(cacheKey, user, TimeSpan.FromMinutes(5));
    
    return user;
}
// Cache hit: 2ms (98% of requests)
// Cache miss: 200ms (2% of requests)
// Average latency: 68ms (66% improvement)

Object Pooling Pattern

C#

How This Was Refactored

  • Problem: Creating 10,000 objects per second (high GC pressure)
  • Fix: Reuse objects from pre-allocated pool
  • Result: 80% reduction in allocations, 50% faster throughput
Before: Create/Destroy Objects
public class MessageProcessor
{
    public async Task ProcessMessagesAsync(IEnumerable<byte[]> messages)
    {
        foreach (var data in messages)
        {
            // Create new buffer for each message
            var buffer = new byte[8192];
            Array.Copy(data, buffer, data.Length);
            
            // Process message
            await ProcessAsync(buffer);
            
            // Buffer eligible for GC
        }
    }
}

// Metrics:
// - 10,000 allocations/sec (81,920 KB/sec)
// - GC Gen0: Every 2 seconds
// - GC Gen1: Every 10 seconds
// - Throughput: 5,000 msg/sec
After: Object Pool
public class MessageProcessor
{
    private readonly ArrayPool<byte> _bufferPool;
    
    public MessageProcessor()
    {
        _bufferPool = ArrayPool<byte>.Shared;
    }
    
    public async Task ProcessMessagesAsync(IEnumerable<byte[]> messages)
    {
        foreach (var data in messages)
        {
            // Rent buffer from pool (reuse)
            byte[] buffer = _bufferPool.Rent(8192);
            
            try
            {
                Array.Copy(data, buffer, data.Length);
                await ProcessAsync(buffer);
            }
            finally
            {
                // Return buffer to pool (don't destroy)
                _bufferPool.Return(buffer, clearArray: true);
            }
        }
    }
}

// Metrics:
// - ~100 allocations/sec (pool misses only)
// - GC Gen0: Every 30 seconds (15x reduction)
// - GC Gen1: Every 2 minutes (12x reduction)
// - Throughput: 7,500 msg/sec (50% faster)

Algorithm Complexity Optimization

TypeScript

How This Was Refactored

  • Problem: O(n²) nested loops for finding pairs
  • Fix: O(n) hash table lookup with complement tracking
  • Result: 100x faster for 1,000 items (500ms → 5ms)
Before: O(n²) Nested Loops
function findPairsWithSum(numbers: number[], target: number): number[][] {
    const pairs: number[][] = [];
    
    // Outer loop: O(n)
    for (let i = 0; i < numbers.length; i++) {
        // Inner loop: O(n) for each outer iteration
        for (let j = i + 1; j < numbers.length; j++) {
            if (numbers[i] + numbers[j] === target) {
                pairs.push([numbers[i], numbers[j]]);
            }
        }
    }
    
    return pairs;
}

// Time Complexity: O(n²)
// Space Complexity: O(1)
// 
// Performance:
// n = 100:    2ms
// n = 1,000:  500ms
// n = 10,000: 50 seconds (unusable!)
After: O(n) Hash Table
function findPairsWithSum(numbers: number[], target: number): number[][] {
    const pairs: number[][] = [];
    const seen = new Set<number>();
    
    // Single pass: O(n)
    for (const num of numbers) {
        const complement = target - num;
        
        // Hash table lookup: O(1)
        if (seen.has(complement)) {
            pairs.push([complement, num]);
        }
        
        seen.add(num);
    }
    
    return pairs;
}

// Time Complexity: O(n)
// Space Complexity: O(n)
// 
// Performance:
// n = 100:    <1ms (2x faster)
// n = 1,000:  5ms (100x faster)
// n = 10,000: 45ms (1,100x faster)

LRU Cache Eviction Strategy

Python

How This Was Refactored

  • Problem: Unbounded cache grows infinitely (memory leak)
  • Fix: LRU eviction with OrderedDict and max size limit
  • Result: Predictable memory usage, 95%+ hit rate maintained
Before: Unbounded Cache
class Cache:
    def __init__(self):
        self._cache = {}  # No size limit!
    
    def get(self, key):
        return self._cache.get(key)
    
    def set(self, key, value):
        self._cache[key] = value  # Grows forever

# Usage over time:
# Hour 1: 1,000 entries (8 MB)
# Hour 6: 10,000 entries (80 MB)
# Day 1:  50,000 entries (400 MB)
# Week 1: 500,000 entries (4 GB)  ← Memory leak!
# 
# Eventually causes OutOfMemoryError
After: LRU Cache
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int = 1000):
        self._cache = OrderedDict()
        self._capacity = capacity
    
    def get(self, key):
        if key not in self._cache:
            return None
        
        # Move to end (mark as recently used)
        self._cache.move_to_end(key)
        return self._cache[key]
    
    def set(self, key, value):
        if key in self._cache:
            # Update existing, move to end
            self._cache.move_to_end(key)
        
        self._cache[key] = value
        
        # Evict least recently used if over capacity
        if len(self._cache) > self._capacity:
            self._cache.popitem(last=False)  # Remove oldest

# Steady state:
# Max size: 1,000 entries (8 MB) - CONSTANT
# Hit rate: 95%+ (hot data stays cached)
# Memory: Predictable and bounded
# Evictions: Only affects cold data
