Code Quality Principles

These timeless principles help you write code that's easier to understand, maintain, and extend.

DRY - Don't Repeat Yourself

Every piece of knowledge should have a single, unambiguous representation.

KISS - Keep It Simple

Simplicity is the ultimate sophistication. Avoid unnecessary complexity.

YAGNI - You Aren't Gonna Need It

Don't build features until they're actually needed.

DRY-01

Duplicated Validation Logic

Same validation rules copy-pasted across multiple components

Angular

How This Was Refactored

Copy-pasted validation logic was extracted into a shared ValidationService and reusable Angular directives. Email validation, password strength checks, and phone formatting now live in one place. Components use declarative validators like [appEmailValidator] instead of duplicating regex patterns everywhere.

Why this matters: When validation rules change (e.g., new password requirements), you update one file instead of hunting through dozens of components.
Before CORTEX 
// login.component.ts
@Component({...})
export class LoginComponent {
    validateEmail(email: string): boolean {
        const regex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
        return regex.test(email);
    }
}

// register.component.ts - SAME CODE!
@Component({...})
export class RegisterComponent {
    validateEmail(email: string): boolean {
        const regex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
        return regex.test(email);
    }
    
    validatePassword(password: string): boolean {
        return password.length >= 8 &&
               /[A-Z]/.test(password) &&
               /[0-9]/.test(password);
    }
}

// profile.component.ts - SAME CODE AGAIN!
@Component({...})
export class ProfileComponent {
    validateEmail(email: string): boolean {
        const regex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
        return regex.test(email);
    }
}

// Bug: regex is slightly different in forgot-password.component.ts!
// Now you have 4 places to update if rules change...
CORTEX
After CORTEX 
// shared/validators/validation.service.ts
@Injectable({ providedIn: 'root' })
export class ValidationService {
    private readonly EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    
    isValidEmail(email: string): boolean {
        return this.EMAIL_REGEX.test(email);
    }
    
    validatePassword(password: string): ValidationResult {
        const errors: string[] = [];
        if (password.length < 8) 
            errors.push('At least 8 characters');
        if (!/[A-Z]/.test(password)) 
            errors.push('One uppercase letter');
        if (!/[0-9]/.test(password)) 
            errors.push('One number');
        return { valid: errors.length === 0, errors };
    }
}

// Reusable validator directive
@Directive({
    selector: '[appEmailValidator]',
    providers: [{ provide: NG_VALIDATORS, useExisting: EmailValidatorDirective }]
})
export class EmailValidatorDirective implements Validator {
    constructor(private validation: ValidationService) {}
    
    validate(control: AbstractControl): ValidationErrors | null {
        return this.validation.isValidEmail(control.value) 
            ? null 
            : { email: 'Invalid email format' };
    }
}

// Usage in any component
<input type="email" appEmailValidator />

Key Improvements

  • Single source of truth: All validation rules in one service
  • Reusable directives: Declarative validation in templates
  • Consistent behavior: Same rules applied everywhere
KISS-01

Over-Engineered Conditional

Complex nested logic that could be simplified

TypeScript

How This Was Refactored

Deeply nested if/else chains were replaced with early returns (guard clauses). Each condition is checked at the start of the function, returning early if not met. This "fail fast" approach flattens the code structure from 6 levels of nesting to 1, making the happy path clearly visible at the end.

Why this matters: Nested code is exponentially harder to understand and test. Each nesting level doubles the cognitive load required to follow the logic.
Before CORTEX 
function processOrder(order: Order): Result {
    if (order) {
        if (order.items && order.items.length > 0) {
            if (order.customer) {
                if (order.customer.isActive) {
                    if (order.paymentMethod) {
                        if (isValidPayment(order.paymentMethod)) {
                            // Finally! The actual logic, 6 levels deep
                            const total = calculateTotal(order);
                            const tax = calculateTax(total);
                            return {
                                success: true,
                                total: total + tax
                            };
                        } else {
                            return { success: false, error: 'Invalid payment' };
                        }
                    } else {
                        return { success: false, error: 'No payment method' };
                    }
                } else {
                    return { success: false, error: 'Inactive customer' };
                }
            } else {
                return { success: false, error: 'No customer' };
            }
        } else {
            return { success: false, error: 'No items' };
        }
    } else {
        return { success: false, error: 'No order' };
    }
}
CORTEX
After CORTEX 
function processOrder(order: Order | null): Result {
    // Guard clauses - fail fast and return early
    if (!order) {
        return { success: false, error: 'No order' };
    }
    
    if (!order.items?.length) {
        return { success: false, error: 'No items' };
    }
    
    if (!order.customer) {
        return { success: false, error: 'No customer' };
    }
    
    if (!order.customer.isActive) {
        return { success: false, error: 'Inactive customer' };
    }
    
    if (!order.paymentMethod) {
        return { success: false, error: 'No payment method' };
    }
    
    if (!isValidPayment(order.paymentMethod)) {
        return { success: false, error: 'Invalid payment' };
    }
    
    // Happy path is now clearly visible
    const total = calculateTotal(order);
    const tax = calculateTax(total);
    
    return {
        success: true,
        total: total + tax
    };
}

Key Improvements

  • Guard clauses: Check and exit early for invalid cases
  • Flat structure: No nesting, easy to follow top to bottom
  • Clear happy path: Business logic is visible, not buried
YAGNI-01

Premature Abstraction

Complex factory pattern for a simple use case

C#

How This Was Refactored

An elaborate factory/strategy/builder pattern hierarchy was collapsed into a simple class that directly solves the current need. The original code had 8 classes to handle 2 notification types "in case we add more later." We replaced it with a straightforward NotificationService that can be refactored when (not if) requirements actually change.

Why this matters: Over-engineering costs time now and makes the code harder to understand. Build for today's requirements; refactor when tomorrow's arrive.
Before CORTEX

public interface INotificationStrategy { ... }
public interface INotificationBuilder { ... }
public interface INotificationValidator { ... }

public class NotificationFactory : INotificationFactory
{
    public INotificationStrategy CreateStrategy(string type) =>
        type switch {
            "email" => new EmailStrategy(),
            "sms" => new SmsStrategy(),
            _ => throw new NotSupportedException()
        };
}

public class NotificationBuilder : INotificationBuilder
{
    // 50 lines of builder pattern
}

public class NotificationOrchestrator
{
    private readonly INotificationFactory _factory;
    private readonly INotificationBuilder _builder;
    private readonly INotificationValidator _validator;
    
    // Constructor with 4 dependencies
    // Send method with 30 lines of orchestration
}

// "We might need push notifications someday!"
// Spoiler: 2 years later, still just email and SMS
CORTEX
After CORTEX 
// Simple, direct solution for current needs
public class NotificationService
{
    private readonly IEmailSender _email;
    private readonly ISmsSender _sms;
    
    public NotificationService(
        IEmailSender email, 
        ISmsSender sms)
    {
        _email = email;
        _sms = sms;
    }
    
    public async Task SendAsync(Notification notification)
    {
        switch (notification.Type)
        {
            case NotificationType.Email:
                await _email.SendAsync(
                    notification.To,
                    notification.Subject,
                    notification.Body);
                break;
                
            case NotificationType.Sms:
                await _sms.SendAsync(
                    notification.Phone,
                    notification.Body);
                break;
        }
    }
}

// When push notifications ARE needed:
// 1. Add IPushSender dependency
// 2. Add case to switch
// Total: 10 minutes, not 2 days of "architecture"

Key Improvements

  • Solve today's problem: Don't architect for imaginary requirements
  • Simple is maintainable: Anyone can understand and modify this
  • Easy to extend: When new types are needed, the path is clear
DRY-02

Magic Strings Everywhere

Hardcoded strings scattered throughout the codebase

C# SQL

How This Was Refactored

Scattered string literals were consolidated into strongly-typed constants and enums. Status codes moved to an OrderStatus enum with a [EnumMember] attribute for database mapping. Column names became constants in a DbColumns class. Now the compiler catches typos, and IDE refactoring works across the entire codebase.

Why this matters: A typo like "Pening" vs "Pending" won't be caught until runtime. With constants, the compiler finds mistakes immediately.
Before CORTEX 
public class OrderService
{
    public void UpdateStatus(int orderId, string status)
    {
        // Magic strings everywhere!
        if (status == "pending") { }
        else if (status == "Pending") { } // Inconsistent!
        else if (status == "PENDING") { } // Another variant!
    }
}

public class OrderRepository
{
    public List<Order> GetByStatus(string status)
    {
        // Typo: "Pening" - won't find anything!
        var sql = "SELECT * FROM Orders WHERE Status = @status";
        return _db.Query<Order>(sql, new { status });
    }
}

// In 15 different files:
// "pending", "Pending", "PENDING", "Pening"
// Good luck finding them all when requirements change!
CORTEX
After CORTEX 
// Strongly typed status with database mapping
public enum OrderStatus
{
    [EnumMember(Value = "pending")]
    Pending,
    
    [EnumMember(Value = "confirmed")]
    Confirmed,
    
    [EnumMember(Value = "shipped")]
    Shipped,
    
    [EnumMember(Value = "delivered")]
    Delivered,
    
    [EnumMember(Value = "cancelled")]
    Cancelled
}

public class OrderService
{
    public void UpdateStatus(int orderId, OrderStatus status)
    {
        // Compiler enforces valid values
        if (status == OrderStatus.Pending) { }
        
        // Typo? Won't compile!
        // if (status == OrderStatus.Pening) { } // Error!
    }
}

public class OrderRepository
{
    public List<Order> GetByStatus(OrderStatus status)
    {
        var sql = $"SELECT * FROM Orders WHERE Status = @status";
        return _db.Query<Order>(sql, new { 
            status = status.GetEnumMemberValue() 
        });
    }
}

Key Improvements

  • Enum type safety: Compiler catches invalid values
  • EnumMember mapping: Clean conversion to database strings
  • IDE support: Refactoring, find references, autocomplete all work
