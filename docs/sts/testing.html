TEST-01

Missing Unit Tests

Critical business logic with zero test coverage

TypeScript

How This Was Refactored

The untested calculateDiscount function was covered with comprehensive unit tests using Jest. Tests follow the AAA pattern (Arrange-Act-Assert) and cover edge cases: tier boundaries, empty carts, negative values, and maximum discounts. Each business rule now has at least one corresponding test.

Why this matters: Untested code is legacy code. Without tests, every change risks breaking existing functionality—and you won't know until customers report bugs.
Before CORTEX
// discount.service.ts - NO TESTS!
export function calculateDiscount(
    cart: CartItem[], 
    customerTier: string
): number {
    const subtotal = cart.reduce(
        (sum, item) => sum + item.price * item.qty, 0
    );
    
    let discount = 0;
    if (customerTier === 'gold') discount = 0.15;
    else if (customerTier === 'silver') discount = 0.10;
    else if (subtotal > 100) discount = 0.05;
    
    // Bug: What if subtotal is negative?
    // Bug: What about 'platinum' tier?
    // No one knows until production breaks!
    return subtotal * discount;
}
CORTEX
After CORTEX
// discount.service.spec.ts
describe('calculateDiscount', () => {
    it('applies 15% for gold tier', () => {
        const cart = [{ price: 100, qty: 1 }];
        expect(calculateDiscount(cart, 'gold')).toBe(15);
    });
    
    it('applies 10% for silver tier', () => {
        const cart = [{ price: 100, qty: 1 }];
        expect(calculateDiscount(cart, 'silver')).toBe(10);
    });
    
    it('applies 5% for orders over $100', () => {
        const cart = [{ price: 150, qty: 1 }];
        expect(calculateDiscount(cart, 'bronze')).toBe(7.5);
    });
    
    it('returns 0 for empty cart', () => {
        expect(calculateDiscount([], 'gold')).toBe(0);
    });
    
    it('throws for unknown tier', () => {
        expect(() => calculateDiscount([], 'invalid'))
            .toThrow('Unknown tier');
    });
});

Key Improvements

  • AAA pattern: Arrange, Act, Assert for clarity
  • Edge cases: Empty cart, boundaries, invalid input
  • Error handling: Tests verify exceptions are thrown
TEST-02

Untestable Code - Tight Coupling

Direct instantiation prevents mocking dependencies

C# xUnit

How This Was Refactored

Concrete dependencies created with new were replaced with constructor injection of interfaces. The OrderService now receives IOrderRepository and IPaymentGateway through its constructor. Tests can inject mocks using Moq to verify behavior without hitting real databases or payment systems.

Why this matters: Tight coupling means you can't test business logic without a real database. Tests become slow, flaky, and expensive to maintain.
Before CORTEX
public class OrderService
{
    public Order CreateOrder(OrderRequest request)
    {
        // UNTESTABLE: Creates concrete dependencies!
        var repository = new SqlOrderRepository();
        var payment = new StripePaymentGateway();
        var emailer = new SmtpEmailService();
        
        var order = new Order(request);
        repository.Save(order);  // Hits real DB!
        payment.Charge(order);   // Hits real Stripe!
        emailer.Send(order);     // Sends real email!
        
        return order;
    }
}
// Cannot test without real database, Stripe, SMTP!
CORTEX
After CORTEX
public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly IPaymentGateway _payment;
    
    public OrderService(IOrderRepository repo, 
                        IPaymentGateway payment)
    {
        _repo = repo;
        _payment = payment;
    }
    
    public async Task<Order> CreateOrderAsync(OrderRequest req)
    {
        var order = new Order(req);
        await _repo.SaveAsync(order);
        await _payment.ChargeAsync(order);
        return order;
    }
}

// Test with mocks:
[Fact]
public async Task CreateOrder_SavesAndCharges()
{
    var mockRepo = new Mock<IOrderRepository>();
    var mockPay = new Mock<IPaymentGateway>();
    var svc = new OrderService(mockRepo.Object, mockPay.Object);
    
    await svc.CreateOrderAsync(new OrderRequest());
    
    mockRepo.Verify(r => r.SaveAsync(It.IsAny<Order>()));
    mockPay.Verify(p => p.ChargeAsync(It.IsAny<Order>()));
}

Key Improvements

  • Constructor injection: Dependencies provided externally
  • Interface abstraction: Mock implementations for testing
  • Verify behavior: Moq confirms methods were called correctly
TEST-03

Missing Component Integration Tests

Component never tested with its template and dependencies

Angular Jasmine

How This Was Refactored

Isolated unit tests were supplemented with TestBed integration tests that render the component with its real template. We use HttpClientTestingModule to intercept HTTP calls, and fakeAsync with tick() to test asynchronous behavior. Tests verify the rendered DOM, not just class methods.

Why this matters: A component can have correct logic but broken template bindings. Integration tests catch issues like missing *ngIf or wrong property names.
Before CORTEX
// NO TESTS AT ALL for UserListComponent!
@Component({
    selector: 'app-user-list',
    template: `
        <div *ngIf="loading">Loading...</div>
        <ul *ngIf="!loading">
            <li *ngFor="let user of users">
                {{ user.name }} - {{ user.email }}
            </li>
        </ul>
        <div *ngIf="error" class="error">{{ error }}</div>
    `
})
export class UserListComponent implements OnInit {
    users: User[] = [];
    loading = true;
    error?: string;
    
    constructor(private userService: UserService) {}
    
    ngOnInit() {
        this.userService.getUsers().subscribe({
            next: u => { this.users = u; this.loading = false; },
            error: e => { this.error = e.message; this.loading = false; }
        });
    }
}
CORTEX
After CORTEX
describe('UserListComponent', () => {
    let component: UserListComponent;
    let fixture: ComponentFixture<UserListComponent>;
    let httpMock: HttpTestingController;
    
    beforeEach(async () => {
        await TestBed.configureTestingModule({
            imports: [HttpClientTestingModule],
            declarations: [UserListComponent]
        }).compileComponents();
        
        fixture = TestBed.createComponent(UserListComponent);
        component = fixture.componentInstance;
        httpMock = TestBed.inject(HttpTestingController);
    });
    
    it('displays users after loading', fakeAsync(() => {
        fixture.detectChanges(); // triggers ngOnInit
        
        const req = httpMock.expectOne('/api/users');
        req.flush([{ name: 'John', email: 'j@test.com' }]);
        tick();
        fixture.detectChanges();
        
        const items = fixture.nativeElement.querySelectorAll('li');
        expect(items.length).toBe(1);
        expect(items[0].textContent).toContain('John');
    }));
    
    it('shows error on failure', fakeAsync(() => {
        fixture.detectChanges();
        httpMock.expectOne('/api/users').error(new ErrorEvent('fail'));
        tick();
        fixture.detectChanges();
        
        const error = fixture.nativeElement.querySelector('.error');
        expect(error).toBeTruthy();
    }));
});

Key Improvements

  • TestBed: Real Angular component testing environment
  • HttpTestingController: Mock HTTP without real network
  • DOM assertions: Verify what users actually see
TEST-04

Flaky Tests - Time Dependencies

Tests fail randomly due to system time or race conditions

C# NUnit

How This Was Refactored

Direct calls to DateTime.Now were replaced with an injectable ITimeProvider. Tests inject a FakeTimeProvider that returns controlled, predictable timestamps. No more tests that fail at midnight or on weekends because they depend on real system time.

Why this matters: Flaky tests erode trust in your test suite. Teams start ignoring failures, thinking "it's probably just flaky"—until real bugs slip through.
Before CORTEX
public class SubscriptionService
{
    public bool IsExpired(Subscription sub)
    {
        // FLAKY: Uses real system time!
        return sub.ExpiresAt < DateTime.Now;
    }
    
    public Subscription Renew(Subscription sub)
    {
        // Test results change based on when you run!
        sub.ExpiresAt = DateTime.Now.AddMonths(1);
        return sub;
    }
}

[Test]
public void IsExpired_ReturnsFalse_WhenNotExpired()
{
    var sub = new Subscription { 
        ExpiresAt = DateTime.Now.AddDays(1) // Flaky!
    };
    Assert.IsFalse(_service.IsExpired(sub));
    // Fails if test runs at 11:59 PM!
}
CORTEX
After CORTEX
public class SubscriptionService
{
    private readonly ITimeProvider _time;
    
    public SubscriptionService(ITimeProvider time) => _time = time;
    
    public bool IsExpired(Subscription sub)
    {
        return sub.ExpiresAt < _time.UtcNow;
    }
}

// Test with controlled time
public class FakeTime : ITimeProvider
{
    public DateTime UtcNow { get; set; }
}

[Test]
public void IsExpired_ReturnsFalse_WhenNotExpired()
{
    var fakeTime = new FakeTime { UtcNow = new DateTime(2025, 1, 1) };
    var service = new SubscriptionService(fakeTime);
    
    var sub = new Subscription { 
        ExpiresAt = new DateTime(2025, 1, 15) // Fixed date
    };
    
    Assert.IsFalse(service.IsExpired(sub)); // Always passes!
}

Key Improvements

  • ITimeProvider: Abstraction over system time
  • Deterministic tests: Same input = same output, always
  • Fixed dates: Tests use explicit, unchanging timestamps
