Arrange-Act-Assert Pattern

TypeScript

How This Was Refactored

  • Problem: Tests are hard to read, unclear what's being tested
  • Fix: Structure tests with clear Arrange/Act/Assert sections
  • Result: Self-documenting tests that are easy to maintain
Before: Unclear Structure
test('cart test', () => {
  const cart = new ShoppingCart();
  cart.addItem({ id: '1', name: 'Book', price: 10 });
  cart.addItem({ id: '2', name: 'Pen', price: 2 });
  expect(cart.items.length).toBe(2);
  expect(cart.getTotal()).toBe(12);
  cart.applyDiscount(0.1);
  expect(cart.getTotal()).toBe(10.8);
  cart.removeItem('1');
  expect(cart.items.length).toBe(1);
});
After: AAA Pattern
describe('ShoppingCart', () => {
  describe('applyDiscount', () => {
    it('should reduce total by percentage', () => {
      // Arrange
      const cart = new ShoppingCart();
      cart.addItem({ id: '1', name: 'Book', price: 100 });
      
      // Act
      cart.applyDiscount(0.1); // 10% off
      
      // Assert
      expect(cart.getTotal()).toBe(90);
    });
  });
});

Testable Code with DI

C#

How This Was Refactored

  • Problem: Hardcoded dependencies make unit testing impossible
  • Fix: Inject dependencies through constructor
  • Result: Can mock dependencies in tests
Before: Untestable
public class OrderService
{
    public async Task<Order> CreateOrder(OrderRequest request)
    {
        // Hardcoded - can't mock in tests!
        var db = new SqlConnection("Server=prod;...");
        var emailer = new SmtpEmailService();
        var logger = new FileLogger("orders.log");
        
        var order = new Order(request);
        await db.SaveAsync(order);
        await emailer.SendAsync(order.CustomerEmail, "...");
        logger.Log($"Order {order.Id} created");
        
        return order;
    }
}
After: Testable with DI
public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly IEmailService _email;
    private readonly ILogger _logger;
    
    public OrderService(
        IOrderRepository repo,
        IEmailService email, 
        ILogger logger)
    {
        _repo = repo;
        _email = email;
        _logger = logger;
    }
    
    public async Task<Order> CreateOrder(OrderRequest request)
    {
        var order = new Order(request);
        await _repo.SaveAsync(order);
        await _email.SendAsync(order.CustomerEmail, "...");
        _logger.Log($"Order {order.Id} created");
        return order;
    }
}

Angular Component Testing

Angular

How This Was Refactored

  • Problem: Testing implementation details, brittle tests
  • Fix: Test behavior from user's perspective
  • Result: Tests survive refactoring, catch real bugs
Before: Testing Internals
it('should toggle', () => {
  // Testing internal state - brittle!
  expect(component.isExpanded).toBeFalse();
  
  component.toggle(); // Testing internal method
  
  expect(component.isExpanded).toBeTrue();
  expect(component.ariaExpanded).toBe('true');
});

// Breaks if we rename isExpanded to isOpen
// Doesn't test what user actually sees
After: Testing Behavior
it('should expand panel when header clicked', () => {
  // Arrange
  const header = fixture.debugElement
    .query(By.css('[data-testid="panel-header"]'));
  const content = fixture.debugElement
    .query(By.css('[data-testid="panel-content"]'));
  
  // Assert initial state
  expect(content.nativeElement).toHaveClass('hidden');
  
  // Act - simulate user action
  header.triggerEventHandler('click', null);
  fixture.detectChanges();
  
  // Assert - test what user sees
  expect(content.nativeElement).not.toHaveClass('hidden');
});
