# Sharpen The Saw (STS) — Live Demo Repositories

> **STS repositories are CORTEX's proof of work.** They contain deliberately broken codebases (the "before") and their CORTEX-refactored counterparts (the "after") — demonstrating every capability in a tangible, reviewable way.

---

## What Is STS?

"Sharpen The Saw" is Stephen Covey's 7th Habit — continuous improvement through deliberate practice. In CORTEX, STS is a structured showcase environment where:

- **BadMonolith** demonstrates common anti-patterns that CORTEX's orchestrators detect and remediate
- **Refactored** shows the exact same codebase after passing through the full LENS → Challenge → Refactor pipeline
- **Examples** provide reusable session templates and scripts

STS is _not_ production code. It is intentionally exempt from CORE-008 (TDD), CORE-011 (type hints), and CORE-028 (snake_case) — because it exists to showcase what CORTEX fixes, not to be production-ready itself.

## The BadMonolith → Refactored Journey

### BadMonolith (Before)

The BadMonolith is a deliberately over-engineered legacy application that demonstrates:

| Anti-Pattern | What CORTEX Detects | CORE Rule |
|-------------|--------------------:|-----------|
| God classes with 500+ line methods | Complexity metrics via LENS AST analyzer | CORE-035 |
| No tests whatsoever | TDD enforcement gate | CORE-008 |
| Hardcoded credentials in source | Security analyzer credential scan | CORE-013 |
| Circular imports between modules | Import analyzer dependency graph | Architecture integrity |
| Mixed naming conventions | FileNamingEnforcementAgent | CORE-028 |
| No type hints or docstrings | TypeHint and Docstring agents | CORE-011, CORE-012 |
| Duplicated logic across modules | DuplicateDetectionAgent | CORE-035 |

### Refactored (After)

The Refactored directory shows the same codebase after CORTEX processing:

1. **LENS Analysis** identified all anti-patterns with confidence scores
2. **Challenge Gate** (CORE-048) presented alternatives for each remediation approach
3. **TDD Cycle** wrote failing tests for every fix before implementing
4. **Sweep Completeness** (CORE-064) ensured every instance of each anti-pattern was fixed — not just the first occurrence
5. **Governance Gate** validated all CORE rules pass on the refactored output

## Using STS for Demonstrations

### Onboarding a New Team

```
/onboard cortex-sts/CortexLabs/BadMonolith
```

This runs the full onboarding pipeline: LENS analysis → security assessment (P0/P1/P2) → SQLite dashboard generation. The output shows exactly what CORTEX would flag and fix.

### Before/After Comparison

```
/digest cortex-sts/CortexLabs/BadMonolith
/digest cortex-sts/CortexLabs/Refactored
```

The digest pipeline extracts key metrics from both versions, producing a side-by-side comparison of code quality, test coverage, governance compliance, and architectural patterns.

### Live Refactoring Session

For live demonstrations, run the refactoring pipeline against BadMonolith in real-time:

1. Onboard BadMonolith — see all anti-patterns detected
2. Run `/audit fix` — watch the 9-stage pipeline identify and fix issues
3. Compare with Refactored — verify the output matches the golden state
