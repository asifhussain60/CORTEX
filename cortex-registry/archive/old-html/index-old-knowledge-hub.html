⚙️ core/

▼

📦 What

4 subdirectories: governance/, config/, wiring/, specifications/

Contains CORE rules (CORE-001 to CORE-048), master orchestrator configuration, system contracts, and execution flow specifications.

💡 Why

Immutable system foundation that defines how CORTEX operates at its core. These files establish governance rules, orchestrator wiring contracts, and execution flow routing that all other components must follow.

🎯 When

Start here when: Debugging governance violations, fixing orchestrator wiring issues, understanding flow routing, or modifying master configuration.

Common scenarios: CORE-XXX rule violations, orchestrator not found errors, intent routing failures, configuration overrides not working.

🔧 How to Troubleshoot

Governance errors? Check core/governance/core-rules.yaml for CORE-XXX definitions and enforcement patterns.

Wiring failures? Verify core/wiring/contract.yaml (interface definitions) and wiring.yaml (orchestrator connections).

Flow routing issues? Review core/specifications/intent-routing.yaml and exec-flow.yaml for routing logic.

Config overrides? Examine core/config/master-plan.yaml and modes.yaml.

Key Files

core/governance/core-rules.yaml 📋
Purpose: 48 CORE rules (CORE-001 to CORE-048) that define CORTEX governance
Usage: Reference for all governance enforcement by EnforcementOrchestrator
core/config/master-plan.yaml 📋
Purpose: Master orchestrator configuration and wiring plan
Usage: Entry point for orchestrator initialization and wiring
core/wiring/contract.yaml 📋
Purpose: Orchestrator interface contracts (inputs/outputs)
Usage: Defines expected inputs/outputs for all orchestrators
core/specifications/exec-flow.yaml 📋
Purpose: Execution flow specifications
Usage: Maps intent → orchestrator routing logic

📄 artifacts/

▼

📦 What

4 subdirectories: response-templates/, phase-templates/, doc-templates/, workflows/

Contains LEGO blocks (7 composable response templates), phase creation templates, documentation templates, and workflow definitions (TDD, migration, security, quality).

💡 Why

Generated outputs and reusable templates that standardize how CORTEX communicates with users, creates phases, generates documentation, and executes workflows. Ensures consistency across all orchestrator outputs.

🎯 When

Start here when: Customizing response formats, creating new phases, modifying workflow steps, or understanding template structure.

Common scenarios: Response format issues, LEGO block composition errors, phase template customization, workflow execution failures.

🔧 How to Troubleshoot

Response format issues? Check artifacts/response-templates/format-standards.yaml for formatting rules.

LEGO blocks broken? Review artifacts/response-templates/content-blocks.yaml (7 blocks: INTRO, CAPABILITIES, LENS, etc.).

Phase creation errors? Verify artifacts/phase-templates/phase-template.yaml structure.

Workflow failures? Examine artifacts/workflows/*.yaml for workflow definitions.

Key Files

artifacts/response-templates/content-blocks.yaml 📋
Purpose: 7 LEGO blocks (INTRO, CAPABILITIES, LENS, ORCHESTRATORS, TUTORIAL, ONBOARDING, NEXT-STEPS)
Usage: Composable educational response templates with zero duplication
artifacts/response-templates/headers.yaml 📋
Purpose: Standard response headers (Tier 0 - immutable)
Usage: Used by all orchestrator responses for consistency
artifacts/workflows/tdd-workflow.yaml 📋
Purpose: TDD workflow definition (RED-GREEN-REFACTOR cycle)
Usage: Template for test-driven development execution

🔗 integration/

📦 What

2 subdirectories: interaction/, patterns/

Pattern enforcement errors? Review integration/patterns/*.yaml for pattern definitions.

Communication timeout? Verify integration/interaction/orchestrator-coordination.yaml for timeout settings.

API design violations? Examine integration/patterns/api-design.yaml for REST standards.

📋 planning/

▼

📦 What

4 subdirectories: phases/{planned, completed, deferred, consolidated}/, registry/, system/

Contains phase lifecycle management files, active plans registry, system roadmap, and phase status tracking.

💡 Why

Manages CORTEX work lifecycle from planning → execution → completion. Tracks all phases, maintains roadmap, and provides visibility into current/future work. Essential for project management and progress tracking.

🎯 When

Start here when: Creating new phases, tracking progress, reviewing completed work, managing deferred items, or checking roadmap status.

Common scenarios: Phase not found errors, status tracking issues, roadmap out of sync, dependency resolution problems.

🔧 How to Troubleshoot

Phase not found? Check planning/phases/planned/ for phase-XXX.yaml file existence.

Phase status wrong? Verify planning/index.yaml registry has correct status.

Roadmap out of sync? Review planning/system/roadmap.yaml for latest entries.

Phase dependencies broken? Check phase YAML file's dependencies field for circular references.

Key Files

planning/index.yaml 📋
Purpose: Active plans registry with status tracking
Usage: Used by PlanRegistry orchestrator for phase lifecycle management
planning/phases/planned/phase-103.yaml 📋
Purpose: Phase 103 - Registry & Intelligence Consolidation
Usage: Defines this registry consolidation effort (you're reading the result!)

📚 knowledge-base/

▼

📦 What

20+ subdirectories: architecture/, security/, testing/, cloud/, domains/, devops/, frontend/, microservices/, etc.

Contains CORTEX default knowledge base with industry best practices, design patterns, security standards, and technology stack guidance.

💡 Why

Tier 0 fallback knowledge that fills gaps when company-specific rules don't cover a scenario. Provides industry standards (OWASP, 12-Factor, SOLID) and best practices that CORTEX uses as default behavior.

🎯 When

Start here when: Company rules don't cover your scenario, you need industry standards, learning best practices, or understanding CORTEX default behavior.

Common scenarios: Missing design pattern, security vulnerability reference, testing strategy guidance, cloud deployment standards.

🔧 How to Troubleshoot

Missing best practice? Search knowledge-base/{domain}/ for relevant YAML files.

Override not working? Check if company/domains/ has higher precedence override (Tier 1 > Tier 0).

Knowledge gap? Review knowledge-base/architecture/ for design patterns and principles.

Need industry standard? Check knowledge-base/security/ for OWASP, knowledge-base/testing/ for TDD practices.

Key Files

knowledge-base/architecture/solid-principles.yaml 📋
Purpose: SOLID principles reference (Single Responsibility, Open-Closed, etc.)
Usage: Design pattern guidance for all CORTEX development
knowledge-base/security/owasp-top10.yaml 📋
Purpose: OWASP Top 10 vulnerability definitions and prevention
Usage: Security scanning rules for LENS and SecurityOrchestrator
knowledge-base/testing/tdd-practices.yaml 📋
Purpose: Test-driven development best practices
Usage: Test-first development guide for TDDOrchestrator

📊 metrics/

▼

📦 What

4 subdirectories: baselines/, reports/, dashboards/, status/

Contains test baseline snapshots, readiness reports, performance dashboard data, and system health status files.

💡 Why

System observability and health monitoring. Captures test baselines for regression detection, generates readiness reports, provides dashboard data, and tracks system status over time. Essential for quality assurance and performance tracking.

🎯 When

Start here when: Checking system health, analyzing performance, validating test results, reviewing historical status, or detecting regressions.

🔧 How to Troubleshoot

Tests regressing? Compare current results against metrics/baselines/*.json files.

Performance degraded? Review metrics/reports/orchestrator-inventory.json for orchestrator performance.

System status unknown? Check metrics/status/cortex-status-*.yaml for latest snapshot.

Dashboard data stale? Examine metrics/dashboards/data/*.json for last update timestamp.
